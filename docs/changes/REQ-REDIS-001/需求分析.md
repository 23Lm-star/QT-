# REQ-REDIS-001｜Redis 最小引入面 ①②需求分析

## 目标与范围

本需求对应 [TODO.md 中“Redis 最小引入面 ①②”](../../../TODO.md) 的已定稿事项。目标是在服务端内部引入可选 Redis 存储，改善验证码状态和在线状态在重连、重启及异常退出场景下的收敛能力。

本轮范围如下：

1. 验证码状态：验证码、冷却、失败计数和失败锁定改为 Redis 状态；失败计数与锁定按 `clientId` 维度维护。
2. 在线状态：Redis 作为在线态权威，同时保留 `user_info.online` 双写和启动期对账，保留回退与回滚窗口。
3. 44 请求增加一个可选 `clientId` 槽。响应布局不变，旧客户端不携带时回退到连接标识（`connId`）。协议编号不新增、不重排。
4. Redis 通过环境变量 `CLOUDDISK_REDIS_URL` 门控。变量缺失时保持现有行为，Redis 运行中出错时当前请求回退现有路径并记录日志。

第③项秒传 SHA-256 存在性缓存、限流缓存、会话服务拆分、多实例共享数据库和客户端独立 Redis 逻辑不属于本需求。

## 当前实现与问题

### 验证码

`Server/msghandler.cpp` 当前在连接对象中保存验证码状态，涉及 `m_captchaCode`、`m_captchaExpiry`、`m_captchaNextAllowed`、`m_captchaFailCount` 和 `m_captchaLockUntil`。状态按连接隔离，换连接可能重置冷却和失败计数，进程重启也会丢失状态。

### 在线态

当前在线态主要写入 `user_info.online`，服务端启动时通过对账清理异常退出遗留状态。正常断开依赖进程内 `handleOffLine`，进程被杀时无法执行，可能留下幽灵在线状态。现有心跳为桌面端单连接 PING，服务端返回 PONG，没有周期性判活扫描。

### 依赖与执行模型

Qt 5.14.2、MinGW 7.3 环境没有现成 Redis 驱动，需要将 hiredis（C 语言 Redis 客户端库）接入 `Server.pro`，并准备本机 `redis-server`。服务端使用单线程事件循环，同步 Redis 命令存在阻塞心跳的风险，因此命令必须使用极短超时，并保留失败回退；实现阶段需结合实际耗时决定是否复用线程池模式。

## 设计要求

### 验证码键和值

- 键格式：`cap:{id}:code`、`cap:{id}:cool`、`cap:{id}:fail`、`cap:{id}:lock`。
- `id` 优先取 44/3 请求携带的 `clientId`，缺省时取 `connId`。
- 验证码内容使用带过期时间的 Redis 值，冷却使用 `SETEX`，失败计数使用 `INCR` 配合过期时间，锁定使用带过期时间的键。
- 失败计数和锁定只按 `clientId` 维护。接受更换 `clientId` 可绕过计数的既定弱点，不叠加用户名维度。
- Redis 不可用时，当前请求回退连接内存状态，不能静默吞错。

### 在线态键和值

- 键格式：`online:{user}`。
- 登录成功和每次 PING 续期使用 `SETEX online:{user} 90 {loginVersion}`。90 秒为三倍 30 秒心跳周期。
- 断开时使用 Lua（Redis 脚本语言）执行 `GET == version` 后再 `DEL` 的 CAS（比较并交换），避免旧连接被踢后误删新连接的在线键。
- Redis 开启时，7/8 在线用户查询按页使用 MGET 判定在线状态。
- `user_info.online` 双写保留，启动期对账保留。Redis 错误或关闭时回退现有数据库路径。
- Redis TTL（生存时间）负责清理进程崩溃后的幽灵在线状态。

### 协议兼容

- 44 请求在 `caMsg` 增加可选 `clientId` 槽，响应布局不变。
- 旧桌面端、旧网页端不携带该槽时，服务端按 `connId` 处理。
- 协议编号零新增、零重排。两端已有登录 `clientId` 发送点保持兼容，并补齐 44 请求的可选发送点。

## 非功能要求与边界

- 默认关闭 Redis 时，现有验证码、在线态、协议和数据库行为零回归。
- Redis 连接、命令超时、返回类型错误和脚本执行失败均须记录可定位日志，并触发当前请求级回退。
- 不把 Redis 密码写入源码、文档或日志。连接信息仅来自 `CLOUDDISK_REDIS_URL`。
- 本需求不改变“单实例管理同一数据库”的既有限制。
- 配置变更涉及 Qt 资源时需保持 CRLF，重新构建服务端。

## 影响范围

| 范围 | 影响 |
|---|---|
| 服务端 | `Server/msghandler.cpp`、在线态处理、Redis 适配及 `Server.pro` 依赖；默认门控关闭时行为保持不变 |
| 协议 | 仅使用 44 请求现有可选空间；编号和响应布局不变 |
| 桌面端/网页端 | 仅需在已有 `clientId` 发送链路补齐 44 可选槽；旧端继续可用 |
| 数据库 | `user_info.online` 保留双写，不新增迁移 |
| 部署 | 可选增加 redis-server 与 hiredis 运行依赖；未配置 Redis 时无需新增运行服务 |

## 验收场景

1. Redis 门控关闭时，现有验证码和在线态相关回归结果与基线一致。
2. 44 请求携带同一 `clientId` 重连后，验证码冷却、失败计数和锁定不被重置。
3. 验证码达到锁定条件后，在锁定 TTL 内拒绝继续尝试，过期后可恢复。
4. 旧客户端不带 `clientId` 时，44 请求仍按 `connId` 完成原有流程。
5. 登录与 PING 能续期 `online:{user}`，TTL 到期后异常退出产生的幽灵在线态自动消失。
6. 新连接登录后，旧连接断开执行 CAS 删除时不会误删新连接的在线键。
7. 7/8 查询在 Redis 开启时返回与 Redis 在线键一致的状态，分页行为保持不变。
8. Redis 停止、连接失败、命令超时或脚本失败时，当前请求回退现有路径并产生日志，服务端和心跳保持可用。
9. Redis 开启与关闭两种配置分别完成服务端构建和协议层定向验证。

## 实施前提与风险

- 需要确认 hiredis 的获取方式、静态或动态链接方式及与 Qt 5.14/MinGW 7.3 的位数匹配。
- 同步 Redis 命令若超时设置不当，会阻塞单线程事件循环。验收须包含第二连接心跳或请求延迟探针。
- Redis 权威在线态与 `user_info.online` 双写短时间不一致时，以 Redis 查询结果为在线态判断，数据库列用于兼容、回退和启动对账。
- `clientId` 由客户端持久化生成。更换 `clientId` 可绕过验证码失败计数，该风险已按用户裁决接受。
- 本文是需求分析，不代表已完成实现、构建、Redis 实机验证或 GUI 验收。

## 计划与待确认项

实施顺序建议为：先建立 Redis 适配层与门控回退，再接入验证码状态，随后接入在线态和 44 可选槽，最后执行定向探针、服务端构建与门控关闭回归。
