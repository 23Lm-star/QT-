### 实施步骤

1. **R1/R2 私聊送达**：`seedchatMsg` 一律写 `issuccess=0`，新增出参回带新行 `id`；`reseed` 改为返回"找到连接且 write>=0"；`chat()` 在该返回值成立时按 id 置 1。`getchatMsg` 只读不写，回带 id 列表；`chatmsg()` 暂存 id，`MyTcpSocket` 在 `seedMsg(respdu)` 成功后调用新增的 `confirmChatDelivered()` 置 1；写失败/断线不标记，由下次 17 重投。语义定为"至少一次"，崩溃窗口可能重复下发（不丢）。
2. **R3 注销级联**：`handleLogoff` 扩为单事务——校验密码 → 本人为 owner 且 active 的群置 `dissolved`、其余 active 成员行置 `left`、删除涉及本人的 pending 邀请 → 本人 active `user_file` 与 `group_file(uploader)` 逐条减引用并软删（复用回收语义，归零置 `pending_reclaim`）→ 删除本人 `upload_session` → 既有 message/friend/user_info/share_link/publish_links/login_record 删除。提交后删除物理用户目录，失败只记日志（REQ-MIG-001 后正文只在 `objects/`，用户目录无文件内容）。
3. **R4 好友邀请持久化**：新增 `friend_request(requester_name,target_name,status,created_at,handled_at)` + 唯一约束（同 requester+target 仅一条 pending）；启动 schema 版本 `kFriendRequestSchemaVersion` fail-fast。`addfriend` 目标在线转发成功时落 pending；`addfriendFin` 在同一事务内锁 pending 行、校验 requester/target、写双向 `friend` 行并置 `accepted`；无 pending 一律失败（回 `0`，协议布局不变）。既有单向历史行不迁移，`flushfriend`/`deletefriend` 已兼容双向合并。
4. **R5/R6 外链**：`createPublishLink` 先做路径门——`cleanPath` 后落在本人用户根内、无 `..`、非空、≤480 字节、`entryByPath` 命中且非目录，否则 `ok=false` 且不落库；`ACTION_NEW` 改调新方法 `replaceShareLink`（同一事务内 DELETE 精确路径 + INSERT）。
5. **R7 文件与链接同步**：`OperateDB` 新增接收 `QSqlDatabase&` 的事务内助手（删除精确+前缀、平移精确+前缀）；`FileObjectStore` 的 `releaseEntry/releaseSubtree/releaseSubtreeByPath/relocateEntry/renameEntriesDir` 增加可选链接维护入参，在既有事务内调用，失败即整体回滚；`deldir/renamefile/movefile` 不再在事务外单独调链接维护。物理改名失败仍按"条目为准 + 告警"处理（不变）。
6. **R8 图片验证码**：`captcha()` 保持状态码与冷却/锁定语义不变，`status==0` 时 `caMsg` 改为 PNG 字节（`QImage`+`QPainter`，150×44，含干扰线），客户端以 PNG 魔数识别；服务端日志去掉验证码明文。桌面端登录/注册表单增加图片标签（点击刷新），网页端 `requestCaptcha` 返回图片并在表单内以 data URL 显示。校验、`validateCaptcha`、错误码、字表不变。
7. **R9 秒传原子化**：`attachExistingObject` 增加可选"完成态会话登记"入参，在同一事务内插入 `upload_session(status='done',file_id,client_request_id)` 并返回 `session_id`；`uk_req` 冲突时整体回滚后回读既有会话，按幂等成功处理；`msghandler` 删除第二步单独调用。
8. **迁移与文档**：`migrate_friend_req_001.sql` + `_rollback.sql`、启动版本检查；README 更新验证入口与部署顺序；PRD 回写业务规则与结论。

### 已确认决定（2026-11-12 人工窗口一）

- **D1 送达判据**：采用"服务端写出成功即标记"（零协议改动；at-least-once，崩溃窗口可能重复但不丢）。
- **D2 R7 失败语义**：链接维护失败 → 文件操作整体失败（一致性优先）。
- **D3 R3 群资产**：注销者创建的群按解散处理，其上传的群文件随账号删除。
- **D4 R8 兼容**：接受旧客户端不可用，三端同版本升级；移除服务端日志中的验证码明文。
- **实施补充（需知会）**：R8 后直连套件无法识读图片答案，故增加测试专用环境变量 `CLOUDDISK_CAPTCHA_TEXT_FOR_TESTS`（存在时 45 回传文本，默认关闭）；该变量已在 README 标注，生产/公网不得设置。

### 影响与风险

- R8 是跨端可见行为变化（45 的 `caMsg` 语义），协议编号与 `protocol.h` 布局零改动；旧客户端会显示乱码 → 三端同版本部署。
- R4 需先执行迁移再启动服务端；未迁移时启动 fail-fast。
- R3 删除的是逻辑条目与引用计数，物理对象由既有回收调度器按宽限期清理，不做同步删盘。
- R7 使"链接记录异常"从静默变为操作失败，客户端会看到操作失败（原为部分成功）。
- 所有改动为服务端内部事务边界与校验，不改变任何既有协议编号、字段布局或群/传输语义。

## 审计与最终结论

- 结论：R1-R9 全部落地，专项 39/39；无本需求引入的回归。
- 行为变化：验证码默认图片（旧客户端需同版本升级）；链接维护失败会让文件操作失败（一致性优先）；删好友仍会清服务端私聊（M4 按决定不修，客户端本地记录可保留）。
- 残余风险：私聊"写出成功即送达"——对端写出后未读取即断的极端窗口仍可能丢失；注销只减引用，物理对象由回收宽限期清理；`CLOUDDISK_CAPTCHA_TEXT_FOR_TESTS` 误开会削弱验证码；验证码失败计数仍按连接隔离；GUI 与网页图片显示未验收。
- 自审（2026-11-12）发现并修复 3 处：注销重算引用计数时 `reclaim_at` 直绑 QDateTime 改为 MySQL DATETIME 字符串；重算前跳过已被回收调度器抢权（`reclaiming`）的对象；外链路径拒绝 `.`/`..` 段，避免写入非规范键导致 R7 平移匹配失败。复核无问题的点：`user_file/group_file` 无指向 `user_info` 的外键（注销删除顺序安全）、`group_file.file_id` 不级联（删个人条目不破群历史）、`share_link` 无 owner+path 唯一键（R7 改名不会撞唯一约束）、测试旁路默认关闭。
