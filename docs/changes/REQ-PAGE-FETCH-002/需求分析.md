## 一、背景与现状

REQ-PAGE-FETCH-001 已把「在线用户」窗口改为「所有用户」（协议 7/8）：含离线用户、排除自己与双向好友、按用户名字典序分页（桌面每页 50 条＋「加载更多」），响应带标准码/total（符合条件总数）/has_more（还有下一页）/count（本页条数），载荷每条 33 字节（名字[32]＋在线标志 u8）。好友列表（协议 11/12）当时裁决为**不做分页**：服务端至多回 200 条（PAGE_MAX_LIMIT），超限置 truncated（截断标志）弹窗提示；查询用 UNION（合并双向好友关系并去重）但**无 ORDER BY，顺序不稳定**；载荷每条 32 字节纯名字，无在线状态。网页端已同步 33 字节条目解析，但弹窗仍一次性全量展示（请求 limit=0 走旧全量语义），无分页与搜索界面；好友数据靠 10 秒轮询全量拉取。

存在的问题：

1. **无搜索**：用户量大时找一个陌生人只能逐页翻，「所有用户」窗口没有按名字定位的入口。
2. **查询结果无总量上限**：total 随注册用户数线性增长；limit=0 全量路径（网页端、旧脚本）响应报文无封顶，COUNT 与深翻页成本无上界。
3. **好友 >200 条不可见**：截断把长期好友隐藏且无法翻到；无排序导致每次刷新顺序可能不同；「截断显示最近 200 条」文案与事实不符（UNION 无时间序，并非「最近」）。
4. **两端能力不等价**：网页端没有分页/搜索界面，与 REQ-WEB-001「网页与桌面完全等价」的长期目标有差距。

## 四、业务规则（草案，待窗口一确认）

### R1 所有用户搜索

1. 关键词放 7 请求 caData[8,40)（32 字节定长槽，UTF-8 ≤31 字节＋NUL）；空关键词＝不过滤（旧端/旧脚本该区域全零，天然兼容）。
2. 服务端匹配规则：用户名**子串匹配**（SQL LIKE '%关键词%'，预编译绑定），与「排除自己、排除双向好友」条件 AND 组合；大小写敏感性沿用库排序规则（utf8mb4_general_ci，ASCII 不区分大小写）。
3. 关键词中的 LIKE 通配符（`%`、`_`、转义符）按**字面字符**处理（服务端转义），不允许用户输入改变匹配语义。
4. 关键词超过 31 字节：名字本身 ≤31 字节，子串匹配天然无命中，回空页 total=0；客户端输入框限长 31 字节并提示，不发送超限请求。
5. 搜索与分页组合：搜索结果按名字字典序稳定排序，total/has_more/count 口径与无搜索一致；「加载更多」携带当前关键词；更换/清空关键词从第 0 页重新拉取。
6. 搜索是在线状态无关的：离线用户同样可被搜到（D1 语义）。

### R2 查询结果总量上限

1. 新增常量 LIST_TOTAL_CAP=1000（两端 protocol.h 同步，可调；默认值待窗口一确认）。
2. 适用对象：7/8 所有用户（含搜索与无搜索）、11/12 好友，**含 limit=0 全量兼容路径**。
3. 语义：实际符合条件总数 > CAP 时，total=CAP、capped=1；可翻达范围仅前 CAP 条（按各自排序）；offset ≥ CAP 回空页；单页有效 limit 钳制为 min(limit, CAP−offset)，不越界返回。
4. 客户端提示：capped=1 时桌面提示条/网页注记显示「结果超过 1000 条，仅显示前 1000 条」（数值随常量）；提示不阻断翻页。
5. limit=0 全量路径行为变更（有意保护）：改前无上限全量，改后至多 CAP 条＋capped=1。旧端不读 capped 字段，表现为「只显示前 1000 条」，功能可用、无解析错位；部署说明须写明。

### R3 好友真分页与排序

1. 11 请求 caData：limit u32@0、offset u32@4（改前全空）；limit=0 保留旧全量语义（受 R2 上限保护），limit>200 钳到 200。
2. 服务端：双向 UNION 去重后按名字字典序升序（ORDER BY 作用于去重后的全集），COUNT 与分页同一口径；连接/查询失败沿用既有「显式告警＋空列表」语义，不伪装成功。
3. 12 响应 caData：ret@0、truncated@4（**保留恒 0**，截断语义已被分页取代）、count@8 不变；追加 total u32@12、has_more u8@16、capped u8@17。载荷仍 N×32B 名字数组，**零布局变更**。
4. 桌面好友页：首页 50 条＋「加载更多」追加；「序号.用户名」编号跨页连续（按已加载条数），删除/私聊按首个 '.' 取名的既有约定不变；刷新按钮、删除好友成功、接受好友成功后**从第 0 页重置重拉**（避免 offset 漂移造成重复/漏行）。
5. 好友 >200 条不再截断隐藏：分页可翻达全部（≤CAP）；原「已截断显示最近 200 条」弹窗随 truncated 恒 0 自然消失。
6. 网页好友面板：分页**展示**＋加载更多（见 D-web）；好友数据层维持全量拉取（limit=0，≤CAP）供既有消费点使用。

### R4 兼容与部署

1. 本次**只占用 caData 空闲区，载荷布局零变更**：001 时代桌面端（请求不带关键词/分页字段）连新服务端——所有用户回全量（≤CAP）、好友回全量（≤CAP）、truncated=0 不弹窗，功能可用。服务端可先行上线，不要求 001 时代的锁步部署（区别于 001 的 33B 载荷变更）。
2. 网页端本次同步升级（D4）：7/8 解析不变（33B），请求改带 limit/offset/关键词；12 解析追加 total/has_more/capped。
3. 协议编号零新增、零重排；两端 protocol.h 常量逐字节一致，由验证入口比对拦截漂移。
4. 既有探针/脚本（limit=0 口径）零改动可跑，但全量断言需按 CAP 口径复核（>CAP 夹具会受上限影响）。

### 设计决定 D-web（网页好友分页形态，建议项，待窗口一确认）

网页 `friends` store 的名字数组被多处当**全量成员集**消费：私聊会话校验（syncFriends 发现 activePeer 不在 friends 即关会话）、ShareView 分享对象选择、OnlineUserDialog 的 isFriend 判断。若 store 改为「只持有已加载页」，未加载页的好友会被误判「已不是好友」而关会话——这是真分页直接照搬到网页的实质风险。

**建议**：网页好友采用「**数据层全量（limit=0，≤CAP 保护）＋展示层分页**」——store 仍全量拉取（≤1000×32B≈32KB，10 秒轮询负载不变），FriendPanel 本地切片展示＋「加载更多」揭示后续，用户可见行为与桌面等价；所有用户弹窗则走**服务端真分页＋搜索**（弹窗按需打开，无全量成员消费点）。若坚持网页好友也走服务端真分页，须先改造上述消费点（成员校验改服务端判定或单独全量成员接口），范围与回归面显著扩大，不建议本期做。

### 主要风险

1. **offset 漂移**（001 已知残余）：翻页期间用户注册/注销、好友增删造成重复/漏行；好友侧以「增删后重置第 0 页」缓解，所有用户侧维持弱一致性口径不变。
2. **LIKE '%kw%' 无法走索引**：全表扫描，成本随 user_info 规模增长；本项目规模可接受，CAP 封住响应与翻页深度上界。不做全文索引/搜索表（范围外）。
3. **limit=0 语义收窄**（无上限→≤CAP）：旧端与既有脚本的全量预期在 >CAP 夹具下会变化，属有意保护，须部署说明＋探针口径复核。
4. **网页全量消费点**：D-web 已识别三处；onlineNames 消费点实施时逐一核查，漏改会造成误关会话/分享对象缺失。
5. **好友编号解析**：「序号.用户名」按首个 '.' 截取，分页追加后编号连续即可，既有删除/私聊路径零改动；用户名含 '.' 的既有歧义不在本次扩大或修复。
6. **001 未合并叠加**：002 改动与 001 工作区改动同文件交织（protocol.h、msghandler、friend、onlineuser、web），提交粒度与 001 收尾顺序需用户裁决（见开放问题）。
