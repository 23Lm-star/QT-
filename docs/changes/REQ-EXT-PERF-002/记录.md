# REQ-EXT-PERF-002｜服务端复算哈希移出主线程

## 目标与当前进展

链接到 [PRD REQ-EXT-PERF-002](../../../PRD.md#req-ext-perf-002服务端复算哈希移出主线程)。
上传完成时服务端主线程同步复算整文件 SHA-256（`hashStaging`），大文件转正阻塞全部连接。目标：复算入线程池，结果回主线程继续转正与应答；算法、协议、判定语义逐字节不变。当前：方案经人工窗口一确认，进入开发。

## 计划与重要决定

2026-10-27 用户确认三条边界：① 小输入哈希（密码 MD5/盐值摘要/token/会话键 SHA1）不线程化；② Web 端 Worker 哈希的主线程分片回退保留；③ T6 迁移 copyOnly 整文件复制阻塞登记 TODO、本需求不做。

实施设计（对齐服务端既有 `UploadWriteTask` 线程池模式）：

1. 新增 `StagingHashTask`（QRunnable）：worker 线程内复用 `FileObjectStore::hashStaging`（只开自己的读句柄，结束即关，避免 Windows 下 rename/remove 被占用拒绝），结果经 `QMetaObject::invokeMethod` 队列回主线程 `MyTcpServer::handleStagingHashFinished(connectionId, transferId, ok, shaHex, sizeBytes)`，按连接号定位存活连接转交。
2. `FileObjectStore` 拆分：`commitUpload` 的复算与大小/摘要守卫部分抽为公开 `commitUploadPreHashed(..., computedSha, computedSize)`；旧签名 = `hashStaging` + 转调，T6 迁移调用方（`operatedb.cpp` copyOnly）行为逐字节不变。
3. `MsgHandler::finalizeUploadOnComplete` 改为"发起异步复算"：保留原有上下文校验、会话置 verifying、S5 释放共享句柄；随后置 `hashInFlight` 与延迟应答类型并投递任务，返回 `CommitResult.deferred=true`。复算落定后在主线程执行原 finalize 的后半段（PreHashed 转正 + 群引用 + 会话 done/failed + 迟到应答）。
4. 四条触发路径：
   - 末块写完（`MyTcpSocket::handleUploadWriteFinished` complete 分支）：32 迟到回——成功写完后跳过原 `sendUploadAck`，复算落定后按存好的 success/ackOffset 补发。32 字段口径与改前一致（success 取写结果、不受转正结果影响——改前转正失败客户端同样收到 success=true 的 32，本需求不改该行为）；变化仅在于 32 从"复算后同步发"变为"复算落定后发"，相对顺序不变。
   - 29 INIT 0 字节/断点到尾（`msghandler.cpp` uploadfileinit）：30 照常即时回，ret/resumeOffset/complete 字段零改动——改前这些分支的转正结果本就被 30 忽略，失败静默语义不变。
   - 97 秒传预检查断点回放到尾（两处 `br.complete`）：98 迟到回——`ctx` 暂存 reqId/session/大小，handler 返回 nullptr 不回 98，落定后按抽取的 `buildFastcheck98` 补发（字段逐字节同改前）。改后暂存行在复算期间保持 uploading，由秒传命中（与 status 无关）与请求键幂等兜底。
   - 群 101 INIT 到尾：102 迟到回，经抽取的群信封响应构造器补发；失败回 code=-2105 同改前。
5. 并发协调（R1）：`hashInFlight` 的槽不被空闲回收（同 `writeInFlight` 口径）；107 到达且 `hashInFlight` → 置 `pendingAbort`，落定后按既有延迟中止路径走 `abortUpload`；断线 `m_uploads.clear()` → 迟到结果丢弃；id=0 槽被后续 97/29 覆盖 → 迟到结果同样按"查不到在途槽即丢弃"。守卫（大小/摘要不符）全部在回调提交时执行，复算结果不会绕过。
6. 已知残余风险（接受并记录）：极端客户端在复算在途对同一暂存发新会话，可能出现两次复算先后提交、后者 rename 失败判 failed——数据不受损，由既有守卫兜住。R2 压测暂不设专用池限流。

## 审计与最终结论

**实现与测试同审结论**（2026-10-27）：

- 确认无缺陷项：转正判定（大小/摘要守卫、群引用撤销、会话状态机 done/failed/expired、释放顺序）整段逐字搬移，5 套回归 + 19 项专项断言一致印证；迟到应答字段与改前逐字节等价（98 reqId 回带、102 transfer_id 回带均有用例）。
- 待验证疑点：无未闭环疑点；`108×复算在途`、`断线×复算在途`、`256MiB×第二连接响应` 已由确定性用例覆盖。
- 非阻塞建议（不纳入本需求）：断线在途会话滞留 `verifying` 可加巡检计数告警；线程池并发转正可压测后决定是否限流（R2）。
- 未验证项（如实声明）：≥500MB 文件的人工真实体验（套件以 256MiB 代理指标覆盖）；多连接同时转正的并发压测未做；GUI 面本需求零客户端改动、不适用。
- 回归遗留归属：TRANSFER-003 的 S-03b/S-03c 失败源于工作区在途 `protocol.h` 改动（本需求未触碰协议头），需主人定归属后单独处置。

**最终结论**：2026-10-27 人工窗口二通过验收。主人决定：① 残余风险保留、本次不处理；② 在途 `protocol.h` 等改动直接随分支提交；③ 提交按"先纯在途、后本 REQ"两步执行（重叠文件无法非交互拆分，在途内容并入 REQ 提交并在信息中注明）；④ 合并回归口径＝本需求 5 套件，REQ-WEB-001 的 17 套件全量与其余遗留问题未来处理。已按此合入 master。
