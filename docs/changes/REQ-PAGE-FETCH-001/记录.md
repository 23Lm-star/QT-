## 计划与重要决定

### 已确认口径（2026-11-14，用户裁决）

1. 「所有用户」：含离线；排除自己；排除双向好友；显示在线状态。
2. 分页机制选型 A：现有类型追加固定分页字段，不新增协议类型号。
3. 范围：三处高风险做真分页；低量列表服务端截断（数量+时间）。
4. 客户端统一「加载更多」按钮。

### 实施中的重要修正（偏离已批计划处）

1. **聊天历史改走新增类型 117/118，不改 17/18**：实施时发现网页端依赖 17/18（消费式离线补发，`web/frontend/src/protocol/commands/chat.js`），改布局会把范围扩大到前端构建链。17/18 保持网页端语义原样，桌面端历史分页走追加的 117/118（协议编号只追加，合规）；7/8、23/24 仍按选型 A 在原类型上加字段。
2. **limit=0 保留旧全量语义**：不发分页字段的请求（网页端、既有探针脚本）服务端按旧全量行为回齐，新增字段回 total/has_more/count；桌面端请求显式带 limit=50。旧脚本零改动兼容。
3. **时间窗口只作用于 pending 类列表**：好友申请 113、群邀请 82 按「最近 30 天 + 200 条」截断；好友 11、子目录 58、群列表 78、群成员 80 无 pending 语义，时间截断会把长期关系数据误伤隐藏，只做 200 条数量截断。裁决原意为「限制数量+时间」，此处按业务无害化解释，如需扩大到全部列表可再调整。

### 本需求实施结论

- 实施中发现并修复一个服务端真缺陷：`getChatHistoryPage` 的双方组合条件与游标条件未加括号，`A OR B AND id<?` 解析为 `A OR (B AND id<?)`，导致游标翻页失效（探针 C-6 首跑暴露，修复后收尽）。
- 已知限制：offset 分页在翻页期间数据增删会漂移（用户/目录列表，弱一致性，聊天用 id 游标无此问题）；群截断字节未实测（环境缺表）；GUI 未人工复验。
- 部署顺序要求：服务端与桌面端/网页端需同步上线（7/8 载荷 32→33B 为布局变更，旧桌面端解析新响应会错位；limit=0 全量语义只保证旧端功能可用，不保证新字段语义）。
