## 目标与当前进展

把一对一消息（15/16/17/18）从「三端都不校验长度」改成「有 2000 字节的业务上限、服务端权威拒绝、任何一端都不越界读写」，并补上让上限真正成立的一次数据库列宽迁移。

进展：实施完成，自动验证全部通过（见下节），已提交在分支 `codex/req-cli-msgboundary-001`（提交 `3ec8317`，未合并、未推送），待人工窗口二；GUI 与旧客户端混跑未验证。

## 计划与重要决定

用户 2026-10-28 确认的六点范围：

1. 服务端超限**直接拒绝**——不入库、不转发、16 回 `stored=false`、连接保持（对齐群聊做法，排除截断与分片两个候选）。
2. 正文上限抬到 **2000 字节**，桌面收发同步改成动态长度容器（排除沿用 109 的零改动方案）。
3. 接收侧防御性钳制时**截到最后一个完整 UTF-8 码点**，不留半个码点。
4. 桌面 18 无钳制与 `Time` 缺终止符**同批处理**。
5. TODO【待复核｜私聊边界】与【缺陷｜服务端私聊长消息定长拷贝】**合并为本需求一条**，两处留去向链接。
6. 追加决定（因迁移前置而问）：`message_info.msg` 改 **varchar(2000)**；桌面发送超限**提示并阻止发送**，不改写内容。

关键前置与实测证据（只读探查，自插的 3 行已按标记删除）：`message_info.msg` 为 `varchar(100)`，按字符计；`sql_mode` 含 `STRICT_TRANS_TABLES`，101 个 ASCII 直接 `1406 Data too long` → 不扩列则 2000 上限形同虚设，且超长正文在 `seedchatMsg` 失败后连转发都不做。表排序规则已是 `utf8mb4_general_ci`，emoji 可正常入库，字符集不动。参照 `group_message.content` 为 `TEXT`。

影响与风险：
- **部署顺序**：新客户端可发 2000 字节，旧服务端从 121 字节起即越界，因此服务端与迁移必须先于客户端/网页上线。
- 协议面无变化：不新增命令编号，`PDU`/`Msg` 布局不动，只在两端 `protocol.h` 追加同名常量。
- 回滚：`_rollback.sql` 会强制会话语态为严格模式再收窄列，库里存在 >100 字符私聊行时 ALTER 失败中止、结构与数据都不动（2026-10-28 应主人要求把「先人工核对残留长行」升级为脚本内建检查，并实测该分支）。
- `message_info` 建表语句不在仓库内（`project-docs/init_test_data.sql` 只建 user_info/friend/login_record），列宽变更只能靠迁移脚本 + README 记录。
- 旧客户端遇到新的长消息仍被自己钳到 109 字节显示，属可接受的向后退化。

## 审计与最终结论

- 已确认缺陷并修复：服务端 `chat()` 的 120 字节栈缓冲 + 不校验的 `msgLen`（远程内存破坏面）；桌面端 18 离线解析的 `char msg[110]` 无钳制与 `totalLen` 未校验步进（本轮新发现，TODO 未登记）；服务端 15 读 `Time` 无终止符、服务端 18 打包与桌面端发送 `Time` 的 30 字节定长拷源越界读。
- 一处遗留疑点（非本轮引入、未处理）：探针不用 ASAN，越界读本身不被断言直接捕获，只由「进程存活 + 长度断言」间接证明；`Server/ConCurrentAlloc` 内存池路径在本需求里未被覆盖（探针用最小 stub 顶替 `MemAlloc`，只替依赖、不替被测代码）。
- 非阻塞建议：`Client/msghandler.cpp` 的 `seedName`/`peerName` 仍是 32 字节 `memcpy` 后直接 `QString(...)`，依赖对端补零；与 TODO【待复核｜I-4 / O-3】同族，本需求未扩大处理，避免顺手改无关路径。
- 顺带价值：16 应答的 `stored=false` 分支现在有了一条**不侵入产品代码**的动态制造手段（发一条超限消息即可），此前登记的验证缺口就此可断言，见 TODO 更新。
- 未验证项如实保留：GUI（人工十一）、旧客户端与新服务端混跑的截断表现、真实外网互操作。
- 相关去向：[PRD REQ-CLI-MSGBND-001](../../../PRD.md#req-cli-msgbnd-001私聊消息长度与边界校验)；TODO 两项已改为转入去向。
