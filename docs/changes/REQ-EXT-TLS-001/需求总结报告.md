## 一、背景与目标

密码、会话凭据与全部业务数据当前以明文 TCP 传输，同网段可被嗅探与篡改。目标：桌面客户端（Qt）与服务端（Qt）之间的 TCP 长连接升级为 TLS 加密通道，保证机密性与完整性；协议内容、编号与字节布局零改动（TLS 只替换传输层）。

## 三、范围

### 在本次范围

1. 服务端：`MyTcpSocket` 改造为 TLS 服务端（证书 + 私钥加载、等待 `encrypted` 信号后才开始 PDU 解析）。
2. 桌面客户端：`QTcpSocket` → `QSslSocket`，对端证书校验；**禁止 `ignoreSslErrors()` 全放行**（否则加密不防中间人，等于没做）。
3. 证书与密钥管理方案落地（见 §四 决定点 D3）。
4. 部署链路：OpenSSL DLL 与 TLS 后端插件进 `dist/`，README 构建/部署说明更新；私钥不入 Git。
5. 配置扩展：证书路径、私钥路径（服务端 8 行配置如何容纳，见 D4）。
6. 测试与回归适配（见 D6）。

### 不在本次范围（建议，待确认）

- 网页网关→服务端的 TLS 化（可拆分或纳入，见 D2）。
- 强密码派生（PBKDF2/bcrypt）、无 token 会话——另属 EXP-SEC 项，不捆绑。
- 协议编号/字节布局变更（任何方案都不需要）。
- 桌面端双向认证（mTLS）——默认不做，见 D3。

## 四、关键设计决定点（需人工窗口一逐条拍板）

**D1 加密范围与共存策略**。选项：
- A. 现有 5000 端口直接切 TLS、不留明文——最干净，但全部 17+ 套件、网页网关立即不可用，需同批改测试与网关；
- B. 双端口：5000 明文（内网/测试）+ 新端口 TLS——改动最小、可灰度，代价是明文通道仍长期存在；
- C. 服务端配置开关（require TLS / 允许明文）——介于两者之间。
- 建议：开发期 B/C、验收后按 TODO「TLS 为 M6 前置」的要求收敛为公网路径强制 TLS。注意：同一端口上无法自动协商裸 TCP 与 TLS，任何"共存"都意味着端口或开关，不存在免费方案。

**D2 网页链路是否纳入**。M6 现状是 Cloudflare Tunnel 终止 TLS（WSS→网关明文→服务端明文）。本机回环两段明文风险低但链路不端到端。若 D1 选 A/B 且服务端 5000 变化，网关 `net.connect`（bridge.js:41）会直接断——本需求至少要为网关选择"继续连明文端口"或"改 `tls.connect`"之一，需明示。

**D3 证书与信任模型**。选项：
- 自签名证书 + 客户端固定校验（内置该证书/私有 CA，`QSslConfiguration` 设自定义 CA 并要求主机名校验）——学习/局域网项目最实际；
- 自建小 CA 签发多张服务端证书——为将来多服务器留余地；
- 公共 CA（Let's Encrypt）——需要域名，与纯 IP 部署冲突。
- Qt 5.14 API 限制：无 `addCaCertificates()` 追加式接口，只能整体替换 `setCaCertificates()`；`PSK`（预共享密钥）在该版本 MinGW 后端支持不确定，不建议依赖。**私钥来源、存放位置、有效期与轮换方式必须在本决定点定下**；私钥文件不得进 Git、日志与文档。
- 待确认：是否只服务端证书（默认）还是 mTLS 双向认证。

**D4 配置承载**。当前两端配置编译进 Qt 资源、CRLF 分行、改动需重构建（REQ-CFG-010 未做）。服务端至少新增证书路径、私钥路径两项：a) 接受"扩资源配置 + 重构建"沿用现状；b) 先做 REQ-CFG-010 外置再挂 TLS；c) 约定固定文件名（如 `dist/certs/`）不进取舍配置。建议 a 或 c，避免把配置外置捆绑进本需求。

**D5 会话内行为**。TLS 握手完成前不得按 PDU 解析字节（两端都等 `encrypted` 信号）；`errorsOccurred`/`sslErrors` 需分类处理并接入现有重连对话框与心跳判失联逻辑；下载 `bytesWritten` 背压与出站有界队列语义不变，但吞吐会因加密有实测下降（预期 10%~30%，需在验收中给基线对比而不是猜数）。

**D6 测试适配口径**。现有 Python e2e 套件全部裸 TCP 连 5000。若服务端切 TLS，每个套件需 `ssl.wrap_socket` 级改造并信任测试证书——成本高。建议：测试环境使用"明文端口保留"（D1-B/C）使套件零改动，另新增一个 TLS 专项套件覆盖握手、拒明文、证书校验失败、篡改检测；该口径需确认。

## 九、Spike 结果（2026-10-28，已通过）

决定点经用户全部确认（D1 双端口、D2 网关留明文、D3 自签+pinning、D4 `dist/certs/` 固定目录、D6 明文端口跑既有套件+TLS 专项套件），PRD 已立项，分支 `codex/req-ext-tls-001`。

环境结论（实测，程序在 `build/sslprobe/`，不进产品代码）：
- `QSslSocket::supportsSsl()=1`，运行时 OpenSSL 1.1.1w。后端 DLL 不在 Qt 目录：`libssl-1_1-x64.dll`/`libcrypto-1_1-x64.dll` 由系统 `C:\WINDOWS\system32` 提供；**部署机若无这两个 DLL 需随 `dist/` 附带**，README 须写明。
- localhost 五场景全 PASS：
  - S1 正常握手+回显（`encrypted` 后才走数据）；
  - S2 客户端 pin server 证书、服务端出示 rogue 证书 → 拒绝；
  - S3 主机名不符（CN=tlsserver，校验名 otherserver）→ 拒绝；
  - S4 过期证书（openssl 3.x `-not_before/-not_after` 造型）→ `CertificateExpired` 拒绝；
  - S5 裸 PDU 打 TLS 端口 → 握手不成立、服务进程存活，随后正常 TLS 客户端仍可握手。
- API 坑（产品实施要遵守）：① `QTcpServer::nextPendingConnection()` 返回的是 `QTcpSocket`，**强转 `QSslSocket*` 必崩**——服务端必须在 `incomingConnection(qintptr)` 里 `new QSslSocket` + `setSocketDescriptor`（与本项目 `MyTcpServer::incomingConnection` 的既有改造点一致）；② Qt 5.14 无 `setCertificate/setPrivateKey` 直挂接口，用 `QSslConfiguration` 整体设置；③ 5.14 信号名是 `error` 非 `errorOccurred`，需 `QOverload` 消歧；④ 客户端 `encrypted` 信号先于服务端计数落定，测试断言要留延迟；⑤ MSYS 下 `openssl req -subj "/CN=..."` 需 `MSYS_NO_PATHCONV=1`。

## 十、实施与验证（2026-10-28，分支 `codex/req-ext-tls-001`）

落地点：
- 服务端：`MyTcpSocket` 基类 `QTcpSocket→QSslSocket`（明文连接行为不变）；`setTlsMode` 登记 TLS 端口连接并在 `recvmsg` 加“握手未完成不解析”守卫；`buildTlsConfig` 从 `dist/certs/` 固定目录加载（缺失即日志说明、不启用）；`MyTcpServer::startTlsListener` 以第二监听实例（主端口+1，共享连接表与僵尸清扫）启动；`Server::initialize` 明文监听成功后尝试 TLS，失败不影响明文。
- 客户端：`sorket` 改 `QSslSocket`；`startConnection()` 按 `dist/certs/server.crt` 在位与否选 TLS(端口+1，pinning 该证书、校验名 tlsserver、TLS1.2)或明文(原端口)；`connectsort/recvmsg/seedMsg` 与 `msghandler.cpp` 写旁路全部加 `tlsPending()` 守卫；`sslErrors` 一律断连提示，无 `ignoreSslErrors` 放行。
- 配套：`Server/make_tls_certs.ps1`（UTF-8 BOM，PowerShell 5.1 可用）；`.gitignore` 追加 `*.key`/`*.crt`；README 验证入口与兼容边界更新。

## 十一、TLS 三/五 收口（2026-10-28）

- 本轮两个实测坑（已写进脚本注释，别重走）：
  1. **工作目录必须纯 ASCII**：本机 temp 目录含中文用户名，路径经 `getenv` 传给 MinGW 程序是 GBK 字节，Qt 按 UTF-8 解释后 `QFile::open` 报"系统找不到指定的路径"，证书/私钥全读成 0 字节 → 所有握手莫名失败。产品代码不受影响（走 `applicationDirPath()`，Windows 宽字符取值）。
  2. **TLS1.2 下"桩服务端握手计数为 0"不能当客户端拒绝的判据**：服务端在客户端完成证书校验之前就已结束本侧握手，实测 rogue/expired 桩各计到 1。判据改为只认客户端侧事实（`encrypted=0` + 错误类型），交叉判据换成"被 abort 之后服务端仍能完成新握手"。

## 十二、人工窗口二：审计结论与剩余风险（2026-10-28）

人工验证两项已补齐：① GUI 在新产物（规则抽出重构后的 `dist/Client.exe`）上复验通过；
② 用户人工断开服务端再重连，操作正常。至此 PRD 的 TLS 一~八 与人工九 全部有依据。

审查实现与测试后的结论，按类别分列（不写"整体通过"这种标签）：

**确认缺陷（非阻塞，建议后续单独修）**
- D-1 证书被拒时的文案误导：`Client::startConnection` 走 TLS，`sslErrors` 弹"安全连接失败"后
  `abort()`；若此前已登录（`m_loggedIn` 仍为 true，重连场景），`disconnected` 槽会再弹
  「连接被服务端关闭，账号可能已在其他设备登录」并打开重连窗——把 TLS 信任失败说成被互踢。
  安全语义不受影响（连接确实被拒），但用户会被引向错误的处置方向。
  建议：`sslErrors` 置一个 `m_tlsRejected` 标志，`onSocketDisconnected` 据此跳过互踢文案。

**非阻塞建议**
- S-1 `m_usPort + 1` 无溢出保护：配置端口为 65535 时，客户端会连 0 端口，服务端
  `listen(0)` 会随机挑一个端口并打出「TLS 端口启动成功，监听 0」。现实配置不会踩到，
  但那行日志会误导排查。建议显式拒绝并记日志。

**待验证疑点**
- Q-1 `tls_e2e.py` T2 的"应答逐字节一致"依赖 `tlse` 账号没有好友（12 应答为空列表）。
  若将来该账号被加过好友，在线状态差异会让这条断言变抖。当前账号名固定、套件自清理，
  暂不改；换夹具账号时要注意。

**口径限制（不是缺陷，但决定验收话术）**
- TLS 五的"在途传输任务收敛"没有 TLS 专项自动化。依据是三段拼起来：
  `Client::onSocketDisconnected` 对明文/TLS 走同一条 `TransferManager::onConnectionLost` 路径
  （该路径由 TRANSFER-003 套件在明文端口回归通过）+ 探针 T5-a 证明 QSslSocket 的
  abort/disconnected 收敛正常 + 用户人工断连重连未报异常。按此判定通过，不再单独宣称
  "TLS 下的传输收敛已被专项覆盖"。
- 双端口共存期间 **5000 明文端口不得暴露到公网**（D1 已确认，公网强制收敛随 REQ-WEB-001 M6）。
  这是当前 TLS 保护的实际边界：只要 5000 可达，攻击面就在，加密收益仅限已走 5001 的链路。
- 部署机若缺 `libssl-1_1-x64.dll`/`libcrypto-1_1-x64.dll`，服务端会静默不启用 TLS 端口
  （仅日志说明），客户端因无 `dist/certs/server.crt` 也回退明文——**看起来一切正常**。
  运维验收要确认日志里出现「TLS 端口启动成功」而不是「certs/ 不可用」。
