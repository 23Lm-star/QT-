# REQ-SHARE-ENTRYID-001｜分享链接源定位改绑条目标识

## 目标与当前进展

对应 [TODO.md 想法条目（2026-11-21）](../../TODO.md)：share_link 与好友分享待接受授权的源定位从「所有者＋源相对路径」改为「所有者＋源逻辑条目标识（user_file.file_id）」，目标：文件改名/移动不再牵动分享链接同步更新，仅条目删除使链接失效。动机含面试稿口径先行对齐。

当前进展（2026-11-21）：澄清、实施与验证完成。分支 `codex/req-share-entryid-001`（基于 master 0e82d9c）。口径四条均按商定落实；存量 share_link 已由 migrate_share_entryid_001.sql 清空（schema_version=2026112101）。

## 已确认口径（2026-11-21 商讨结论）

1. **服务端解析绑定**：客户端协议完全不动。Qt 客户端与网页端仍按路径发起好友分享（33/36）与外链创建/查询（52/56）；服务端在受理点把路径解析为 `user_file.file_id` 落库；54 解析按 token→file_id 定位条目。TODO 原口径中「请求 33/36/52/54 源路径字段改条目标识、协议编号只追加不复用」**不再执行**——线上字段不改、不追加协议编号，条目标识仅体现在服务端存储与内部定位。原因：当前文件列表（23/24）的 `FileInfo` 只有名字＋类型（`Server/protocol.h:328`），客户端无处取得 file_id，改携 ID 需先扩列表载荷并牵动分页改造，范围大且非本需求目标所必需。
2. **同步清理**：保留「条目删除与链接清理同一事务」规则；删除（含目录级联删除）在同一事务按条目标识清理对应 share_link 行；重命名/移动不再联动（移除 `updateShareLinkPathTx` 及其调用）。54 解析对已清理行自然失效。
3. **存量直接清空**：不迁移，一次性清空全部存量 share_link 行（2026-11-21 用户确认直接清空、不保留），所有旧链接失效、需重新创建。好友分享待接受授权是服务端内存态，重启即清空，无存量迁移问题。
4. **握手改名窗口放行**：好友分享邀请发出后、接收者点同意前，源条目被改名/移动的，同意时按条目标标识放行：授权登记改为（接收者，file_id，邀请时文件名），同意时按提交路径的文件名匹配邀请名、按 file_id 取当前条目引用；条目已删除才拒绝。

## 改动方向（供实施计划细化）

- 表结构：`share_link.relative_path` → `file_id BIGINT NOT NULL`（引用 user_file.file_id，**不设外键**，避免阻塞条目删除事务）；保留 owner_name 用于注销清理与归属断言。
- operatedb：按 file_id 重写增删查/续期接口；删除 `updateShareLinkPathTx`、按路径与 LIKE 前缀匹配的接口。
- fileobjectstore：移除 787/1051 两处平移调用；557/629/1087/1108 清理改为按删除事务内的条目 id 集合。
- msghandler：33/36/52/56 四个受理点路径→file_id 解析（解析即隐含归属与 active 校验）；54 按 file_id 取条目并复查 active 非目录；好友分享授权登记改（接收者，file_id，邀请名），同意按邀请名匹配。
- 存量清理载体：建议按既有惯例出一次性迁移 SQL（`Server/migrate_share_entryid_001.sql`，DELETE FROM share_link），与 `schema_version` 机制一致——实施前确认。

## 风险与影响

- 存量链接一次性失效：已确认接受；旧 token 解析返回链接无效。
- 协议不动：服务端单侧升级，两端客户端零改动、无兼容窗口。
- file_id 为 AUTO_INCREMENT 主键不复用，无删除后重绑风险。
- 引用计数与对象回收不受影响：54 解析与好友分享仍走 `attachExistingObject`/`attachEntry` 零复制引用，逻辑不变。
- 54 解析的即时失效依赖同步清理事务正确性（口径 2 保留该事务）。
