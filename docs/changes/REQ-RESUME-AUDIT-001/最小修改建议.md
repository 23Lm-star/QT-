# 最小修改建议

配套文档：[断点续传分析报告.md](断点续传分析报告.md)。
约束：不改协议字段、不改数据库表结构、不引入新依赖；每项可独立上线、独立验证。

## 0. 修复策略

先说结论：不需要重写续传。现有“确定性暂存 + 停等分块 + 服务端复算”的骨架是对的，缺的是三个不变量：

1. **续传起点 ≤ 服务端已确认偏移**（现在的起点是磁盘大小）；
2. **同一逻辑上传的内容身份不能被静默替换**（现在只看名字和大小）；
3. **转正结果必须回传客户端**（现在固定回成功）。

按“先止血、再补身份、最后加固”的顺序实施。

## M1 服务端：续传起点以 `confirmed_offset` 封顶（P0-1）

改动位置：`Server/msghandler.cpp:1270-1297`、`1636-1656`、`2849-2881` 三个 `beginStaged` 调用点。

做法：

1. 在 `OperateDB` 增加按暂存路径查询的轻量接口（复用现有 `UploadSessionLookup` 结构）：
   ```sql
   SELECT session_id, confirmed_offset, status FROM upload_session
   WHERE owner_name=? AND staging_path=? ORDER BY session_id DESC LIMIT 1
   ```
2. `beginStaged` 返回后执行：
   ```
   offset = min(result.offset, db.confirmedOffset >= 0 ? db.confirmedOffset : result.offset)
   若 result.offset > offset：releaseStagingFile 后 resize(.part, offset)
   ```
3. 用该 `offset` 覆盖 `br.offset` 再写 `restartUploadSession` / 回 `30`、`98`、`102`。

为什么这样最小：不动写路径、不动协议；进度落库节流是 1 MiB / 2 s（`Server/mytcpsocket.cpp:530-540`），最坏重发约 1 MiB，可接受。

风险：M1 引入 `.part` 截断，若同时存在另一连接的写入（P1-3），截断会打断对方。建议 M1 与 M6 同批上线，或在 M1 上线时把 `verifying` 移出复用白名单。

## M2 服务端：续传不再清空已登记摘要（P0-2，性价比最高）

改动位置：`Server/operatedb.cpp:241-252`（`restartUploadSession`）。

做法：`clientSha256` 为空时**不更新该列**（动态拼接 SQL，去掉 `client_sha256=?`），而不是写入 `NULL`。调用点 `Server/msghandler.cpp:1284-1286` 继续传空值即可。

效果：续传时 commit 仍会拿“首次 97 登记的真实摘要”复算比对。破坏性后果从“静默入库错误内容”变成“明确失败 + 暂存被删除”（`Server/fileobjectstore.cpp:282-288`），用户重试即从头开始并成功。

代价：用户合法替换了同名同大小文件时，会先失败一次再重传。需要在失败原因里能看懂，可配合 M3 的错误码文案处理。

## M3 服务端：`32` 应答反映转正结果（P0-3）

改动位置：`Server/msghandler.cpp:1885-1891`。

做法：

```cpp
case DeferredDataAck32:
    act.needDataAck = true;
    act.ackSuccess = r.ok;              // 原：ackSuccess（写盘成功）
    act.ackOffset  = r.ok ? ackOffset : 0;
    act.complete   = r.ok;              // 原：固定 true
    break;
```

注意 `HashFinishAction` 目前只有 `ackSuccess/ackOffset`，需要补一个 `ackComplete` 字段，`handleStagingHashFinished` 透传给 `sendUploadAck`（`Server/mytcpsocket.cpp:545-558`）。

效果：客户端 `Uploader::acknowledge` 收到 `success=false` 会走失败分支（`Client/uploader.cpp:61-64`），任务显示失败而不是完成。这是**行为修正**，不是兼容性回归；老客户端只是从“假成功”变为“失败”。

## M4 客户端：偏移连续性与显式 seek（P1-4）

改动位置：`Client/uploader.cpp:61-67,77-99`。

做法：

1. 记录 `m_sentLen = chunk.size()`；`acknowledge` 要求 `nextOffset == m_nextOffset + m_sentLen`，否则失败。
2. `sendNextChunk` 读取前 `m_file.seek(m_nextOffset)`，失败即报错。

规模约 10 行。作用是把“服务端偏移异常”变成本地可见失败，避免错位数据继续发送。

## M5 服务端：暂存键加入作用域（P1-2）

改动位置：`Server/resumableuploadsession.cpp:77-101`。

做法：`beginStaged` 增加 `scope` 参数（默认 `"p"`），键改为 `owner|scope|parent|display|size`；群上传调用点（`Server/msghandler.cpp:2849-2850`）传 `"g:" + groupId`。

影响：旧 `.part` 不再命中，已验证的断点会重传一次；旧文件由 6 小时 TTL 回收（`Server/reclaimscheduler.h:71`）。无协议改动。

## M6 可选：同一暂存路径的单写者互斥（P1-3）

项目按“服务端单实例管理同一数据库”部署（项目 AGENTS 规则），进程内注册表足够：

- 新增 `static QHash<QString, QPair<quint64,quint64>> s_activeStaging`（暂存路径 → 连接号 + 传输号）。
- 登记时机：`beginStaged` 成功且会话获得 `transfer_id` 后；`97` 占位槽的登记在 `29` 采纳时迁移。
- 释放时机：`abortUpload`、转正落定、连接销毁。
- 冲突时回 `ret=false`（个人）或 `-2106`（群），客户端按“并发上限/稍后重试”处理。

规模约 20-30 行。如果暂时不做，至少把 `verifying` 从可复用白名单移除（`Server/operatedb.cpp:277-279`），消除 P2-2 的双提交。

## M7 可选：内容身份（P1-1 / P1-5）

两条路线，按成本选择：

- **路线 A（不改协议，推荐先做）**：恢复/续传任务一律先发 `97`，用已有摘要 + 请求键续传。删掉 `Client/transfertask.cpp:1153` 的 `needFastcheck=false`，并在快照里保存 `shaHex`（`Client/transfertask.cpp:71-99`）避免整文件重算。代价是“继续”多一次摘要计算。
- **路线 B（协议追加）**：`29` 的 `caData` 还有空闲区（44-47、56-63），放 8 字节 SHA-256 前缀作为 `identityTag`，服务端拼进暂存键。需要 Qt、Web、服务端三端同步；属追加字段，不影响旧字段偏移。

P1-5（31 字节截断）单独处理：个人上传的 name 字段只有 32 字节（`Server/msghandler.cpp:1234-1243`、`web/frontend/src/protocol/commands/drive.js:217-222`），要么把 29 的名字改走 `caMsg`（像 97 那样带长度），要么在客户端入队时拒绝超过 31 字节的文件名并提示改名。后者是 1 行校验，建议先做。

## 8. 验证用例

| 编号 | 场景 | 步骤 | 通过标准 |
|---|---|---|---|
| T1 | 断电/崩溃续传 | 传大文件中途 `kill -9` 服务端，重启后继续；另做一次人为在 `.part` 尾部追加 1000 字节垃圾 | 最终文件 SHA-256 与本地一致；若内容不可信必须明确失败并可重传成功 |
| T2 | 同名同大小换内容 | 传 A 到 50% 暂停，用同大小 B 覆盖同名文件后继续 | 要么直接传成 B，要么失败一次后重传成 B；**禁止** A 前缀 + B 后缀 |
| T3 | 转正失败可见性 | 临时让 `objects/` 不可写，或构造摘要不符 | 客户端必须显示失败；服务端 `upload_session.status=failed` |
| T4 | 双连接并发 | 同账号两个客户端同时续传同一文件 | 一方成功、另一方明确失败/排队；无交错内容 |
| T5 | 长文件名 | 上传 40+ 字节中文名并暂停续传 | 入库名与选择名一致；续传起点非 0（或明确提示不支持续传） |
| T6 | 群/个人同名 | 个人根与群各上传同名同大小文件 | 互不复用暂存，各自独立完成 |
| T7 | 正常路径回归 | 新文件上传、秒传命中、群上传、暂停后继续各一次 | 与修改前一致，无额外失败 |

## 9. 改动顺序与规模

1. M2（约 3 行）→ 立刻缩小“静默损坏”面。
2. M3（约 10 行，含 `HashFinishAction` 字段）→ 让失败可见。
3. M1（约 30 行，含 DB 查询）→ 修正续传起点语义。
4. M4（约 10 行）→ 客户端偏移防线。
5. M5（约 15 行）→ 暂存作用域隔离。
6. M6 / M7 视 T2、T4 结果决定。

M1/M2 完成后跑 T1、T2；M3 跑 T3；M5 跑 T6；M4 与 M6 跑 T4。T7 每步都跑。

## 10. 不建议现在做

- 不引入 tus/HTTP 分片协议、外部对象存储或分块位图（chunk bitmap）；停等顺序写已满足当前规模。
- 不为续传新增哈希索引表；先验证 M2 的“复用旧摘要”是否足够。
- 不做“续传加密/签名”这类重型方案；当前缺口是状态一致性，不是传输机密性。
