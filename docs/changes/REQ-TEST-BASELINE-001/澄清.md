### 第 1 项｜sec001_regression.py X3a 陈旧断言

**现状证据**：TODO 行号与机理全部成立，无漂移。
- `project-docs/evidence/REQ-EXT-FILE-001/sec001_regression.py:245`：`ca.ask(pdu(T_CHAT,...), n=0, t=0.8)`。`ask()` 定义在同文件 83-90 行：`n=0` 时收集循环体一次都不进入，直接返回空表——发送后不读任何报文，服务端应答留在 socket 缓冲。
- `:252-253`：X3a 用默认 `n=1` 取第一个包并断言 `r[0][0]==T_LOGOFF_R(49) 且 ret 失败`。
- 服务端侧：`Server/msghandler.cpp:887-900`（REQ-CLI-MSGSTORE-001 注释明写「给发送方回一条 16 应答」，caData[0,32)=对方名）。16=`ENUM_MSG_TYPE_CHAT_RESPOND`（Server/protocol.h:53），49=`ENUM_MSG_TYPE_LOGOFF_RESPOND`（protocol.h:86）。
- 机理：X2 发的私聊（收件人 V 未登录、无回发）使 `ca` 缓冲残留一条 16，X3a 第一个取到 16：类型 ≠49 且 caData 首字节为对方名首字符（非零）→ 断言两条件皆假 → 误报 FAIL。同组 X3b PASS 佐证注销实际被拒，非鉴权失效。

**修法候选**：
- A（推荐）：X3a 取包改为按报文类型过滤——循环 `ask` 直到取到 49，读到的 16 记为排空；断言与预期结果一字不动。对将来服务端再新增应答类型鲁棒，且与 TODO 登记的修法方向一致。
- B（极简备选）：`:245` 的 `n=0` 改 `n=1`，让 X2 段当场消费掉那条 16。改动最小，但依赖「ca 此刻恰只回一条 16」这一现状（当前成立），后续再加应答会复发。

**影响面与风险**：只动该套件文件，不碰服务端/客户端。风险极低；验证时需起服务端与 MySQL。
