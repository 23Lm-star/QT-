## 计划与重要决定

### 商讨结论（2026-11-22，用户问「用户目录获取走物理还是数据库树」）

- **答**：flushfile（23/24 列目录）现为**数据库条目树权威 + 物理目录壳兜底合并**的混合形态——条目来自 `FileObjectStore::listEntries`（user_file 表 parent_path+display_name）；物理扫描仅并入**目录**（文件一律来自条目），且按条目名去重、软删墓碑（`deletedDisplayNames`）过滤、`.staging`/`objects` 不外显（msghandler.cpp:1092-1118）。
- **探针实证**（build/ghost_probe.py，临时不入库）：MKDIR→FLUSHFILE（含）→DELDIR(25) 成功→FLUSHFILE **已不含**该目录（2026-11-14 的墓碑过滤在位，TODO 原描述「删除成功但目录仍出现在列表、需二次删除才消失」**不复现**，该 TODO 的复现描述已过时）；但**物理目录壳残留磁盘**（True），且列表已不显示 → 用户没有任何入口做「第二次删除」→ 孤儿目录壳长期留存（同名重建前）。
- **方案取舍**：(a) 软删成功后同步删物理壳（推荐，采用）vs (b) flushfile 跳过软删条目对应物理目录（b 已被墓碑过滤实现，剩余问题仍是磁盘残留）；D5 后文件不物理落用户树、目录为空壳、对象在 filesys/objects——(a) 无数据风险。
- **决定**：采用 (a)；清理失败不推翻软删结果，交目录补偿队列（`enqueueDirectoryFailure`）重试；「无条目残留回收」分支（deldir delFileType==0 物理分支）保留兜底历史孤儿。
