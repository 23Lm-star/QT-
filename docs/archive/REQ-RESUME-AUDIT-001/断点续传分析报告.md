# 断点续传分析报告

范围：个人上传（97/98 预检 + 29/30 初始化 + 31/32 分块）、群上传（101/102）、服务端暂存与转正。
性质：静态代码分析，未执行真实断点续传/断电/并发测试。

## 1. 结论

主链路可以跑通，但“续传正确”依赖三个不成立的假设：

1. 暂存文件（`.staging/*.part`）的**物理大小**等于服务端已确认写入的数据；
2. `(owner, 目录, 文件名, 文件大小)` 能唯一代表**文件内容**；
3. 转正（commit）失败会被客户端感知。

三个假设分别对应 P0-1、P0-2、P0-3。最坏结果是：**客户端显示“上传完成”，服务端落库的文件内容被旧前缀污染，或根本没有文件**。

问题统计：P0 三项、P1 五项、P2 四项。

## 2. 当前实现的数据流

1. 个人上传：`97` 秒传预检（带完整 SHA-256 与请求键）→ `98` → `29` 初始化 → `30` 回带续传起点 → `31/32` 停等式逐块上传。
2. 暂存路径：`filesys/.staging/<sha1(owner|parent|display|size)>.part`，确定性生成，同一组参数重连命中同一文件（`Server/resumableuploadsession.cpp:90-101`）。
3. 续传起点：直接取 `.part` 的 `QFileInfo::size()`（`Server/resumableuploadsession.cpp:109-121`）。数据库 `upload_session.confirmed_offset` 只在节流时更新（`Server/mytcpsocket.cpp:530-540`），**续传时不读**。
4. 写盘：`UploadWriteTask` 在 `QThreadPool` 中 `seek + write + flush`（`Server/uploadwritetask.cpp:24-41`），主线程收到成功回调后才推进 `receivedSize`（`Server/mytcpsocket.cpp:496-543`）。
5. 转正：末块落定后线程池复算整文件 SHA-256，再 `commitUploadPreHashed` 校验大小/摘要、rename 进 `objects/`（`Server/msghandler.cpp:1768-1806,1811-1922`）。
6. 完整性校验只有在 `expectedSha` 非空时生效（`Server/fileobjectstore.cpp:279-288`）。`expectedSha` 只由 `97` 的摘要或 `97→29` 采纳链路带入。

## 3. 问题清单

### P0-1 续传起点不设“已确认”上限，崩溃后的尾部垃圾被当成有效数据

- 证据：`Server/resumableuploadsession.cpp:109-121`（`existingSize` 直接作为 `offset`）；`Server/msghandler.cpp:1281-1287`（把 `result.offset` 写回数据库，覆盖 `confirmed_offset`）。
- 触发：服务端被 `kill`、断电、崩溃、磁盘写满导致末块只写了一半。`.part` 的物理大小会包含“未确认或被截断”的尾部。
- 后果：下次续传从物理尾部继续，损坏字节被永久保留；`confirmed_offset` 这个已有的安全基准被绕过。`abortUpload` 的截断补偿（`Server/msghandler.cpp:1403-1419`）只覆盖“优雅中止”，覆盖不了进程崩溃。
- 影响面：Qt 客户端、Web 前端、群上传共用的暂存层。

### P0-2 续传链路主动丢失摘要校验

- 证据：
  - `29` 只携带魔数，不带摘要；服务端每槽初始化先清空摘要（`Server/msghandler.cpp:1255`），仅在“同一连接 97→29 采纳”时恢复（`1274-1277`）。
  - 复用会话时传入空摘要，SQL 把 `client_sha256` 写成 `NULL`（`Server/operatedb.cpp:241-252`），**把上一轮 97 登记的摘要也抹掉**。
  - Qt 客户端续传跳过 97（`Client/transfertask.cpp:1153`），恢复的任务也不保存摘要（`Client/transfertask.cpp:71-99` 快照字段无 `shaHex`）。
  - Web 前端“继续”同样 `skipFastcheck`（`web/frontend/src/stores/transfer.js:349-402`）。
- 后果：恰好是**最需要校验的续传场景**，服务端退化为“收到多少信多少”，commit 因 `expectedSha` 为空而跳过内容比对。P0-1/P1-1/P1-3 产生的任何混合内容都可以被静默转正。
- 说明：`97` 重放路径会使用会话行里的旧摘要（`Server/msghandler.cpp:1636-1656`），但这要求客户端愿意重算整文件摘要；Qt/Web 的“继续”都故意绕开了。

### P0-3 转正失败仍向客户端回 success + complete

- 证据：末块写成功后先登记 `deferredAckSuccess = success`（写盘成功），复算/转正落定后 `DeferredDataAck32` 无条件使用该值（`Server/msghandler.cpp:1885-1891`）。转正失败（大小不符、摘要不符、数据库不可达）只写数据库 `failed` 并删除暂存（`Server/fileobjectstore.cpp:271-288`）。
- 客户端：`Uploader::acknowledge` 收到 `success=true, complete=true` 即 `finish(true)`，任务显示完成（`Client/uploader.cpp:61-71`）。
- 后果：**文件没有入库，用户看到上传成功**。这是把 P0-2 的“可检测失败”变成“不可见数据丢失”的关键放大点。

### P1-1 暂存身份只含元数据，同名同大小不同内容会拼接

- 证据：`Server/resumableuploadsession.cpp:92-95`。
- 触发：用户修改文档/图片后另存，文件名与字节数恰好不变（同一编辑器、同一导出模板很常见）；或同名不同版本文件。
- 后果：服务端返回旧 `.part` 的长度作为起点，客户端 `seek` 到该点继续发送 → 最终文件 = 旧文件前缀 + 新文件后缀。P0-2 使其可以在无校验的情况下入库。

### P1-2 群上传与个人根目录共用暂存键，`groupId` 不参与

- 证据：群上传固定 `parent="/"`（`Server/msghandler.cpp:2848-2850`）；个人上传根目录同样是 `/`；键里没有群维度。
- 后果：同一用户向两个群（或群与个人根）上传同名同大小文件时共用同一 `.part`。串行会错误续传；并发会互相写坏（见 P1-3）。

### P1-3 同一账号多连接并发续传同一键，没有跨连接互斥

- 证据：`MsgHandler` 按连接创建（`Server/mytcpsocket.cpp:37`），`m_uploads`、`MAX_PARALLEL_UPLOADS`、`releaseOtherStagingHandles` 均为连接级（`Server/msghandler.cpp:1358-1371`）。
- 触发：同账号两台设备/两个窗口同时上传同名同大小文件，或断线重连后旧连接尚未被回收。
- 后果：两套 `receivedSize` 各自判连续，却写同一个 `.part`，内容交错；两行 `upload_session` 共享同一 `staging_path`，状态互相覆盖。有摘要时表现为转正失败；无摘要时静默入库。

### P1-4 客户端不校验服务端偏移连续性，也不按确认偏移 seek

- 证据：`Client/uploader.cpp:61-67` 只检查 `nextOffset < m_nextOffset`；`sendNextChunk` 依赖文件顺序读，未 `seek(m_nextOffset)`（`Client/uploader.cpp:83-99`）。
- 后果：服务端给出跳跃偏移时，客户端会用旧位置的数据配上新偏移头发出；服务端只校验头部偏移，正文可能错位。当前服务端不会产生这种值，但协议层没有防线，任何一侧的续传 bug 都会变成静默错位。

### P1-5 长文件名在 97 与 29 之间身份不一致（32 字节截断）

- 证据：`29` 的 name 字段为 32 字节定长（`Server/msghandler.cpp:1234-1243`、`web/frontend/src/protocol/commands/drive.js:217-222`、`Client/transfertask.cpp:548`）；`97` 允许 210 字节（`Server/msghandler.cpp:1514-1525`）。
- 后果：超过 31 字节（约 10 个汉字）的文件名在 29 被截断，`97→29` 的采纳条件（`Server/msghandler.cpp:1265-1269`）永不成立：97 建立的暂存被孤立、29 另建一份、最终入库名被截断。更严重的是，两个前 31 字节相同、大小相同的长文件名会落到同一暂存键，直接复用彼此的半成品。

### P2-1 `.part` 物理大小等于总大小即视为完成

- 证据：`Server/resumableuploadsession.cpp:116-120`。
- 后果：只要文件长度到齐就跳过“末块已确认”的证明；断电恰好写满整文件时会走这条捷径。

### P2-2 `verifying` 会话可被复用，复算与续传并发

- 证据：`Server/operatedb.cpp:277-279` 的可复用状态白名单包含 `verifying`；复算线程正在读同一 `.part` 时，新连接可以把同一行重置为 `uploading` 并再次提交。
- 后果：双提交、rename 失败、数据库状态互相覆盖；不会静默损坏内容（有摘要时），但会产生难以解释的失败。

### P2-3 暂存缺少按用户配额

- 单连接 3 个并发（`Server/protocol.h:334`），`.part` TTL 6 小时（`Server/reclaimscheduler.h:71`），会话 1 小时。多连接可长期占用磁盘，清理依赖 TTL。

### P2-4 暂存键拼接无长度前缀、无版本

- `sha1(owner|parent|display|size)` 使用裸分隔符拼接（`Server/resumableuploadsession.cpp:92-93`）。Windows 文件名/路径不能含 `|`，账号名约束未核实，实际风险低；但改键格式（如 P1-2 修复）时没有版本位，旧 `.part` 只能靠 TTL 回收。

## 4. 真实场景推演

**S1 断电续传**
上传 2 GB 文件到 60% → 机房断电 → `.part` 尾部残留半块 → 服务端重启 → 用户点“继续” → 服务端按物理大小从半块之后继续（P0-1），本次续传无摘要（P0-2）→ 内容已损坏 → 转正成功（`expectedSha` 为空）→ 用户拿到损坏文件。即使摘要存在，转正失败也会回“完成”（P0-3）。

**S2 同名替换**
上传 `季度报告.docx`（8,388,608 字节）到 50% 暂停 → 修改后另存，字节数碰巧相同 → 继续 → 旧前缀 + 新后缀混拼（P1-1）。客户端无感知。

**S3 双设备并发**
同一账号在台式机和笔记本同时上传 `照片集.zip`（大小相同）→ 两个连接各自续传同一 `.part`（P1-3）→ 交替写入 → 文件损坏或转正失败，两者状态都不可解释。

**S4 长文件名**
`2026年第三季度财务分析报告-终版.xlsx`（UTF-8 超过 31 字节）→ 97 用全名建暂存，29 用截断名新建 → 续传永远从 0 开始，入库名为截断乱码（P1-5）。

**S5 群与个人根**
个人根目录的 `资料.zip` 与发到群的 `资料.zip` 同名同大小 → 共用 `.part`（P1-2）→ 跨场景续传/互相写坏。

## 5. 现有的有效防线（避免误判）

- 停等协议 + `acceptWrittenChunk` 的连续块校验（`Server/resumableuploadsession.cpp:143-150`）挡住了乱序、空洞、重块。
- `abortUpload` 在优雅中止时把 `.part` 截断到已确认偏移（`Server/msghandler.cpp:1403-1419`）。
- 转正有大小/摘要双守卫，失败会删除暂存（`Server/fileobjectstore.cpp:271-288`），提供了“失败后重传即可恢复”的基础。
- 下载续传有客户端护栏 `checkResumeRespond`（`Client/transfertask.cpp:717-725`），上传没有对应物。
- 暂存有 TTL 回收（`Server/reclaimscheduler.cpp:380-410`）。

## 6. 影响面与未验证

- 受影响客户端：Qt 客户端、Web 前端（两者续传都跳过 97）。
- 受影响功能：个人上传、群上传、秒传预检后的普通上传；下载续传不在本次范围。
- 未执行：真实断电/进程崩溃、双连接并发、长文件名、同名替换的端到端复现。上述结论均来自代码路径与协议字段分析。
- 未检查：网关对 29/31 的转发是否附加超时/重试、TLS 层、旧版本客户端兼容策略。
