# 个人云盘与目录：25—30

实现定位：[文件页面](../Client/file.cpp)、[目标目录选择](../Client/folderselectdialog.cpp)、[服务端目录处理](../Server/msghandler.cpp)、[逻辑文件条目](../Server/fileobjectstore.cpp)、[物理内容回收](../Server/reclaimscheduler.cpp)。`user_file`（用户逻辑文件表）记录归属、逻辑父路径和名称，`file_object`（物理文件对象表）管理实际内容，两者不能混为一份物理目录树。

### 25. 浏览、刷新文件和目录列表

#### 功能目标

展示当前账号、当前目录下可操作的文件与文件夹，列表按页取回。逻辑条目记录文件归属、名称和父路径，物理文件对象保存实际字节，目录实体参与导航与沙箱校验。

#### 主回答（完整业务实现链路口述版）

客户端进入目录或点击刷新时，带上页起点和页量发送列表请求。服务端先校验认证状态、路径是否属于当前账号以及分页参数，再统计符合条件的条目，按稳定顺序取出当前页，并多读一条判断是否还有下一页。响应中同时返回总数、本页数据和分页信息，客户端校验记录边界后，首页替换列表、后续页追加列表。请求失败时保留已有内容，不把失败结果伪装成空目录；检测到目录发生变化时重新拉取。

#### 表达脉络（记忆钩子）

1. 进入目录或点击刷新 -> 2. 提交页起点和页量 -> 3. 校验身份、路径和分页参数 -> 4. 统计并稳定排序后取页 -> 5. 返回总数、本页和续页信息 -> 6. 客户端替换或追加，失败和变更时重拉

失败分支：路径越界、页参数非法、查询失败分别返回，不返回其他账号目录、不伪装成空目录；翻页按条目 ID 去重，被并发写入挤走的一条靠刷新补齐，不承诺跨页严格一致快照；深翻用锚点游标而不是加大页起点；界面合并刷新不等于请求去重

#### 追问卡片

**原完整链路补充（追问时展开）**

**进入与请求**：登录成功后云盘页面按认证账号确定用户根目录和当前浏览目录；首次进入或用户点击刷新时，客户端把「目录路径 + 页起点 + 页量」封装成目录列表请求 23，首页页起点为 0，之后每次以已加载条数作为新的页起点。页面缓存和本地拼接结果都不能作为服务端归属或完整性的依据。

**接入与路径授权**：服务端完成协议数据单元拆帧、认证状态和登录版本核验，以认证主体确定用户根目录，检查请求目录路径及其物理规范路径没有越界；同时校验分页参数——页起点不得为负、页量不超过服务端上限，参数越界直接返回失败，不用默认值兜底。

**定位与统计**：将当前浏览目录转换为该账号作用域内的逻辑父路径，先按同一组条件（账号、逻辑父路径、有效状态）统计该目录有效条目总数，供应答带回。计数和取页必须共用这一组过滤条件，否则总数与本页内容对不上。

**分页取页**：在同一条件下按「展示名升序、条目 ID 兜底」做稳定排序，用页起点跳过前若干行、按页量取一段；实际多读一条（页量 + 1）判断后面还有没有下一页，而不是拿「页起点 + 本页数量 < 总数」去猜，因为总数和取页是两次查询，其间可能已有并发写入。稳定排序加 ID 兜底是为了让同名条目在两次请求里位置固定，翻页不重不漏。

**组织列表与应答**：普通文件的目录列表项从个人逻辑条目取得展示名和类型，文件正文由关联的物理文件对象保存，大小取对象快照；目录项没有对象，大小按 0 处理；不能通过用户根目录下是否存在同名磁盘文件判断文件有效性。服务端把总数、页起点、页量、本页条目数量与条目字段按协议布局写入响应 24；查询失败、路径失败、参数非法分别返回失败，不返回其他账号目录，也不把失败伪装成空目录。

**客户端更新**：客户端检查响应长度和记录边界，按页起点区分两种合并方式——页起点为 0 时整体替换列表，非 0 时按条目 ID 去重后追加，同一页被重取不会出现重复项；总数用服务端统计值更新「已加载 / 总数」，滚动到底或点「加载更多」时带新页起点取下一页。翻页期间若发生刷新、目录变更事件或当前目录被切走，就丢弃手上的页起点从第一页重拉，否则旧偏移会套在新快照上，出现跳项或重复。界面刷新调度只合并控件重建次数，不改变分页语义。

**边界**：用户可从结果进入子目录、改名、移动、删除或下载，各操作提交时服务端重新核验条目归属和当前状态，列表展示不是持久权限凭证；分页解决的是「一次返回多少」，不解决「翻页期间目录变了」——并发插入或删除会让同一页起点前后的内容位移，客户端靠条目 ID 去重挡掉重复，被挤走的一条要靠刷新补齐，不能承诺跨页严格一致快照；页起点很深的翻页要跳过前面所有行，成本随偏移增长，需要深翻时改用上一页最后一条（展示名 + 条目 ID）作锚点的游标翻页，而不是继续加大偏移；连续刷新可以合并界面更新，但不能因此宣称每次请求都被去重。

- **个人云盘的目录列表为什么不直接扫描用户磁盘上的目录得到？** 列表的权威来源是 `user_file` 的个人逻辑条目，一行带账号归属、逻辑父路径、展示名和类型，服务端用认证主体派生的用户根目录限定查询范围。扫盘会漏掉没有对应磁盘文件的逻辑条目，表达不了同一个物理对象被多账号引用的多对一共享，还会把本机存储布局变成业务判断的一部分；扫盘只能用来对账物理残留。代价是目录存在性、父子关系和路径解析的一致性要自己维护。
- **客户端请求目录列表时，为什么不把磁盘上的绝对路径直接发给服务端？** 接受客户端给的路径，沙箱就变成客户端说了算。请求只带当前浏览目录和相对路径，服务端从连接认证会话确认主体，用账号推出用户根目录，把传来的路径归一化成根内逻辑键，涉及实体再比规范路径。绝对路径踩两个坑：暴露存储布局，把越权范围放大到能读哪块盘；字符串拼接边界难判，父级标记、重复分隔符都可能让前缀比较失效。代价是客户端要自己维护当前浏览目录，切目录和返回上级都得重算相对路径。
- **既然数据库里已经有目录树了，用户根目录下的物理路径是不是就没用了、可以不保留？** 不是没用，它是存储层本体而不是目录树的冗余副本。业务判断确实走 `user_file` 的逻辑父路径，但三件事数据库给不了：正文要流式读写真实文件，大文件塞库会撑大库体积和备份；沙箱比的是解析出的规范路径，没有真实目录就没有锚点，只能退化成字符串判断；权限、配额、句柄和回收清理也只能作用在实体目录上。砍掉它就得把层级、归属、边界全搬回数据库，还要另找落盘方案。代价是两侧不在同一事务，一致性靠双侧写加周期性补偿维持。
- **刷新目录列表为什么你要排序发过去，而不是直接使用目录id来直接发过去？为什么使用服务端进行排序然后发给客户端，不能客户端来排序？** 页起点分页是「跳过前 N 行再取一段」，只有服务端按固定顺序取数这句话才成立，所以排序天然落在服务端。让客户端自己排，它只能重排手上这份旧快照，发现不了增删改移，拿不到分页外的条目，本地顺序还和服务端翻页边界对不上，翻页就会重复或漏项。条目 ID 只做同名兜底、不单独当排序键：ID 是创建序，改名后位置不动，不符合按名浏览的习惯。排序客户端可以只用于展示，刷新必须回服务端重新取数。
- **个人云盘里的文件路径和文件名是怎么校验，才能挡住目录穿越和越权访问的？** 分三层。路径格式：目录路径先归一成用户根内的逻辑键，要求斜杠开头结尾，反斜杠、空段、点和点点直接失败，不做默认修正。名字本身：展示名禁路径分隔符并限字节长度，防夹带整条路径和父级跳转。真边界：涉及实体的读写按认证主体派生用户根目录，对规范路径做前缀确认，根外拒绝。不把前两层放客户端，报文可以手工构造，客户端声明一律不采信。成本是每条请求多一次归一化和规范路径计算，换来的是越界判断只依赖服务端自己算出来的东西，安全性提高。
- **我这个云盘里，目录、个人逻辑条目和物理文件对象三者是什么关系？** 分开的三层。目录是用户可见层级，数据上是 `user_file` 里一条类型为目录的条目，同时对应磁盘目录实体，用于导航和实体路径授权；文件是两条记录配合，个人逻辑条目回答内容在谁的哪个目录、叫什么，`file_object` 保存字节、大小和摘要。所以同一物理对象可被多账号条目或群文件引用，不合成一张表就表达不了这种多对一共享，代价是每次操作要维护两侧一致。判断有效性只看条目和对象，不看磁盘同名文件。
- **如果客户端把请求里的目录路径改成另一个用户的目录，会发生什么？** 拿不到内容，可见范围按身份算，不按请求路径算。服务端先在连接认证会话确认主体和登录版本，用账号推出用户根目录，传来的路径按相对根归一：指向别人的写法要么落到根外判越界，要么是不存在的路径返回失败。报文里的身份字段没有权重，账号只从会话取；要防的是「路径在库里存在就返回」，所以查询全带账号条件，`user_file` 归属列参与过滤。同账号自己的目录间不做二次隔离，不在我的边界内。
- **目录和文件数量变大时，这个列表功能哪里会先出现压力？** 先放大的是统计与深翻页：每页都要在同一条件下做一次计数，页起点越大数据库要跳过的行越多。单页条数有上限，所以压力从「一次传多少」变成「翻多深、翻多频」。解决思路是深翻改成锚点游标，避免大偏移跳行；计数只在首页算或允许缓存与近似，给过滤和排序条件建覆盖索引。这样压力就从「翻多深」回到可控的单页查询。
- **如果让你重新设计一次目录模型，你会改动哪里？** 改变目录条目的构建，将每一个目录条目锚定为几级目录以及父目录的id,目录名更改和目录所在位置无关，目录的所有操作就只需要改变目录的级别以及父目录即可，所有的文件路径使用目录id来进行定位，从而减少路径字符串级联更新。当前目录仍大量使用路径定位，父目录变化会牵动许多后代字符串；分享链接已改为绑定源条目标识，不受父目录变化影响。
- **每次目录一变动就跳回第 0 页重拉，不浪费吗？体验也不好，有什么更好的方案？** 跳回第 0 页是正确性兜底，确实浪费。改进分三档：局部修补，变更应答带受影响条目，客户端只改那一行、页起点不动，代价是服务端要算影响范围；增量同步，客户端带版本号，服务端只回差量，代价是维护变更序号、位移自己算；事件推送，实时性最好，要处理丢事件后的全量校准。底线是都要保留全量刷新做校准兜底，增量丢了本地状态会悄悄漂移；当前先把正确性钉死，体验优化是明确的下一步。

### 26. 进入子目录、返回上级目录

#### 功能目标

维护个人云盘的导航位置，并限制在本人根目录之内。客户端路径状态是交互状态，服务端沙箱校验才是安全边界。

#### 主回答（完整业务实现链路口述版）

用户双击目录项进入子目录时，客户端先检查条目类型，普通文件不会被当成目录进入，再按当前浏览目录生成目标请求路径；返回上级时去掉最后一层目录名，并在界面阻止越过用户根目录。客户端发送切换目录请求后，服务端拆帧、核验认证状态与登录版本，从认证主体取得用户根目录，依次检查请求路径格式、目录是否现存以及物理规范路径是否仍在本人根目录内；目录切换处理确认目标确实是可访问目录，解析失败、目录已被删除、父级跳转或指向根外的链接都不能放行。服务端以切换响应返回结果，客户端只有成功才更新当前浏览目录，并把页起点归零请求该目录列表首页，失败时保留可解释的当前位置并提示。新的目录列表按个人逻辑条目的逻辑父路径组织、按页返回，物理目录只用于导航和实体路径授权，不把对象存储目录暴露成用户可浏览目录；切换成功不代表永久放行，随后创建或上传时服务端再次校验本次提交的父目录，规范路径检查与实际文件操作之间仍存在本机并发修改的边界。

#### 表达脉络（记忆钩子）

1. 检查条目类型生成目标路径 -> 2. 发送切换目录请求 -> 3. 核验身份路径与规范边界 -> 4. 拒绝越界跳转与根外链接 -> 5. 成功归零页起点取首页 -> 6. 后续操作仍再校验边界

#### 追问卡片

- **做目录沙箱校验时，为什么不能只判断路径是不是以用户根目录的字符串开头？** 因为前缀相等不代表真的在同一个目录里面，能绕的口子有好几个。第一是相似前缀，用户根如果是某个账号目录的前半段，比它多一个字符的相邻目录也算以它开头，别人的目录就进来了，所以我比前缀时把分隔符当边界，根目录统一带结尾分隔符再比。第二是父级跳转和混合分隔符，字符串看着在根内，解析之后就跑到根外，得先归一化再判断。第三是要新建的目标本身还不存在，没有真实路径可比，这时只能退去校验它已存在的父目录。这几步都建立在用认证主体派生的用户根上，不拿客户端传来的根做比较，否则前面全部白做。
- **用户双击进入某个目录时，这个目录刚好被另一个操作删掉了，服务端怎么处理？** 我不在客户端预判，双击就发切换目录请求，结果看服务端应答。服务端先确认这条个人逻辑条目在当前账号作用域里还存在并且类型是目录，再看对应的目录实体和它的规范路径还在不在本人根内，任何一步不成立就返回失败。客户端只有拿到成功应答才更新当前浏览目录并取该目录的列表；失败时保留原来可解释的浏览位置，提示目录已经被删除，让用户自己刷新。实现的结果是用户会看到一次失败提示，并且换来了界面不会跳进一个不存在的目录、显示的却是别处的内容。
- **怎样测试路径穿越、相似目录前缀、符号链接和伪造用户名，确认只能访问本人的目录？** 准备本人根、相邻同前缀目录和另一账号目录，提交父级跳转、混合分隔符、绝对路径及指向根外的链接；账号字段与连接身份也故意不一致。检查规范化后的真实边界、认证主体及条目归属，不能只按字符串开头判断。测试不仅看导航应答，还要核对没有泄露目录内容或修改其他用户数据，并在列表、移动和下载入口验证同类边界。

### 27. 创建文件夹

#### 功能目标

在当前用户有权访问的目录下建立子目录，同时登记逻辑目录条目。磁盘创建和逻辑登记存在非原子边界。

#### 主回答（完整业务实现链路口述版）

用户在当前浏览目录输入文件夹展示名，客户端检查空名与非法分隔符后发送创建目录请求。服务端完成报文边界、认证状态和登录版本检查，按认证主体确定用户根目录，校验真实父目录存在且处于本人范围；创建目录处理再单独校验新名称，防止用新名称夹带完整路径或父级跳转，新目标尚不存在时不要求其自身已有物理规范路径。登记目录条目，保存账号归属、逻辑父路径、展示名和目录类型，使逻辑层级与目录实体对应，最后再尝试创建目录实体。目录实体与数据库登记不在同一事务，数据库操作失败就是创建文件夹失败，数据库操作成功就是创建文件夹成功，目录创建失败了可以使用周期性任务补偿创建。最后服务端将结果装入响应返回，客户端提示并从第一页刷新当前目录列表，新目录可通过正常导航进入。

#### 表达脉络（记忆钩子）

1. 校验空名与分隔符发请求 -> 2. 核验父目录存在与范围 -> 3. 单独校验新名防夹带路径 -> 4. 先建实体按创建结果返回 -> 5. 登记条目两侧非同一事务 -> 6. 刷新列表并区分失败点

#### 追问卡片

- **创建文件夹时，为什么要在磁盘上真的建一个目录实体，而不是只在数据库登记一条逻辑条目？** 因为我的目录导航和沙箱校验都要用到实体目录，只有数据库记录的话这两件事不成立。用户根目录、当前浏览目录和规范路径检查都落在磁盘上，一个纯逻辑目录没有真实路径可以解析，也就没法判断它到底在不在本人根内；后续进入这个目录、在里面创建或者上传，还要反复确认目标目录确实存在。所以创建文件夹时我既登记个人逻辑条目，也建对应的目录实体，让逻辑层级和磁盘层级对得上。纯逻辑目录我也考虑过，好处是改名和删除没有磁盘副作用，代价是目录存在性、父子关系、路径解析全要在数据库里自己维护一致性，还得另找一套机制保证文件真能落盘。现在这套的代价是两侧不在同一事务里，任何一侧失败都按实际执行结果返回，实体侧的缺口用周期性补偿任务重建。
- **创建文件夹时同名目录已经存在，服务端应该怎么返回？** 直接返回失败，原因标明「名字已存在」，客户端提示用户改名；判断条件是账号、逻辑父路径加展示名，唯一性只要求同一个父目录下不重名，不同目录允许同名。结果就是重复点击会看到失败提示，但这个失败反映的是真实状态，保证了同目录不重名的结果。
- **要新建的目录本身还不存在，这时候的真实路径检查该怎么做？** 拆成父目录和名字两部分做。目标路径先按逻辑键归一，确认没有父级标记和多余分隔符；然后取它已存在的父目录，用认证主体派生的用户根对父目录做规范路径前缀检查，这一步能拦住把整条绝对路径或者根外位置塞进新名字的做法。新名字自己单独校验，禁止路径分隔符并限制长度，不允许它再表达任何层级。边界情况是检查与实际创建之间仍有时间窗，父目录在这一瞬间被换掉只能靠真正落地时的结果兜住。
- **如果目录解析使用的真实物理路径，那么如果在数据库逻辑路径和磁盘物理路径不统一的时候，不会出现解析错误的情况吗？这种情况怎么解决？** 会出现，不一致的窗口这套设计承认存在——登记和建目录不在同一事务里，改名移动的级联也可能只完成一侧——所以我从不假设两侧一致。处理分三层：第一，业务权威放在数据库，列表、定位、归属判断全走 `user_file` 的逻辑父路径，不碰磁盘，对于物理目录删除失败残留的情况可以解决；第二，涉及实体的操作先逻辑后物理，先按账号加逻辑父路径确认条目存在，再解析实体做规范路径边界检查，解析失败就按实际结果返回失败，不用逻辑路径硬拼物理路径去打开，也不静默兜底，路径错位时硬拼就是把内容写进错误位置，这个解决了物理目录创建失败的情况，只不过可能会出现目录实际存在但是创建目录失败的异常情况窗口；第三，缺口靠周期性补偿任务收敛，登记成功但实体没建成的按数据库记录重建目录实体，磁盘上多出来的空目录不影响业务，留给对账清理。代价是不一致窗口内该目录的实体操作会失败、用户要重试，换来的是不会出现按错位路径写入的静默错误。
- **创建文件夹时名称里禁止出现的符号有什么，你列举一下？** 分三类。一是路径分隔符：正斜杠、反斜杠，挡住用一层名字夹带整条路径或做父级跳转。二是 Windows 文件系统保留的七个符号：冒号、星号、问号、小于号、大于号、竖线、双引号——冒号是盘符分隔，星号问号是通配符，其余是重定向和引用符，这类名字磁盘上根本建不出来。三是控制字符：0 到 31 全禁，包括换行和制表符，避免污染日志和列表渲染。另外首尾空格和结尾的点也去掉，防止肉眼同名、库里两条。代价是规则跟着平台走，换操作系统要重新核对保留符号。

### 28. 重命名文件或文件夹

#### 功能目标

改变用户可见名称，同时保持物理文件对象和子目录关系正确。逻辑文件改名通常不需要搬移共享内容。

#### 主回答（完整业务实现链路口述版）

用户选择文件或文件夹并输入新展示名，客户端保存原展示名、条目类型和当前浏览目录后发送重命名请求。服务端拆帧、核验认证状态与登录版本，以认证主体做逻辑路径授权，目录操作同时进行实体路径授权并独立限制新名称；再按账号、逻辑父路径和原展示名定位个人逻辑条目，确认类型与目标冲突，不能用客户端提供的路径操作其他账号的条目。文件改名只更新个人逻辑条目的展示名，不修改关联对象标识、内容摘要和物理文件对象正文，也不会改掉其他账号或群的展示名；目录改名还要修改目录实体名称，并级联更新后代个人逻辑条目的逻辑父路径，逻辑层级和磁盘层级都需处理。分享链接绑定的是源逻辑条目标识而不是源路径，重命名只改条目自身的展示名或父路径，已发出的分享链接不受影响，不需要同步更新。服务端返回重命名响应，客户端成功后从第一页重新获取当前目录列表，失败保留结果提示并以刷新后的状态为准；数据库条目和目录实体不在同一事务，中途失败须区分哪一侧已经变更，再决定重试或补偿。

#### 表达脉络（记忆钩子）

1. 保存原名类型发重命名 -> 2. 双重授权并独立限新名 -> 3. 按父路径原名定位查冲突 -> 4. 文件只改展示名不动正文 -> 5. 目录级联后代逻辑父路径 -> 6. 刷新核对哪侧已变更

#### 追问卡片

- **给文件重命名时，为什么不去改物理文件对象的名字？** 因为名字和正文在我这是两层东西，重命名的动作范围只覆盖上层。具体流程：文件重命名只更新 `user_file` 里那条个人逻辑条目的展示名这一个字段，关联的对象的所有内容一律不动。原因在于同一个物理对象不止这一条引用——本账号别的目录、别人接收保存的副本、群文件都可能指着它，改对象名字等于一个人的界面操作改掉所有引用者看到的东西，别人的下载和列表跟着失效。所以名字只留在逻辑条目这一层改，物理对象保持中立，改名就落成一次便宜的数据库更新，不复制也不搬运字节。代价是判断文件有效要同时看条目和对象，展示名和实际存储位置会长期不一致，排查内容得按对象标识找，不能顺着展示名找。
- **重命名时新名字在这个目录下已经被占用，服务端怎么处理？** 我先查冲突再拒，不做静默覆盖。服务端按账号、逻辑父路径和原展示名定位到个人逻辑条目、确认类型之后，用同一组作用域条件去查目标名字有没有被有效条目占用，命中就返回名字已存在的失败，由客户端提示改名。那为什么不自动加个后缀？因为用户明确要叫这个名字，程序悄悄换成另一个，他后面按名字找不到，而且对于创建目录来说一般不会使用后缀的方式来解决重命名。自动加后缀是移动那条路径上我给的重名安置方式，重命名这边保持失败。最终方案的代价是重名时要把决定交回用户，多一次交互，换来的是同一个目录下名字完全由用户决定并且不会出现重名的情况。
- **文件夹重命名之后，已经发出去的分享链接会自动跟着改吗？** 不需要跟着改，因为分享链接绑定的是源逻辑条目标识，不是源相对路径。重命名只改条目自身的展示名或父路径，条目标识不变，链接按标识仍能定位到同一条目，所以重命名的成功分支里没有任何分享记录更新动作，也不存在改名和链接更新不在一个事务的问题。访问时按条目标识定位源条目，校验条目有效和分享记录有效后再走挂接，链接展示的文件名实时取条目当前展示名。代价是分享记录的定位从路径换成条目标识，写入和解析规则都按这套口径维护；条目被删除后标识查不到有效条目，链接按删除语义失效，而不是靠路径定位不到来失败。
- **一个账号只允许一个登录，是不是就不存在重命名并发了？** 不是，单登录只排掉两个人用同一账号这一种情况，同一个客户端自己就能造出并发。我发请求不阻塞界面：连点两次重命名、上一个重命名还没回就点了移动，或者后台上传任务正占着同一个目录，都会让几个请求同时在链路上排队，服务端按到达顺序处理，后一个看到的是前一个改完之后的状态。列表这边更明显，屏幕上那份数据是上一次应答的快照，从显示到点击之间条目可能已经被改名或者移走，客户端拿旧的名字加父路径去定位就会落空。所以我依赖的是服务端每次请求重新按账号、逻辑父路径和展示名定位并重查目标冲突，不依赖只有一个登录所以不会撞，从而直接进行操作。
- **两个重命名，或重命名与移动、删除同时作用于同一条目，怎样判断结果和界面是否正确？** 我开两个客户端窗口对同一条目交错发操作来读结论。用一个文件和它的父目录做组合：一边发文件重命名，另一边同时发父目录改名或者父目录删除；再试两个重命名抢同一个目标名字。每一步记下服务端应答，然后去 `user_file` 查这几行的账号归属、逻辑父路径、展示名和有效状态，看有没有出现两条有效条目指向互相矛盾的位置，或者目标名字把一条无关条目覆盖掉。目录改名要额外核对磁盘上的目录实体名字和后代条目的逻辑父路径是不是同步改过来了，分享记录的源条目标识没有跟着变动、仍指向原条目，单独再查一遍。界面这边看的是失败之后停在哪、刷新一次能不能回到服务端的状态，不能永久显示成功。预期我按规则定而不按当前输出定：不覆盖无关条目，不留半改名的子树，因为目录实体和逻辑条目之间没有一个共同事务。
- **两个请求都基于同一份旧列表去改同一个条目，后发的那一个会怎么样？** 一般落在失败上，这正是服务端每次重新定位的原因。两个请求带的是同一份原展示名加原父路径：先提交的一方把名字或者父路径改掉了，后发的请求再按账号、逻辑父路径和展示名去定位就找不到那一行，返回目标不存在；如果这期间同目录下恰好出现了一条新的同名条目，还会撞上限定在这个父目录范围内的唯一性检查。所以改不到是预期行为而不是异常，比按位置盲改要安全。我没有靠稳定标识去避开这个问题，因为那需要另加一套条目稳定标识并在每次操作前重查归属，而现在的定位方式已经能保证不会改到别人的条目。代价是用户可以碰到一次操作失败，需要刷新后重做，换来的是不会把新名字安到一条无关条目上。


### 29. 移动文件或文件夹

#### 功能目标

在本人的云盘内改变条目父目录，防止跨用户移动、覆盖冲突或把目录放进自己的子树。

#### 主回答（完整业务实现链路口述版）

用户在目录列表中选择源条目后打开移动目标选择器，客户端先请求查询可选子目录，服务端按认证主体返回子目录浏览列表；确认目标后，客户端把源位置、源展示名、条目类型和目标位置封装成移动请求发出。服务端完成拆帧、认证状态与登录版本核验，分别检查源归属、源是否存在、目标目录可访问及物理规范路径边界；目录移动额外检查不能放入自身或自身后代，同目录无效移动与目标重名按当前规则处理，不因客户端选择器已经限制就省略服务端校验。执行时文件条目调用条目位置变更调整逻辑父路径和最终展示名，重名安置按规则选择可用后缀，物理文件对象保持原位；目录条目还要调整目录实体位置并级联改写后代的逻辑父路径，不能把所有移动都描述成搬运正文或单次数据库更新。分享链接绑定条目标识，移动只改条目父路径，已发出的分享链接不受影响，不需要同步更新；服务端回传结果和最终展示名，客户端收到后才提示并刷新源、目标相关视图，不能先挪动界面条目就当作成功。并发删除、重命名或上传可能使先前路径失效，后续传输任务按自己的目标重新初始化，当前不能保证所有任务自动跟随目录移动。

#### 表达脉络（记忆钩子）

1. 先查可选子目录再定目标 -> 2. 封装源类型目标发请求 -> 3. 核验归属存在与目标边界 -> 4. 禁入自身文件只改父路径 -> 5. 目录级联非共事务 -> 6. 收到结果后才刷新界面

#### 追问卡片

- **把一个目录移动到它自己的子目录下会发生什么，服务端怎么拦？** 直接拒绝，这是目录移动比文件移动多出的一条检查。逻辑上它会把父子关系拧成环：这个目录的父路径变成自己某个子孙的路径，从它往下遍历会绕回自身，导航进得去出不来，删除时收集子树也可能一直递归。判断不能只比源路径和目标路径两个字符串相等，那只挡得住原地移进同一个目录；我拿目标路径和源目录整棵子树比前缀，命中就说明目标落在自己的后代里，返回失败。子树集合是在内存里按逻辑父路径前缀收集的，不用数据库的模糊匹配来做这个业务判断。代价是移目录前要先算出整棵子树的条目集合，深层目录多一次遍历，比只改一行的文件移动贵。
- **移动一个正在被上传任务使用的目录，会发生什么？** 举例说：往 `/相册/旅行/` 传一个大文件传到一半，把 `旅行` 这个目录移到 `/备份/` 下面。结论是上传不受影响、照常完成，但它不跟随目录搬家。上传任务在初始化时就把目标目录和落地路径算好、锁死在自己的会话状态里，之后只认这份记录；移动只负责搬目录本身（改数据库父路径、搬磁盘实体），不会回头修改在途任务。这样划边界是因为：半路去改一个正在写盘的任务的目标，它正在写的位置和记录的目标就对不上，比「文件没出现在预期位置」难收拾得多。落到现象上：上传完成后条目按任务开局锁定的那份目标登记，旧位置看不到这个文件，刷新后在 `旅行` 目录现在所在的新位置看到它——这个结果对用户是反直觉的，需要向用户解释一句。移动之后才发起的新上传，初始化时按新位置算目标，正常落进新位置。要真正做到在途任务跟随移动，得给目录一个稳定标识、任务只存标识不存路径、每次写之前重新解析当前位置。
- **移动与源目录改名、目标目录删除并发时，怎样验证没有幽灵条目或者越界安置？** 我构造的是选择器返回之后世界变了这个窗口。开两个客户端窗口，先在源目录上打开移动目标选择器拿到候选目录，这个对话框不动，去另一个窗口把刚才选的目标目录改名或者直接删掉，再回头提交移动。看服务端应答，然后去 `user_file` 查这条记录最终的账号归属、逻辑父路径和展示名，确认落点真是我要的那个目录而不是同名复用的另一条。目录移动还要核对磁盘上的目录实体位置和后代条目的逻辑父路径有没有一起改写，分享记录的源条目标识没有跟着变动、仍指向同一条目，单独查一遍。文件移动的预期是 `file_object` 那一侧正文不动，只换父路径，所以两侧分开核对。失败时界面要停在原位置并给出可解释提示，刷新一次看能不能回到服务端的真相，不能提前把条目挪过去当成已经成功。

### 30. 删除文件或文件夹

#### 功能目标

删除本人条目或整棵目录子树，并正确释放引用，避免把其他人或群仍使用的物理内容一起删掉。

#### 主回答（完整业务实现链路口述版）

用户选定文件或文件夹并确认删除后，客户端把当前浏览目录、展示名和条目类型封装成删除请求。服务端完成拆帧、认证状态和登录版本检查，从认证主体确定用户根目录并执行逻辑路径授权，目录删除同时检查实体路径边界。定位属于该账号的个人逻辑条目后，文件条目通过条目释放在事务中标记删除并减少对象引用计数；目录条目通过目录子树释放处理当前账号范围内的目录及后代条目，释放子树内各个文件的引用，不能只标记最上层目录。清理目录实体与子目录和数据库条目更新不构成跨资源事务，任何失败要按实际执行结果返回。服务端封装删除响应，客户端提示结果并从第一页刷新当前目录列表；界面消失只表示个人条目不再展示，不等于共享正文已删除或磁盘空间立即释放。零引用的物理文件对象进入回收规则，回收调度器同时核对对象回收状态、宽限期、实际个人条目和群文件引用，取得回收权后才删除物理对象，删除失败保留可重试状态由后续轮次处理，不能忽略仍在使用的句柄或其他有效引用，正在下载的场景还要区分初始化前与已经打开源句柄后。分享接收者已建立的独立个人条目和群文件对象引用不随源条目自动删除，删除本人的文件不能撤回别人已保存的内容；绑定被删条目的分享链接按标识查不到有效条目，随之失效。

#### 表达脉络（记忆钩子）

1. 确认删除封装删除请求 -> 2. 认证授权并查实体边界 -> 3. 文件标记删除减引用数 -> 4. 目录释放整个子树引用 -> 5. 界面消失不等于删净 -> 6. 回收核对引用宽限期

#### 追问卡片

- **删除文件时，为什么不立刻把物理文件从磁盘上删掉？** 因为一条个人逻辑条目告诉不了我这个物理文件对象还有没有别人在用。正文存在 `file_object` 里，可以被同一个账号的多个条目、别人接收保存的副本以及群文件同时引用，删除请求只表达我这一份不要了。真在这一刻删磁盘，任何一个还在引用它的人下次下载就是文件不存在，这种错误不可逆也补不回来。所以我走引用释放：文件条目在事务里标记删除并把对象引用计数减一，目录条目要递归释放子树里每一个文件的引用，不能只标记最上层那条。计数归零的对象才进回收规则，回收调度器还要再核对对象的回收状态、宽限期和实际的个人条目与群文件引用，取得回收权才真删。结果是空间不会立即下降，零引用内容要多留一段宽限期，换到的是共享正文不会被一个人的删除牵连，以及待回收的物理文件可以被之后新的逻辑文件复用。
- **这个个人云盘有没有回收站和文件恢复功能？** 没有面向用户的回收站，我不会把对象还留着说成有这个功能。删除走的是引用释放：个人逻辑条目标成无效、对象引用计数减一，零引用对象还要过一段宽限期才由回收调度器真删，所以内容在物理上确实晚一点才消失。但这不等于回收站，用户这边没有任何入口能列出被删掉的条目、挑一条还原，也看不到期限是多久；条目一旦无效就不出现在任何列表里，它的逻辑父路径和展示名还可能被后续同名新建复用，还原时要放回哪一层并没有定义。要做恢复得补三件事：一张能查的已删条目视图、一个把条目重新置为有效并放回原父目录的动作，以及和引用计数、宽限期对齐的期限与权限判断。现在这套里只有最底层的对象延迟删除是现成的。
- **删除与改名、移动同时发生，怎样验证不会删错条目或者多减一次引用？** 我围绕同一条目交错发这几种请求来读结果。先让一个文件条目和另一个账号的条目共享同一个物理文件对象，然后构造两套时序：一套是先改名再删除，另一套是删除请求已经发出去、还在排队时用旧路径提交移动。每一步记下应答，再去 `user_file` 看这条记录的账号归属、逻辑父路径、展示名和有效状态，去 `file_object` 看引用计数和回收状态。我要读出两个结论：删除只命中我指定的那一行，不会因为名字或父路径刚变过就误删了占用同一个原名的另一条；同一个删除重复发不能把计数多减一次。目录删除额外核对整棵子树的后代条目是否都释放了。数据库更新和磁盘清理只完成一侧时按实际残留说明，不把局部成功讲成整体原子成功。
- **删除一个文件后，怎样验证只释放当前引用，没有删掉其他用户或群还在使用的正文？** 让两个账号和一个群分别建立指向同一物理文件对象的有效引用，逐个删除并检查各侧列表、下载结果、引用记录和物理对象。仍有有效引用时正文必须可用；最后一个引用释放后再驱动回收，检查实际引用和对象状态，而不是要求删除应答一到空间就立刻下降。还要覆盖重复删除和回收期间重新建立引用，防止错误回收共享内容。
- **删除大目录需要多少数据库和磁盘操作，怎样测试耗时及对其他业务的影响？** 分别增加条目数量、目录深度和共享对象比例，记录删除总耗时、数据库语句及事务时间、磁盘操作和内存峰值，同时持续发送心跳与聊天。用请求延迟判断递归清理是否占住事件循环，不能仅以删除最终成功证明没有阻塞。测试结束还要核对子树引用完整释放、外部引用仍可用；超大目录是否需分批或后台清理属于测试后再评估的设计。
- **删除一个正在被下载的目录，会发生什么？** 这两件事要分开看：删的是个人逻辑条目的可见引用，下载拿的是已经打开的内容句柄，不是同一个东西。目录子树释放会把当前账号范围内这个目录和它的后代条目标成无效，并逐个释放子树内文件的引用，界面上立刻消失，之后从列表已经点不到它。已经在传的那一路不会回头重查目录，它按自己会话里定下的目标继续读，物理内容因为仍有引用不会被回收调度器在这时删掉，可以读完。受影响的是还没开始的下载：条目已经无效，服务端按账号、逻辑父路径和展示名定位不到，返回失败而不是偷偷给一份看不见的文件。所以综合来看，能够保证的是不会出现目录删除导致正在执行的下载任务失效。
- **删除一个文件之后，磁盘空间为什么不一定会马上释放？** 因为用户点删除释放的是自己这一份可见引用，不是磁盘上的字节。正文在 `file_object` 里是共享的：同一个人可以在两个目录放同一份内容，别人接收文件和群里保存文件也各自形成一份引用，都指向同一个物理对象。删除只把当前条目置为无效并把引用计数减一，只要还剩任何一条有效引用，物理内容就必须留着，否则那个人的下载会直接坏掉。计数归零之后也不马上删，对象要先进回收规则、过完宽限期，回收调度器再核对对象状态、实际的个人条目和群文件引用，确认没有仍在使用的句柄，取得回收权才真删，删除失败还会留在可重试状态等后续轮次。代价是空间下降是延迟且不确定的，不能拿删除应答回来了当作磁盘占用该下降的依据。
- **引用计数和数据库不在同一个事务里，出现不一致时怎么处理？** 我把可回滚的放事务里，不可逆的放事务外。删除的数据库动作是一步：在一个事务里把条目标记无效并给引用计数减一，这一步要么整体成功要么整体回滚，所以列表状态和计数不会各说一套。真删物理文件不在这个事务里做，因为它失败的原因和数据库无关，文件被占用、权限、磁盘状态都有可能，硬塞进事务只会让一次删除两边都拿不到明确结果。计数归零的对象由回收任务扫出来，过了宽限期再重查实际引用才删，删失败就把对象留在可重试状态等下一轮。所以计数即使因为某次异常偏了，也不会只靠一个零值就把还有人在用的正文删掉，回收前的实际引用检查是第二道依据。代价是磁盘释放滞后，中间态需要一个任务持续在跑。
- **回收器删错文件的最坏影响是什么，当前怎样降低这个风险？** 最坏情况是一次误删打掉所有引用者的正文。同一份内容可能被几个账号和群文件同时指向，回收器要是只看计数归零就动手，删掉的不只是某个人的目录项，而是所有共享它的人下次下载都读不到的东西，而且没有还原入口。所以我把风险压在不可逆动作之前的几道检查上：对象要先在回收规则里并且过了宽限期才成为候选；候选时不单独信计数，去实际查有效的个人逻辑条目和群文件引用，查到任何一条就不回收；删除的路径必须限制在允许的存储根内做规范化检查，不拼未经校验的路径；确认之后由它取得回收权才删，删失败保留可重试状态而不是静默跳过。代价是垃圾会在对象表里堆一段时间，磁盘回收变慢，这比误删便宜。
- **已经有对象引用计数了，为什么删除物理内容前还要再查一遍实际引用？** 因为计数是一个会漂移的推导状态，实际条目才是事实。引用计数记在物理文件对象那一侧，靠上传落库、删除、释放这些路径去增减，只要有一次异常回滚、重复释放或者跨资源失败没补上，它就会偏。少减一次只是空间晚点回收，多减一次就把还有人在用的对象算成零引用，回收器据此删正文，后果是所有引用者的下载坏掉，而数据库里那些条目看着仍然有效。所以真删之前我再拿实际引用做一遍依据：按对象标识去查有没有有效的个人逻辑条目和群文件引用，查到了就不回收。为什么不把计数当真值？它的意义是让业务快速判断状态，便宜且能走索引；不可逆的删除要的是可复核的证据。代价是每轮回收多一类查询。
