
# 好友管理：09—12

### 09. 用户查询

#### 功能目标

分页展示当前账号能发现和添加的陌生用户，默认每页 50 条，附带查询那一刻的在线/离线标记。在线标记只用来展示，不当成权限判断依据。

#### 主回答（完整业务实现链路口述版）

我给在线用户列表做了分页，每页默认 50 条。用户打开这个窗口，或者换了搜索词，我先把本地列表清空、页码归零，然后发第一页请求——请求里带三个东西：每页要多少条、从哪里开始翻、还有搜索关键词。

服务端收到后按当前登录人排除自己和已经是好友的人，再按关键词搜名字。这里我做了两件关键的事：一是先查符合条件的总共有多少人，二是按名字排好序取一段。总数超过 1000 的话就封顶，服务端会告诉客户端还有没有下一页，客户端据此显示"加载更多"按钮。这样用户不会一下子看到几千条，也能按需往下翻。

#### 表达脉络（记忆钩子）

1. 用户打开窗口或换搜索词 → 2. 客户端清空列表、页码归零 → 3. 发带 limit+offset+关键词的请求 → 4. 服务端排除自己和好友、搜关键词 → 5. 查总数、按名字排序取一段 → 6. 回总数+还有没有下一页+本页条目 → 7. 客户端追加、显示"加载更多"

#### 追问卡片

**面试官追问时这样答：**
- **"用户列表为什么每次都实时向服务端拉取，而不是本地缓存一份？"** 我是把这份列表定义成参考信息才这么选的：陌生用户列表的可添加性受太多事件影响——有人注册注销、有人改名、我自己这边加了好友，任何一条发生本地缓存就脏了，而且失效时机客户端根本感知不到。具体做法是每次打开窗口或换搜索词就清空本地列表、页码归零，按 limit=50、offset=0 重新发请求，在线标记也是服务端查询那一刻现算的。代价我认：同样的查询反复打到服务端，多一遍数据库访问和来回报文。替代方案是本地缓存加过期时间、或者服务端推送失效通知，但要再搭一整套同步逻辑，换来的只是省几次本来就不重的查询，而且缓存一脏就会出现"加了好友列表里还挂着这个人"的尴尬。所以我用另一条路兜底：展示允许过期，真要加好友时服务端拿当前登录人重新校验，脏缓存不会造成错误操作。
- **"分页是怎么设计的？"** 我用的是 limit/offset 模式。客户端翻页时把"已经加载了多少条"当作新的 offset 继续请求。服务端的好处是简单——同一套逻辑就能处理任何一页。唯一要注意的是翻页期间如果有人注册新号或者被删号，offset 可能会漂移，跳过或者重复一两条，但用户刷新一下就好了，这个取舍是值得的。
- **"为什么不用游标分页？"** 游标分页我考虑过，没用上是因为它解决的问题在这个场景不存在。游标要拿上一页最后一条记录当锚点，适合聊天历史那种一条都不能错、不能漏的严格连续列表，而且不方便跳页。用户查询这边就是 limit/offset：客户端把已加载条数当 offset 传上去，每页 50 条，服务端同一套查询换个 offset 就能出任意一页，实现和理解成本都低。这里的诉求只是"看到有哪些可添加的人"，翻页期间有人注册或注销导致 offset 漂移，跳过或重复一两条，刷新一下就自愈；换游标省下的就是这点漂移，代价是多维护锚点字段和比较逻辑。量级和精度要求摆在这里，offset 够用。
- **"用户一直点加载更多会不会重复追加？"** 不会，我在客户端拦了一道：这个页面有个在途标志 m_inFlight，请求发出前置真、响应处理完清零，"加载更多"的点击在途期间直接 return，第二个请求根本发不出去；搜索入口同样被它挡住，避免两次搜索的响应交错混页。退一步说，就算真按同一个 offset 重复请求了，服务端返回的也是相同条件的同一页内容，追加结果不会多出一条重复。另外换搜索词或者重新打开窗口，都会把 offset 归零整体重置，旧页数据不会混进新结果。代价是在途期间用户再点没有反馈，按钮短暂无响应——我认为这比列表里出现重复条目划算。
- **"为什么给查询总数设 1000 条上限？"** 这个 1000 封的是总数不是单页——单页一直是 limit=50。理由是陌生人查询的总数会随注册量一直涨，如果如实报一个几万条的总数，用户真的一路翻到底就是几百次请求、几万条渲染，客户端和服务端都白扛，而这个列表本来也不需要穷举。做法上服务端查总数时按 1000 封顶，超了就在响应里带上截断标记，客户端记着这个封顶状态，界面提示"结果太多，只显示前 1000 条"，翻到顶之后不再给出下一页。代价是"要找排在 1000 条之后的某个陌生人"光翻页找不到，所以我留了搜索关键词这条路：按名字过滤后的结果集一般远小于 1000，真要找特定的人应该是搜而不是翻。
- **"在线用户列表里的在线/离线标记准不准？"** 它就是查询那一刻的快照，从响应离开服务端开始就在过期，所以我不把它当准确状态用，只当展示参考。为什么必然不准：在线状态由登录注销频繁驱动，列表拉回客户端之后没有任何反向推送去修正这些标记。因此凡是真正吃状态的动作——加好友、发私聊消息——服务端都拿当前登录人和目标账号重新查一遍，在线字段不作为任何判断依据，客户端缓存的东西服务端不认。替代方案是上下线时服务端推变更、客户端局部刷新标记，但这张列表是可丢弃的参考页，为它专门维护一条推送同步链路不划算，我选择靠下次查询自然刷新。边界就一句：展示可以过期，操作必须现场校验。
- **"用户关键词搜索这条路上有什么坑？"** 主要有两个我实际处理了。一个是超长关键词：客户端先拦一道，过长的词直接不发请求，免得无意义的模糊匹配反复打数据库。另一个是 LIKE 的通配符：关键词里的 % 和 _ 不处理的话会被当通配符，用户输入本意是字面字符，匹配范围却被放大成意外结果，所以服务端拼 LIKE 模式前把这两个字符连同转义符一起转义掉，按字面匹配。至于注入，这一层根本不成立——所有 SQL 都走预编译语句绑定参数，关键词只是参数值，进不了语句结构。验证办法也直接：在搜索框里输入 % 或者带引号的串发一次，看结果是不是按字面匹配、有没有报错，就能确认这两道处理生效了。
- **"从用户列表上看到某人可加，到真正发出加好友请求，中间两人关系变了怎么办？"** 客户端展示的列表永远只是参考，不参与任何判断。加好友请求到达服务端时，我会用当前登录人、目标账号、现有好友关系这三个条件现场重新校验一遍——目标还在不在、两人是不是已经是好友、有没有待处理的申请，全部以数据库此刻的状态为准，绝不采信客户端之前拉到的缓存。所以从看列表到点添加之间，哪怕对方注销了或者你从别的入口已经加过他，请求也会被当场拦下，不会出现错误的好友关系。为什么不加锁把关系在看列表那一刻冻住？因为锁得一直持有到用户做完决定，他可能盯五分钟，也可能再也不点——把一个可选操作的窗口锁成长事务，白白挡住别人的申请和删除，代价不成比例。我选乐观校验：绝大多数请求状态没变，撞上变化的就拒绝并让用户刷新列表，用一次失败请求换整条链路的简单可靠。

### 10. 添加好友

#### 功能目标

把陌生账号变成好友，申请和接受分成两步，对方离线也能先登记申请。

#### 主回答（完整业务实现链路口述版）

用户选中一个账号发加好友请求，客户端把当前登录人和目标人带上一起发给服务端。服务端先确认目标账号存在、双方还不是好友、没有待处理的申请，没问题就登记一条申请记录。目标在线的话顺手推个通知弹窗，不在线也没关系，申请存着等对方下次来看。对方同意后，服务端再校验这条申请确实还在待处理状态，然后建立双方好友关系。客户端收到成功回调就把好友分页重置、从第一页重新拉。

#### 表达脉络（记忆钩子）

1. 用户选中目标发申请 → 2. 服务端校验目标和重复申请 → 3. 登记申请、在线就通知 → 4. 对方同意后再校验 → 5. 建立好友关系 → 6. 客户端重置好友分页重拉

#### 追问卡片

**面试官追问时这样答：**

- **"目标离线能不能加好友？"** 能，这是设计里明确支持的。申请不依赖对方在不在线，直接登记进数据库的 friend_request 表，状态是待处理；在线推送只是即时提醒，目标恰好在线就多弹个通知，不在线就跳过，登记本身不受影响。对方下次登录或者刷新申请列表时，服务端把状态还是待处理的记录查出来给他，点同意再走正式的接受流程建立关系。为什么不规定双方必须在线才能加？那样加好友就变成实时撮合，对方作息不凑巧功能就不可用，而且在线状态本身就不可靠，拿它当功能开关等于把一个会过期的展示字段当权限依据。代价只是多维护一条申请记录和它的状态流转，换来的是申请随时可提交、事后能处理。
- **"加好友为什么要拆成申请和接受两步？"** 因为好友关系必须双方各自同意才成立：发起方意愿明确，接收方还没表态，一步到位就是单方面替别人做决定。分两步之后，第一步在服务端登记一条待处理的申请记录，第二步由对方主动点同意，服务端校验这条申请仍然待处理才写好友关系，不同意或者放着不处理都不产生关系。代价是要多维护一张申请表和它的状态机，同意、拒绝、待处理这些分支都得有地方表达。但顺带有个好处：发起和接受是两条独立请求，服务端分别用当前连接的登录身份校验"你是不是当事人"，冒名同意、冒名发起在入口上就出不来，比一个接口直接建关系的边界清楚得多。这个代价不算取舍，是必须付的。
- **"通知发出去了对方一直没点，怎么知道申请的真实状态？"** 以服务端存的申请记录为准，通知本身不携带任何状态语义。推送只负责"有个新申请，你来看看"，发出去不代表对方看到了，更不代表同意；申请的真实状态一直是 friend_request 那条记录的状态字段——待处理、已同意、已拒绝，谁处理了服务端就更新什么。客户端每次打开申请列表都重新拉一遍当前状态，不拿旧缓存充数，所以哪怕对方几天后才处理，这边一打开看到的就是最新结果。没做的只有"已读"回执：发起方在主动刷新之前不知道对方看没看到过。我认为这可以接受，因为发起人真正关心的是最终同意与否，刷一下列表就能确认。
- **"连点两次发送会不会登记两条一样的申请？"** 不会，两层各挡一道。第一层在登记之前：服务端先按双方账号查申请表有没有待处理的申请，有就不再插入，正常的重复提交在这一步就被挡掉。第二层落在数据库：friend_request 表按申请人、目标人、状态建了联合唯一索引，登记语句用的是 INSERT IGNORE——两个重复请求万一碰得足够近、同时通过了第一层检查，后提交的那条也会被唯一约束拦下并静默跳过，落库的待处理申请始终只有一条。返回给客户端的表现也一致，不会出现两行一模一样的申请。代价是要把"重复被跳过"当成正常路径处理，翻译成申请已存在的语义返回，而不是给用户弹一个数据库错误。
- **"有人在请求里把'申请人'改成别人，能替别人发申请吗？"** 不能，因为服务端根本不信请求体里自称的申请人。申请人不是从报文里解析出来的，而是取当前这条 TCP 连接绑定的登录身份——连接在认证那一步已经确定了这是谁，之后所有以"我"为主语的请求都以连接上的身份为准，报文里的申请人字段就算被改掉，登记进申请表的申请人也永远是当前登录人。所以伪造这个字段唯一的效果是让报文自己说谎，替别人发申请在数据层面就没有入口。这也是我服务端的一致原则：身份看连接，参数看请求，凡是能决定权限的信息都不采信客户端上报。代价是请求里那个申请人字段实际是冗余的，服务端校验时直接用连接身份覆盖它，不额外增加复杂度。
- **"好友申请怎么变成正式好友？"** 靠同意这一步带校验的状态迁移。对方点同意之后，服务端先取出那条申请记录，校验两件事：这条申请确实是发给当前登录人的，不能替别人同意；状态还是待处理，已经被拒绝或已经处理过的申请不能再翻案。校验时用了行级的锁定读防止两个人并发处理同一条申请，两个条件同时成立才往好友关系表写入这一条关系，同时把申请状态更新成已处理并记下处理时间。之后同意成功这边的客户端把好友分页重置、从第 0 页重新拉，新好友立刻出现在列表里；发起方下次刷新申请列表时看到的也是处理后的状态。后续就算对方离线，私聊记录也能先存着，下次上线就能收到。

### 11. 好友列表

#### 功能目标

分页展示已经建立的好友关系，默认每页 50 条，按用户名字典序稳定排序，支持"加载更多"增量追加。

#### 主回答（完整业务实现链路口述版）

我把好友列表也改成了分页，每页 50 条。用户进入好友页、加好友成功或者删了好友，我都会先把本地列表清空、页码归零，然后发第一页请求。请求里带两个东西：每页要多少条、从哪里开始翻——用户点"加载更多"时，就把"已经加载了多少条"当成新的起点继续请求。

服务端这边，好友关系表只存一条记录，当前登录人可能在关系的左边也可能在右边，所以我先从两个方向把自己能找到的好友名字合并去重，然后查总数、按名字排好序取一段。总数超过 1000 就封顶，服务端告诉客户端还有没有下一页。客户端把本页好友追加到列表末尾，编号按已有条数继续往下排，这样跨页编号也不会断。

#### 表达脉络（记忆钩子）

1. 进入页面或加删好友成功 → 2. 客户端清空列表、页码归零 → 3. 发带 limit+offset 的请求 → 4. 服务端双向查好友、合并去重 → 5. 查总数、按名字排序取一段 → 6. 回总数+还有没有下一页+本页好友 → 7. 客户端追加、跨页连续编号、显示"加载更多"

#### 追问卡片

**面试官追问时这样答：**

- **"为什么好友关系要双向查？"** 因为关系表只存一条记录——A 加 B 为好友，表里只写一行。当你是 A 的时候，你在左边；当你是 B 的时候，你在右边。所以每次查好友都要同时从左右两边找，合并起来才是完整列表。好在我用 UNION 做合并的同时自动去重，不会出现同一个好友出现两次。
- **"好友关系只存单向的一条记录，你不会觉得这样存储有问题吗？"** 这是我有意做的取舍：单向一条先把存储省下来——A 和 B 是好友只写一行，表大小天然是双向存储的一半。真正的代价不在空间在查询：每次拉好友列表都要从左右两个方向各查一遍再 UNION 合并去重，比双向表多一步。但这个代价可控——一个人好友撑死几百上千条，整张表百万行量级下 name 和 friendName 两个方向都有索引，双向查询加去重完全扛得住。真要膨胀到千万行查不动，退路也是现成的：Redis 缓存热门用户的好友列表，或者拆回双向各写各的、用事务保一致。如果让我重来，我还是存单向：一条记录写入本身原子，比双向两行更难出不一致，删好友时同一事务里连关系带私聊记录一起清也只用对准一行；唯一会补强的是给记录加上修改时间戳字段，为以后做增量同步留个抓手。
- **"为什么必须按名字排序？"** offset 分页必须有稳定的排序依据，不然两次查询顺序不一样，翻页时就会重复或者漏掉人。我选按名字字典序排，简单稳定还和在线用户列表的排序口径统一。当然极端情况下好友量上千，每次分页都排序确实有开销——到那个量级就得考虑换游标或者加缓存了。
- **"服务端怎么判断还有没有下一页？"** 服务端直接算给客户看：同一套筛选条件先 COUNT 出总条数（超过 1000 按 1000 封顶随响应返回），再拿已经翻过的 offset 加上本页实际返回的条数去和总数比，小于总数就置还有下一页的标志，客户端据此决定"加载更多"显不显示。我不让客户端用"本页不满 50 条就是到底"来猜：最后一页刚好凑满 50 条时这种猜法会误报还有下一页，还得再多翻一次空页才发现结束；而总数被封顶之后，也只有拿封顶值做减法才能明确告诉客户端翻到头了。代价是每次分页查询都多跑一遍 COUNT，在当前量级和有索引的条件下这点开销可以忽略，换客户端完全不用处理边界猜测。
- **"翻页期间删了好友，offset 会不会错位？"** 会漂移，这是 offset 分页的固有缺点。但我有两个兜底：第一，加好友成功、删好友、重新进好友页这三个场景都会重置分页，从第 0 页重新拉，不会拿旧的 offset 继续往后翻；第二，就算漂移了，用户手动刷新一下也就自愈了。用户名列表不像聊天历史那样要求严格连续，这个代价可以接受。
- **"每一次好友列表都从服务端拉取，每次加删好友都从第 0 页重新拉，不觉得浪费带宽吗？"** 这个取舍是我故意做的，起因就是怕 offset 漂移把事情搞砸：好友列表在服务端是双向 UNION 去重、按名字排序之后再分页的，删掉 Alice 这种名字靠前的人，Bob 会顶到 Alice 原来的位置，之前翻到 offset=100 对应的那个人此刻已经错位，在旧 offset 上做增量更新反而容易出错，所以加删好友之后我直接从第 0 页整体重拉，换确定性和实现简单。代价我也认下来：删一个好友就重拉一页，好友多的人翻到第 4 页删一个，前面 3 页请求就白做了；删完列表跳回首页，用户刚才滚到的位置没了，体验被打断；刚加的好友如果名字按排序很靠后，得翻好几页才看得到，实时性也差。
要改的话方向也是清楚的。最省的是客户端本地持久化好友列表，服务端给记录加修改时间戳做增量同步，每次只拉上次以来变化过的好友；更贴合实时体验的是加删好友时用推送触发局部更新，直接在本地列表里插入或删除一行——好友列表只有名字，没有在线状态那种每次都要现查的字段，局部更新完全够用；如果还想保住分页一致性，就把 offset 换成游标分页，锚点用上一页最后一个好友的名字，删掉 Alice 之后从"小于 Bob 的最后一个名字"接着翻，游标不会因为排序变化而错位。当前项目量级小，没人真有几百上千好友，简单可靠优先级最高，我接受这份浪费；真要做产品级 IM，这几条里至少推送局部更新和游标分页得补上。
- **"连续点加载更多会不会发两次请求？"** 不会。我用了一个客户端标志位 m_friendInFlight——发请求前设 true，收到响应处理完后设 false。按钮点击时先检查这个标志，在途期间直接 return，连请求函数都不会调用，请求根本发不出去。而且这个标志还防止了响应乱序的问题——同一时刻只有一个分页请求在飞，响应回来直接往列表里追加就行，不用按 offset 匹配。
- **"好友数量超过 1000 怎么办？"** 说实话这个封顶放在好友列表上是个妥协——在线用户封顶没事，陌生人找不到可以搜关键词；但好友是你必须能找到的人，封顶了第 1001 个好友就真找不到、没法聊天、没法分享文件。
当前项目量级小没人真有 1000+ 好友所以没问题，但如果真遇到这个量级我会改三个地方：第一，好友列表加搜索——按名字子串搜，复用在线用户搜索的现有逻辑，想找谁搜谁，不管你有多少好友都能命中；第二，加本地历史会话列表——客户端本地维护最近聊过天的好友，从聊天窗口也能点进去继续聊，不依赖好友列表；第三，如果用户真的有精力翻完 1000 个好友，那把封顶撤掉让分页翻到底也没成本——分页本身已经把单页控制在 50 条了。
- **"跨页编号为什么能连续？"** 我追加新一页好友的时候，编号是用"当前已有多少条 + 1"来生成的。比如第一页 50 条编号 1-50，第二页进来时已有 50 条，新编号就从 51 开始。删除的时候我按编号里的点号截取出真实用户名，所以编号怎么变都不影响删除逻辑——这是一个小技巧，既保证了编号连续，又不用改删除和私聊的既有路径。
- **"客户端缓存的好友列表能当权限用吗？"** 不能，客户端的一切展示状态在服务端眼里都只是参考。缓存天然会过期：对方删了好友或者双方关系解除了，本地列表可能还挂着名字，更别说报文本身可以被伪造。所以任何拿好友关系当门槛的操作——发私聊消息、删好友、给对方分享文件——服务端都用当前登录人和目标账号重新查一遍好友关系表，两个方向的条件都查，查到关系才放行，查不到直接拒绝。这样就算客户端揣着一份永远过期的列表、或者有人构造了请求，也越不过数据库此刻的真实状态。代价是每个敏感操作多一次关系查询，用一点数据库开销换权限边界完全收敛在服务端这一侧，这笔账在我这里很清楚：展示归展示，判定归判定，两者永远不共用一份数据。
- **"好友表撑不住了怎么办？"** 关系行随好友数线性增长是正常的，每个好友一条，就算有 1 万个好友也就 1 万行。关键是查询侧用双向去重 + 排序 + LIMIT/OFFSET 分页控制单页成本，再给 name 和 friendName 两个方向建索引，常见规模完全扛得住。真到了极端规模再考虑加缓存或者换方案。

### 12. 删除好友

#### 功能目标

解除双方好友关系，服务端顺带清理双方私聊记录，客户端重置好友分页。

#### 主回答（完整业务实现链路口述版）

用户点删除好友，客户端把当前登录人和要删的目标带上发给服务端。服务端确认操作者是当前登录人没错，然后把双方的好友关系从表里删掉，并且同时清理双方的私聊记录，使用统一事务保证操作的原子性。客户端收到服务端的删除成功回调，就把好友分页重置、从第一页重新拉，同时关掉已经打开的聊天窗口。本地和对方存储的聊天记录不会被删除，会一直保留在本地。

#### 表达脉络（记忆钩子）

1. 用户点删除好友 → 2. 客户端把登录人和目标带上发请求 → 3. 服务端确认操作者身份 → 4. 同一事务内同时删双方好友关系+清双方私聊记录 → 5. 客户端收到成功回调 → 6. 好友分页重置从第 0 页重拉 → 7. 关掉已打开的聊天窗口 → 8. 本地和对方本地记录保留不动

#### 追问卡片

**面试官追问时这样答：**

- **"删完好友旧聊天窗口还能发消息吗？"** 发不出去了，两层各管一段。客户端这边收到删除成功回调就把该好友已打开的聊天窗口关掉，入口直接消失，正常操作下用户不会再发；但这只是体验层的收口，真正兜底的是服务端的发消息校验：每次私聊消息进来，服务端都会拿当前登录人和目标账号重新查一遍好友关系，关系已经不在了就校验失败、拒绝发送，客户端收到明确的失败提示。为什么两边都做而不是只关窗口？因为客户端不可信：另一端可能还开着窗口、消息可能比删除回调先到、报文还可能被伪造，这些都只能以服务端此刻的数据库状态收口。代价是每条私聊消息多一次好友关系查询，在当前量级可以忽略，换来的是删除语义在整条链路上没有缝。
- **"删好友时把好友关系和私聊记录放在同一个事务里删，会不会造成事务长阻塞？"** 按当前项目的量级正面回答：不会。朋友之间的私聊记录撑死几百上千条，按双方名字的一条 DELETE 瞬间完成，事务持有时间可以忽略，删完立刻提交返回，不存在好友迟迟删不掉的情况。但我清楚这个结论的前提是量级：如果两个人攒了几万条聊天记录，一条 DELETE 要扫描删除大量行、较长时间持有行锁，不光堵住这批数据上的其他写入，连删关系这步用户可感知的操作也被拖着。真要改，方向是解耦：删好友关系单独走一个小事务，毫秒级完成先给用户返回；清私聊记录降级成后台异步任务，每次删 1000 条提交一批，分批不再绑同一个事务。更省的做法是不真删——消息表加一个"双方已非好友"的标记位，删好友瞬间只改关系表加打标记，查询时过滤掉，留存的行等定时任务慢慢清理。核心原则是用户能感知的删除必须快，清历史是后台慢活。现在没这么改，是因为异步清理会引入新的要处理的点：清到一半失败要能重试且幂等，清理期间不能留下点得进去的死会话入口——这套机制的成本在当前量级换不回来，消息量真上来再上。
