### 31. 个人文件上传：普通上传、秒传、断点续传与完整性校验

#### 功能目标

把本机普通文件变成当前账号可见的云盘条目，并统一处理秒传、普通分块上传、上传中断后的断点续传、失败重试和最终转正。秒传只跳过正文传输，不能跳过认证、目录授权、条目创建和完整性检查。转正之前还要核对实际收到的总大小与摘要，防止客户端声明和真实内容不一致；这一步只校验内容一致性，不判断文件是否安全或是否归用户所有。

#### 主回答（完整业务实现链路口述版）

客户端选择文件后创建上传任务并进入受限调度队列，读取文件大小并计算 SHA-256 摘要。服务端先校验认证主体、目标目录、请求幂等信息和摘要参数。若已存在状态有效且可复用的物理文件对象，就在事务中为当前账号创建逻辑条目并返回秒传成功，不发送正文；若未命中，则登记上传会话并创建或恢复暂存文件。客户端从服务端认可的连续偏移开始分块发送，服务端确认每块已经写入并刷新后返回下一偏移。任务中断时不能相信客户端进度条，而要重新初始化并以服务端暂存文件和会话状态确定起点。正文接收完成后，服务端复算实际摘要和大小，创建物理文件对象、个人逻辑条目并完成会话转正，客户端收到最终结果后更新任务和云盘列表。

#### 表达脉络（记忆钩子）

1. 创建任务并计算摘要 -> 2. 校验账号、目录和幂等请求 -> 3. 命中对象就建立逻辑引用 -> 4. 未命中则创建或恢复暂存并连续分块写入 -> 5. 中断后以服务端认可偏移继续 -> 6. 完成后复算摘要、建立正式条目并返回结果

#### 完整实现链路回答

用户在云盘页面选择本地文件和当前目录，客户端检查文件可读、名称和大小，创建个人上传任务，分配稳定任务键和本轮传输 ID，加入受限队列。调度器在网络可用且并发名额允许时启动，后台计算 SHA-256 作为客户端声明摘要，计算阶段同样占活动上传名额，失败按任务失败收尾。

拿到摘要后先做秒传预检：客户端以账号作用域的幂等键、名称、大小、逻辑父路径和摘要发预检查 97，群上传把预检信息放进初始化 101。服务端拆帧检查认证状态、登录版本、目标目录授权或群成员资格，以及展示名、大小、摘要格式和幂等键作用域；先查上传会话记录，同一请求已完成就回放最终条目结果，未完成按状态判断能否继续，不重复创建逻辑结果。未直接回放时以摘要和大小查找可复用的物理对象并核验状态，命中就在数据库事务里处理目标目录、展示名冲突和引用计数，复用既有条目或按重名安置新建；群上传还要建立有效的群文件条目和独立引用、检查群状态与成员关系，不能只返回个人成功就宣称群文件可见。提交成功后写明会话最终结果，响应 98 或 102 回传命中标志、个人条目 ID、群文件 ID 和最终展示名，正文不再发送。摘要命中不等于完成授权或条目创建，当前秒传也没有内容持有证明，知道有效摘要和大小就有取得引用的风险。

未命中时登记上传会话记录和待采纳预检，客户端发上传初始化 29（群上传 101）。服务端按传输 ID 查重并检查并发上限，创建上传上下文与可续传会话对象，以认证主体、逻辑父路径、展示名和期望大小作为暂存定位键定位暂存文件——这个键不等于内容摘要——采纳匹配的预检记录或查找已登记会话，响应 30 返回初始化结果和服务端认可的起点。上传正文发送器打开源文件定位到该偏移，逐块发协议 31 的偏移与正文块，不能把已发送字节数当确认偏移；服务端路由到对应上下文，检查块偏移等于连续接受位置、块长与总长合法、无冲突在途写盘，再提交 `UploadWriteTask` 到线程池执行定位、写入和刷新；写盘结果按连接号和传输 ID 回主线程重找有效上下文，成功才推进确认偏移、按时间或字节阈值节流保存会话进度，并以 32 返回下一偏移。

暂停、失败或恢复快照后进入续传：客户端保留源路径、目标父路径、展示名、期望大小和上传请求信息，检查源文件仍可读；继续或重试为本轮分配新的传输 ID 重新排队，拿到并发名额后重新预检，处理已完成、秒传命中或暂存不存在等变化，再重新初始化，服务端用同样的定位键找到暂存，按当前文件长度和会话状态建立可接受起点；会话记录保存持久状态，内存确认偏移和文件长度按中止、失败规则对齐，客户端必须按服务端认可起点定位源文件，不能沿用断线前自己发出的字节数。随后继续逐块发送，块偏移必须精确等于当前确认偏移且不越总长，异步写盘成功回主线程才推进并应答；显式中止时释放暂存句柄、把多出的未确认尾部截回确认位置，更新记录后释放上传上下文。

正文收齐后进入接收完毕：先释放当前及其他引用同一暂存的句柄，避免 Windows 文件占用阻止改名或删除，设置复算在途标记、登记会话状态、记录延迟应答类型，把 `StagingHashTask` 提交到 Qt 线程池，分块读取暂存独立计算实际大小和 SHA-256，不整文件读入内存，也不在工作线程操作套接字或数据库；结果携带连接号和传输 ID 排队回主事件线程，重找仍存在且处于复算阶段的上下文。若期间有延迟中止，优先按中止规则对齐暂存、更新会话并释放上下文，不把复算成功当上传成功；否则清除在途标记，核对实际大小、摘要与期望值。核对通过后调用上传转正（`commitUploadPreHashed()`）开启事务，按摘要复用或新建物理对象，把暂存正文落实到对象存储相对路径，建立或复用个人逻辑条目、处理展示名冲突、维护引用计数，群上传再挂接群文件条目及独立引用，最终会话记录保存条目结果；数据库失败时回滚，正文已搬到对象区就尽力搬回暂存，但数据库和文件系统不共享事务，搬回失败仍会留下需后续处理的状态。

收尾时按转正结果落定会话记录、释放上下文和名额，发送等待中的 98、102 或末块 32；客户端释放并发名额、保存传输快照并调度后续任务，成功按最终展示名刷新云盘，失败保留原因与可续传资料。当前边界：末块 32 仍沿用写盘成功值、完成位不能完整代表转正成功，群非秒传的最终安置路径未再次完整复核群状态和成员状态；校验只证明收到的大小、摘要与约定一致，不证明文件没有恶意内容、用户拥有内容或秒传命中完成内容持有证明，线程池的工作复用也不等于实现了自研线程池。

#### 追问卡片

##### 普通上传追问

- **上传大文件时你为什么先写一份暂存文件，而不是直接写进云盘目标位置？** 因为暂存文件把“没收完的内容”和“用户能看见的云盘文件”隔开。未命中秒传后，服务端用认证主体、逻辑父路径、展示名和期望大小派生暂存定位键，创建或恢复一份暂存文件，协议 31 的块只往这里写，写盘刷新成功才推进确认偏移并由 32 回下一偏移。正文收齐后我分块复算实际大小和 SHA-256，核对通过才执行上传转正，把暂存搬到对象存储相对路径并建立个人逻辑条目。直接写目标位置的话，用户会在云盘里看到半截文件，中断和重连也没有可对齐的已确认前缀，重名安置与引用计数还得在内容未定稿时处理。代价是多一次搬运和一份临时空间，转正失败要尽力把正文搬回暂存，而文件系统和数据库不在同一个事务里，所以这里能说的是状态可对齐，不是零残留。
- **把写盘放到线程池里，主线程就完全不会被上传阻塞了吗？** 不能这么讲。我挪进线程池的是两件重活：协议 31 每块的定位、写入和刷新，以及上传完成后 `StagingHashTask` 的整文件复算，主线程不再同步等这两段。但链路上还有一串留在主线程的活：29 初始化里查上传会话记录、采纳预检、打开暂存句柄，以及末块之后的转正事务，建物理对象、挂个人逻辑条目、处理重名、维护引用计数，这些都是数据库操作。另外所有连接共用同一个事件循环收发，某条连接一次排空大量入站包时，别的控制消息照样排在后面。所以我的说法是“单块写入和整文件复算不再堵住界面和心跳”，不是“上传全程无阻塞”。要把剩下的也挪走，跨线程的上下文生命周期和迟到回调就得额外管理，我按风险只挪了最耗时的两段。
- **最后一个分块的写盘应答成功，能不能证明整次上传已经完成？** 不能，这是我特意分开的两个位置。末块 32 只说明这一块的字节已经写入暂存并刷新、确认偏移推到了期望末尾，后面的路还长：我要释放暂存句柄、把 `StagingHashTask` 提交到线程池分块复算实际大小和 SHA-256、与客户端声明核对，通过后才开转正事务，按摘要复用或新建物理文件对象、把正文落到对象存储路径、建立个人逻辑条目并维护引用计数，最后才把条目结果回给客户端。所以“完整上传”成立的意思是数据库里那条个人逻辑条目和它指向的有效物理对象都成立。按现有口径我保留一句：末块 32 应答沿用写盘成功值、完成位没有完整反映最终资产提交结果，客户端进度满格不等于云盘条目已经可用。
- **暂停或者重试之后，为什么每一轮都要换一个新的传输 ID，沿用旧的会带来什么问题？** 暂停只是本地停发，之前发出的块确认和数据块还在网络上、会晚到；若沿用旧编号，这些应答会被当成新一轮的有效结果，把上一轮的偏移或数据串写进新的传输流程。任务在界面上的稳定键不变，但每轮通信分配一个单调递增的传输 ID，恢复时先摘掉旧 ID 的映射再换新 ID，旧应答按 ID 查不到活动任务就直接丢弃。续传起点由服务端回带的偏移（上传）或本地分片大小（下载）决定，与编号无关，所以换号不影响续传。
- **断电之后重启，上传和下载是不是一定能无损续传？** 不一定，分上传和下载两侧看，本地文件、快照或服务端任一环失效就续不上：

  **一、上传续传失败场景**

  1. **本地源文件被删除或改名**：上传恢复依赖快照中的文件路径，源文件不存在时，任务直接失败。
  2. **本地源文件内容被修改**：文件内容与原快照不一致，原分片无法证明仍对应当前文件，不能继续无损上传。
  3. **本地上传分片丢失或者被超时回收**：续传位置依赖本地分片的物理大小，分片缺失后无法确定可信进度，通常需要从头上传。
  4. **服务端文件内容发生变化**：服务端返回的续传起点与本地分片不一致时，系统会判定已有前缀不可信，删除相关分片并退化为全量上传。

  **二、下载续传失败场景**

  1. **本地下载分片被删除或损坏**：下载进度依赖本地已保存分片的物理大小，分片不存在或内容损坏时，无法从原位置继续，只能重新下载对应内容或整个文件。
  2. **本地下载目标文件被移动或改名**：快照记录的目标路径失效后，恢复任务找不到原下载位置，续传失败。
  3. **本地已下载内容或者服务端源文件被修改**：本地文件前缀与服务端文件不一致，系统无法继续追加数据，必须重新下载不可信部分。
  4. **服务端源文件被删除**：服务端找不到原文件，客户端无法继续下载，只能报告失败。

- **空文件、单字节、刚好一整块、整块倍数和大文件这些边界大小，你上传时怎么逐个确认没问题？** 我按大小造文件直接跑一遍再看落点：零字节、一字节、比块大小少一点、正好等于一块、一块多一点、整块整数倍、多块大文件各准备一份，每个传完再从云盘重新下载回来，比对条目里的大小、暂存是否已经搬走、对象存储里的实际字节数和 SHA-256，三者要和客户端声明一致。空文件是我要反复确认的分支：它必须要么按契约成功建条目，要么明确失败，不能停在“进行中”一直挂着。整块整数倍重点看完成判定，我只在确认偏移等于期望大小时判定收齐，不依赖额外的短尾块，所以正好落在块边界上也能正常转正。大文件我只盯内存，分块读写加流式复算，不该出现整文件常驻。
- **偏移不对、重复块、长度越界、声明大小和内容不符，你怎么确认服务端对这几种分块异常处理得是对的？** 我用一个自己写的小客户端按协议手动发包，不走正常界面。偏移故意发成当前确认偏移的前一格和后一格；重复块就在收到 32 之后把同一段再发一次；越界就在末块之后再补一块让总长超过期望大小；内容不符就声明一个和真实字节对不上的大小或摘要。这几种我都看同一组东西：32 有没有回一个新的被推进的偏移、上传会话记录里那行的确认偏移和状态有没有变、暂存文件实际长度有没有超出认可前缀、断开后上下文是否被释放。关键是不把某次写盘成功当成整条资产提交成功，异常之后我还会重新初始化一次，看服务端给的起点是否仍在可信前缀内。
- **上传大文件的时候，你怎么确认聊天、心跳和其他用户没被你阻塞，真阻塞了又怎么定位来源？** 我另开一个客户端账号，让它持续发私聊和群消息、维持心跳，同时在主账号上传大文件和一批密集小文件，然后看这个旁观客户端的应答是否仍按序到达、有没有明显等待或超时。有异常我再分开归因：临时把某次上传的块改回同步写盘、把摘要计算挪回主线程、把转正事务里的一句查询放慢，逐个复现看旁观客户端的反应，同时看带连接号和传输 ID 前缀的日志里，写盘线程从入队到回主线程各段耗时有没有被拉长。这样能区分开单块写入、整文件复算和数据库提交三种卡顿；共享 TCP 连接上的排队还得单独看队头，那部分不受线程池影响这件事不能假设。
- **物理文件对象为什么要按摘要前缀分子目录，磁盘文件名却用对象编号而不是摘要？** 两件事分开看：摘要负责内容识别，编号负责对象身份。我用摘要前几位划分子目录，是为了不把全部正文堆在一个目录里，让目录遍历和人工排查还做得动；落盘文件名用数据库给这个对象分配的对象编号，因为摘要是内容的函数，一旦哪天要在同摘要下并存不同对象、或者做迁移重建，用摘要当物理名就把内容地址和存储位置焊死了。用户看到的名字不在这一层，它存在个人逻辑条目的展示名字段里，同一份正文可以被多个条目引用。要说边界：分桶纯粹是存储组织方式，不表达任何授权，谁能读由条目和权限决定，桶数量也只是分散目录项，不替代完整性校验也不承担容量规划。
- **上传和下载的分块大小是怎么定的，为什么是这个值？** 上传块在 64KiB 到 1MiB 之间按文件大小自适应，目标是一个文件大致拆到千块左右；下载固定 64KiB，配 256KiB 的写缓冲高水位。这两个值解决的不是同一件事。上传一头是往返开销，块太小就要一轮轮地发 31 等 32；块太大则是一次写盘的抖动和内存占用，而且块是续传粒度，太大意味着中断后要回退更多，所以我让小文件继续用小块、大文件抬到接近 1MiB 压住块数。下载面对的是多条流同时往外推，出站泵每拍全局只推 1 块、靠环游标在流之间轮转，块越小轮转越细、多流公平性越好，代价是包数和头部开销上去。这两个值是我按两侧各自的取舍定的，没有拿压测数字来撑。
- **分块上传的过程中，会不会对每一块单独做一次内容校验？** 没有做逐块摘要。我这一层每块校的是元信息：偏移必须精确等于当前确认偏移、块长加上已收不能越过期望大小、同一上下文不能有冲突的在途写盘；字节本身的传输正确性交给 TCP 校验，落定之前再把暂存分块重读一遍，独立复算实际大小和 SHA-256，与声明一致才转正。为什么不做逐块摘要：一是客户端和服务端每块都要多算一次哈希；二是报文要多带一个摘要字段，协议是双方的兼容边界，加字段比看上去麻烦；三是逐块摘要也只能证明这块和客户端当时的字节一致，挡不住整文件版本被换掉。真要更早发现错位，逐块校验的价值在续传定位，最终完整性用整文件哈希已经覆盖。
- **你为什么把文件资产拆成上传会话记录、个人逻辑条目和物理文件对象三类，它们要保持什么关系？** 因为这三样的生命周期和读者完全不同，合成一张表就会互相拖累。上传会话记录是过程状态：谁在传、期望多大、暂存在哪、确认偏移推到哪里、最终回放过什么结果，它服务续传和幂等重试。物理文件对象是内容本身，按摘要去重、被多个条目引用、有引用计数和回收状态。个人逻辑条目是用户视图，一行代表云盘里看得见的文件，带归属、父目录和展示名，改名和重名安置只动它。要保持的关系是：条目必须指向一个状态有效的对象，对象只有在引用为零时才允许进入回收，会话记录只有在转正成功后才写最终结果。代价是一次上传要同时更新三处，所以我把它们放进同一个数据库事务，失败分支靠回滚和尽力搬回暂存来对齐。
- **暂存上传为什么要区分好几套时间规则，它们各自约束什么？** 因为它们管的是三种不同东西的寿命，混成一个超时会做出错误动作。第一套是连接里上传上下文的空闲回收：一条连接上的会话长时间没有块推进，空闲检查会释放它占的并发槽位，我当前用的空闲阈值是六十秒，目的是不让卡死的任务一直占名额。第二套是上传会话记录自身的期限和状态，决定重连之后还让不让继续，它回答“这轮业务还成不成立”。第三套是暂存文件在磁盘上的保留期，清理时还要看修改时间、有没有活跃的写盘或摘要复算，回答“这块正文还能不能被复用”。释放槽位不等于立刻删暂存，暂存没到期也不代表会话还能续，两套判断各自独立，才不会因为一个超时把用户本来能续的东西清掉。
- **为什么要把个人逻辑条目和物理文件对象分成两层，而不是一个文件一行记录？** 分开之后名称归属和内容各管各的，同内容只存一份正文。甲把自己那份叫报告、乙把完全相同的内容叫备份，这是两条个人逻辑条目指向同一个物理文件对象，对象引用计数为二；甲改名或删除只动条目和计数，正文不动，乙不受影响。不拆的话，改名要重写归属和路径，删除要判断还有没有别人在用，同一份内容会被反复落盘，秒传也没有可挂的目标。代价是读一次文件要多走一层关联，回收要靠引用计数和带条件的状态更新来推，写错就会留下悬空引用或者误删正文，所以我把加减引用和条目创建删除放在同一个事务里，不给它们各自提交的机会。
- **如果两个内容不同的文件碰巧算出同一个摘要，你这套会怎么样？** 我只能说这种情况按 SHA-256 的抗碰撞性接受，没有做逐字节的二次判同。秒传查询是摘要加期望大小一起用的，两个文件要同时撞上同一个摘要又同一个大小才行；真发生了，后果是后上传的人把自己的条目挂到了别人的正文上。为什么不做二次校验：判同就得把候选对象整读一遍逐字节比，命中路径本来省掉的正是这次读和这次传输，加上它秒传就没有性能优势了；而且对象是内容寻址不可变的，也没法靠“再写一次”纠正。所以现在能声称的是：摘要相同且大小相同我就当成同一份内容，这是密码学假设下的工程判断，不是数学上的等同证明。
- **如果攻击者篡改上传请求里声明的文件大小字段，会造成什么问题，你怎么挡住？** 大小在我这条链路上只是客户端声明，不是事实，乱报会有两类后果。报得很小：块偏移和长度校验会按期望大小卡住，但实现稍不注意就会让暂存长到期望之外，或者把收齐判定做错。报得很大：它占住暂存空间和一路上传会话，还可能挤占并发名额，让别人排队。我的挡法是把声明值和物理事实交叉核对：协议 31 每块同时检查偏移等于当前确认偏移、块长加已收不超过期望大小；显式中止时把多出来的未确认尾部截回确认位置；末块之后用 `StagingHashTask` 独立复算暂存的真实长度和 SHA-256，与声明不符就不执行转正、不建条目，直接按失败收尾。所以谎报最多浪费一段临时资源，换不来一个内容不对的正式文件。
- **两个人几乎同时第一次上传同一份新内容，会存下两份正文吗？** 不会存两个正式对象，但也不保证两边都一次成功。甲乙各自预检 97 都没命中，就各登记一条上传会话、各写各的暂存，正文收齐后都复算出同一个摘要，然后都进上传转正：先到的那个在事务里插入物理对象行，后到的撞摘要唯一约束或者在同一行上等锁，等锁释放后重新看到对象已存在，就改走复用，只给自己的账号建一条个人逻辑条目并把引用计数加一。所以磁盘上是一份正文、两个条目。代价体现在竞争方可能先拿到一次唯一键冲突的失败应答，需要它正常重试或者按已存在对象重新走一遍引用，而不是把这轮当成上传彻底失败。
- **个人上传和群上传的文件名和大小都一样时，会不会共用同一份暂存互相覆盖？** 按现在这条链路不能保证隔离，这是暂存定位键的设计决定的。我定位暂存用的键由认证主体、逻辑父路径、展示名和期望大小这几样派生出一个稳定名，里面没有群标识，也没有一个显式字段把个人和群两个业务域分开。所以同参数下两路上传有可能算出同一个暂存，结果就是一轮的未确认尾部被另一轮截掉，或者两路的块混写进同一个前缀。同参数重连能找回同一份暂存，这正好是续传需要的行为，但它同时也是这里的共享来源。要彻底分开得把业务域或群标识纳入定位键，而那是一次键变更，已有暂存会找不回来，需要配套处理，所以我没有顺手改。
- **能不能从用户点下“上传”按钮开始，完整讲一遍到文件出现在云盘里经过了哪些步骤？** 用户选好文件和目录，客户端检查可读性和大小，建任务并分配稳定任务键和传输 ID 进队列；拿到名额后在后台整文件算出 SHA-256 当声明摘要，发预检查 97。服务端验认证主体、目录授权和参数格式，再用摘要和大小找可复用对象：命中就在事务里建个人逻辑条目并处理重名，98 直接回命中标志和条目 ID，正文一字节不发。未命中就登记会话，客户端发 29 初始化，服务端用认证主体、父路径、展示名和大小派生的定位键找回暂存，30 回认可起点。之后是停等循环：31 发偏移加块，服务端交线程池写入刷新，回主线程才推进确认偏移，32 回下一偏移。收齐后用 `StagingHashTask` 分块复算大小和摘要，核对通过才执行上传转正，把正文落到对象存储路径、建物理对象和条目，客户端收到应答后云盘才可见。
- **上传正文之前为什么要先查一遍目标目录？** 为了在花钱最少的位置把注定失败的请求拒掉。目标目录授权是这条链路上最先能判定成败的条件之一：目录不存在、不属于当前认证主体、路径非法，这些和文件内容毫无关系，客户端算完摘要、发完正文也改变不了结果。所以我的顺序是先验认证主体和目录授权，再谈幂等键和摘要复用。不先查的话，未授权的请求照样能走完 29 初始化、创建暂存、按块写盘，占住暂存空间和一路并发名额，最后才在转正阶段失败，等于把一个鉴权检查变成了可被批量利用的资源消耗。代价是多一次目录查询，落在初始化那一次往返里。至于查完之后目录才被删的窗口，真正的兜底是转正事务里的再次安置和展示名冲突处理，不是这次预查。
- **TCP 本身已经保证可靠传输了，为什么还要在应用层为每个块做一次 ACK 应答？** 因为两者确认的不是同一件事。TCP 的确认只表示字节进了对端协议栈，它不知道服务端有没有把这段正文定位到暂存的正确偏移、有没有刷新成功，也不知道这段该算在第几号传输上。我这层的 31/32 确认的是业务状态：服务端校验块偏移精确等于当前确认偏移、块长不越过期望大小，提交 `UploadWriteTask` 完成定位、写入和刷新，回到主线程重新找到仍然有效的上下文之后，才推进确认偏移并把下一偏移回给客户端。续传也依赖它：重连后客户端必须按 30 回带的起点定位源文件，不能拿自己已发送的字节数当进度。代价是每块要停等一次往返，吞吐受往返延迟影响，缓解办法是把块调大、按时间或字节阈值节流保存会话进度，而不是取消确认。

##### 秒传追问

- **秒传为什么用内容摘要判定命中，而不是用文件名加大小？** 因为文件名和大小不能唯一决定内容，摘要才更接近“同一份内容”这件事。同名同大小的两个文件可能完全不同，用它们做命中条件，秒传就会把用户的条目挂到别人的正文上，这是正确性事故；反过来内容相同但改了名，用文件名又认不出来，白白重传一遍。所以我用 SHA-256 加期望大小做内容寻址，展示名只在个人逻辑条目那一层参与重名安置。代价很清楚：客户端要先整读一遍文件算摘要，小文件这笔开销可能比直接传还贵，大文件才划算；另外摘要相同不等于内容相同，我不能把它说成绝对不可能撞。
- **客户端如果随便报一个摘要，能蒙混过秒传吗？** 要分两条路。真正上传正文的蒙混不过去：末块之后服务端释放暂存句柄，用 `StagingHashTask` 分块重读暂存，独立复算实际大小和 SHA-256，和声明不一致就不执行转正、不建条目，直接失败收尾。但秒传命中这一路没有正文可验，我确实拿不出“这个账号手里真有这份内容”的证据，只要摘要和大小对上已有且状态有效的对象，就会在事务里给它建一条个人逻辑条目。这是稿子里已经定下的安全边界，我不美化：知道一个有效摘要和大小，就有换到他人内容引用的风险。补内容持有挑战能收窄这个面，但那要在链路上多一轮随机分块问答，属于另一种设计取舍。
- **那你为什么不做内容持有挑战，让客户端证明它真的持有这个文件？** 我做的是优先级取舍：先保证内容复用和上传链路简单。常规做法是预检命中后服务端下发一个随机偏移加长度，让客户端把源文件那一段原样回传或算摘要，通过后才建条目。它确实能挡住纯猜摘要的请求，但代价是多一次往返和一次源文件随机读，秒传“零正文传输”的收益被削掉一块，而且合法用户的每次重复上传都要付这笔开销。替代方案还有账号内去重，只在同账号内复用、跨账号一律真传，或者可信授权继承，都能缩小泄露面，但会减少跨账号命中带来的存储节省。我现在的选择是把边界如实写明，不把命中成功说成已经通过授权校验。

- **秒传为什么用 SHA-256 而不是更快的 MD5？** 因为这里的摘要是内容身份，不是校验码。MD5 已经有可用的碰撞构造，两个人能故意造出摘要相同、内容不同的文件，命中路径一旦用它做判定，后来者就会把条目挂到别人的正文上，这是能被主动利用的正确性问题，不只是概率低。SHA-1 我也不拿来判去重，强度同样在往下走；它在我这儿只用于暂存命名，撞错的后果是找回同一份暂存这种可核查的事，不涉及资产归属。至于“更快”这个理由其实站不住：算摘要的瓶颈是整文件读盘的 IO，算法差别摊不上多少。MD5 真要找个位置，适合当客户端本地的缓存键，不适合当服务端的信任依据。
- **你这个秒传实际真有用吗，不同用户上传完全相同文件的概率不高吧？** 我不把跨用户命中率当它的主要价值。对我最有用的两类是同一用户重复上传，比如改了名再传、删了再传、多设备各传一次，以及多处引用同一份内容，这直接省掉整轮正文传输和一份磁盘副本。跨用户命中确实取决于内容是否天然公共，热图、通用安装包、同一份课件容易撞上，个人照片基本不会。另一半必须一起做的东西是：命中不等于可以直接返回成功，服务端还要校验认证主体、目录授权、对象状态和引用计数，未命中就正常登记会话走分块上传。所以秒传省的是正文传输，不是校验和授权。
- **摘要碰撞在你这套里怎么处理？** 我把摘要当候选定位线索，不当等同证明。命中时不是只看摘要：查询条件是摘要加期望大小，取到对象还要核验它的状态是否允许引用，最后落定时实际大小和 SHA-256 要一起核对通过才建条目。这样“摘要相同但大小不同”一定被排除，剩下的风险只是同摘要同大小的不同内容，那要逐字节比对才能发现，我没有做。为什么不默认做：判同要把候选对象整读一遍，正好把秒传省掉的这次读加回来，代价按命中次数持续付，换的是一个密码学上认为极不可能的场景。所以我的口径是工程判断，不是数学保证。
- **只要摘要很难猜，秒传是不是就没风险了？** 不能这么保证。猜不出来只挡住随机试探，挡不住摘要从别处泄露。摘要本身不是秘密：文件哈希在公开下载站、校验值清单里都很常见，用户自己也可能在别的服务见过；我这边任何把摘要回给客户端的地方，比如预检应答和条目信息，都算一次暴露面。一旦某个有效摘要和它的大小落到外部，而命中路径没有内容持有证明，就足以换回一条指向该内容的个人逻辑条目。所以按现有口径保留：秒传命中不校验持有，风险来源是摘要可外泄，不是算法强度不够。要压这个面有账号内去重和持有挑战两条路，各自牺牲跨账号收益或多一次往返。
- **数据库报唯一键冲突，是不是就说明这次已经重复上传成功了？** 不是，冲突只代表这一份内容已经有人把对象行插进去了，不代表我这一轮的条目也建成了。我在上传转正的事务里遇到摘要唯一约束冲突时，正确处理是回滚本事务，重新按摘要加期望大小查一次对象，确认它状态可用，再走复用路径给自己建一条个人逻辑条目并把引用计数加一；如果复用这一步也失败，就按失败应答回去让客户端正常重试。把冲突直接翻译成“重复成功”会在对象状态不匹配时留下指向不可用内容的引用；当成彻底失败则把本来能复用内容的请求打回全量上传，两种都不对。
- **秒传复用已有对象失败时，还能继续引用这个对象吗？** 不能。复用失败本身就说明这个对象当前处在不可引用的状态，可能是已经被推到回收中、引用早已释放，或者元数据和实际正文对不上。这时候正确的动作是把这次预检按失败结果处理：要么让客户端正常走 29/31/32 的分块上传，由服务端复算后生成一个新对象，要么明确返回失败让它重传，同时把上传会话记录写成失败而不是已完成，避免重试时被幂等回放射成一个成功。我不能做的是把复用失败当命中回报，因为条目一旦建起来就指向了一份取不到或者正在被清掉的正文，用户看得见却下载不了，回收侧还会以为它仍有引用。判断依据是那次带条件的状态更新的受影响行数：更新不到就说明对象不归我采用，只能退回上传路径。
- **客户端已经把摘要报上来了，服务端转正前为什么还要自己复算一遍？** 因为客户端那个摘要只是声明，不能证明暂存里的字节就是它。在真正上传了正文的分支上，末块之后我释放暂存句柄，用 `StagingHashTask` 分块重读暂存文件，独立算出实际大小和 SHA-256，两者都和期望值对上才执行上传转正，把正文落到对象存储路径、建物理对象和个人逻辑条目。这一步挡住的是伪造声明：谎报大小或摘要的请求最多占一段暂存，进不了正式区，也不会变成一个可以被别人复用的对象。代价很直白，就是整文件多扫一遍磁盘，只在上传完成时付一次。至于秒传命中那条没有正文的路径，不能拿这次的复算去声称也覆盖了它。

- **秒传命中、未命中、并发首次上传、摘要伪造、对象正在回收这几种情况，你分别怎么确认行为是对的？** 我不靠一张用例表，而是每种情形做一个能读出结论的动作。命中：先传一份建立对象，把条目删掉后换个展示名再传一次，看 98 回里的命中标志、新条目指向的对象编号是否与原对象同一个、引用计数有没有加一，同时看链路日志里确实没有 29 和 31。未命中：用一份新内容，确认它登记了上传会话并进入分块写盘。并发首次：两个客户端同时传同一份新内容，事后查对象表该摘要只有一行、条目表两行、计数为二。回收撞上复用：让计数归零后马上再发预检，查会话记录和对象状态，确认要么把对象从待回收拉回可用，要么明确拒绝，不会给出指向已删正文的条目。摘要被伪造这一类我要说清前提：当前命中路径没有内容持有证明，我不预设它一定被拒，更不能把命中成功报成授权验证通过。
- **零引用对象即将被回收时，恰好有一次秒传复用，双方怎样决定谁可以继续？** 不能双方先读一次状态就各自操作。复用需要在允许的对象状态下增加引用并恢复可用状态；回收需要按条件将候选对象改为回收中，检查更新是否成功。复用先成功会使回收条件不满足；回收先取得处理权后，复用不能继续采用该对象。决定权来自带条件的状态更新及受影响行数，单纯延长回收等待时间不能消除竞态。
- **秒传命中之后，如果原来那份文件的内容被改了会怎么样？** 在这套设计里改不了。物理文件对象是内容寻址且不可变的：摘要就是它的内容身份，正文落定之后不再原地写；要“换成另一份内容”实际是再走一次上传，得到另一个摘要和另一个对象编号，占一个新的对象行。所以命中拿到的那条引用指向的正文不会被动过。会变的是引用计数和对象状态：所有条目删完、计数归零，对象才成为回收候选，回收前还要用带条件的状态更新去抢处理权；如果命中正好落在待回收状态上，我在事务里把对象拉回可用再加引用。真正跳在这套约束外面的是有人绕过接口直接改磁盘上那个文件，那已经不是这条链路能保证的范围。
- **预检查 97 进来以后，服务端按什么顺序决定回放、命中还是转去正常上传？** 先看这轮请求是不是重复，再看内容能不能复用。第一步拿账号作用域的幂等键查上传会话记录：同一请求已经完成过，就直接回放里面存的最终条目结果，不再新建任何东西，避免重试造成两份条目；状态仍可继续的按会话给出的起点走原路径。没有可回放记录，才用摘要加期望大小去找可复用对象，并核验对象状态是否允许引用；命中就在数据库事务里处理目标目录、展示名冲突和引用计数，建好个人逻辑条目，通过 98 回命中标志、条目 ID 和最终展示名。都没命中才登记一条新的上传会话和待采纳预检，让客户端发 29 初始化去写暂存。这个顺序是因为幂等回放比内容复用更该先做，也不该被复用抢先。
- **用户甲能不能靠秒传拿到乙的私有文件内容？** 按当前这条链路，甲有机会拿到一条指向同一份正文的自己条目，这一点我照现有口径如实说。预检 97 用的是全局范围的摘要加期望大小去查已存在对象，命中之后服务端校验的是甲自己的认证主体和目标目录授权，并不要求甲事先拥有那个对象，也没有任何正文持有证明。所以只要拿到一份有效摘要和它的大小，就能在自己云盘里建出一条能下载的条目。我不把它写成“绝对拿不到”，因为那需要内容持有挑战或账号内去重才能成立，两者都会牺牲跨账号命中收益或多付一轮往返。能说清的边界是：命中之后走的仍是正常的授权和下载路径，不会绕过认证，风险点集中在“摘要不是秘密”。
- **两个请求几乎同时上传同一份新内容，服务端会怎么处理？** 落到转正事务上就是行锁加唯一索引。两个请求都会预检未命中、各写各的暂存、各自复算出同一个摘要，然后同时进上传转正：先拿到对象插入位置的那个把物理对象行写进去，另一个在同一行上等锁或者撞摘要唯一约束；等锁释放后它重新看到对象已存在，就转成复用，只给自己建一条个人逻辑条目并把引用计数加一。所以最终是一份正文、两个条目，唯一索引是最后一道保险。要小心的是复用失败这个分支：如果这时对象已经不在可引用状态，我不能继续挂引用，得按失败让客户端重试。代价是竞争方多付一次回滚加重查，比让它各存一份正文便宜。
- **秒传命中一个同名文件时，会不会把用户已有的那份覆盖掉？** 不会覆盖，复用只是共享正文，条目层各自独立。个人逻辑条目是按归属、父目录和展示名这一组条件建的，命中之后我在事务里先看目标目录下这个名字有没有被占，被占就走带 (N) 后缀的重名安置，建新的一条条目，不动已有那条。所以同一个人第二次秒传同一个文件，得到的是“同名 (1)”这样的另一条记录，两条指向同一个对象编号，引用计数为二；删掉其中一条只减计数，正文留在原地。代价体现在界面上会出现重复条目，我没有做“已存在就提示不新建”的合并，那是展示层取舍，不是数据层风险。真正会失败的是目录授权不通过或对象状态不可引用，这两种都返回明确错误。
- **秒传到底按什么判定命中，并发重复上传和引用计数又靠什么保证不出错？** 判定条件是摘要加期望大小，两者对上且对象状态允许引用才算命中，走 97 预检、98 应答；命中后不发正文，直接在事务里把当前账号的个人逻辑条目挂到那个已有对象上，重名走安置。并发正确性我不靠应用层判断，交给数据库：对象表上摘要的唯一约束加行锁，保证同一时刻只有一个请求能把新对象插进去，其余等锁后改走复用；引用计数的加减和条目创建删除写在同一个事务里，不会出现条目建好了计数没动，或者条目删了计数还留着。哈希碰撞按 SHA-256 的抗碰撞性接受，不做逐字节二次判同，因为那等于把秒传省掉的整读加回来。边界仍然是命中路径没有内容持有证明。
- **服务端会自己复算摘要，是不是就能挡住有人偷用别人的摘要？** 挡不住，这两件事不在同一条路径上。复算只发生在真正上传了正文的分支：末块之后我把暂存分块重读一遍，算出实际大小和 SHA-256 跟声明核对，这一步保证的是“落定对象里的内容确实等于这次传的字节”。偷摘要走的是秒传命中，根本没有正文进来，也就没有可复算的东西，我手上只有摘要和大小两个声明值可比。所以命中路径的授权问题不能靠复算解决，只能靠内容持有挑战、账号内去重或者要求引用前先持有同源对象这类机制，这些都不在当前链路里。稿子里我也是这么写的：校验只证明收到的大小和摘要与约定一致，不证明用户拥有这份内容。

##### 上传断点续传追问

- **断点续传时为什么不能直接相信客户端界面上的进度条？** 因为那个数很可能只是已发送字节数或者上一轮的本地缓存，和服务端真正落定多少没有关系。我这边的块是停等推进的：客户端发 31，服务端校验偏移、写盘并刷新、回到主线程确认之后才推进确认偏移，再用 32 回下一偏移。中断正好卡在中间时，客户端以为发出去的那一块在服务端可能根本没落盘，也可能只在暂存尾部留了一半。所以恢复时我让客户端保留源路径、目标父路径、展示名和期望大小，为这一轮分配新的传输 ID 重新排队，重新预检和初始化，服务端用同一套定位键找回暂存、按当前文件长度和会话状态给出起点，客户端必须按这个起点定位源文件。界面上的百分比只用于展示，不参与任何决策。
- **服务端的上传会话记录里存的偏移和暂存文件的实际大小，续传时以谁为准？** 不能笼统回答数据库永远权威，这是我实际反复判断过的一处。会话记录里那一列确认偏移是按时间或字节阈值节流保存的，本身就允许落后于真实进度；而当前打开续传的路径是按暂存文件的实际长度派生可接受起点，因为正文有没有落进去是文件系统说了算。我分两种收尾：显式中止时有对齐动作，释放暂存句柄、把多出来的未确认尾部截回确认位置、更新记录再释放上下文，两边一致；异常崩溃没走这段对齐，重启后就得专门核查一次，比较数据库值和文件长度，取可信前缀作为起点，不能默认哪边都对。把节流后的数据库值当唯一真值，结果是把已经写好的内容再传一遍。
- **服务端已经回了写盘成功的确认，断电之后这一块内容一定还在吗？** 不能这么声称。我做的是写入之后刷新，把数据交给操作系统，但刷新不等于操作系统强制落盘的持久化屏障，介质、文件系统和缓存策略都会影响最终结果，所以确认偏移表达的是“应用写入并刷新成功后推进的偏移”，不是“断电后一定还在”。另外会话进度是节流保存的，两次保存之间断电，数据库里那一列本身也会落后。要严格到断电可恢复，需要更强的同步语义，比如带屏障的写入、追加式临时文件加重命名，再加一套重启后核对前缀的恢复流程，这些都要额外付延迟。我的边界说法是：正常暂停、失败和显式中止后的续传按对齐规则处理，任意乱序分片和断电无损都不在承诺范围内。
- **上传中途用户把本地源文件的内容改了，续传会怎么样？** 现在不能可靠地发现，这是我明确写下的限制。恢复时我只检查源文件仍可读，然后按服务端给的起点定位继续发，而路径、展示名和期望大小这三样都证明不了它是同一个版本：用户如果在原路径上就地改写，前面的块已经落进暂存、后面的块来自新内容，拼出来是一份混合正文。兜底是末块之后的复算，暂存的 SHA-256 和最初声明的摘要对不上，这轮就按失败收尾、不建条目，坏内容不会变成正式对象。但失败不等于正确续传，用户得从头重传。更完整的做法是加文件版本指纹，或者在恢复前重算一次源文件摘要再和上传请求里钉住的声明比对，代价是多一次整读。

- **续传时服务端那份暂存文件已经被过期清理掉了，你怎么处理？** 我按“没有可续前缀”处理，不伪造进度。恢复流程还是先重新预检再发 29 初始化，服务端用认证主体、逻辑父路径、展示名和期望大小这组定位键去找暂存，找不到就在应答里回一个零起点，客户端把源文件定位到开头重新发，会话记录要么新建要么把确认偏移重置，不能沿用上一次的数值。我不做的一件省事的事是拿本地残留分片的长度当起点，那等于用一份已经不存在的暂存去推断服务端状态，一旦这组键被另一轮同名同大小的上传复用，就会把不相关的字节接在前缀后面。代价很直白：用户之前那一轮白传了，进度归零，界面上要给出能理解的失败原因，而不是继续显示原来的百分比。
- **暂存文件比服务端的上传确认偏移还长，多出来那一段怎么处理？** 多出来的是已写盘但还没被确认的尾部，不能算进可信前缀。我为此在显式中止时做对齐：先释放当前以及其他引用同一份暂存的句柄，避免 Windows 上文件占用挡住截断，然后把暂存从当前长度截回确认偏移的位置，更新会话记录，最后释放上传上下文。恢复初始化时我按同一个原则处理，起点取确认偏移和文件长度里可信的那一段，不默认暂存长度就是进度。为什么不能留着：这一段可能来自一个已经作废的在途块，也可能来自同参数的另一轮上传，接上去会让末尾的整文件复算和声明对不上，转正直接失败。代价是最坏情况重传一块。

- **写完一块后确认应答丢失就断线，两端进度不一致，你怎么确认续传既不会重复写入也不会漏内容？** 我就构造这个错位：让服务端写完一块、把 32 丢掉不回，然后断开重连。恢复后把四个数摆在一起看——客户端自认为已发送的字节、客户端记住的已确认偏移、暂存文件的实际长度、初始化 30 回带的起点。判据很清楚：起点不能大于可信前缀，那会漏掉没落盘的内容；也不能明显小于它，导致同一段被接两遍；之后每一块的偏移必须精确等于当前确认偏移，错一格就该被拒绝且不推进。传完我再用独立手段核对结果，比较条目里的大小、重新下载回来的字节数和 SHA-256 与源文件是否一致。另外两种错位我也分别看：写盘任务还没回主线程就断线，以及数据库进度因为节流落后于暂存长度，这两种都不能把节流后的数据库值或客户端发送量当成真值。
- **上传空闲 60 秒、上传会话有效期和暂存文件默认保留 6 小时，这三个时间分别约束什么？** 它们管的是三种不同寿命，不能互相顶替。连接上的上传上下文空闲约 60 秒后进入回收检查，作用是把长期没有块推进的并发槽位放出来，别让它一直占着上传名额；这个回收只动内存里的上下文和槽位。上传会话记录自身的有效期和状态决定重连后这轮还能不能继续，也就是服务端认不认这个起点。暂存文件默认保留 6 小时，清理时还要看修改时间以及有没有活跃的写盘或摘要复算，决定的是磁盘上那份正文还能不能被复用。所以释放槽位不等于马上删暂存，暂存没到期也不代表会话还能续。还有一点：到达阈值不等于准点删除，要等下一次扫描并且条件都满足才动手。
- **断点续传时，服务端是靠什么找回同一份暂存并定出继续位置的？** 靠稳定的定位键，不靠上一轮的传输 ID。客户端暂停、失败或者从快照恢复后，保留源路径、目标父路径、展示名和期望大小，为这一轮分配新的传输 ID 重新排队，拿到并发名额后重新预检再发 29 初始化。服务端用认证主体、逻辑父路径、展示名和期望大小这四样派生出同一个暂存定位键，找回那份暂存文件，按它当前的实际长度和会话记录里的状态建立一个可接受起点，通过 30 回给客户端；客户端必须按这个偏移定位源文件，之后每块偏移严格等于当前确认偏移，写盘刷新成功回到主线程才推进。之所以不能用旧 ID 找磁盘：ID 只是本轮通信的路由身份，重连就会变，磁盘上的文件身份靠的是上面那组参数。
- **每轮换一个新的传输 ID，是不是就能把上一轮的残留数据隔离开？** 不能，换号只解决应答归属，不解决文件身份，这两层我得分开说。传输 ID 的作用是路由和丢弃迟到包：旧 ID 的块或应答回来时按 ID 查不到活动上下文，直接扔掉，不会把上一轮的偏移串进新流程。但暂存文件的身份是另一套键，由认证主体、逻辑父路径、展示名和期望大小派生，这是故意设计成跨轮稳定的，否则续传就找不回原文件。所以同一组参数重启上传一定落回同一份暂存，这既是我要的续传行为，也正是隔离不彻底的地方。真正兜住不拼错的是严格连续偏移校验和末块之后的整文件复算，任何不一致直接失败收尾，不做猜测。
- **续传时你怎么保证既不漏块也不重复写，偏移和最终完整性靠什么校验？** 上传侧我把它收成一条硬规则：每个块的偏移必须精确等于当前确认偏移，也就是 chunkOffset == receivedSize，不匹配就拒绝且绝不推进；块长加上已收还不能超过期望大小，所以既写不重也写不越界。确认偏移只在服务端定位、写入、刷新都成功并回到主线程找到有效上下文之后才前进，起点由初始化按暂存实际长度给出。最终完整性不靠逐块，靠末块之后 `StagingHashTask` 独立复算实际大小和 SHA-256，与客户端声明核对通过才执行上传转正、建物理对象和个人逻辑条目。下载侧是对称的思路：客户端声明的续传起点必须被原样采纳且文件大小不变，任何不一致一律失败而不是猜一个位置继续。

##### 上传完整性校验追问

- **整文件摘要计算为什么不直接在网络线程里同步做？** 因为它耗时不可控，而网络线程上还有别人的事在排队。大文件要整读一遍磁盘，快慢取决于文件和磁盘状态，如果算在主线程，这段时间同一连接上的心跳、其他协议的应答、别的用户的消息全都在等，界面也跟着卡。我的做法是末块收齐后先释放暂存句柄、设复算在途标记，把 `StagingHashTask` 提交到 Qt 线程池，工作线程分块读暂存，不把整文件读进内存，也不在工作线程上碰套接字和数据库；结果带着连接号和传输 ID 排队回主事件线程，主线程重新找到仍处于复算阶段的有效上下文再继续核对和转正。这样只把耗时的读和算挪走了，跨线程的对象生命周期仍然靠回主线程重发来管，迟到的回调要能识别上下文已销毁并直接丢弃。
- **如果转正时正文已经搬到对象区，数据库事务却失败了，怎么办？** 这是我明确不追求零残留的一处。数据库和文件系统不是同一个原子资源，事务回滚只会撤销对象行、条目和引用计数，已经改名的那份正文不会跟着回去。所以我在提交失败的路径上尽力补偿：按记录把正文从对象存储相对路径搬回暂存，让这一轮还能按续传逻辑重来，同时把会话记录落定为失败、释放上下文和并发名额。搬回本身也可能失败，比如进程被杀、权限问题或者目标位置已被占用，这时会留下一份不受事务保护的正文，需要后续按对象状态把它核对出来。反过来改成“先提交数据库、成功后再搬正文”也行不通到底，那样正式区会短暂存在有条目但没正文的状态，两边各有各的空窗，我选了残留可核对的这一边。

- **上传进度到百分之百之后，你怎么确认这次资产真的提交成功了？** 依次在末块写盘、整文件摘要核对及对象和条目提交处制造失败，对照任务状态、应答、暂存会话、有效条目和重新下载结果。只有实际内容与条目均成立，才能据此证明本次提交完成。当前末块 32 应答沿用写盘成功值，完成位没有完整反映最终提交失败；测试应能暴露这个边界，不能拿进度满格或该应答代替提交验证。
- **摘要计算挪进线程池后，你怎么确认界面和心跳确实不再被拖慢，取消、连接销毁和迟到回调这些分支怎么看？** 用相同文件对比摘要任务排队、实际计算和回主线程提交三个阶段的耗时，同时观察界面交互及心跳延迟；大量任务时还要看工作线程与磁盘是否饱和。计算期间暂停、取消、断开连接并触发结果回调，检查回调重新验证连接和传输上下文，不访问已释放对象、不复活任务也不重复提交。若加入计时观测，要说明这些是验证手段，不能声称已有固定的性能收益。
- **服务端在上传完成时自己再复算一遍 SHA-256，不是挺慢的吗？** 确实是整文件多扫一遍，这我不否认，但它只在正文收齐之后做一次，不是每块都算一次。换来的是一次不信任客户端声明的机会：暂存里实际有多少字节、算出来的摘要是什么，都得我自己算过才算数，两项都对上期望值才执行上传转正、建物理文件对象和个人逻辑条目。不做的话，谎报大小或摘要就有机会让一个内容与声明不符的对象进正式区，还可能被后面的秒传复用，把错误扩散给别人。成本上看，这轮上传本来已经付过一次等量的读和写，多一次顺序读的边际开销比整轮传输小，而且是线程池里分块读的，不占主线程。所以我认为这笔代价是该付的。
- **为什么不干脆给每个上传任务开一个线程，非要共用线程池，提升在哪里？** 因为一次性线程的成本随任务数累加，收益只在真有并发时才体现。每任务新建线程要付创建、销毁、线程栈内存和调度的代价，而写盘和摘要这两类活短促且高频，任务一多就是反复创建销毁；线程数还没有上界，突发时会同时打开大量文件句柄和缓冲区，内存与句柄都不受控。共享线程池复用固定数量的工作线程、集中配活动线程数，我提交进去的就是 `UploadWriteTask` 和 `StagingHashTask` 两类。但也要说清楚：线程复用不等于排队任务、内存和文件句柄已经全部有界，那几样还得各自另有约束；任务量本来很小的时候，两种做法的差别基本感觉不出来。
- **那多加工作线程，处理速度能按线程数成倍上去吗？** 不能，我这儿的活不是纯计算。首先单个文件的摘要任务不会因为提交进池就被拆成多线程并行算，池里并行的是不同任务，单任务耗时不变。其次这些任务共享同一块磁盘：分块写盘和整文件复算都是 IO，读写一竞争，磁盘先饱和，再加线程只是在队列里排更长的队；摘要计算那部分还要争处理器和缓存，线程一多上下文切换和排队成本反而上来。所以活动线程数要结合处理器、存储设备和跟心跳、数据库这些业务混跑时的整体表现来定，不能按客户端连接数线性配。真要提速，比加线程更有效的是限制同时打开的暂存数量和单块大小。
- **那要做些什么，才能证明线程池是真的改善了系统响应，而不只是把等待从主线程挪到了队列里？** 我会准备三种执行方式做对照：同步在主线程算、每任务新建线程、走线程池，用同一份文件、同样的任务数量和同样的构建条件。分别看三段耗时：任务提交到真正开始执行、实际计算、结果回到主线程处理，同时让另一个客户端持续发心跳和轻量业务请求，看它们的应答有没有被拖慢。除了完成时间，我还要看队列长度是不是在持续增长、线程数和磁盘占用有没有饱和、突发一批任务时会不会雪崩。判据是明确的：如果队列一直涨、轻量请求照样明显变慢，那就只是把等待挪了个地方，不能因为有后台线程在跑就宣称优化有效。
- 表达脉络：设三组对照：同步执行/每任务一线程/线程池 -> 固定文件、任务量与构建条件 -> 分段计时：提交、执行、完成到主线程处理 -> 持续发心跳与轻量请求观察响应 -> 比较延迟、吞吐、资源与队列长度 -> 覆盖磁盘饱和与突发任务 -> 判据：队列持续增长或普通请求仍变慢即不称成功

### 32. 个人文件下载：普通下载与断点续传

#### 功能目标

将当前账号有权访问的云端普通文件保存到本机，并统一处理普通流式下载、下载中断后的断点续传、失败重试、最终落盘和完整性边界。目录不作为普通文件直接下载。

#### 主回答（完整业务实现链路口述版）

客户端选择文件后创建下载任务并保存源定位、本地目标路径和展示名。服务端收到请求后重新校验认证主体、登录版本、逻辑条目归属、物理对象状态和请求偏移，打开源文件并返回文件元数据及实际采纳起点。首次下载从零开始，恢复下载则以本地接收分片的实际物理长度声明起点，不能只相信快照百分比。服务端按下载流轮转发送数据块并执行背压，客户端按新的传输标识写入本地分片。断点续传会使用新的传输标识，旧轮次迟到的数据不能写入新任务。收到完成通知后，客户端关闭句柄、释放并发名额并更新任务状态，同时检查写入结果和文件长度。当前长度检查不能替代端到端摘要校验，源文件变化、分片损坏或最终落盘不完整时必须失败或重新下载。

#### 表达脉络（记忆钩子）

1. 创建下载任务并校验权限 -> 2. 服务端打开源文件并返回元数据与采纳起点 -> 3. 客户端按传输标识接收并写入分片 -> 4. 中断后读取分片实际长度并以新传输标识恢复 -> 5. 服务端校验起点并继续发送 -> 6. 完成后检查落盘结果并更新状态

#### 完整实现链路补充

##### 普通下载的完整实现链路补充

**创建任务**：用户选择普通文件并发起下载，客户端创建个人下载任务，保存源用户根相对路径、本地保存位置和展示名，加入下载等待队列。

**初始化请求**：取得下载并发名额后分配本轮传输 ID，首次下载通常以零作为声明偏移，将请求 40 发到服务端。

**服务端初始化**：服务端拆帧并检查认证状态、登录版本、并发名额和传输 ID，以认证主体执行逻辑路径授权检查，定位有效个人逻辑条目及其物理文件对象；核实可读、大小与偏移范围合法后打开源句柄，失败返回元数据或完成失败、不建立可正常发送的流；随后以下载元数据响应 41 返回大小、名称和采纳偏移，在单连接建立下载流（`MyTcpSocket::DownloadStream`）并加入下载轮转环。

**客户端准备**：核验响应归属当前传输 ID，打开或恢复下载接收分片；本地文件不可写、定位失败或空间不足时终止该任务并释放对应远端传输。

**流式传输**：服务端下载轮转调度每次从某一下载流读取有限数据并以协议 42 发送，网络写出背压达到阈值时暂停继续生产、等写出事件再调度；客户端按传输 ID 找到稳定任务键对应任务并把数据块写入本地句柄，写入字节数吻合才推进进度，写入不足分支记录警告并返回。

**完成与边界**：读完或读失败后发完成通知 43 并从轮转环移除、关闭源句柄，客户端只对仍在运行的任务采纳通知，当前主要按通知中的成功字段设置完成或失败；客户端关闭接收句柄、释放名额、保存快照并启动后续任务，失败保留可恢复分片；网页端改为浏览器下载聚合缓冲完成后触发保存；下载写失败和最终落盘长度复核的边界必须说明，不能把任务完成等同于已独立证明本地正文完整，列表展示、下载初始化与正文完成是三个阶段，源条目删除或对象不可用都可能使下载失败。

##### 下载断点续传的完整实现链路补充

**本地准备**：下载暂停或失败后，客户端保留稳定任务键、源定位及接收分片路径，继续时先确认本地分片存在且可打开。

**新一轮**：移除旧传输 ID 归属并为本轮分配新 ID，从分片真实大小读取声明偏移，不使用上次进度条缓存值；任务重新进入下载等待队列，取得并发名额后发请求 40 或群文件下载请求 105。

**服务端核验**：重新核验连接认证上下文、登录版本、个人条目归属或有效群成员关系，确认源对象可读且起点没有越过源大小；在元数据响应 41 或 106 中返回采纳偏移及真实大小。

**接收新轮次**：客户端检查采纳起点与本地分片关系，定位接收句柄后才接收新数据；服务端建立新的下载流并加入轮转环，通过协议 42 继续发块，背压约束发送堆积但不保证独占带宽。

**隔离旧数据**：客户端仅将新传输 ID 的数据追加到本任务分片，旧轮次迟到数据因为映射已撤掉而丢弃，不能写入新任务。

**收尾与边界**：收到完成通知 43 后按当前任务状态和成功字段收尾，关闭句柄、释放名额、更新面板与快照；当前该结束入口没有强制复核最终落盘长度，不能把元数据续传护栏扩大成完整内容校验；分片缺失、过大、源变更或服务端拒绝起点时需明确失败或按界面规则整文件重下，不能自动在错误位置追加，浏览器页面缓冲不等于桌面分片恢复。

#### 追问卡片

##### 普通下载追问

- **本地磁盘满了怎么办？** 写入失败就结束为失败，不能因为服务端还在发送就继续显示正常。保留分片能否继续要看实际落盘结果。

- **分享后源文件删除，接收者还能下载吗？** 接收者取回后有自己的逻辑条目和对象引用，源条目删除只释放其引用，仍有有效引用的正文应保留。
- **只检查路径前缀能防越权吗？** 不能，还要检查规范化结果、账号归属、条目状态和分享授权。
- **为什么列表有却下载不到？** 两次操作之间可能发生删除、移动或对象不可用。
- **直接提交对象 ID 可以吗？** 编号不能替代账号条目的授权关系。

- **下载怎样覆盖空文件、大文件和最后一块边界，并区分程序完成判断与内容正确？** 用不同大小的已知内容下载，覆盖从零开始、合法尾部偏移和分块整数倍，比较元数据大小、本地实际长度和服务端完成结果，再由测试工具独立计算摘要核对字节。服务端源缺失、本地写满和完成应答缺失也要明确失败或收敛。测试工具做了摘要比较不代表客户端已经实现端到端摘要校验，当前程序的大小检查不能发现所有内容错误。
- **慢客户端下载不动时，怎样观察发送缓冲和内存，确认背压真的生效？** 限制一个下载接收端的读取速度，同时保留一个正常接收端，持续记录各连接待发送字节、进程驻留内存、下载速率及聊天延迟。观察缓冲达到控制阈值后是否停发并在排空后恢复，慢端不能触发无限应用层排队。内存中包含连接、任务和缓存开销，不能要求绝对不增长，但稳定负载下应检查是否持续无界上升，以及快端是否长期得不到调度。
- **下载压测时怎样确认瓶颈在服务端，而不是压测客户端、网络、磁盘或数据库？** 同时观察两端处理器占用、磁盘读写延迟、网卡速率、服务端发送缓冲和数据库耗时；增加独立接收端或更换一侧资源后复测。固定冷热缓存条件与文件分布，避免客户端落盘或单机生成压力先饱和却误归因于服务端。吞吐平台只是现象，应结合资源证据和单因素对比定位；同机回环结果也不能直接外推到真实网络。
- **下载读 64KiB 也是阻塞 IO，为什么不放池？** 它要更新轮转游标和每连接的高水位，放池就得给调度器加锁；单次 64KiB 的顺序读在页缓存命中时很快，当前放在主线程更简单。
- **用户点下载后，服务端怎样从目录项找到内容？** 先按账号与逻辑位置找到授权条目，再通过条目的对象关联定位物理文件正文。列表中的名字只是当时的展示项，下载请求到来时仍需重新授权。

##### 下载断点续传追问

- **为什么不保存每块下载偏移？** 实际分片长度可以恢复进度，减少快照写频率；代价是文件被同长度改写无法被长度检查发现。
- **分片被手工删除呢？** 当前提示缺失并回到整文件下载，不应悄悄装作继续成功，也不能删除用户无关文件来恢复状态。
- **服务端文件变了呢？** 路径和总大小不够构成版本身份；需要稳定对象版本或摘要核对。不能把当前后缀续传说成已经解决所有源文件替换问题。
- **续传起点超出文件大小怎么办？** 服务端必须拒绝非法范围，不能直接定位并宣布完成；客户端应呈现失败或重新下载的明确结果。

- **下载中途退出后，怎样验证续传位置有效，分片过长、被修改或源内容变化怎么办？** 分别留下完整前缀、缺失分片、超长分片和被等长篡改的分片，再重新初始化下载，检查起点来自真实分片大小、服务端范围校验及异常提示。对源内容变更也独立比较最终字节。当前仅按长度恢复和完成检查，不能识别所有等长篡改或同大小内容变化；测试工具的摘要对比用于揭示缺口，不能把源版本绑定和端到端校验说成现有保证。
- **下载断点续传怎样避免从错误位置追加？** 从本地分片物理大小声明起点，服务端接受后再按该位置接收。客户端保留未完成下载的实际路径，暂停后继续时读取现有分片大小，不信界面旧百分比。
- **下载分片和服务端文件版本不一致怎么办？** 41 返回的文件大小和客户端记录不一致时，客户端删除分片、从 0 重下，不在旧内容上拼接。

### 33. 暂停传输任务

#### 功能目标

暂时停止一个任务，释放并发名额，并保留继续所需数据。暂停不是断开整条业务连接。

#### 主回答（完整业务实现链路口述版）

用户点击暂停后，客户端先把任务从调度队列中移出，停止继续取数和发送，并释放当前传输资源。服务端也要根据传输标识停止或拒绝后续数据，防止已经在途的旧响应继续推进任务。任务本身保留为暂停状态，旧传输标识与下一轮任务隔离，不能只修改界面文字后仍让后台继续传输。

#### 表达脉络（记忆钩子）

1. 用户发起暂停 -> 2. 客户端停止调度和取数 -> 3. 释放当前传输资源 -> 4. 服务端按传输标识停止或拒绝 -> 5. 保留任务为暂停状态 -> 6. 隔离旧响应，不能只改界面文字

#### 追问卡片

**原完整链路补充（追问时展开）**

**入口与状态检查**：用户在传输任务面板选择任务并点击暂停，面板把稳定任务键交给暂停任务入口（`TransferManager::pause()`）；管理器检查任务种类与状态，尚在等待队列时移出相应队列，摘要阶段则撤销后续任务归属，迟到摘要结果不能再次启动上传。

**停止本地收发**：正在上传时停止上传正文发送器；正在下载时关闭接收句柄但保留下载接收分片，并撤掉旧传输 ID 映射，防止迟到正文写入。

**释放远端传输**：对于已有远端传输的任务，发送传输释放请求 107；服务端检查连接认证与传输归属，再按该传输 ID 处理上传上下文或下载流。下载分支从轮转环移除并关闭源句柄；上传分支若无在途操作，则释放暂存句柄、对齐未确认尾部、保存确认偏移并将上传会话记录按现有规则结束。

**在途操作的延迟中止**：上传写盘在途或复算在途时先设置延迟中止，等待完成回调后再安全释放；不能提前删除仍被工作线程使用的文件或上下文。

**应答与本地收尾**：服务端返回传输释放响应 108；客户端把任务置为暂停、归还相应并发名额并调度其他任务，不占着名额等待远端应答；管理器发出任务变化通知并保存传输快照。

**边界**：暂停保留继续所需资料，不创建新的服务端“暂停”会话状态，也不保证暂存永久保存。

- **为什么不关闭 TCP 连接？** 同一连接还承载其他任务、消息和心跳，断连接会扩大影响；任务级中止成本更细，但需维护多路状态。

- **暂停与完成、断线或迟到确认同时发生时，怎样测试任务不会卡死或重新启动？** 在排队、计算摘要、分块写盘和等待完成应答时分别暂停，再交错断线及迟到回调。核对暂停的任务不再发送新数据，其他任务能使用释放的名额，旧标识的数据或摘要结果不能重新启动它。在途写盘可能先安全收尾，测试应观察最终确认位置和暂停结果，不能要求点击瞬间所有底层操作立即消失；断线后的状态按既定失联规则核对。
- **暂停时正在写盘怎么办？** 服务端标记 pendingAbort，等写盘任务完成再释放上下文，避免写回调落空；客户端那边已经停止发块。
- **暂停、继续、取消分别改变什么状态？** 暂停保留恢复意图，继续新建本轮传输，取消终止任务；服务端上传释放未必立即删暂存。
- **暂停就删除暂存吗？** 不是，当前释放上传上下文后保留暂存。

### 34. 继续传输任务

#### 功能目标

把暂停或允许恢复的失败任务重新送入调度，并重新确认传输条件。它不是恢复旧套接字里未完成的一次回调。

#### 主回答（完整业务实现链路口述版）

用户点击继续后，客户端保留原业务任务，但重新创建一轮线上传输并分配新的传输标识。客户端先向服务端确认当前暂存文件或本地分片的实际起点，服务端返回采纳偏移后再继续发送或接收。旧一轮迟到的响应会因传输标识不同被丢弃，任务完成条件仍以最终完整性校验和落库结果为准。

#### 表达脉络（记忆钩子）

1. 保留原业务任务 -> 2. 创建新一轮传输标识 -> 3. 查询服务端或本地真实起点 -> 4. 按采纳偏移继续传输 -> 5. 丢弃旧轮次迟到响应 -> 6. 以完整性和落库结果判定完成

#### 追问卡片

**原完整链路补充（追问时展开）**

**入口检查**：用户选暂停任务并点击继续，面板传稳定任务键给继续任务入口（`TransferManager::resume()`），先检查连接状态、当前账号及任务是否允许继续。

**上传分支准备**：核对源文件仍存在且可读，清理旧失败原因，撤销旧传输 ID 归属并为新轮次分配传输 ID，加入上传等待队列；恢复自传输快照的个人上传按规则重新计算或检查摘要并执行秒传预检查，再走上传初始化，不能假定断线前上传上下文仍存在。

**下载分支准备**：下载分支进入恢复下载（`resumeDownload()`），检查下载接收分片，读取其真实大小作为下载声明偏移，换新传输 ID 后加入下载等待队列。

**重新初始化**：取得对应并发名额后重新发送初始化请求，服务端重新完成认证、登录版本、目录或群成员关系、源对象与起点检查。

**恢复收发**：客户端收到有效初始化或元数据响应后，按上传确认起点、下载采纳偏移定位相应本地文件，再恢复分块发送或接收；每次确认或写入更新同一稳定任务键的进度，面板保持同一任务行，初始化失败释放名额并保留失败原因。

**收尾与边界**：完成、暂停或再次断线分别进入对应收尾并更新传输快照；继续不继承旧传输 ID 的授权，也不能把“点击继续”当成已经恢复传输。

- **为什么继续后还会排队？** 暂停时已释放名额，名额可能给了其他任务；继续不应突破并发上限，代价是无法保证立即开传。
- **暂停期间群被移除了呢？** 重新初始化必须再次鉴权，失败就明确展示，不能凭过去成功过而绕过成员检查。
- **旧的确认晚到怎么办？** 旧标识映射已撤掉，不能把它推进到新的发送器或接收文件。

- **继续操作与重复点击、取消或断线交错时，怎样验证不会重复入队或同时启动两轮？** 对同一暂停或可恢复任务连续点击继续，并在重新初始化时取消或断线，检查稳定任务仍只有一个、本轮传输标识更新、名额只占一次。源文件、目录、分片和群权限失效应明确失败，不能直接沿用暂停前的授权。旧轮次迟到数据不得写入新任务；任务真正获得名额并重新初始化成功后才应进入传输状态。

### 35. 取消传输任务

#### 功能目标

结束用户对该任务的继续意图，并回收客户端任务资源。服务端暂存内容不等于同步从磁盘立刻彻底删除。

#### 主回答（完整业务实现链路口述版）

用户确认取消后，客户端立即移除任务的继续入口，停止调度并删除本地下载分片。服务端根据传输标识拒绝后续数据，把上传暂存标记为过期并释放或交给回收任务处理。取消响应只说明任务状态已经收敛，不能承诺客户端和服务端两边的磁盘残留会在同一时刻全部删除。

#### 表达脉络（记忆钩子）

1. 用户确认取消任务 -> 2. 移除继续入口并停止调度 -> 3. 删除本地下载分片 -> 4. 服务端拒绝后续旧数据 -> 5. 上传暂存标记过期并交回收 -> 6. 取消成功不承诺两端立即无残留

#### 追问卡片

**原完整链路补充（追问时展开）**

**入口与排队清理**：用户在传输任务面板选中任务并确认取消，管理器按稳定任务键定位任务及当前种类、状态；等待中的任务移出等待队列，摘要中的任务清理归属，使后台迟到结果不能再创建新传输。

**停止与释放**：已有远端上下文时发送传输释放请求 107，停止上传正文发送器或关闭下载接收句柄，撤掉传输 ID 映射并归还本地并发名额；服务端按当前连接与传输 ID 处理释放，下载流摘出轮转环并关句柄，上传按无在途立即中止或有在途延迟中止的路径收尾。

**服务端对齐**：上传中止对齐上传暂存文件与上传确认偏移，更新上传会话记录并移除上传上下文；文件保留及后续清理由会话和废弃暂存清理规则决定。

**本地清理差异**：客户端下载取消会删除本任务管理的下载接收分片，和暂停保留分片不同；不能删除不属于该任务的任意本地文件。

**应答与收尾**：客户端移除任务行或按终止规则排除该任务，写回剩余传输快照，发任务变化通知并调度下一项；服务端返回 108 后不复活该任务。

**边界**：取消是用户放弃本任务，不自动回滚先前已提交的个人逻辑条目、群文件条目或已完成上传；重新上传或下载需创建新任务。

- **为什么不马上删服务器暂存？** 文件可能仍有后台写入或共享句柄，立即删除会引入竞态。安全释放与延迟回收更稳妥，代价是暂时占用磁盘。
- **取消后还能收到数据吗？** 网络在途数据仍可能到达，但标识已经解绑，不能归入新任务。
- **取消和服务端完成撞在一起呢？** 取决于已经提交到哪一步。若文件已转正，取消本地任务不等于远端文件删除；需要另走文件删除操作。
- **为什么不直接删除整个下载目录？** 取消只能清理自己管理的分片路径，删除目录会伤及其他任务及用户文件。

- **取消后再次点击继续会怎样？** 客户端应根据终止状态拒绝直接续传，需要重新创建任务或按失败重试流程发起新的传输。

- **取消与服务端完成、后台摘要回调同时发生时，怎样验证任务不会复活或误删文件？** 在多种传输阶段取消，再投递已在途的确认、完成消息和摘要结果，检查旧标识已失去归属、任务行及快照不再恢复、活动计数只释放一次。下载取消只删除该任务管理的分片，不得删除其他任务或用户文件；上传暂存按服务端会话和回收规则保留。取消不等于已撤销服务端先前完成的提交，需分别核对远端条目和客户端任务终止。
- **下载中取消会保留分片吗？** 当前取消会尝试删除，暂停和失败则用于恢复。

### 36. 失败任务重试

#### 功能目标

重新尝试一个失败业务任务，尽可能利用保留数据，同时重新验证失败原因是否已消除。

#### 主回答（完整业务实现链路口述版）

用户点击重试后，客户端沿用任务恢复流程，但先重新检查权限、源文件和服务端暂存状态。若本地分片不存在就重新下载，若服务端暂存不存在就重新初始化上传，权限或文件状态已经失效则直接报告失败。只有重新完成起点确认、传输和完整性校验后，任务才可以从失败状态转为完成，不能只清除错误提示。

#### 表达脉络（记忆钩子）

1. 用户发起重试 -> 2. 重新检查权限和源文件 -> 3. 没有本地分片就重下 -> 4. 没有服务端暂存就重建 -> 5. 重新确认起点并传输校验 -> 6. 真正完成后才离开失败状态

#### 追问卡片

**原完整链路补充（追问时展开）**

**入口**：用户在面板选择失败任务并点击重试，入口（`TransferManager::retry()`）检查任务状态，仍用原稳定任务键定位该任务行。

**分类准备**：上传按继续任务流程核对本地源文件、目标逻辑父路径、摘要和群信息；下载按恢复下载流程检查下载接收分片及真实大小。

**换轮次**：撤掉上一轮传输 ID 映射，分配新传输 ID，清理上一轮失败原因和过期状态，放回对应等待队列。

**重新初始化**：调度器在连接可用且并发名额允许时启动，重新发预检查、上传初始化或下载初始化，不绕过当前账号认证和服务端权限检查。

**服务端判定**：服务端按当前上传会话记录、物理文件对象、个人逻辑条目或群文件状态决定回放、续传、重新开始或拒绝，客户端只接受本轮有效应答；取得响应后定位文件并分块推进，进度以服务端确认或本地实际接收结果为准。

**收尾与边界**：成功释放名额并更新任务、面板和快照，再次失败也释放名额、写清新的失败原因并保留可恢复资料；重试不等于无条件从零开始，也不保证同一错误自动消失，源文件缺失、权限撤销和暂存被清理必须展示给用户。

- **重试会建重复文件吗？** 部分路径有请求幂等和同对象条目复用，但不能把全链路所有初始化、群引用和历史客户端行为都概括为绝不重复，需按具体提交分支说明。
- **只重试网络发送够吗？** 不够。失败可能在写盘、摘要、提交、目录或权限，必须重新建立合法上下文，而不是原样重发最后一块。

- **只收到完成报文就显示成功吗？** 不应，还要核对实际接收是否完整。
- **失败后本地分片会删吗？** 通常保留用于恢复，取消才走删除分片路径。

- **失败重试与连续点击、再次断线同时发生时，怎样测试状态和名额不会失控？** 让初始化、写入或网络阶段失败，再连续触发重试并交错断线，检查同一任务不会生成多个运行实例，新旧传输标识不会串用，名额不会重复占用或释放。重试前重新检查连接、权限、源和续传数据，失败应保留原因并回到可解释状态。不能为了让用例通过而自动从零开始或直接标完成，最终仍需核对真实文件和条目。
- **为什么下载的继续和重试采用相似流程？** 两者都重新核对分片与服务端状态，再建立新的本轮传输。暂停说明用户主动停止，失败说明上一次没有正常结束，但两种情况下客户端都不能信任旧连接和旧编号。

### 37. 多任务排队与有限并发

#### 功能目标

把大量任务限制为有上限的同时活动任务，兼顾吞吐、内存和交互响应。单连接上传三路、下载三路，个人与群共享对应方向额度。

#### 主回答（完整业务实现链路口述版）

客户端把多个上传和下载任务放入按方向管理的队列，只允许不超过上限数量的任务同时处于活动状态，服务端也执行自己的并发限制。多个文件通过传输标识复用现有长连接，下载任务按轮转方式推进并根据接收端处理速度做背压。这样限制的是活动任务数和数据推进速度，不是为每个文件无限创建线程或连接。

#### 表达脉络（记忆钩子）

1. 按上传下载方向建立队列 -> 2. 限制客户端活动任务数量 -> 3. 服务端再次限制并发 -> 4. 多文件复用长连接和传输标识 -> 5. 下载轮转并执行背压 -> 6. 不为每个文件无限创建线程连接

#### 追问卡片

**原完整链路补充（追问时展开）**

**入队**：用户连续选择文件时，管理器为每项创建独立稳定任务键、任务种类和传输 ID，放进上传或下载等待队列，初始显示排队。

**名额控制**：任务调度（`pump()`）分别检查上传与下载并发名额，当前单连接每个方向最多 3 个，个人任务与群任务共享对应名额；上传在摘要计算或初始化时占名额，下载在启动初始化时占名额，未真正启动的排队项不能伪装为正在传输。

**预检串行**：个人秒传预检查使用独立串行调度及待采纳信息，防止连接级预检结果错配；这不等于全部文件只能串行传输。

**服务端限流**：服务端按传输 ID 建立上传上下文或下载流，并再次限制各方向并发数量与重复 ID，不能依赖客户端自律。

**传输与背压**：上传分块按传输 ID 路由到对应上下文，写盘结果按连接号与传输 ID 回流；下载流加入轮转环按轮次发送有限数据；网络写出背压达到阈值时停止填充发送缓冲、等写出事件再继续，任务等待队列、群消息出站队列和套接字写缓冲各自负责不同资源。

**收尾与边界**：完成、失败、暂停或取消时按原状态归还名额并释放远端资源，再次调用调度器启动后续任务，避免双重扣减或永久占槽；每次状态变化通知面板并保存必要快照；所有任务共享网络连接、主事件线程、磁盘和工作线程池，有限并发不承诺固定带宽或完全互不阻塞。

- **单连接并发会完全互不影响吗？** 不会。它们共享 TCP、有队头阻塞，也共享线程池、磁盘和主线程；有限并发只改善调度，不提供资源隔离保证。
- **为什么服务端也要限流？** 客户端不可信，服务端才是资源保护边界；同时要避免把纯秒传预检占位误算成正在上传。
- **一个慢下载会无限占发送缓冲吗？** 调度检查缓冲压力并轮转，但仍需容量上限和失败处理；背压表示控制生产速度，不是让慢网络消失。

- **服务端确认就保证断电不丢吗？** 不能，当前确认语义不等于磁盘强制持久化承诺。
- **为什么摘要也要占名额？** 摘要会占用 CPU 和磁盘读取，若不计入，正文名额虽有限，实际资源仍可能被大量预处理压满。
- **暂存被清理了怎么办？** 预检返回真实状态，任务进入失败或重新开始，不能伪造原进度。
- **下载也要等上传的三个名额吗？** 两方向分别计数，但仍共享连接资源。
- **为什么旧数据不会写进新一轮？** 旧编号已摘映射，继续又使用新编号。
- **暂停会撤销已经上传的数据吗？** 不会自动撤销已接受前缀。
- **优先发聊天就绝不延迟吗？** 不能越过已进入同一 TCP 流的旧字节。
- **编号就是全局永久文件编号吗？** 不是，它只表示当前传输活动。
- **为什么不全部启动？** 会同时放大缓冲、磁盘竞争和管理成本。

- **同时选择大量文件，怎样验证上传和下载各自的并发上限，以及个人与群任务共享名额？** 混合创建个人和群的上传、下载任务，分别记录排队、摘要、初始化、传输和结束时间，并观察服务端活动上传槽和下载流。任一时刻同连接上传与下载各自最多三路，个人与群不能分别再拿一套名额；上传摘要阶段也要计入相关活动名额。完成、失败、暂停和取消后检查名额准确释放，绕过客户端限制直接发请求时服务端也要按上限处理。
- **大文件和大量小文件混合传输时，怎样评价公平性，小文件会不会长期等不到服务？** 同时提交大小差异明显的文件，记录每个任务的排队时间、首次服务时间、完成时间和实际字节速率，而不只比较总吞吐。区分已经启动的下载流之间轮转与尚未取得名额的任务排队：前者有轮转不代表后者有抢占或小文件优先。再混入聊天和心跳观察交互延迟；若所有名额被长任务占用，小文件等待应如实记录。
- **提高传输并发一定能提高吞吐吗，怎样找到只增加延迟、内存和失败率的临界点？** 在独立对比实验中固定文件分布、网络、磁盘、加密方式和客户端数量，逐级改变并发负载，同时测有效完成字节数每秒、任务排队时间、尾部完成延迟、错误率及内存峰值。吞吐趋于平台而延迟和资源继续上升，通常说明瓶颈转移或已接近容量边界。调参实验不能代替当前三路并发规则，也不能把排队任务数量说成真正并行工作的数量。
- **混合聊天、登录和文件传输怎样设计压测比例，怎样避免不同吞吐单位混为一谈？** 按用户行为设定空闲、交互、传文件和重连的比例，分别覆盖稳定到达、突发请求及长任务占槽。聊天看成功消息数每秒，登录看成功请求数每秒，文件看成功传输字节数每秒，并同时看各业务延迟与错误率。不要把这些数字相加成总吞吐，也不能只测持续大文件就代表登录和聊天能力；目标比例、并发连接数和试验时长要随结果一起记录。
- **项目中的“协议级多路复用”具体指什么？和 TCP 连接复用、线程多路复用有什么区别？** 一条 TCP 连接上同时跑多条独立的文件传输流，用 transfer_id 区分；复用的是“连接内的协议通道”，不是 TCP 连接，也不是线程。
- **为什么上限是 3+3？** 这是我当时拍的：单连接 6 条流已经能掩盖单流的 RTT 和写盘抖动，再往上收益递减，而服务端内存和 MySQL 连接数都吃不消。客户端排队，服务端还有硬兜底。
- **为什么不给每个文件开一条 TCP 连接？** 连接数会随文件数线性涨，登录态、心跳、权限校验都要复制；而且服务端连接表是线性扫描，连接越多越慢。
- **transfer_id 是如何分配和回收的？会不会冲突或复用？** 客户端每个连接一个单调递增的 64 位计数器，分配后不复用；服务端按 (连接, transfer_id) 建上下文，重复 id 直接拒绝；0 永久保留给旧单流路径。
- **高水位为什么是 256KiB？** 大约四块 64KiB，够吸收一次网络抖动，又不会让每条下载流占太多内存；按连接数乘一下就是最坏内存量。
- **多个下载任务如何公平调度？会不会出现大文件饿死小文件？** 一个轮转环，每 tick 只给环上的下一条流发一个 64KiB 块；大文件和小文件在环上权重相同，所以谁也不会被无限期跳过。 所有活跃下载流挂在一个环上，服务端用一个定时器驱动。
- **为什么不做加权公平？** 没有业务上的优先级需求，等权最简单也最可预测；真要做，可以给小文件更高权重或者更早完成。
- **并发上传下载的上限是怎么验证的？第 4 路会发生什么？** 客户端第 4 路在本地排队，不会发出去；如果绕过客户端直接发，服务端会按 3 路上限拒绝 29 或 40，未知/超限的传输不会回退到 0。 正常客户端路径：TransferManager 的队列是 3 路上传、3 路下载，第 4 个任务状态是“排队中”，等前面某个完成或失败释放槽位才发 29/40。
- **一个文件能不能并行上传？如果要做，怎么保证正确？** 当前实现是多文件并行、单文件单块停等；单文件并行需要把确认偏移从单值扩成分片状态。 当前一个 Uploader 同一时刻只允许一块在途，多个文件通过 TransferManager 分配不同 transfer_id 并行推进，这样服务端可以用 confirmed_offset 保证顺序写入。
- **为什么一个传输任务需要稳定任务键和传输 ID 两个键？** 稳定任务键保留同一任务行，传输 ID 区分每一轮网络活动。用户暂停后继续，应该还是界面中的同一个任务，但旧响应可能仍在路上。
- **下载怎样轮转发送，背压又限制什么？** 按活动任务轮流发一片，写缓冲过高就停，等排空后再推进。服务端维护下载任务轮转队列，每次选一项发送有限分片，再移动游标，避免一个任务一次塞完整文件。
- **同一文件双击上传两次，两个任务会互相影响吗？** 网络编号可以不同，但同一逻辑上传可能指向同一暂存，不能承诺完全独立。两个任务有各自界面标识和网络编号，不代表磁盘资源不同。
- **如果想改善多文件带宽体验，还缺什么？** 建议补全全局资源预算和任务公平策略，现有轮转不等于带宽控制。当前有有限任务数、下载轮转和写缓冲背压，主要避免单任务长期占满发送路径或内存增长。
- **你怎样评价当前控制模型，最稳妥和最需补强的分别是什么？** 值得肯定的是旧轮次隔离和进度分权，需要补强的是内容身份与全局资源边界。稳定任务标识配合每轮新编号，能让迟到应答失去归属。
- **上传和下载同时进行时会不会互相影响？心跳和普通消息会不会被大文件阻塞？** 两个方向独立调度，但共享同一条 socket 的写缓冲；下载有高水位、上传是客户端驱动的，心跳是 76 字节的小包，正常情况下能插进去，极端拥塞时会被排在大块后面。 上传和下载在服务端是两个独立的状态：上传等 31 来、写盘、回 32。
- **如果流很多，一个 tick 轮一圈不是很慢？** 会，可以按活跃流数调整 tick 或者一次给多条流各发一块；当前连接内最多 3 路下载，一圈很小。
- **背压会丢掉正文吗？** 主要是停止继续生产，已生成的数据仍按连接顺序发送，不是任意丢分片。
- **是不是每个客户端一个线程？** 不是，任务按需要提交到共享 Qt 线程池。
- **有线程池就代表并发受控吗？** 不代表，还要限制队列、文件句柄、内存和数据库连接等实际资源。

### 38. 传输任务面板

#### 功能目标

让用户看清每个任务的方向、进度、状态和失败原因，并能针对单任务控制。面板显示必须对应真实状态。

#### 主回答（完整业务实现链路口述版）

传输面板直接读取任务管理器中的任务状态、进度和错误，不另外维护一套容易过期的状态。用户点击暂停、继续、取消或重试时，面板只提交操作意图，任务管理器根据当前状态决定是否允许以及如何执行。状态变化和失败原因再由管理器通知面板刷新，保证按钮状态与实际传输状态一致。

#### 表达脉络（记忆钩子）

1. 管理器维护真实任务状态 -> 2. 面板读取进度和错误 -> 3. 按钮只提交用户意图 -> 4. 状态机决定操作是否合法 -> 5. 管理器发事件驱动刷新 -> 6. 面板状态与实际传输保持一致

#### 追问卡片

**原完整链路补充（追问时展开）**

**创建与持有**：文件传输任务由传输管理器持有，任务面板（`TransferTaskPanel`）在用户打开或需要展示时创建，面板本身不持有服务端上传上下文。

**订阅与组织**：面板订阅任务变化信号，通过稳定任务键取得任务种类、展示名、状态、完成字节、总字节和失败原因，按一项任务一行组织。

**进度口径**：上传的传输进度来自服务端确认偏移，下载来自本地实际接收字节；排队、摘要计算、初始化和已完成不能仅靠一个百分比混为同一状态。

**只表达意图**：用户点暂停、继续、重试或取消，面板仅把稳定任务键和操作意图交给管理器，不直接读写网络连接和本地文件；管理器校验状态并执行队列、传输 ID 映射、名额及收发资源处理，收到协议应答或后台结果后再更新任务。

**刷新与收尾**：任务变化信号驱动面板重读状态和错误文本，成功、失败、暂停和取消分别呈现，服务端写日志不等于用户已看到失败原因；关闭面板不自动取消任务，任务结束或用户取消后按任务模型移除或保留行，传输快照按管理器规则更新。

- **为什么不让每一行自己管理上传器？** 会把网络和界面生命周期绑在一起，关闭窗口容易影响传输；集中管理更方便限并发和恢复，代价是管理器职责需要控制。
- **进度到百分之百为何还不一定完成？** 可能还在摘要复算或资产提交；字节进度与业务终态需要分开解释。
- **失败后为什么保留任务行？** 给用户诊断和重试入口，不能只弹一次框后丢掉上下文；完成与取消的保留策略则另有规则。

- **为什么不一直复用同一个 ID？** 旧数据可能仍在网络或回调队列中，复用会让上一轮数据看起来属于新一轮。
- **为什么不能只用文件名？** 会重名、改名，也无法区分前后轮次。

- **多个任务传输同一文件或同名文件，怎样验证应答、进度和操作不会串到其他任务？** 同时创建同路径和不同路径同名任务，对照稳定任务键、每轮传输标识、目标文件及面板行，交错暂停、重试和迟到确认。检查每次变化只影响应有任务，重新分配标识后旧应答不能更新新一轮。若同源并发被当前实现显式限制，也应验证拒绝和原因；不能把文件名当作任务唯一键，或假定所有同源任务天然隔离。
- **实际测过哪些传输指标，吞吐、平均延迟、P95/P99、错误率和资源占用分别说明什么？** 回答必须以实际记录为准，没有数据就说明尚未压测。可观察单位时间成功完成的有效字节数、排队至真正完成的时长及分阶段耗时；P95/P99（第 95/99 百分位延迟）描述较慢请求，平均值可能掩盖少量卡顿。错误率要说明按任务还是尝试次数计算，重试也要单独计数，并关联处理器、内存、网络和磁盘。面板显示进度不代表已内置这些统计，更不能直接证明最终资产提交成功。

### 39. 未完成任务保存与恢复（含断线收敛）

#### 功能目标

桌面端保存未完成任务的意图，重启或再次登录后恢复可继续的任务。快照不是服务端字节进度或认证凭证的副本。网络断开时，还要让运行中的任务及时退出正常传输状态并释放名额，避免永久显示“进行中”；保留恢复材料但不假装自动成功。

#### 主回答（完整业务实现链路口述版）

客户端退出或异常关闭前，把未完成任务保存为快照，记录文件、目标位置、方向和恢复所需的标识。快照不把网络进度当成绝对事实，应用重新启动后，上传要重新向服务端查询暂存文件起点，下载要检查本地分片的实际长度。用户确认后再恢复调度，已完成、已取消或源文件已变化的任务不能直接按旧快照继续。

连接断开时，客户端先停止把任务显示为正常运行，释放活动计数和当前传输资源，同时保留可恢复的任务快照。重连和重新登录只恢复网络及认证条件，不直接把所有失败任务标记为成功；每个任务仍要重新确认源文件、权限和续传起点。这样用户能看到任务确实失败或等待恢复，也不会因为活动计数没有释放而把后续任务全部卡住。

#### 表达脉络（记忆钩子）

1. 退出前保存未完成任务快照 -> 2. 记录文件、目标和恢复标识 -> 3. 不把快照进度当最终事实 -> 4. 上传重问服务端起点 -> 5. 下载检查本地分片长度 -> 6. 用户确认后恢复，已结束任务不按旧快照继续

断线分支：1. 停止正常运行状态并阻断调度 -> 2. 释放活动计数和传输资源 -> 3. 保留可恢复快照 -> 4. 重连只恢复网络和认证条件 -> 5. 每项任务重新确认源、权限和起点 -> 6. 失败状态收敛后允许后续任务继续

#### 追问卡片

**原完整链路补充（追问时展开）**

**保存时机与范围**：管理器在任务创建、状态变化、显式保存及退出等节点保存传输快照，以当前账号分组写本地 JSON，避免不同账号任务混用；快照保存稳定任务键、任务种类、源路径、目标逻辑目录、展示名、群标识及接收分片路径等可恢复信息，完成与取消任务不作为待恢复项。

**不保存什么**：快照不保存仍然有效的网络连接、远端上传上下文或逐字节权威进度，传输 ID 也不能作为跨重连的长期任务身份。

**账号切换**：用户重新登录成功后设置当前账号（`setCurrentUser()`），切换账号前先保存原账号任务，再读取目标账号快照，按稳定任务键与内存任务合并以免重复恢复。

**恢复判定**：恢复上传先检查本地源文件，存在的按暂停等待继续，缺失或不可用的保留失败说明，不能照搬快照里的运行状态；恢复下载保留分片路径，真正继续时从文件真实长度读取声明偏移，分片缺失明确提示，不凭快照里的百分比继续追加。

**重新走链路**：用户继续恢复项后重新分配传输 ID、进入等待队列，按方向重走秒传预检查、上传初始化或下载元数据链路，重新经过服务端认证及授权；服务端用当前会话记录和对象状态决定真实起点或最终结果，客户端按有效应答恢复收发并更新同一任务行。

**边界**：文件损坏、源变更、暂存过期或权限变化都可能使恢复失败，保留可读原因并再次保存；浏览器刷新后不能据此宣称拥有桌面快照和原文件对象恢复能力。

- **为什么不持续保存每个字节进度？** 高频写快照会增加 IO（输入输出）和一致性负担，真实进度可由服务器暂存与本地分片恢复；代价是恢复时要重新核对。
- **为什么恢复成暂停？** 让用户明确确认，并避免登录后立即占满网络或读取已变化文件；自动恢复可提升便利性，但需要更完整的重试和权限策略。
- **写快照过程中进程崩溃呢？** 当前直接写文件，不应宣传成强原子或崩溃绝不丢；原子替换、版本和校验是可改进方向。
- **网页刷新页面后，未完成的上传也能像桌面端一样从快照恢复吗？** 不一样。刷新后浏览器里选中的文件对象已经失效，当前没有跨刷新自动恢复上传的承诺；桌面端的本地快照能力不能直接搬到网页上，网页要恢复必须重新选择文件并按服务端暂存续传。

- **快照保存运行状态吗？** 只保存恢复线索，恢复后必须重新认证、握手和核对文件状态。
- **为什么恢复不复用 id？** 旧 id 可能还有迟到的 32 或 42 在路上，复用会让这些块落进新上下文；换新 id 让迟到的块自然失效。

**断线时任务状态收敛（原完整链路补充，追问时展开）**

**阻断调度**：套接字断开或客户端心跳失联后，传输管理器进入连接丢失处理（`onConnectionLost()`），先阻止调度器启动新传输。

**任务转失败**：将运行或摘要计算中的任务转失败并记录断线原因，停止上传正文发送器、关闭下载接收句柄并撤销本轮传输 ID 归属；归还上传和下载并发名额、清理预检查等待归属，防止迟到初始化、写盘确认或摘要结果把任务重新改成运行。

**保留可恢复项**：排队、暂停和已结束任务保留各自含义，本地下载接收分片不因断线删除，必要任务信息写入传输快照。

**服务端清理**：服务端在断连清理中关闭所有下载流、清空轮转环、移除上传上下文与出站队列；断连路径与显式传输释放路径不同，不能一概声称已经对所有上传会话记录执行同一中止写库。

**迟到结果处理**：后台异步写盘或摘要复算完成后回主线程，通过连接号和传输 ID 查找上下文，找不到就不继续转正或向旧连接应答。

**暂存收敛与恢复**：上传暂存文件和会话记录由其状态、期限及回收调度器收敛，不因断连立即全部删除；网络重连并重新登录成功后调用连接恢复处理（`onConnectionRestored()`），解除调度阻断，排队任务可再次启动，失败任务仍由继续或重试重新初始化；此流程的含义是任务不再永久显示正常传输并保留恢复依据，不是保证断电不丢数据或所有任务已自动恢复成功。

- **为什么不把所有任务都删掉？** 会丢失用户意图和已下载字节；全部保留为运行又会误导。按状态分别处理更准确，代价是收尾路径较多。
- **后台计算回来了会不会把失败改成功？** 必须校验任务是否存在、状态和轮次是否仍匹配；迟到结果不能重新激活已经收敛的上下文。
- **服务端来不及收到中止怎么办？** 断连和空闲回收最终释放上下文，但不能保证上传暂存马上消失；恢复时要重新查询。

- **空闲回收会删完上传内容吗？** 不等同，主要释放上传上下文，暂存另行回收。

- **断线与暂停、取消、后台回调交错时，怎样验证所有任务会收敛而不是永久进行中？** 在运行、摘要计算、排队和暂停四类状态下断线，再重复触发失联处理并注入迟到结果。检查运行及摘要任务按规则转失败，排队和暂停任务保持相应状态，发送器、句柄、标识映射和计数没有重复释放；本地分片继续保留。重新登录后确认可调度任务能够推进，失败任务仍需按重试流程核验，不能由迟到回调自行变回成功。
- **暂停、取消、断线和空闲回收都要中止上传，怎样避免清理代码各走一套？** 它们需要共同对齐服务端认可的暂存前缀、更新上传会话状态并释放连接上传上下文，同时保留各自的任务终态。若写盘或摘要任务仍在途，先记录中止意图，在完成回调中收尾，避免过早处理仍被后台使用的文件。暂存能否保留和何时回收由独立规则判断，不等于取消后台工作就立即删文件。
- **写盘任务完成时连接已经断了怎么办？** 回调里按 connectionId 在连接表里找，找不到就丢弃结果，不会去碰已销毁的对象。
- **断连时正在写盘怎么办？** 上传上下文标记失效，写盘任务完成后回调找不到上下文就丢弃；暂存文件保留，重连后按物理大小续传。
- **写盘任务失败了怎么通知？** 回调里带失败标记，主线程把上传会话标记失败、释放槽位；暂存文件保留，客户端重试时按物理大小续传。
- **连接断开时，后台摘要还在计算，怎样收尾？** 计算结果不直接操作旧连接，回主线程后按标识重新查上传上下文。后台任务可能比连接活得更久，因此只携带连接号、传输 ID 和暂存位置等必要数据，不捕获旧连接指针去写应答。
- **重连成功后为什么不能把所有任务直接改成进行中？** 任务可能已失败、暂存已清理或分片已变化，必须按各自权威状态重新初始化。
- **上传中止有哪些收敛路径？** 显式释放、连接清理和空闲回收都要走统一的进度对齐与上传上下文释放。第一类是用户暂停或取消，客户端明确要求释放当前传输。
- **传输失败怎样呈现，怎样避免永久显示进行中？** 失败要进入终态并释放编号与名额，不能只留一条错误日志。连接断开、心跳失联、服务端拒绝、读写错误或续传信息不匹配，都会影响任务状态。
- **断线立刻停掉所有计算吗？** 当前不能这样说，主要通过结果接收与状态收敛保护业务。
- **为什么不让工作线程直接改套接字？** 要遵守对象线程归属，并避免连接已断开时仍使用旧对象。
- **为什么不在后台直接返回成功？** 连接和任务状态可能已改变，直接使用旧上下文有风险。
