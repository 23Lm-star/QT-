## 一、背景与动机

### 1.1 这个项目是什么背景，你为什么做，想达成什么目的？

**问题**：这个项目是什么背景，你为什么选择做它，想达成什么目的？

**核心**：**项目起源于高中同学的课程项目，我在基础云盘和私聊功能上继续独立扩展，逐步把它做成完整的云盘聊天工程实践。**

**回答**：这个项目最初来自一位高中同学的课程项目，课程要求是做一个带简单聊天功能的云盘系统。我先完成了文件管理、上传下载和好友私聊这些基础功能，交付基础版本后，又从实际使用场景出发继续完善。比如网络长时间传输需要心跳和断线恢复，重复上传同一内容可以用秒传减少重复写盘，多文件同时上传需要并发控制和传输编号。后来我又加入了自研内存池、MySQL 连接池和群聊模块，最终形成了现在这套基于 C++11和 Qt 5的客户端、服务端项目。

我做这个项目的目标不是做一个可以直接商用的网盘，而是把账号、聊天、文件传输和持久化串成一条完整链路，并在这个过程中解决协议分帧、传输恢复、资源复用和并发状态这些实际问题。

**表达脉络**：

1. 先交代聊天与文件协作的项目背景
2. 用网络、状态和存储说明技术目标
3. 补上本人真实的立项原因与预期

**可能被追问**：

- 现在的全部功能都是立项时计划的吗？ → 不是。最初只有云盘基础功能和好友私聊，心跳、断点续传、秒传、资源池和群聊都是后续逐步加入的。

### 1.2 聊天系统面向什么场景，支持私聊还是群聊？

**问题**：聊天系统面向什么场景？是一对一聊天还是群聊，主要解决什么问题？
**核心**：**从功能定位看，面向同一账号体系下的联系人聊天、群内沟通和文件协作，私聊与群聊都支持。**

**回答**：用户登录后，可以维护好友、进行一对一私聊，也可以创建群、邀请成员并发送群文本；需要交换文件时，可以使用个人云盘、好友分享或群文件。把这些功能放到一起，目标是让聊天身份、资源归属和文件访问沿用同一套账号与服务端规则。

所以它不只是一个公共聊天室，私聊和群聊有各自的数据、成员和权限边界。这个项目主要是我个人持续完善的工程实践，最初服务的是课程项目场景，后续扩展主要用于验证我自己的设计。它没有经过长期商业运营，我会把它定位成可运行、可演示、可继续演进的个人项目。

**表达脉络**：

1. 先说联系人、群沟通与文件协作场景
2. 明确私聊和群聊都已具备
3. 说明共享账号但业务边界各自独立

**可能被追问**：

- 群聊是不是多人私聊的简单循环？ → 不是，群有成员、角色、消息序号及已读等独立状态。

### 2.2 整体架构分成哪些部分，一次请求怎样流动？

**问题**：整体架构分成哪些部分，一次请求怎样流动？

**核心**：**客户端负责交互与本地状态，服务端负责身份和业务，数据库与文件系统分别保存不同事实。**

**回答**：桌面端用 Qt Widgets（桌面界面组件）处理用户动作，封装 PDU（协议数据单元）经长连接发送。服务端先拆帧和核对连接认证上下文，再交业务处理器，读写 MySQL（关系数据库）元数据或文件内容，最后返回应答、消息事件或传输确认。整文件摘要和上传写盘等任务进入线程池，结果回事件线程更新状态。

客户端还用 SQLite（嵌入式数据库）保存近期消息和独立快照恢复传输线索。

**表达脉络**：

1. 先按界面、服务端和持久资源分职责
2. 串起封装、拆帧、鉴权与业务应答
3. 补充后台任务回主线程
4. 说明本地存储的位置

**可能被追问**：

- 为什么客户端也有数据库？ → 它保存本机近期记录，不替代服务端权威数据。

## 三、技术选型

### 3.1 为什么选择 C++ 和 Qt，服务端不画界面为什么也用 Qt？

**问题**：为什么选择 C++ 和 Qt？服务端不需要渲染界面，为什么也选择 Qt？

**核心**：**项目要的是双端同协议、一个进程接住多连接并长期在线、单人维护且跨平台；Qt 把界面、事件循环、异步网络、数据库接口和线程池一并提供且可分模块使用，服务端不画界面也能只链核心与网络模块运行。**

**回答**：项目有三个前提：桌面要有界面；服务端一个进程要接住多连接、长期在线；双端共用一套协议。而且只有我一个人维护。

Qt 提供的正好是这些：界面、异步套接字和事件循环、数据库接口、线程池；而且这些模块不带界面也能单独用，服务端只链接核心和网络模块就能起事件循环。

如果自己手写：每条连接的收包缓冲和半包切割要自己维护，断线重连后没传完的文件分片和进度也得自己按连接清掉，否则旧分片会算进新任务；数据库接口是阻塞的，还得自备连接池和工作线程。

用 Qt 最实在的收益有一条：协议和数据结构两端只写一份，事件循环和线程池都是现成的，省下的时间花在分帧、续传和权限上，这些框架不管，只能自己写。

**表达脉络**：

1. 先交代项目对技术栈的四条约束
2. 再说明 Qt 各模块提供了什么，且可分模块使用
3. 用自己手写的四条麻烦说明不选它的代价
4. 收敛到成本收益，并指出框架边界

**可能被追问**：

- Qt 只有界面组件吗？ → 不是，网络、线程、数据库及事件循环可以独立于界面使用。
- 那你不就是在调框架，核心逻辑写了什么？ → 框架管事件分发与 I/O 通知；协议分帧、传输状态、断点续传和权限判断没有现成实现，是自己写的。
- 有没有对比过更适合服务端的网络框架？ → 没有在项目里实战用过，不据此下结论；判断依据是双端同栈、单人维护、并发量不大这三条约束。
- 重做会一定换掉 Qt 服务端吗？ → 不一定，应按目标负载和维护约束选型，先解释当前真正的瓶颈。

### 3.2 为什么用自定义二进制协议，不直接用 HTTP 和 JSON？

**问题**：为什么用自定义二进制协议，不直接用 HTTP 和 JSON？

**核心**：**当前选择长连接统一承载消息与文件，代价是自己维护编码、分帧和跨端一致性。**

**回答**：二进制报文有长度、类型、参数和变长正文，可以在同一连接里表达聊天事件、文件分片与控制应答，减少重复文本字段，便于学习协议边界。HTTP（超文本传输协议）和 JSON（文本数据格式）也能完成这些业务，生态与可观察性通常更成熟；不能把自研说成一定更快或唯一可行。

当前基础报文还有平台布局与字节序约束，其他语言客户端接入时需要明确复现编码。若重做公开接口，应按维护成本选择成熟传输与序列化方案，而不是为了自研而继续扩展固定字段。两端必须对类型编号、字段布局和编码含义采用相同约定。

**表达脉络**：

1. 说明长连接统一承载的需求

### 3.3 为什么服务端用 MySQL，客户端又用 SQLite？

**问题**：为什么服务端用 MySQL，客户端又用 SQLite？

**核心**：**MySQL 是独立服务进程，面向多连接并发写与事务一致性；SQLite 是嵌入式文件库，单进程访问、免部署、查询无网络往返。前者对上服务端的共享权威数据，后者对上客户端的本机近期记录。**

**回答**：MySQL 的特点是一个独立运行的服务进程，客户端通过网络连接访问，天生面向多个客户端并发读写；它支持事务、行级锁和唯一约束，能在并发写入的同时保证跨表变更一起成立，代价是要单独部署、维护连接池。服务端正需要这几点：账号、好友关系、群成员和文件引用要被多条连接同时访问，唯一约束防止重名和重复关系，事务保证服务端操作的原子性，行级锁让不同用户的写入不互相阻塞。

SQLite 的特点相反：它是嵌入式库，不是服务进程，一个本地文件就是整个数据库，不需要部署也没有账号权限体系，查询没有网络往返；但写操作是全库串行的，只适合单进程单用户。客户端正好是这种形态：只保存当前设备的近期消息，一个用户一个进程，不存在写竞争；装上就能用，去重和按会话截断都是本地毫秒级操作。

**表达脉络**：

1. 先讲 MySQL 的形态与能力，再对上服务端的并发写与跨表一致性
2. 再讲 SQLite 的形态与限制，再对上客户端的单用户与免部署

**可能被追问**：

- 本地库加密了吗？ → 当前是明文。
- 为什么不用一个大文件？ → 聊天会话查询、去重和截断需要自行维护更多索引与更新逻辑。
- SQLite 单写者会不会成为瓶颈？ → 客户端只有一个用户一个进程，写入频率由收发消息决定，量级远低于库级锁的饱和点，真正的上限在本地文件读写。

### 3.4 服务端怎样管理多连接，事件循环与线程池怎样分工？

**问题**：服务端是多线程的吗？如何管理多个连接、收发请求，并把工作分派到对应线程？

**核心**：**套接字与多数业务由同一个事件线程管理，上传写盘和整文件摘要等明确任务交 Qt 线程池，不是一连接一线程。**

**回答**：不是一连接一线程。服务端用 QTcpServer（TCP 监听组件）监听，谁连上来，我就在连接到达的回调里创建套接字、登记到连接表；所有套接字都挂在同一个事件循环上，哪个连接有数据就触发哪个的读事件，收包、拆帧、按类型分派业务都在这条线程里做。没有选一连接一线程，是因为连接一多，线程切换和内存都吃亏，而且 Qt 对象有线程归属，套接字挪进工作线程后所有回调都得跨线程，得不偿失。

真正费时的活不让事件线程干。上传分片写盘和上传收尾的整文件摘要，这两类明确的耗时任务交给 Qt 自带的 QThreadPool（Qt 线程池）；后台只干活、不决策，结果带着任务标识排队回主线程，由主线程重新定位连接和任务，再决定推进还是丢弃。数据库查询和大部分业务目前还在事件线程里同步执行，单条慢查询会拖慢所有连接，这也是当前我最想重构的地方。

1. 先说监听、创建套接字与连接登记
2. 说明多连接共享事件循环而非各占一线程
3. 列出实际进入 Qt 线程池的耗时任务
4. 解释结果为何回事件线程修改状态
5. 指出数据库等仍存在同步路径

**可能被追问**：

- 客户端也是主线程等待消息吗？ → 桌面端由主线程事件循环接收网络通知，同时处理界面事件，不是用阻塞读取一直等消息。
- 为什么不让工作线程直接改套接字？ → 要遵守对象线程归属，并避免连接已断开时仍使用旧对象。
- Qt 能把每个请求自动分派到线程池吗？ → 不能，框架提供机制，项目必须明确提交任务和处理结果。

### 3.5 为什么实现内存池与数据库连接池，它们分别解决什么？

**问题**：为什么实现内存池与数据库连接池，它们分别解决什么？

**核心**：**内存池减少频繁分配的管理开销，连接池复用昂贵连接，但自实现也增加维护成本。**

**回答**：

服务端每收一个报文、每拆一次帧都要分配一个 PDU，分配频率跟着连接数和消息量走。PDU 的分配没有走通用分配器，而是走自己实现的内存池：小块按线程缓存、中央缓存、页缓存三层取用，从哪一层取的就还回哪一层，跨线程释放另有回收路径。这样做主要降低了两件事：一是小块反复分配造成的碎片，二是并发分配时对同一把锁的争抢；向系统申请内存也从每次分配变成按页批量申请。代价是内存不轻易还给操作系统，线程缓存还会让长时间运行时的内存驻留偏高。2026-11-17 的分配微基准实测：单线程报文负载比 malloc/free 快约 2.3–4.1 倍，驻留内存更高，4 线程小负载因中央桶锁争用收窄到约 1.3 倍；这是分配微基准，不等于整机加速。

建立一条 MySQL 连接要完成握手和认证，开销远大于一次查询，所以池子预留空闲连接，用完归还而不是关闭，既省下建连成本，也不让连接数随并发失控；归还由 RAII（作用域管理资源）句柄在析构时自动完成，业务分支提前返回或抛异常也不会漏还、把池耗尽。

**表达脉络**：

1. 先给触发点：PDU 分配频率随连接数和消息量增长
2. 说明三层取用与按层归还，降的是碎片和锁争抢
3. 交代代价：内存不还给系统，长跑驻留偏高
4. 说明建连成本远高于一次查询，因此复用而不是反复重建
5. 归还交给 RAII 句柄，收口到自实现的维护成本

**可能被追问**：

- 连接池会让查询变异步吗？ → 不会，同步查询仍可能阻塞事件线程。
- 有内存池就没系统分配了吗？ → 不是，大块和回退路径仍可能使用系统资源。

### 3.6 Qt 会锁住主线程吗，事件循环是否只能在主线程？

**问题**：Qt 会不会锁住主线程？事件循环是否只有一个且只能在主线程，连接与接受连接会不会让整个线程卡住？

**核心**：**事件循环不会天然锁死线程，阻塞来自其中执行的具体操作；其他线程也可以有自己的事件循环。**

**回答**：事件循环不断分发网络、定时器和界面事件，某个回调结束后才能处理这个线程里的下一个事件。QTcpSocket（TCP 套接字组件）的异步连接和 QTcpServer（TCP 监听组件）的连接到达通知，不要求主线程停在那里等待对端完成交互，所以注册多个连接并不等于主线程逐个阻塞读取。

但异步通知不意味着回调里的业务也自动异步。若在槽函数中同步查数据库、做大文件操作或调用等待型接口，事件线程仍会被占住，其他连接和心跳都可能延后。Qt 的工作线程也能运行各自的事件循环；本项目当前主要使用一个事件线程管理网络，部分文件任务进入线程池，这和“Qt 只能有一个循环”是两回事。

**表达脉络**：

1. 先说明事件循环按顺序执行回调
2. 区分异步连接通知与同步等待接口
3. 举数据库或长文件任务占住回调的例子
4. 区分 Qt 能力与本项目实际线程模型

**可能被追问**：

- 线程池任务一定需要自己的事件循环吗？ → 普通计算或写盘任务不一定需要，异步事件对象则依赖其所属线程的事件循环。
- 三次握手本身是阻塞的，这个握手过程是主线程还是工作线程做的？ → 都不是。TCP 三次握手由操作系统内核完成，握手成功的连接进入监听套接字的 accept 队列；QTcpServer 的 newConnection 通知只是从队列里取出已经建好的连接并创建套接字对象，主线程并不参与握手等待，所以不会卡在握手上。真正可能占住事件线程的是回调里的同步业务，而不是 accept 本身。

### 3.7 信号和槽怎么用，一个信号或槽能连接多少个对象？

**问题**：信号和槽具体怎么使用？一个槽能接几个信号，一个信号能连接几个槽？

**核心**：**使用 connect（建立连接）关联信号和处理函数，数量关系是多对多，执行线程由连接类型和线程归属决定。**

**回答**：例如把套接字的 readyRead（数据可读）信号连接到接收槽，事件到来后读取可用字节，再交给拆帧逻辑。一个信号可以连接多个槽，一个槽也可以接多个参数类型匹配的信号；这只是在描述通知关系，不能据此认为每个槽会开一个线程。

默认的 AutoConnection（自动连接）在信号发射时比较当前执行线程与接收对象所属线程：同线程通常直接调用，跨线程通常排队投递到接收线程的事件循环。DirectConnection（直接连接）在发射线程执行，QueuedConnection（排队连接）则等接收线程处理事件。因此主线程槽里做同步长任务仍可能卡住界面或网络；跨线程使用自定义参数时还需要满足参数复制及元类型要求。

### 3.10 服务端怎样通过 Qt 使用 MySQL？

**问题**：服务端也用 Qt 连接 MySQL 吗？数据库连接怎么获取和管理，查询是同步还是异步？

**核心**：**服务端用 Qt SQL（数据库访问模块）的 QMYSQL 驱动加项目封装的连接池访问 MySQL，租连接、执行语句、自动归还；池子复用连接，不改变同步查询的性质。**

要说清楚的是，池子只是复用连接，查询本身还是同步的：在事件线程里执行语句，这条线程就要等数据库返回；池的上限用尽时，当前实现是快速返回失败让客户端重试，不是排成无限等待队列。

## 四、亮点

### 4.1 请说三个技术亮点。

**问题**：请说三个技术亮点。

**核心**：**三个亮点分别落在协议、消息、存储三层：报文分帧与按类型分发、群消息缺口恢复、文件条目与正文分离。每个都对应一个具体模块。**

**回答**：第一，协议层的报文分帧与按类型分发。实现上，每个报文都有定长头部：总长度、正文长度、类型和 64 字节参数区，后面接变长正文；接收端按连接维护缓冲，先等够一个头，再按总长等完整正文，循环切出完整报文。它解决两个问题：一是 TCP 本身不保留消息边界，半包和粘包只能靠长度字段恢复；二是同一条连接上聊天、群操作、文件分片并存，按外层类型分发，文件族再按传输编号找到对应任务。

第二，消息层的群消息缺口恢复。实现上，群内消息带递增序号，客户端为每个群保存连续已读位置，以及超过已读位置的缓冲区；收到的序号不连续就说明中间有缺口，按已读位置向服务端补拉已读之后的后续消息；并且通过不断的接收消息往后增加已读位置。它解决的是业务层并发带来的顺序问题：TCP 保证单条连接上字节有序，但多成员几乎同时发言时，服务端仲裁出的序号顺序和各端本地展示顺序可能不一致；重连补拉回来的历史消息又会和实时消息交错。序号和连续已读位置把这几类来源归成一条确定的总序。

第三，存储层的文件条目与正文分离。实现上，逻辑条目保存账号、目录、名称和对物理对象的引用，物理对象只保存正文；上传先对内容算摘要，命中已有对象就只建条目加引用，不重复写盘；删除条目减引用，引用归零才回收正文。它解决同一份内容被多账号、多目录引用时的重复存储，以及分享、改名、删除各自独立时正文不被误删。

**总述**：三个亮点不在同一层，但思路一致，都是在“网络只给字节、业务需要状态”的落差里建立状态依据：协议层用长度和类型恢复边界，消息层用序号和连续位置恢复顺序，存储层用摘要和引用计数恢复归属。每个机制的权威状态都在服务端，而不是客户端暂存。

**表达脉络**：

1. 协议层：先讲定长头部的字段布局，再讲接收缓冲如何按长度循环切帧，最后落到按类型与传输编号分发，对应解决半包粘包与同连接多业务并存
2. 消息层：先讲序号、连续已读位置和缓冲区怎么保存，再讲缺口如何发现、按已读位置补拉并随接收推进，最后点明顺序问题来自并发仲裁与补拉交错，而不是网络乱序
3. 存储层：先讲条目与正文的分工，再讲上传按摘要命中建条目、删除按引用归零才回收，最后落到重复存储与误删正文的消除
4. 总述：三个机制分别在边界、顺序、归属上建立状态依据，权威状态都放在服务端

**可能被追问**：

- 为什么不把包大小限制住来避免半包和粘包？ → 发送方可以控制自己，但 TCP 是字节流，接收方不能假定一次读取正好是一个包；小会粘、大会半，边界只能由长度字段恢复。
- 群消息已读为什么不用收到的最大序号？ → 最大序号可能跳过了中间缺口，直接当已读会把缺口里的消息永久漏掉；只有连续覆盖到的位置才是安全的已读。
- 摘要命中会不会把别人的文件错认成同一份？ → 命中要同时校验内容摘要和长度，只凭其中一项存在碰撞风险；回收正文之前必须确认引用归零，否则会把还在被引用的内容删掉。

## 五、不足与重做

### 5.1 项目目前有哪些不足？

**问题**：项目目前有哪些不足？

**核心**：**按“不足 + 对应补法”讲四点：慢操作移出主线程、分享升级为实时链接、私聊补确认闭环、凭据与本地存储收敛。**

**回答**：我按“现在哪里不足、打算怎么补”讲四点。

第一，主线程负担。数据库查询和目录操作目前还在事件线程里同步执行，一条慢查询或一次大目录扫描会拖慢所有连接。补法是把这些操作移到子工作线程：数据库连接在线程内创建和使用，操作结果带着请求标识排队回事件线程更新状态，事件线程只保留拆帧、鉴权和状态收敛。

第二，分享语义。目前好友分享更接近一次性快照，接收方拿到的是取回那一刻的内容，源文件之后更新了接收方感知不到，也没有独立的权限和有效期控制。补法是做成更贴近真实云盘的分享：接收方引用同一个物理对象而不是拷贝副本，源文件更新后接收方看到的就是新版本；分享链接带独立的权限、过期和撤销机制。

第三，私聊可靠性。私聊目前把“对方在线”和“投递成功”绑得过早，缺少接收确认和稳定的消息身份，断线时序下可能漏补或重复。补法是给每条私聊分配稳定消息 ID，接收端落库成功后回 ACK，服务端按 ACK 推进投递状态，没确认的消息按 ID 补拉，把“已保存、已转发、对方已收到”三个状态分开。

第四，凭据与本地存储。口令派生还是快速加盐 MD5，本地消息库也是明文保存。改进方向是换带成本参数的慢口令派生算法，并为本地库增加加密和访问控制。

这四点分别对应性能、功能语义、可靠性和安全四个面，都不是多加几个界面功能能解决的。

**表达脉络**：

1. 主线程负担：数据库和目录操作同步执行拖慢所有连接 → 移到子工作线程，结果排队回事件线程
2. 分享语义：一次性快照、源更新不可见 → 引用同一物理对象，链接带权限、过期、撤销
3. 私聊可靠性：在线标记过早绑定投递、缺接收确认 → 稳定消息 ID、落库 ACK、按 ID 补拉
4. 凭据与本地存储：快速加盐 MD5、本地明文库 → 慢口令派生、本地加密

**可能被追问**：

- 这四点哪个最优先？ → 看目标。改善日常体验先做主线程异步化，公开部署则优先处理凭据派生和本地数据保护。
- 把数据库操作移到子线程要注意什么？ → 数据库连接有线程归属，必须在对应线程创建和使用，不能跨线程共用一条连接；结果要排队回事件线程改状态。
- 这些是现状还是设想？ → 不足是当前实现的真实状态，补法是改进计划，都还没有实现。

### 5.3 你最不满意的一个设计是什么？

**问题**：你最不满意的一个设计是什么？

**核心**：**从维护角度看，是大量业务身份仍依赖可变路径字符串。**

**回答**：目录和暂存仍在不同程度上用路径描述资源，一次改名或移动就可能牵动后代条目，后台任务和恢复也要认相同位置；分享链接已改为绑定源条目标识，不受改名移动影响。路径能用于实际文件访问，却不适合承担所有稳定业务身份。更好的方向是把用户、条目、内容版本与上传会话分开编号，再保留路径映射。这个评价不等于否定现有功能，也不能说稳定编号改造已经完成。

2. 举移动影响暂存与恢复，说明分享已改绑条目标识
3. 区分访问位置与稳定业务身份
4. 提出分离编号的长期方向

**可能被追问**：

## 六、质量与工程习惯

### 6.1 客户端与服务端表现不一致时，怎样定位跨端问题？

**问题**：客户端与服务端表现不一致时，怎样定位跨端问题？

**核心**：**沿同一请求的编码、分帧、业务结果和界面处理逐段核对。**

**回答**：项目没有正式线上故障，所以我会把它回答成一套本地排查方法。比如下载没有进度时，我先确认客户端是否真的发出了请求，再检查服务端是否按预期类型和长度拆帧，业务层是否返回拒绝，最后确认客户端是否把响应路由到了当前任务。长度、字节序和旧编号迟到都可能让两端对同一段字节产生不同解释。定位时我会围绕连接号、请求类型、传输编号和状态变化看日志，不记录密码、令牌或完整文件正文。

**表达脉络**：

1. 把界面现象定位到一次请求
2. 按发送、解析、业务、路由逐段追踪
3. 检查长度字节序与迟到编号
4. 说明日志保密与真实案例边界

**可能被追问**：

- 服务端打印成功客户端为什么仍没动？ → 还要看成功指哪一层，以及应答是否正确到达并匹配任务。

### 6.2 两端协议怎样保持一致？

**问题**：两端协议怎样保持一致？

**核心**：**两端共用同一份 protocol.h，报文字段布局和类型编号完全一致；协议只追加编号，不改旧含义。**

**回答**：两端各有一份 protocol.h，里面的报文布局、字段顺序和类型编号是同一份契约，报文怎么组就怎么拆。改协议时只追加新编号，旧编号的含义和字段位置不动，老报文到了新版本也照样解析。另外有 Python 测试脚本按同一布局组包，相当于第三只手在验证两端没有各说各话。

**表达脉络**：

1. 共用同一份 protocol.h，布局与编号就是契约
2. 扩展规则：只追加，不改旧编号
3. 测试脚本按同一布局组包，兜住两端偏差

**可能被追问**：

- 其他语言客户端没有 protocol.h 怎么办？ → 按协议文档复现字段顺序、字节序和长度规则，并用跨语言测试确认与 C++ 客户端互通。
- 两份文件改着改着不一致了怎么办？ → 共享的报文定义部分内容相同，测试脚本按固定布局组包发请求，一端解析出错就会立刻暴露。

## 七、性能与规模化

### 7.1 系统能支持多少用户，主要瓶颈在哪里？

**问题**：系统能支持多少用户，主要瓶颈在哪里？

**核心**：**目前没有确定容量数字，应分开讨论空闲连接、活跃消息和大文件负载。**

**回答**：大量空闲在线连接主要占对象、缓冲与心跳资源；同群高频发送竞争群序号与持久写入；大文件又增加磁盘、摘要和队列占用。当前多数业务仍在事件线程，数据库和部分文件操作同步执行，所以一条长操作可能拖慢其他请求。连接池和线程池只是资源管理方式，不能把池大小换算成在线人数，更不能把已注册账号数当并发容量。

**表达脉络**：

1. 先区分三类用户负载
2. 沿事件线程找共享同步路径
3. 说明群热点与文件资源竞争
4. 明确没有可报的确定用户数

**可能被追问**：

- 增加工作线程就线性扩容吗？ → 不会，数据库锁、磁盘和有序连接仍是约束。
- 多实例能直接开吗？ → 当前连接认证会话和启动对账依赖单实例，需要先改共享状态模型。

### 7.2 数据库会不会成为瓶颈，连接池能解决多少？

**问题**：数据库会不会成为瓶颈，连接池能解决多少？

**核心**：**可能，连接池减少建连开销，不消除同步查询、锁竞争和数据量增长。**

**回答**：群消息要持久写入并分配序号，目录要查条目，登录与引用更新也使用事务。连接池先复用空闲连接，上限用尽时当前返回不可用句柄，并不自动排成无限等待队列。即使每次都能取到连接，同步查询仍占事件线程，热点群记录也仍串行。扩展要从请求路径、索引与事务范围分析，不把“有池”解释成数据库不再限制系统。

**表达脉络**：

1. 说明哪些业务会访问数据库
2. 讲连接复用和耗尽行为
3. 指出同步查询与热点锁仍存在
4. 按具体查询路径讨论改进

**可能被追问**：

- 给连接池加锁就能跨线程共享连接吗？ → 不能，Qt 数据库连接仍有线程归属。
- 扩大上限一定更快吗？ → 未必，可能只是把更多压力同时推给数据库。

### Q2 为什么出现半包粘包，你怎样恢复消息边界？

**问题**：为什么会产生半包、粘包，项目怎样解决？

**核心**：**TCP 只保证有序字节流，不保留业务消息边界，接收端必须按协议总长度拆出完整帧。**

**回答**：发送两条消息，不保证接收时恰好读两次；一次读取可能只有第一条的一部分，也可能同时包含第一条尾部和后续消息。这分别表现为半包与粘包，原因是应用的读写边界不等于 TCP 字节流的交付边界，不能归咎于 Qt 把消息打乱。

项目先把本次读取的字节追加到每连接缓存。缓存达到固定头长度后，检查总长范围、正文长度与总长关系以及类型范围；头合法但整条消息还不够就继续等待。够一整帧才交业务处理并从缓存前部移除，然后循环解析后续完整帧，剩余半帧留给下一次可读通知。普通报文和上传数据报文分别有长度上限，缓存也有限制，不能无限等待或分配。

**表达脉络**：

1. 先说明 TCP 不保留应用消息边界
2. 用一次读取半条或多条解释现象
3. 先查头部再等待完整总长
4. 循环消费完整帧并保留尾部半帧
5. 补上报文与缓存的资源边界

**可能被追问**：

- 一次读取到三条消息怎样处理？ → 按顺序循环解析三帧，不能只处理第一帧后丢弃剩余字节。
- TLS（传输层加密）会自动恢复业务消息边界吗？ → 不会，加密记录也不等于应用层 PDU 的边界。

### Q9 自定义 PDU 有哪些字段，分别表示什么？

**问题**：自定义 PDU（协议数据单元）的字段按什么顺序排列，每个字段有什么作用？

**核心**：**当前固定头为三个 4 字节整数加 64 字节参数区，共 76 字节，后接变长正文；消息类型不是联合体。**

**回答**：当前两端共享的布局依次是 uiTotalLen（整包总字节数）、uiMsgLen（正文总字节数）、uiType（消息类型编号）、caData（64 字节固定参数区），最后是 caMsg（变长正文）。前三项在当前目标环境各占 4 字节，因此固定头是 76 字节，正文长度不算进 sizeof(PDU)（报文结构固定头大小）；有效报文需要满足总长等于固定头加正文长度。

总长用于从字节流定位一帧，类型决定交给哪个业务处理，固定参数区按不同类型承载账号或传输控制参数，较长消息和文件分片放在正文。参数的具体含义还要结合消息类型解释，不能认为这 64 字节能无条件当成字符串。当前做法依赖约定的整数宽度、编码与字节序，其他语言接入时必须显式匹配，不能直接照搬任意机器的结构体内存。

**表达脉络**：

1. 按总长、正文长、类型、参数、正文讲顺序
2. 算清固定头 76 字节及长度关系
3. 说明类型分派和参数区复用
4. 补上跨语言布局与编码约束

**可能被追问**：

- 类型字段是 union（联合体）吗？ → 不是，当前 uiType 是一个无符号整数，用枚举编号解释。
- 扩展类型能插到旧编号中间吗？ → 不能，已发布编号只追加，不复用或重排。

### Q10 接收缓冲区多大，有没有上限，不限制会怎样？

**问题**：服务端接收缓冲区设置多大，是无限空间吗，有没有大小限制，不限制会有什么问题？

**核心**：**每连接应用待处理缓存使用动态字节数组，但设有 1 MiB 加 8 KiB 的检查上限；这不是进程全部内存的硬上限。**

**回答**：缓存不是预先固定分配后永不变化的数组，它会随追加和消费增长缩小。当前服务端把每连接应用待处理缓存上限设为 1 MiB（1,048,576 字节）加 8 KiB（8,192 字节），也就是 1,056,768 字节；普通入站整包上限是 16 KiB，上传数据整包例外放宽到 1 MiB 加 4 KiB，以容纳较大文件分片。这几项分别约束缓存总量和单包声明长度，不能混为一谈。

不限制时，攻击者可以不断发送不完整消息，或声明巨大长度诱导缓存持续增长；即使单连接正常，多连接累计也可能耗尽内存。当前实现是先 readAll（读取当前可用字节）并追加，再检查是否超过缓存阈值，超出即清理并断开，因此可能短暂超过这个值，Qt 与操作系统的缓冲也不包含在该数字里。源码部分注释和警告还写旧的 256 KiB，面试应以实际常量为准，不能照旧日志报数。

**表达脉络**：

1. 区分动态缓存和资源检查上限
2. 分别说明每连接缓存与单包长度的约束
3. 解释不完整消息和多连接的内存风险
4. 说明先追加后检查及旧注释的局限

**可能被追问**：

- 是不是整个服务端最多占一兆内存？ → 不是，这是一个连接的应用待处理缓存阈值，还要考虑其他连接和各层缓冲。
- 单包上限能防住所有慢速发送吗？ → 不能，还需要按协议进展、连接数量和资源预算补充约束。

### Q11 大量恶意超大包怎样识别和处理？

**问题**：如果有人恶意发送大量超大数据包，服务端怎样筛选、拒绝和处理？

**核心**：**先检查每连接缓存和头部长度契约，再决定是否等待正文；连续非法头达到 5 次会断开，但现有防护不等于完整抗攻击体系。**

**回答**：服务端收到字节后先检查待处理缓存是否超限；达到固定头长度后，再检查声明总长不能小于头部、不能超过对应消息类型上限，正文长必须和总长减固定头一致，类型编号也必须处于允许范围。这样不需要等一个任意巨大的声明长度全部到达，才知道它不能被当前协议接受。

遇到非法头，当前实现累计连续非法计数并丢弃相应缓存，尝试恢复解析；计数达到 5 次就清缓存、断连接。合法头会把计数清零，即使整帧还没收齐，所以这个阈值不能说成“累计收到五个异常包永久拉黑”。缓存整体超限会直接断开。当前主要覆盖畸形长度与乱包资源风险，合法小包洪泛、多连接总资源和慢速进度等还需要限速、连接预算与更严格进展规则，不能只凭这几项检查宣称不会被打爆。

**表达脉络**：

1. 先查缓存总量再解释头部长度契约
2. 说明不同类型有各自入站整包上限
3. 解释连续非法计数与合法头重置
4. 把现有防护与待补的限速预算分开

**可能被追问**：

- 阈值是十次吗？ → 当前常量是连续非法头 5 次，不能沿用旧面试说法。
- 收到大包一定就是恶意吗？ → 不一定，上传数据有更大合法范围，应按类型和长度契约判断，不能一律按普通消息拒绝。

### Q12 TCP 已经保证有序，为什么应用还需要接收缓冲区？

**问题**：TCP 已经保证有序，为什么应用还需要接收缓冲区？

**核心**：**TCP 的有序交付与应用消息是否完整是两件事，缓存保存顺序字节以便分帧，不负责绕过丢失字节取后面的包。**

**回答**：如果前面的 TCP 字节确实缺失，接收应用不会越过缺口直接拿到后面的字节；应用数组也没有能力替协议栈重排或补出这些数据。需要缓存，是因为即使收到的字节完全有序，一次读取仍可能停在一条业务消息中间，或者包含几条消息，协议栈不认识我们定义的消息长度。

例如第一次读到第一条消息的半个正文，先保留；第二次拿到它的剩余部分、第二条完整消息以及第三条的前缀，按顺序追加后，第一条现在完整了，就先解析第一条，再解析第二条，把第三条前缀留待后续补齐。这里没有跳过未完成的第一条去取第三条，也不是 Qt 信号槽违反 TCP 顺序；数组解决的是应用层收集与消费字节的问题。

**表达脉络**：

1. 先承认 TCP 不会向应用越过缺字节交付
2. 区分字节有序与业务消息完整
3. 举半条加后续完整条目的两次读取例子
4. 强调按顺序消费且不跳过未完成消息

**可能被追问**：

- 一次 readyRead（数据可读）不就代表一整包吗？ → 只代表有字节可读，不承诺恰好一条业务消息。
- 数组有大小限制会不会破坏 TCP 有序性？ → 不会，超限策略决定应用是否拒绝连接，不会改变 TCP 的字节顺序。

> 这一节回答"私聊/群聊/云盘/鉴权是怎么实现的"这类不落到具体协议号、但考架构叙述能力的开放题。每题只给一条端到端主线与关键分工，字段布局、状态流转和逐项追问仍以《面试-业务功能逐项讲解》对应小节为准，本节不复制细节。

### 13.1 私聊是怎么实现的？

**问题**：撇开具体报文，一对一私聊整体是怎么跑通的？

**核心**：**私聊是"入库即受理 + 在线实时转发、离线留待拉取"两条投递路，排序与去重都按消息 ID，没有群内连续序号。**

**回答**：发送前客户端校验正文并按好友关系发起；服务端把消息写入私聊记录并分配一个稳定的消息 ID，写入即视为受理成功。之后分两条路：对方在线就经同一条长连接实时转发，接收端成功应答后才记为投递成功；对方离线就留在服务端，等其登录后按消息 ID 拉取。私聊的排序和去重都以消息 ID 为准，不依赖连续序号，也没有补洞语义——这是一对一所必需的复杂度上限。它和群聊的差别集中在可靠性模型：群聊靠群内 seq 建立全序、`client_msg_id` 保证幂等、按游标补拉补齐缺口，私聊当前只做到"入库即受理 + 两条投递路"，接收确认与稳定身份还不完整，这正是我在 5.1 里列为不足的第三点。完整链路与追问见《面试-业务功能逐项讲解》好友私聊一节。

**表达脉络**：

1. 校验正文与好友关系后发起
2. 入库分配消息 ID 即为受理
3. 在线实时转发、离线留待拉取两条路
4. 按消息 ID 排序去重，无连续序号与补洞
5. 对比群聊可靠性，如实标注当前不足

**可能被追问**：

- 私聊会不会重复或漏投？ → 取决于接收确认闭环，当前"对方在线"和"投递成功"绑得过早，仍在改进。
- 为什么不复用群聊那套序号？ → 群聊需要群内全序、补洞和已读水位，私聊是一对一，按消息 ID 更简单、代价更低。

### 13.2 群聊（含群管理）整体是怎么实现的？

**问题**：群聊这一整套——建群、成员、消息——整体是怎么设计的？

**核心**：**群聊等于"群与成员管理 + 群消息"两部分，全部写操作是事务内锁群行、按当前成员关系授权、先提交后通知，权威状态都在服务端。**

**回答**：群与成员部分：建群在同一短事务里既插群记录又把创建者置为群主，避免"有群无主"；邀请、设置角色、转让、解散都是锁群行后按群主/管理员/普通成员三级角色校验权限，被移除者靠服务端成员校验失权，而不是靠界面禁用。群消息部分：发送带连接级请求号（同连接去重）和 `client_msg_id`（业务幂等），服务端事务内按群水位原子分配群内 seq、先落库再广播；客户端按 seq 发现缺口就补拉，命中幂等键则回放原 seq 与 msg_id、既不重新分配也不重复广播；已读只认连续前缀，未读由服务端用群最大 seq 减本人 last_read_seq 派生计算，不逐成员存未读以免写放大。这里要把三层编号讲清：请求号管"这次要不要执行"、`client_msg_id` 管"这条消息会不会建两次"、seq 管顺序补洞与已读；请求号只是连接级去重、断连归零、不落库，不等于幂等，带结果回放的幂等靠 `client_msg_id` 与邀请 `request_key`。逐项实现见《面试-业务功能逐项讲解》群与成员管理、群消息两节。

**表达脉络**：

1. 群管理：事务锁群行 + 角色授权 + 先提交后通知
2. 建群同事务插群与群主，避免无主窗口
3. 群消息：请求号去重、幂等键、事务内原子分配 seq
4. 客户端按 seq 补洞、按连续前缀已读、未读派生计算
5. 三层编号分工，收口到"去重不等于幂等"

**可能被追问**：

- 群请求号和幂等键到底差在哪？ → 去重 ≠ 幂等：请求号保证同连接一次动作不重复执行但不回放结果，幂等键保证换号重发仍拿回原结果。
- 群聊和私聊最大的实现区别？ → 群聊多了群内全序、成员权限校验、补洞与已读水位，私聊没有这些。

### 13.3 你的云盘系统是怎么搭建的（含群文件与分享）？

**问题**：云盘这一套存储和传输整体是怎么组织的？群文件和分享又怎么接进来？

**核心**：**逻辑条目 + 去重物理对象 + 引用计数三层分离，上传走分片、断点续传与 SHA 秒传，删除只减引用、归零才回收；群文件和分享都只新增引用或授权，不复制正文。**

**回答**：云盘把"目录树"和"文件内容"分开：逻辑条目保存账号、目录、名称和对物理对象的引用，物理对象按内容摘要去重、同一份正文只存一次。上传先分片写入暂存区，完成后服务端复算 SHA——命中已有对象就只建条目加引用（秒传，零正文传输），没命中才把暂存转正落盘；断点续传靠服务端确认偏移推进进度，暂停或续传会更换传输编号，使旧一轮迟到的数据不会被误认成当前任务。删除条目只减引用，引用归零才由回收调度器物理删除正文，保证同内容被多账号、多目录引用时不误删。个人云盘、群文件、好友分享和分享链接复用同一套物理对象：群文件是挂在群作用域下、按有效成员鉴权的一组引用，解散只切群状态、清理由周期任务分批释放引用；分享链接绑定源逻辑条目标识，是只读授权，改名或移动不影响链接，只有源条目删除才使链接失效。当前两个明确薄弱点要如实交代：目录改名仍要级联更新整棵子树的逻辑父路径、条目多时事务会变长；好友分享仍偏一次性快照，源文件更新接收方看不到（见 5.1、5.3）。逐项实现见《面试-业务功能逐项讲解》个人云盘与目录、文件传输与任务管理、群文件、好友分享与分享链接各节。

**表达脉络**：

1. 逻辑条目与去重物理对象分离、靠引用计数管生命周期
2. 上传分片 + 确认偏移续传 + 完成复算 SHA 秒传
3. 删除减引用、归零才回收，避免误删共享正文
4. 群文件按成员鉴权的一组引用、分享是绑定条目标识的只读授权
5. 交代改名级联与分享一次性快照两个不足

**可能被追问**：

- 秒传会不会把别人的文件错认成同一份？ → 命中同时校验内容摘要与长度，且回收前确认引用归零；跨账号引用的授权收敛仍是待处理风险。
- 群文件和分享会不会复制正文？ → 不会，二者都只是新增引用或授权关系，正文仍去重共享。

### 13.4 登录与鉴权整体怎么做，如何防越权和伪造身份？

**问题**：从连上到能操作业务，身份和权限这一层整体是怎么保证的？

**核心**：**身份以连接绑定的 actor 为准、客户端自报一律被覆盖；TLS 只给传输安全不替代业务授权；写操作靠业务幂等键防重复。**

**回答**：连接层先做 TLS 固定证书握手并校验服务端身份名，握手和证书验证没完成前不发业务报文，失败直接拒绝而不回退明文。业务身份不取决于报文里"我是谁"这类字段，服务端一律用已认证连接派生的 actor，防止替别人操作或伪造归属；受保护请求先核连接认证上下文与登录版本，旧连接靠登录版本失效，不把"账号在线标志"当认证依据。每个群、目录、文件操作都先查服务端当前成员或归属关系（走唯一索引）判断有效性与角色，越权由这一道挡住——界面禁用只是体验，服务端每次都重新核验，被移除者的旧窗口再发请求也会因身份失效被拒。口令是客户端哈希加服务端随机盐、不明文落库，当前用的是快速加盐 MD5，属明确不足，方向是换成带成本参数的慢口令派生。写操作有业务幂等键（`client_msg_id`、`request_key`、上传会话请求令牌）防重复执行；普通查询重放没有副作用，真正要防的"重放一次有副作用的写"靠幂等键，更进一步可用 nonce 加时间窗。要强调 TLS 和业务授权是两层：TLS 管传输机密性与完整性，绝不等于业务授权，越权、凭据派生和幂等仍需各自治理。详细见《面试-业务功能逐项讲解》账号与连接、底层技术能力两节。

**表达脉络**：

1. TLS 握手与固定证书校验，未完成不发业务报文
2. 身份取连接绑定 actor，覆盖客户端自报，防伪造归属
3. 每次操作先查服务端当前成员/归属关系判权，不信界面
4. 口令加盐哈希不落明文，写操作靠幂等键防重放
5. 收口 TLS 与业务授权是两层，各自独立治理

**可能被追问**：

- 用了 TLS 是不是就安全了？ → 不是，TLS 只保护传输，业务越权、凭据派生、防重放仍需独立处理。
- 客户端伪造群标识或 actor 能生效吗？ → 不能，群标识只是定位参数、actor 来自已认证连接，权限由服务端当前成员关系决定。

### A2 协议深挖（5 题）

3.2 已答二进制与 HTTP/JSON 的取舍，Q9 已答 PDU 字段，Q10–Q12 已答缓冲区与超长包；柔性数组的副作用只在 Q9 追问里出现一句。

1. 为什么用二进制协议而不是 JSON/Protobuf？柔性数组解决什么问题、有什么副作用（非标准、跨编译器、长度校验）？（原 #26）
   - **回答**：最初选择自定义二进制协议是为了直接练习 TCP 字节流分帧和文件分片。固定头包含长度、类型和参数区，正文按长度读取。柔性数组可以表达变长正文，但会带来非标准布局、对齐、跨编译器和长度校验问题，所以当前实现依赖固定编译环境，并在解析时显式校验长度。
2. 字节序怎么统一？结构体对齐、序列化与反序列化、跨平台兼容怎么保证？（原 #27）
   - **回答**：协议字段按明确的字节长度读写，不能直接把带指针或隐式填充的 C++ 结构体当网络报文。当前布局、字段长度和字节序按两端协议约定使用，跨语言客户端按同一规则解析即可。协议编号只能追加，不能重排，旧字段的含义和位置保持不变。
3. 协议版本如何兼容：新增字段、未知消息类型、旧客户端分别怎么处理？（原 #30）
   - **回答**：已有消息编号和字段布局冻结，新功能只追加编号。新字段优先放在带长度的正文中，新消息族可以带自己的版本。旧客户端遇到未知类型时应拒绝或忽略，服务端要保留旧路径，不能修改旧编号的含义。
4. 有没有校验和、CRC、加密、防重放？没有的话，完整性攻击与重放的风险怎么评估？（原 #33）
   - **回答**：所有 PDU 都通过 TLS（传输层安全协议）加密通道发送，TLS 提供传输机密性、完整性和服务端证书校验。业务层仍通过认证主体、登录版本和幂等键防止越权与重复执行，不能把 TLS 等同于业务授权。
5. 说"彻底解决粘包"，怎么证明？列出边界测试用例（1 字节头、半帧、多帧粘连、超长声明、非法长度）。（原 #36）
   - **回答**：不能只说"彻底解决"，要用测试证明拆帧逻辑能处理 1 字节头、半帧、多帧粘连、超长声明和非法长度。服务端先缓存字节，达到固定头后校验总长和正文长，完整一帧才交业务，剩余半帧留给下一次读取。当前验证重点是这些协议边界，不代表所有网络异常都已覆盖。

3.4、3.11、Q4 已答"事件线程 + 局部后台任务"；Q11 已答恶意包；C 篇（会话与在线态）4.1 已答关闭回调重入。以下四点未覆盖。

1. 多客户端并发时共享数据有哪些？锁粒度多大？有没有死锁风险，怎么排？（原 #43）
   - **回答**：共享数据主要是连接表、账号会话版本、在线状态、资源池和数据库状态。网络业务大多收拢在事件线程，后台任务只把结果排队回来，减少共享状态并发写入。需要加锁的地方保持临界区短并固定锁顺序，当前项目没有生产级死锁监控，主要靠代码检查和并发场景测试。
2. 如果底层用 epoll/select，水平触发和边缘触发怎么选？EAGAIN、惊群、空转怎么处理？（原 #44）
   - **回答**：当前项目使用 Qt 事件循环和 QTcpSocket，没有直接编写 epoll 或 select。若以后改原生事件模型，我会优先选择更容易维护的水平触发，并确保循环读到 EAGAIN，避免边缘触发下漏事件。这个问题属于未来底层替换时的设计判断，不是当前实现。
3. 服务端做没做限流、熔断、降级？实际做到哪一层，缺哪一层？（原 #48）
   - **回答**：当前有报文长度上限、连接级缓存上限、传输并发限制和部分失败返回，但没有完整的按用户限流、熔断和多级降级体系。连接池或线程池耗尽时应快速失败并让客户端重试，不能无限堆积请求。
4. 连接映射表、在线用户表、群成员表怎么保证线程安全？（原 #49）
   - **回答**：连接映射和在线会话主要由事件线程维护，账号登录版本用于判断旧连接是否仍有效。群成员的权威状态在 MySQL，由事务和权限条件保护。后台任务不能直接修改这些对象，要把值和结果排队回业务线程处理。

### A4 池化组件深挖（7 题）

3.5 与 Q5、Q6 只讲到"三层缓存协作"和"RAII 句柄归还"这一层名字；分级策略、参数、拒绝策略、监控指标均未落文字。

1. 三层缓存具体是哪三层？对象大小如何分级？申请与归还分别走哪条路径，怎么减少锁竞争和内存碎片？（原 #101、#102）
   - **回答**：内存分配路径按线程缓存、中央缓存和页级缓存分层，小块优先在线程本地取得，缺货时批量向中央和页缓存申请，归还时沿匹配路径回收。它减少了频繁系统分配，但不是全程无锁；2026-11-17 分配微基准实测单线程报文负载快于 malloc/free 约 2.3–4.1 倍，驻留内存更高，该倍数不代表整机收益。
2. 内存池相对 malloc/free 的收益有没有量化？什么场景下反而更慢（大块、突发增长、回退系统分配）？（原 #103）
   - **回答**：已量化——2026-11-17 同机、同 MinGW 7.3 -O2 构建、独立进程对照：单线程小报文 75.5→32.8 纳秒/对（约 2.3 倍），混合到 256KB 约 4.1 倍，4 线程小负载因中央桶锁争用收窄到约 1.3 倍；驻留内存小负载 7.6→27.5MiB。它更适合频繁的小块协议对象；冷启动、突发增长或多线程争用下收益收窄，封装层保留系统分配回退。这是分配微基准，不能换算成整机吞吐。条件与数据表详见《面试-业务功能逐项讲解》55 项末补充追问。
3. 对象回收后怎么防悬空使用？和智能指针、RAII 怎么配合？（原 #104）
   - **回答**：异步任务不直接持有可能已经销毁的连接对象，完成后回到业务线程按连接号和任务编号重新查找。QObject（Qt 对象）用父子关系或 deleteLater（延迟删除）管理，数据库句柄用 RAII（作用域资源管理）自动归还，内存块必须按来源匹配释放。
4. 线程池线程数、队列长度、拒绝策略、任务异常处理怎么定？任务里做阻塞 IO 有什么问题，慢 SQL 与慢文件怎么隔离？（原 #105、#106）
   - **回答**：当前线程池主要承担写盘和整文件摘要，线程数不能只按 CPU 核数决定，还要考虑每个任务持有的缓冲和磁盘能力。任务队列应有上限，超过后返回忙或排队失败。数据库慢查询和文件任务最好分开预算，避免一种资源耗尽拖住另一种。
5. 连接池连接数怎么定？获取连接超时怎么办？连接泄漏怎么检测？RAII 自动归还与事务回滚的先后顺序是什么？（原 #107、#108）
   - **回答**：连接数要和 MySQL 的最大连接数、业务并发和单请求持有时间一起定，不能越大越好。当前连接池使用 RAII 句柄自动归还，池耗尽时快速失败。长期持有句柄、异常路径和事务未回滚仍需要通过代码约束和指标检查。
6. 三个池同时使用，有没有互相等待或死锁风险？服务端关闭时怎么优雅释放？怎么发现某个池已经出问题？（原 #109、#110、#111）
   - **回答**：风险在于线程池任务等待数据库连接，数据库操作又等待文件任务或事件线程。我的原则是固定资源获取顺序、缩短事务和避免后台任务同步等待业务线程。关闭时先停止接收新请求，再让任务完成或取消，最后释放连接池和内存池。当前没有完整的长时间关闭演练。
7. 连接池被慢查询占满时，怎么限流、降级或熔断？（原 #112）
   - **回答**：先限制单用户和全局查询并发，获取连接超过等待时间就快速失败，保留心跳和必要控制请求。对非关键列表可以返回稍后重试，不能把无限请求堆在事件线程。熔断和自动恢复目前属于生产化待补能力。


### A5 稳定性、可观测性与工程质量（8 题）

6.1 已答跨端定位，6.2 已答两端协议一致；8.1 已答 TLS 和业务鉴权边界。以下属"没做过但要能答"的部分。

1. 日志分几级？会不会把密码、凭据、文件路径打进日志？脱敏规则是什么？（原 #128）
   - **回答**：日志按网络、数据库、文件、认证和应用类别区分级别。认证只记录结果和账号，协议只记录类型、长度、连接号和错误，不记录密码、令牌、正文或完整文件内容。当前本地日志和 SQLite 仍有隐私风险，公开部署前要补统一脱敏和访问控制。
2. 有没有做故障注入：断网、丢包、重复包、乱序包、超大包、非法包？（原 #133）
   - **回答**：没有做过完整的自动化故障注入，也没有生产故障经历。我做过或重点验证过半包、非法长度、断线、重复请求、暂停继续和超限传输等协议及状态场景。丢包、乱序、进程崩溃和长时间资源耗尽仍需要专门脚本补齐。
3. 在线数、消息成功率、文件传输成功率、重连率、池等待时间怎么监控？（原 #134）
   - **回答**：当前以分类日志和关键计数器为主，能记录连接建立和断开、请求成功或失败、传输任务状态及资源池使用情况。还没有集中监控面板和稳定的 P95/P99 指标。后续应统一事件字段，再接入采集和告警。
4. 做过哪些压测？并发连接数、消息吞吐、文件吞吐、内存与 CPU 曲线、P95/P99 尾延迟分别是什么量级？没有数据时怎么如实说明？（原 #144、#148）
   - **回答**：我做过协议级并发和传输回归，重点验证连接、并发名额、续传、暂停释放、断线收敛和唯一登录互踢，目标是正确性而不是刷吞吐。没有正式压测得到并发连接数、文件吞吐或 P99 尾延迟，所以不会报具体容量结论。
5. 性能瓶颈怎么定位？用过 perf、火焰图、Valgrind、ASan、耗时埋点吗？有没有实际修过的泄漏、悬空或数据竞争？（原 #145、#146）
   - **回答**：当前主要靠日志、状态计数和代码路径分析定位，明确看到整文件哈希和部分数据库操作可能占用事件线程，因此把哈希放入线程池。没有做过完整的 perf、火焰图、Valgrind 或 ASan（地址和内存错误检测）审计；但 2026-11-17 用自写探针加临时归属断言定位并修复了内存池五处真实缺陷（尺寸混桶、切块尾部越界、大对象未标记在用、合并后脏页映射、MinGW 线程局部属性失效），这是可以完整讲清的内存错误排查案例，不是生产事故包装。
6. 构建、配置、部署怎么做？服务端如何启动、守护、升级、回滚？（原 #149）
   - **回答**：当前按 Qt 5.14.2、MinGW 7.3 和本地 MySQL 环境构建，配置文件提供数据库、端口和目录参数，资源配置修改后需要重建。服务端主要手动启动，没有守护、滚动升级和自动回滚体系，这些属于生产化补充工作。
7. 有没有单元测试、集成测试、协议边界测试、断点续传异常测试？（原 #151）
   - **回答**：已有协议级和业务级脚本覆盖会话授权、消息及文件传输的一部分场景，也验证过半包、粘包、续传、重复和超限。没有完整的单元测试覆盖率报告，也没有把所有磁盘、数据库和进程崩溃故障自动化，面试时会明确这个范围。
8. 说"高性能、高并发、无锁竞争"，分别有什么数据和证据支撑？没有证据时怎么改口径？（原 #156）

## 附二：跨文档汇总问答（2026-11-11）

> 由 `面试问答-Qt云盘聊天系统.md` 与 docs 下各专题面试文档提取，2026-11-14 整编：删除与正文各章、十二问题库及附录重复的条目，业务功能类条目由《面试-业务功能逐项讲解》覆盖，保留正文未覆盖的项目级与架构取舍问题 30 条，口径与正文一致。

### 一、项目整体与架构

- **几千连接的内存你估算过吗？** 粗算过，入站上界加出站高水位，单连接最坏是 MB 级，几千就是 GB 级；实际不会每条都打满，但峰值要按最坏算。
- **为什么不直接重写协议？** 重写最省事，但旧客户端、旧测试、旧数据全要跟着动；我想练的是在约束下演进，不是推倒重来。
- **怎么保证修一个坑不引入另一个？** 每个修复都对应一个可复现的 e2e 场景，而且旧编号、旧路径的帧要逐字节不变；新测试过了不算，旧测试也得全过。
- **有没有跑过长时间稳定性？** 做过连续的连接/传输回归，盯句柄数和暂存目录有没有单调增长；工具级的内存长跑是上生产前要补的一环，当前靠所有权约定和 RAII 保证不累积。

### 二、自定义 PDU 协议与 TCP 通信

- **为什么不用 `QDataStream` 的事务机制？** QDataStream 的 startTransaction 也能做，但协议头是我自己定的，直接用长度字段更直观，也少一层封装。
- **请求和响应如何关联？如果响应丢失或乱序到达，客户端怎么处理？** 同一连接上服务端串行处理请求，响应天然按请求顺序返回，普通业务靠这个隐式配对；需要并发的文件流用 transfer_id 显式关联，秒传用请求令牌回带，群操作用 requestId。 普通业务请求没有独立的请求号。
- **串行处理会不会让一个慢请求挡住所有请求？** 会挡住同一条连接后面的请求，但不会挡住别的连接；这也是我把慢操作（写盘）丢线程池、把事务压短的原因。

### 三、线程池、并发与连接池

- **为什么不用 `QtConcurrent::run` 写盘？** 可以，但 QThreadPool 对任务对象生命周期和优先级更可控，也能统一观察 active 数；写盘是明确的“任务”，不是一次性的函数调用。
- **数据库为什么不能像写盘一样丢池？** 可以，但 DB 调用和业务状态强耦合（事务里要读连接、更新会话），丢池就要把整个业务对象搬过去；正确做法是“按连接亲和”而不是“单次调用丢池”。
- **为什么不用读写锁？** 读多写少时读写锁有收益，但这里的临界区都是微秒级，普通互斥量更简单；真正的开销在网络写和 DB，不在锁竞争。
- **快速失败会不会让用户觉得系统不可用？** 会，但比“所有请求一起卡住”好；客户端可以提示重试，服务端仍然能处理心跳和其他连接。

### 四、稳定性与可观测性

- **怎么区分“连接泄漏”和“用户就是多”？** 看建立和断开的差值是否随时间单调增长，以及同一用户是否有多条连接；正常用户数会波动，泄漏不会回落。
- **为什么不做实时看板？** 单机项目优先把状态机和正确性做扎实；指标接口留好，接采集端是增量工作。

### 五、Qt 客户端与工程实现

- **客户端为什么把网络和文件 IO 放在 GUI 线程？界面为什么不会卡？** 网络和文件操作都在 GUI 线程，但都切成小块——网络靠事件驱动，上传一次只读一块、下载一次只写一块，哈希放工作线程；真正可能长的操作都不在 UI 线程上连续执行。 Qt 的 QTcpSocket 是事件驱动的，readyRead 和 bytesWritten 都在 GUI 线程回调，读写本身不阻塞。
- **为什么不把网络也放子线程？** Qt 的 socket 可以移到子线程，但所有回调都要跨线程，状态同步成本高；当前连接少、单块小，GUI 线程足够。
- **`deleteLater` 和直接 delete 有什么区别？** deleteLater 把删除排到事件循环，当前调用栈里的代码不会踩到已释放对象；在信号回调里删发送者是典型场景。
- **为什么用 QTcpSocket 而不是自己封装 socket？粘包处理在客户端和服务端是同一套吗？** QTcpSocket 直接接进 Qt 事件循环，跨平台且省掉自己写 epoll/select；两端共用同一套“缓冲 + 总长循环”的拆包逻辑，只是内存分配器不同。 QTcpSocket 封装了原生 socket，提供 readyRead、bytesWritten、disconnected 这些信号，直接挂在事件循环上。
- **`write` 返回小于数据长度怎么办？** Qt 会缓存在内部，bytesWritten 继续推进；只要不主动丢弃 PDU，数据不会丢。
- **客户端和服务端代码重复怎么办？** 拆包逻辑可以抽成共享的 FrameDecoder，但两份实现都很短，且各自绑定的内存策略不同；真要抽，先抽常量和不变量。
- **你是怎么测试协议和传输的？有没有用过抓包或自动化脚本？这些脚本能进 CI 吗？** 主力是 Python 裸 socket 自动化脚本——自己按 protocol.h 组 76 字节帧，可以精确构造半包、坏包、乱序和并发；数据库结果用 MySQL 客户端断言，日志按 category 打开对照。 裸 socket 脚本的好处是“可控”。脚本能进 CI：前提是有一个可重置的测试库和固定端口；当前是手动跑，步骤已经脚本化。

### 六、测试、性能与边界

- **为什么不做全局上限？** 单连接上限已经能防止一个客户端吃满服务端；全局上限需要跨连接计数和公平策略，规模上来再加。

### 七、开放性与深挖追问

- **如果要把这个项目迁到 Linux 或支持跨平台，需要改哪些地方？MySQL 在 Linux 上有什么不同？** 协议字节格式、路径语义、文件句柄语义、编码和构建工具链是四类主要工作；协议只要把新族的显式小端推广到全部字段，线上格式可以保持不变。 协议层要做的不是改字节，而是去掉对平台默认值的依赖：把所有多字节字段换成固定宽度类型，读写走显式小端函数，头部加 static_assert 钉住 sizeof(PDU) == 76。 MySQL 方面，大小写敏感的表名和排序规则可能不同，连接串和 schema 要一起核对。
- **如果要支持多实例部署，当前架构需要改什么？** 协议和数据库层基本不用动，真正要改的是“进程内状态”——在线连接表、登录版本登记、群广播和暂存目录；把它们换成共享注册表、消息总线和共享存储。 第一块是唯一登录。
- **这个项目里你最满意的一段代码是什么？为什么？** commitUpload——它把“内容校验、对象去重、引用计数、命名冲突、崩溃回滚”收在一个事务边界里，是秒传、续传、共享三条链路最终汇合的地方。 上传落定看起来只是“把暂存文件挪到正式目录”，实际上要同时满足五个不变量：内容必须和客户端声明的一致；同样的内容只能有一个对象。

### 八、真实面试问法补充

- **这个项目为什么使用 TCP？** 当前客户端是 Qt 桌面程序，需要一条可控的双向长连接来承载自定义二进制协议、文件分块、心跳和服务端主动推送。Qt 客户端直接使用 QTcpSocket，可以在一条登录长连接上同时承载聊天、文件传输、心跳和控制消息。

### 九、架构与实现取舍

- **当前实现里最大的风险是什么？** 主线程上的整文件哈希和事务时长；正确性靠不变量保证，性能要靠把哈希移出主线程来解决。
- **为什么不直接调用另一个对象的方法？** 信号槽能利用 Qt 的线程归属和队列连接，异步边界更清楚；直接调用容易把 socket 或控件放到错误线程。
- **为什么不把每个请求派到 worker？** 当前连接状态和协议顺序都在主线程，直接拆开需要消息队列和更多锁；当前规模先保持状态简单，扩容时再按连接亲和拆分。



## 附三：项目级查漏补缺（2026-11-13）

> 本节只补充面试官围绕“项目能否被交付、维护和演进”提出的项目级问题。回答时仍需区分仓库已经实现的事实、本人实际做过的工作和面向生产环境的设计设想。

### 一、需求边界与验收

1. **这个项目最小可交付版本是什么？哪些功能是后来追加的？**
   - **回答**：最小版本是登录、文件目录、上传下载和好友私聊，先让账号、文件和消息三条基础链路跑通。群聊、分享、心跳、断点续传、秒传和多文件并发都是我后续根据使用场景追加的能力。
2. **你怎样判断一个功能已经完成，而不是界面上能点通？**
   - **回答**：我不会只看界面有没有弹出成功提示，而会同时确认协议应答、数据库状态和文件状态，再验证断线、重复请求和失败重试后的结果是否符合预期。只有这些状态都收敛，才算功能完成。
3. **需求之间发生冲突时，你如何决定先做什么？**
   - **回答**：我会先保证身份校验、数据正确性和旧协议兼容，再处理界面体验和规模化。比如在扩展秒传时，我先确认服务端是否真的拥有内容并且当前账号有权引用，再考虑减少重复上传，避免为了速度放宽授权。
4. **项目中有哪些明确不支持的场景？为什么不支持？**
   - **回答**：当前明确不支持长期多实例共享会话、完整云端历史、多设备长期同步和正式公网运营。这些不是界面没做完，而是涉及共享会话、数据同步、运维和恢复的额外系统能力，当前项目没有把它们包装成已经完成。

### 二、发布、配置与环境

1. **这个项目的配置是怎么管理的，开发和部署有什么差别？**
   - **回答**：开发和测试环境主要区别在数据库地址、日志级别、文件根目录、端口、调试开关和 TLS（传输层安全协议）证书。当前部分配置会编译进 Qt 资源，修改后需要重新构建，不能只替换运行目录里的旧文件。
2. **发布一个新版本怎样避免旧客户端无法使用？**
   - **回答**：协议编号只追加，不复用和重排已有编号，旧消息的字段布局保持不变。服务端先兼容旧客户端，新能力放进新消息族。遇到无法理解的版本或字段时明确拒绝，不把未知数据当成成功处理。除编号不能重排外，字段兼容由长度和版本规则保证。
3. **升级失败或数据库迁移失败时，怎样回滚？**
   - **回答**：程序可以回退到上一版，配置可以恢复旧值，数据库和文件对象则需要依赖备份或人工补偿。当前项目没有完整自动化的升级回滚和灾备演练，所以我会把数据库恢复、文件对账和迁移验证列为正式上线前必须补的运维能力。

### 三、故障恢复与数据生命周期

1. **服务端进程突然退出，重启后哪些状态可以恢复，哪些必须重新建立？**
   - **回答**：数据库里的账号、消息和文件元数据可以保留，内存中的连接、在线状态和上传上下文会丢失。客户端有传输快照时可以恢复任务线索，但服务端重启后仍要重新登录并重新建立传输会话，启动时还要清理残留在线标记。
2. **数据库和文件系统出现不一致时，谁是最终依据？**
   - **回答**：数据库负责逻辑条目、对象元数据和引用关系，磁盘负责暂存文件和正式正文。数据库事务不能自动回滚文件搬移，所以发现不一致时要根据暂存状态、对象摘要和有效引用做扫描、补偿或隔离，必要时人工修复。
3. **备份恢复后，消息序号、文件对象和在线状态怎样重新对账？**
   - **回答**：恢复后先清理在线标记，再检查消息序号连续性、文件对象摘要唯一性和无效引用。当前项目没有做完整灾备演练，所以这些恢复步骤属于设计和局部验证范围，不能说已经证明具备生产级灾备能力。

### 四、测试证据与可观测性

1. **你最有信心的三个验收场景是什么，为什么选它们？**
   - **回答**：我最有信心的是正常私聊、三路以内多文件传输和断线后续传或重复请求。它们分别能验证基础业务、传输编号与并发限制、状态恢复与幂等。判断结果时我会同时看协议日志、数据库状态和文件大小或摘要。
2. **测试失败时，怎样判断是代码缺陷、环境问题还是测试数据问题？**
   - **回答**：我会先固定代码版本、端口、数据库和测试数据，确保问题可以重复。然后按客户端发包、服务端拆帧和业务日志、数据库状态、磁盘文件状态逐层核对，先排除环境和夹具问题，再判断是否是代码缺陷。
3. **怎样证明测试没有只覆盖成功路径？**
   - **回答**：我会覆盖半包、多帧粘连、非法长度、重复请求、断线、超限并发、数据库失败和磁盘失败。每类测试都要断言状态和结果，例如非法长度应拒绝并释放连接，重复请求应返回旧结果或明确重复，断线后不能把未确认字节当成已完成。
4. **线上没有集中监控时，你怎样发现系统正在恶化？**
   - **回答**：当前主要依靠分类日志和关键计数器观察连接数、失败数、重连数、传输任务数和资源池等待情况。没有集中监控时，我会通过异常日志和趋势对比发现恶化。后续接入集中采集，需要统一连接号、用户、请求类型、传输编号和耗时字段。
5. **为什么不能只看“客户端显示成功”判断服务端正确？**
   - **回答**：客户端显示成功只说明界面收到了某个结果。真正判断要区分协议应答、数据库提交、文件写盘和异步任务完成。例如上传界面显示发送完成，不代表服务端已经确认写盘，更不代表最终对象已经转正。

### 五、权限、隐私与运维责任

1. **日志、数据库备份和本地 SQLite（嵌入式数据库）会不会泄露隐私？**
   - **回答**：密码、令牌、消息正文和完整文件路径不应进入普通日志，日志只保留类型、长度、连接号和结果。当前客户端 SQLite（嵌入式数据库）和部分本地日志仍有明文风险，我会明确承认这一点，公开使用前需要补加密、权限控制和清理策略。

### 六、个人判断与后续演进

1. **如果只能投入一周改进项目，你会先做什么、怎么安排？**
   - **回答**：第一天先固定基线并补连接数、主线程阻塞、数据库等待、传输失败等指标，第二到三天补最关键的断线、重复和超限测试，第四到五天处理最高风险的主线程慢任务或数据一致性问题，最后做回归和文档同步。
2. **哪些地方你会坚持保留，哪些地方会直接替换？**
   - **回答**：我会保留已有协议编号、传输状态语义和客户端兼容路径，因为它们是现有功能的边界。优先替换主线程中的慢数据库和整文件哈希任务，再考虑把连接状态按连接亲和迁移到 worker，避免为了重构而重写全部业务。
3. **这个项目最重要的技术债是什么，为什么一直没有优先解决？**
   - **回答**：最重要的技术债是部分数据库操作和长耗时任务仍在事件线程，其次是自动化部署、灾备演练和本地明文缓存不足。早期项目重点是完成课程功能和验证协议，所以先接受了这些边界。现在如果面向公开环境，我会优先处理会阻塞请求和影响数据恢复的部分。
4. **如果面试官质疑你没有生产经验，你怎样准确回答？**
   - **回答**：我会直接说明这是个人项目，主要做过本地运行、协议测试和异常场景验证，没有长期云部署、真实生产用户或线上故障处理经验。我能从源码和测试解释协议、传输、状态和资源管理，但用户规模、长期稳定性、灾备恢复和生产运维能力，需要真实线上数据和演练才能证明。
