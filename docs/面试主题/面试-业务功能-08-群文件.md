
# 群文件：40—43

实现定位：[群文件界面](../Client/groupfile.cpp)、[共享传输管理](../Client/transfertask.cpp)、[群文件协议处理](../Server/msghandler.cpp)、[群文件权限](../Server/operatedb.cpp)、[引用安置和释放](../Server/fileobjectstore.cpp)。`group_file`（群文件引用表）与个人条目共享物理文件对象，群不是一个允许所有人随意读写的公共磁盘目录。

### 40. 查看群共享文件列表

#### 功能目标

让有效群成员按群查看共享文件、上传者及分页信息。群文件列表不能复用个人路径检查替代成员检查；群文件请求共用群协议信封与群请求号判重。

#### 主回答（完整业务实现链路口述版）

客户端进入群文件窗口后，带上群标识、请求号和分页参数请求列表。服务端校验认证状态、登录版本、群是否存在以及当前账号是否仍是有效成员，再查询属于该群且状态有效的文件引用并统计总数。响应返回分页起点、页量、本页数量和总数，客户端校验每条记录的边界后更新列表和分页入口；请求失败时保留原列表，不用空结果覆盖页面。

#### 表达脉络（记忆钩子）

1. 进入群文件窗口并取请求号 -> 2. 提交群标识和分页参数 -> 3. 校验认证、版本、群和成员资格 -> 4. 查询有效群文件并统计总数 -> 5. 返回分页数据并校验记录边界 -> 6. 更新列表入口，失败保留原结果

失败分支：非成员、已退出、被移除拒绝查询；解散群仅可查列表，上传与下载均被拒绝；数据库失败、无记录、已到末页是不同结果，不能统一说成群已解散。

#### 追问卡片

**原完整链路补充（追问时展开）**

**请求**：用户从群管理页面进入群文件窗口，客户端取下一个群请求号，以群标识、页起点和页量封装群文件列表请求 99。

**接入与判重**：服务端完成协议数据单元拆帧、连接认证上下文、登录版本和群协议信封检查，比较群请求号判重后解析群文件请求。

**权限与查询**：群文件操作（`handleGroupFileOperation()`）确认群存在及查询者具有有效群成员关系，已解散群仅保留列表的只读查询，上传与下载一律拒绝；数据库查询该群状态有效的群文件条目，统计总数，按群文件 ID 排序取得指定页，返回展示名、大小快照和上传者账号等信息。

**应答与客户端**：服务端将页起点、页量、本页数量、总数和条目装入响应 100；客户端校验每条长度与记录边界，用群文件 ID 维护选中项，更新群文件列表及分页入口，页偏移不能与上传确认偏移、下载采纳偏移混用。

**后续动作与边界**：用户点击下载、上传或删除时重新发送对应动作，服务端重新核验当前群和成员状态，列表中曾看见某条目不代表之后一直可访问；非成员、已退出或被移除账号拒绝查询，数据库失败、无记录和页面已到末尾是不同结果，不宜统一解释为群已解散。

- **群文件列表为什么按引用表来列，而不是直接列物理文件对象？** 因为列表要表达的是这个群能看见哪些文件，这个语义只有引用承载。我的群文件列表（请求 99、响应 100）查的是 group_file 引用表里群标识匹配且状态有效的条目，按群文件 ID 排序、用 offset/limit 取本页，每行的展示名、大小快照、上传者账号都写在引用行上，因为这些属于群内视图：同一个物理文件对象传到两个群，展示名可以各不相同。物理文件对象只有内容摘要和引用计数，直接按对象列会把别人群里的内容混进来，等于泄露对象范围。代价是列表要连着引用做统计、每次上传多维护一行挂接；这套列表是全项目唯一有分页的，单页 200 条，我选 offset 而不是游标分页，是因为要返回总数给分页入口，群内条数有限，offset 够用。
- **群解散后群文件列表还能只读查看，是不是解散后所有群接口都还能用？** 不是，我是按接口分开定的。解散后 99/100 的群文件列表查询仍然放行，成员可以回看这个群有过哪些文件；但群文件上传初始化 101 和下载元数据 105 会检查群有效性，一律拒绝，不再创建上传上下文或下载流，103 这类写操作同样在接入阶段被拒。群消息拉取是另一条规则：它要求群有效，解散后不能拉。之所以能这么分：列表只是查 group_file 里已留存的引用记录，不产生新流量、不改共享对象；上传和下载会让一个已经不存在的群继续占存储和带宽。所以被问到解散后还剩什么能力时，我按列表只读、上传下载拒绝、消息拉取要求群有效这三句分开答，不会混成一个说法。

### 41. 上传群文件

#### 功能目标

把成员的本地内容发布为指定群可见文件，复用个人传输机制，但增加群权限和群引用提交。初始化 101 同样带群请求号，重发被丢弃，不会重复创建上传上下文。

#### 主回答（完整业务实现链路口述版）

客户端选择本地文件后创建群上传任务，提交群标识、展示名、大小、摘要和传输标识。服务端校验认证状态、群成员关系和请求号，若已有可复用的物理对象，就建立个人条目和群文件引用并直接返回命中；未命中时创建上传上下文和暂存文件，返回服务端确认的起点。客户端按连续偏移发送数据块，服务端写盘并确认下一起点，全部接收后复算摘要，先落正式物理对象和个人条目，再创建群文件引用并提交。完成后客户端刷新群文件列表，失败时不能把暂存文件当成已发布文件。

#### 表达脉络（记忆钩子）

1. 选择文件并创建群上传任务 -> 2. 提交群标识、摘要和传输标识 -> 3. 校验认证、成员关系和请求号 -> 4. 命中对象挂接引用，未命中创建暂存 -> 5. 连续写入、复算摘要并转正 -> 6. 建立群引用后返回并刷新列表

失败分支：群引用挂接失败要撤销已建部分，不能只有个人条目就报群上传成功；非秒传最终安置没有再次复核群与成员状态，末块 32 成功也不等于转正成功。

#### 追问卡片

**原完整链路补充（追问时展开）**

**建任务与初始化**：用户在群文件窗口选择本地文件，保存群标识、群文件展示名、源路径和期望大小，创建群上传任务并进入上传等待队列；获得名额后计算客户端声明摘要，取群请求号，将其与群协议信封、上传请求信息和本轮传输 ID 一起放入群上传初始化 101，不另发个人秒传预检查 97。

**接入与判重**：服务端完成认证、登录版本和信封校验，先比较群请求号判重，再确认群有效、认证主体具有有效群成员关系，并检查名称、大小、摘要及上传名额。

**命中分支**：命中已有可复用物理文件对象时，完成个人逻辑条目及群文件条目挂接，保存上传者账号、群文件展示名和大小快照，增加独立群文件对象引用，成功才回 102 命中结果。

**未命中与分块**：未命中时创建群上传上下文，保存群标识、展示名、会话记录号和摘要，打开暂存文件，响应 102 返回上传起点和非完成状态；客户端发送器按该起点发 31 正文块，正文块不带群请求号，重复块由连续偏移与长度校验拦住、不会重复写盘，写盘完成后回主线程以 32 确认下一偏移。

**复算与转正**：全部正文接受后释放暂存句柄，提交异步摘要复算；回主线程重新确认上下文和中止状态，核对实际大小与服务端摘要；转正先落实物理文件对象及关联个人条目，再挂接群文件条目和独立引用，挂接失败按当前路径执行相应撤销，不能仅有个人条目就报告群上传成功。

**应答与边界**：落定上传会话结果并发送本阶段延迟应答，客户端释放名额、更新任务和传输快照，成功后重新查询群文件列表；当前非秒传最终安置没有再次完整复核群状态与成员状态，末块 32 也有写盘成功不完整代表转正成功的边界。

- **群文件为什么不把内容复制到每个群自己的目录，而要共享物理对象？** 因为复制模型下同一份内容传几个群就占几份磁盘，而且和个人目录之间也没法去重。我的做法是：上传初始化 101 带客户端声明的摘要，命中已有物理文件对象时一个字节都不写，只给对象加一条独立引用、往 group_file 插一行带群标识和展示名的记录，直接回 102 命中；未命中才建暂存文件，按 31/32 收块、复算摘要转正，再挂个人逻辑条目和群引用，也不另发个人秒传预检查 97。共享的代价是引用计数、解除引用和回收都要在事务里维护，删除不能再直接删文件。真要隔离可以把群做成独立副本目录，但展示名本来就允许按群不同，内容去重才是常态收益，所以我选了引用模型。
- **群文件上传到一半时上传者被移出群或群被解散了会怎样？** 入口有检查，但中途我不能承诺即时撤权。初始化 101 进来时服务端先按群请求号判重，再确认群有效、认证主体仍有有效成员关系，非成员拿不到上传上下文和暂存文件。而非秒传路径在末块接收、异步摘要复算之后，回调直接进入物理对象和个人条目、群引用的安置，没有再次完整复核群状态与成员状态，所以传输中途被移出时，最终引用仍可能落地。要更即时就在最终提交事务里重查成员关系，失败时把暂存和已建个人条目安全收敛掉；当前版本没有这一步复核，也没做时序复现。这条边界只影响上传者自己这一个文件是否落成引用，不会让其他人因此多出一项不该有的群内容读权限。
- **个人文件和群文件同名时上传会互相覆盖吗？** 不会覆盖，因为名字在我的模型里不是唯一键。三层身份是分开的：物理文件对象按内容摘要认；个人逻辑条目代表我自己在目录里看得到它；group_file 引用代表某个群看得到它以及它的展示名。同样内容的文件先传个人再传群，摘要命中同一对象，只是各挂一条引用；同名但内容不同就是不同摘要，各建各的对象和条目。展示名存在引用行自己的字段里，群内显示同名两行也能按群文件 ID 和上传者区分。如果我反过来用名字当业务条目的定位键，同名个人文件和群文件就会错误共用一条记录，删一边伤另一边，所以宁可每行引用单独存展示名和大小快照。

- **两个群里上传同名同大小的文件，记录会串到对方群吗？** 业务条目层不会串，因为每个群文件的读写请求都是双条件：99 列表按群标识过滤，105 下载要求群文件 ID 属于该群，103 删除按群文件 ID 加群标识一起锁定，同名同大小也只是各自 group_file 行里的展示名和大小快照碰巧一样。内容也相同才会在摘要命中后共享同一物理对象，这是设计要的共享，各自加独立引用，一边解除不影响另一边。边界在暂存这一层：当前群上传的暂存定位键里没有群标识，跨群同名同大小存在混用风险，我不能说这一层已经完全隔离。收法是暂存定位改成包含群标识的键，不让暂存识别依赖跨群可相同的属性。

### 42. 下载群文件

#### 功能目标

从指定群的文件引用获得有权访问的内容，并复用下载、暂停和续传能力。仅知道物理对象标识不构成权限；下载元数据请求 105 同样经群请求号判重。

#### 主回答（完整业务实现链路口述版）

客户端选中群文件条目后创建下载任务，提交群标识、群文件标识、传输标识和声明偏移。服务端校验登录版本、群成员关系、文件是否属于该群且仍然有效，再通过引用找到物理对象，检查源文件、偏移和下载资源额度。服务端返回文件元数据和实际采纳的起点，客户端核对传输标识后按该起点接收正文并完成本地写入。整个过程沿用个人下载的分片、完成和完整性校验规则。

#### 表达脉络（记忆钩子）

1. 选中群文件创建下载任务 -> 2. 提交群标识、文件标识和声明偏移 -> 3. 校验版本、成员和文件状态 -> 4. 通过引用定位物理对象并检查起点 -> 5. 返回元数据和采纳偏移 -> 6. 核对传输标识后接收并完成本地写入

失败分支：群号与文件号不匹配、非成员、源不可读分别失败；初始化后每块不再重新鉴权，成员被踢不保证立即停流。

#### 追问卡片

**原完整链路补充（追问时展开）**

**建任务与请求**：用户从群文件列表选中条目，以群标识、群文件 ID 和本地目标信息创建群下载任务并加入等待队列；取得下载并发名额后取群请求号、分配本轮传输 ID，将声明偏移与请求字段封装为 105，续传起点来自本地接收分片的真实大小。

**接入与判重**：服务端完成拆帧、连接认证与登录版本核验，检查群协议信封并比较群请求号判重，确认群存在及认证主体仍有有效成员关系，已解散群直接拒绝下载，只保留列表查询。

**定位与校验**：数据库要求群文件 ID 确实属于该群且状态有效，以群文件对象引用定位物理文件对象，不能因关联个人条目被删除就直接判群文件不存在；检查源可读、声明偏移合法和下载名额后，以响应 106 返回元数据、采纳偏移及传输信息并建立下载流。

**客户端接收**：核对请求关联、传输 ID、源大小与采纳起点，打开本地接收文件，失败按任务失败收尾，不能直接拼接未经确认的前缀。

**传输与完成**：服务端把下载流加入轮转调度，按网络写出背压发送 42 正文块与 43 完成通知；客户端按传输 ID 写入该任务的接收分片并更新进度，完成通知只对仍在运行的任务生效，随后关闭句柄、移除映射、归还名额、更新面板与快照。

**边界**：下载块写失败与最终完成的实际边界同个人下载，不能宣称已有完整端到端校验；暂停、继续、取消与个人下载共享管理器，新续传请求重新检查成员关系和群文件状态，初始化后的每一块并不会自动重新执行完整成员鉴权。

- **下载群文件时把另一个群的群文件 ID 塞进请求里会发生什么？** 会被拒绝，因为这条请求要同时过两道闸。105 带群标识和群文件 ID，服务端在群协议信封和请求号判重之后，先确认查询者仍是这个群的有效成员，再由数据库按群文件 ID 等于传入值、群标识等于传入值且状态有效这三个条件查 group_file：属于别的群的那行不满足群标识条件，根本查不出来，也就走不到通过引用定位物理对象那一步。我最开始就排除了只按全局群文件 ID 逐条查的写法，否则任何成员换个号就能拉别的群的内容。代价是每个下载请求多带一个归属条件，这条查询要吃到群标识加状态的索引才不随表变大变慢；客户端列表只会给出本群 ID，但服务端完全不依赖这一点。
- **群文件下载为什么复用个人文件的正文传输协议，而不是单独设计一套？** 因为数据面完全一样。授权定了之后，42 正文块和 43 完成通知只携带传输 ID、偏移和内容，个人文件和群文件的分片接收、断点续传、写出背压调度是同一套逻辑，再写一份群专用流只是复制代码和客户端接收分片。两者的差别全部收在入口：个人下载校验路径和个人条目，群下载走 105/106 校验成员关系与引用归属，发出下载流后进入同一个轮转调度。复用要保住的是路由正确：响应带本轮传输 ID，客户端按它把块写进对应任务的接收分片，个人和群任务同时跑也不串写。以后若群侧要逐块审计或动态撤权，就得把流的来源标识再分层，按现在的需求我把差异留在入口。
- **群文件下载传到一半这个人被踢出群了，正在发送的内容会立刻停吗？** 我不会承诺立刻停。鉴权点在 105 元数据请求：服务端校验登录版本、成员关系、文件属于该群且状态有效，通过后建立下载流；之后的每个 42 正文块只按传输 ID 和连续偏移推进，不再重跑成员检查，所以被移出后已建立的流仍可能续完。暂停、继续、取消走的是新请求路径，恢复续传会重新检查成员关系和群文件状态，旧任务因此有自然的重鉴时机。要做即时停止，得按用户登记活跃下载流，在移除成员或解散群时主动中止并归还下载名额，而且已发出的字节收不回，只能算止损。我选入口鉴权是因为逐块重查等于每块一次数据库判断，大文件下载时这个开销比撤权时延更先碰到。
- **群文件被删除之后，对方已经打开或正在进行的下载会怎么样？** 分两层看。引用释放和文件句柄不是同一个事实：删除只是把 group_file 那行标成已移除并减物理对象引用计数，对象若还被上传者的个人逻辑条目或其他群引用持有就远没有到回收条件，正在读它的下载流不受影响；加上正文块不重新鉴权，传输中的流不会因删除自动停，已经送达的字节更收不回。反过来，删除之后再发起的新下载或断点续传，105 会查不到状态有效的引用行而被拒。客户端侧下载面板不会实时感知删除动作，删除应答回到客户端后是重新请求 99 刷新列表。所以我不把删除按钮描述成撤销手段，它的语义是不再让这个群看见，收敛靠回收调度器复核引用归零后处理对象。

- **被移出群之后，成员还能下载他在旧列表里看到的群文件吗？** 新请求不能，只剩在途的流是窗口期。任何新的下载或续传都要发 105，服务端当场重新校验：认证登录版本是否还是当前会话、认证主体对该群是否仍有有效成员关系、这个群文件 ID 在 group_file 里是否状态有效且属于该群，任一不满足直接拒绝，不下发元数据和采纳偏移。旧列表缓存只是客户端内存里的群文件 ID 展示行，从来不是凭证，稿子里的说法是列表中曾看见某条目不代表之后一直可访问。被踢后他点下载得到拒绝，点刷新连 99 列表查询也会在成员检查这一步被拒。唯一不覆盖的是已建立下载流的在途字节，那属于流生命周期问题，不是权限延续。

- **移群之后你用什么实际操作确认旧列表缓存和续传请求不能再给这个人权限？** 我用群主和普通成员两个账号分别登录两个客户端：先以成员身份进群文件窗口拉一次 99 列表，让旧窗口把条目缓存住；再由群主把他移出。回到成员那个没刷新的旧窗口点下载发起新的 105，再对一个已暂停的任务发起带声明偏移的续传，看两次是不是都返回拒绝而不是元数据和采纳偏移——这个动作能读出的结论是服务端确实在每个新请求上重跑成员校验，而不是沿用初始化时的放行。再把请求里的群文件 ID 换成另一个群的号伪造一次，确认按群标识加归属双条件查引用同样拒绝。在途流单独看：对已建立的下载观察 42 块是否继续发，不从新请求被拒顺推在途字节已被实时撤回。

### 43. 删除群文件引用

#### 功能目标

取消某文件在群中的可见引用，维护共享对象安全。当前权限是群主可删任意群文件，上传者可删自己上传的文件。删除请求先经群请求号判重。

#### 主回答（完整业务实现链路口述版）

客户端确认删除群文件后，提交群标识、群文件标识和请求号。服务端校验认证状态、群成员身份和请求去重，在事务中锁定群文件引用，确认条目属于该群且操作者是群主或文件上传者本人。通过后把引用标记为已移除并减少引用计数，没有其他引用的物理对象进入待回收状态。事务提交后返回结果，客户端重新查询群文件列表；这次删除的是群引用，不等于立即删除共享物理对象。

#### 表达脉络（记忆钩子）

1. 选中群文件并确认删除 -> 2. 提交群标识、文件标识和请求号 -> 3. 校验认证、成员身份和请求去重 -> 4. 锁定引用并校验群主或上传者权限 -> 5. 标记移除、减少引用并安排回收 -> 6. 提交应答后重新查询列表

失败分支：非群主且非上传者、条目已移除、跨群文件号均拒绝；重复删除按当前状态返回；物理对象回收由调度器复核引用后处理。

#### 追问卡片

**原完整链路补充（追问时展开）**

**提交**：用户在群文件列表选择条目并确认删除，客户端取下一个群请求号，以群标识和群文件 ID 发送 103。

**接入与判重**：服务端拆帧并核验认证状态、登录版本和群协议信封，比较群请求号判重后确认群有效、操作者仍为有效成员，已解散群的写操作拒绝。

**权限与锁定**：群文件删除调用群引用释放（`releaseGroupFile()`），取得数据库连接租约并开启事务，按群文件 ID 与群标识一起锁定条目；要求条目状态有效且属于当前群，只有群主或上传者账号本人允许删除，管理员身份本身不赋予删除所有人群文件的权限。

**引用变更与提交**：将群文件状态改为已移除，减少关联物理文件对象的引用计数，变为无引用则按对象回收状态及锚点进入待回收；事务提交成功后返回响应 104，失败则回滚条目状态和引用变化，客户端不能先删界面行就当操作成功。

**客户端与回收**：客户端匹配应答并重新请求群文件列表；删除只释放群文件对象引用，不连带删除上传者个人逻辑条目或其他群、个人引用，真正物理删除由回收调度器复核无有效引用后处理，重复删除按当前条目状态返回结果。

- **群管理员能不能删除群里所有的群文件？** 不能这么概括，我的规则只认两种身份：群主，或者该条目的上传者本人。删除 103 走到 releaseGroupFile()，按群文件 ID 和群标识一起锁定那行 group_file 后，看操作者是不是群主，或者操作者账号是否等于这行的上传者账号字段，命中其一放行，否则拒绝；管理员若不是上传者，仅凭管理员身份删不掉别人的文件。我特意收窄，是因为群文件内容的所有权挂在上传者的个人逻辑条目和共享对象上，放给管理员等于让他替所有人处置条目；群主作为兜底，是他对群内秩序负责。代价是上传者失联时群主之外没人清得动乱文件。以后要放开管理员删除，改这一个判断就行，引用计数和回收路径不用动。
- **删除群文件时权限检查通过、但真正提交前群主或成员角色变了怎么办？** 我把权限判断和写入放进同一个事务来压这个窗口。releaseGroupFile() 先取数据库连接租约开启事务，按群文件 ID 加群标识锁定这条引用行，锁到手后才读群当前归属、上传者账号和条目状态做权限判断，然后把状态改成已移除、给物理对象引用计数减一也在同一事务写下去，最后一起提交或一起回滚。这样并发改群主的事务要么排在锁后、要么让我们回滚，判断依据是锁定时点的事实。要避免的写法是先在事务外查出一个表示有没有权限的布尔值，再到另一个没有保护的步骤里执行删除，角色变化正好能钻进这两步之间。失败时条目状态和引用计数一起回滚，客户端收到 104 应答后重新拉列表，不能先删界面行当作成功。
- **删除一个群文件会不会把磁盘上的文件正文一起删掉？** 默认不会，删除的是群侧引用。103 在事务里只做两件事：把 group_file 那行状态从有效改成已移除，再把关联物理文件对象的引用计数减一；上传者的个人逻辑条目、其他群或分享对该对象的引用、磁盘上的正文都不动，所以同一份内容别的群还能看到，展示名和大小快照本来就在被删的引用行上。只有计数减到零、没有任何个人条目或群引用还持有它，对象才按回收状态和锚点进入待回收，由回收调度器复核确无有效引用后才做真正的物理删除。我不在删除请求里同步删文件，因为引用判断出错时删文件不可恢复，物理删除留在可复核、可调度的最后一跳。重复删除按当前条目状态返回，不会二次减计数。
