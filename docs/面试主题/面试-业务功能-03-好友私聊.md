### 13. 好友私聊

#### 功能目标

完成文本发送、在线接收、离线补发、本地保存、历史加载与本地清空。每条消息都携带服务端入库时分配的消息 ID：它是消息的唯一标识，接收端的排序和去重都以消息 ID 为准；发送端的待确认匹配按客户端生成的请求 ID 进行。入库成功即视为消息发送受理，之后的投递分为实时转发与离线拉取两条路，接收端成功收到并返回响应后才记录投递成功；没有群消息那样的严格连续序号与补洞机制，入库成功、对方收到、对方已读必须分开说。

#### 主回答（完整业务实现链路口述版）

 **发送消息**：用户点发送，客户端先校验正文非空而且不超过2000 字节，然后先把消息显示在窗口里标记"发送中"，同时生成本地唯一请求id,携带这个请求id的同时携带发送人和接收人发给服务端消息。服务端收到后不信任客户端自称的发送人，用当前登录身份覆盖，再独立校验一次正文，然后写入数据库分配递增的消息 ID，写入时投递状态先置成"待投递"。入库成功就算这次发送被受理了，服务端立刻回给发送端一个受理应答，受理应答里面带有当前发送消息的id以及请求id。发送端收到应答后，按请求id匹配之前登记的待确认项，成功了才把自己这条消息正式存进本地库，失败就改成发送失败等后续重新拉取。受理应答只代表服务端存好了，不代表对方收到了或者看到了。 

 **在线接收**：入库之后服务端查接收方在不在线——在线就通过其网络连接直接把消息推过去，消息里带好服务端分配的消息 ID和发送人。接收端收到推送后，按"发送人+当前账号+消息 ID"做去重（防止重复到达），去重后进行本地存储，存完立刻发回一个接收确认告诉服务端哪些 ID 已经处理了。服务端收到确认后，才按"收件人=自己+发送人+待投递+ID 命中"这个条件把投递状态置为已送达。展示时所有消息按服务端分配的消息 ID 排序，不依赖客户端时钟，也不依赖到达顺序。 
 
 **离线消息分页接收**：如果对方不在线，服务端入库后就不动了，消息保持"待投递"状态留在数据库里。用户双击好友打开窗口，客户端先从本地消息库按"当前账号+当前会话"读出历史灌进界面，然后同时发历史分页请求给服务端。 
 这里重点讲历史分页：我用的是**游标分页**。游标就是"上一页最新那条消息的 ID"。打开窗口时游标传 0，意思是"从最新的消息开始取"，服务端按消息 ID 倒序取 50 条，返回里同时带回本页最新那条的 ID，作为下一次翻页的游标。翻更早的历史时就拿这个游标去查，条件是"只取 ID 小于这个游标的消息"——因为消息 ID 是递增分配的，新消息的 ID 肯定比游标大，所以翻历史的过程中就算有新消息进来，新消息完全不会跑到你当前正在看的页里，不会出现好友列表那种"加删一条全列表页码漂移、翻到第 4 页突然错位"的问题。这是游标分页天然比 offset 分页适合聊天场景的原因。 
 **关闭会话重开时还是这套流程**：先读本地历史再补拉服务端最新一页，重叠的消息靠 ID 去重兜底。 
 **补充说明**：清空本地记录只删当前设备，不影响服务端。本地存库有水位概念——记录连续已处理的消息 ID 上限，用来处理乱序到达的情况，不会因为中间有缺口就跳过。



最后一定要说清楚三层成功：入库成功（服务端受理，发件人收到应答）→ 接收成功（收件人回了 ACK，服务端投递状态置已送达）→ 已读（当前没回执），这三个绝不能混。
#### 表达脉络（记忆钩子）

入口占位发请求 → 服务端覆盖入库分 ID 回受理 → 按请求 ID 落本地 → 在线推、去重、回 ACK 才置已送达 → 离线留库、游标翻页、打开先本地 → ID 排序去重加水位数，三层成功分开说。

失败分支：入库失败即发送失败、不进投递；入库应答只代表受理，已读无回执

#### 追问卡片

##### 一、链路与成功口径

- **为什么我这个私聊链路要先入库再转发，而不是收到就直接推给对方？** 持久化必须排在投递前面。服务端 chat() 里正文先过 checkChatMsgStrict，通过后由 seedchatMsg 写进 MySQL 的 message_info 表，id 自增分配消息 ID、投递列 issuccess 一律先写 0，之后才去连接列表找接收方、用 deliverChat 推 109。这样消息身份和落库事实先定下来：转发只是让在线的人早一点看到，推失败、连接断了、对方压根不在线，消息都还在库里保持待投递，他下次用 111 拉就能拿到。反过来先推再入库，推送那一刻消息 ID 还不存在，接收端没法稳定去重；写库一旦失败，我连这条消息存在过都说不清，重投和查询都没有权威依据。代价是每条私聊多一次同步写库的延迟，我用它换可恢复性。
- **发送方收到服务端的成功应答，最多能证明到哪一层，后面两层还要看什么？** 只证明第一层：服务端已经把它写进 message_info 并分到消息 ID。服务端 chat() 入库后回 16 应答，caData 里带入库结果码、正文原样回带，客户端 Chat::handleSendAck 拿它匹配 m_pendingSelf 里登记的待确认项，命中且结果为成功才把这条自发消息落进本地库，匹配不到就一直停在发送中。第二层接收成功不由这条应答决定，要看接收端保存之后回的 110，服务端 markChatDeliveredFor 按“收件人等于自己、ID 命中、issuccess 仍是 0”把行置成已送达。第三层已读在这条链路里没有对应报文，前两层再完整也推不出对方看过了，界面最多说到已送达。
- **发送方一直没收到 16 应答，能断定这条消息一定没入库吗？** 不能断定，只能说结果未知。有两种情况在客户端看起来完全一样：seedchatMsg 写库前就失败，message_info 里没有这一行；或者行已经插进去、消息 ID 也分配了，只是回包在路上丢了。两种情况下 m_pendingSelf 里的条目都还停在发送中。所以我不会把它当成确定失败就换一条内容重发，那样库里可能留下两条几乎一样的消息，我自己的本地历史和对方看到的就对不上。该做的是先去服务端确认：把这段会话用 117 从最新一页拉一次，历史里有没有它就说明服务端有没有它。要把结果未知彻底收掉，第一步是给发送请求做幂等键，重试复用同一个键拿回原来那个消息 ID，而不是让客户端去猜。
- **对方此刻离线，服务端却回了发送成功，这两件事矛盾吗？** 不矛盾，因为成功应答说的不是对方收到了。seedchatMsg 把行插进 message_info、issuccess 写 0，随后 deliverChat 遍历连接列表找接收人，找不到就打一条“目标无在线连接，留待补发”的告警返回 0，这不影响它给发送方回 16 入库成功。对方上线后双击打开会话，客户端先读本地历史，再用 111 把“发给本人且仍未送达”的行按 112 拉回来，渲染落库之后回 110，投递状态才推进到已送达。我这里省掉的是一个同步的在线前置检查：入库和受理跟对方在不在线无关，实时推还是补拉只是路径不同，最后都收敛到同一个状态列上。
- **我能不能在私聊界面显示“对方已读”？** 不能，因为这条链路里根本没有“已读”这个事件。能读到的状态只到两处：服务端 message_info 的 issuccess 由 0 变 1，代表接收端把这条消息保存成功并回了 110；以及接收端本地表落了这一行。用户真正打开窗口把消息看进去，发生在客户端界面上，没有任何报文回到服务端，服务端那张表和那列都不知道。要补这个能力，第一步是加一条已读上报，协议号只追加、不复用 109 和 110 的语义，服务端在 message_info 上另开一列记已读时间，跟 issuccess 分开，不能一列兼两个含义；第二步是定多端合并规则：同一账号在一台设备上读过算不算另一台已读。这个规则不定，显示出来也是错的，所以我宁可只显示到已送达。
- **双方当时都在线，可实时转发那一瞬间网络断了，这条消息后面会补发还是会重试？** 会补发，不会重试。实时转发只负责早一点送到：deliverChat 里对目标连接 write，返回负值就当作失败返回 0，服务端不会把 issuccess 置 1，也不会再发第二条，消息原地留在 message_info 里等对方来取。断线重连之后，客户端打开会话用 111 拉“发给本人且仍未送达”的行，走 112 回来，落库后回 110 置已送达，链路就补齐了。我不做发送端定时重发同一条，因为受理应答已经说明入库成功、消息 ID 已定，再造一条只会让接收端多认一次；真要靠重试收敛，前提也是请求标识复用保证幂等，否则重试就变成两条消息。极端情况是转发和补拉都到了，接收端按同一个消息 ID 判重，只落一份。

##### 二、发送侧校验与身份

- **私聊正文为什么按两千字节限制，而不是按两千个字符？** 因为协议的长度字段、内存缓冲和数据库列只认字节。常量 CHAT_MAX_BODY_BYTES 在两端 chatbounds.h 里同值定义为 2000，客户端 chat.cpp 点发送时先算正文 toUtf8 之后的字节数，超限就弹提示、把原文留在输入框里不改写用户内容；服务端 chat() 用 checkChatMsgStrict 独立再校验一次报文声明长度和实际字节。中文和表情在 UTF-8 下是一到四字节，按字符数限就等于两端各算一套口径，客户端放行、服务端拒收，用户只看到一句发送失败。截断在我这里只是接收端解析已有报文时的防御性钳制，而且必须走 utf8TrimIncomplete 保留完整码点，宁可少几个字也不能截出乱码。
- **我抓包改掉私聊报文里的发送人字段，能不能冒充别的用户发消息？** 不能。服务端 chat() 第一件事就是不信任 caData 前 32 字节的发送人：拿这条连接认证时绑定的身份 m_actorName 跟它比，不一致就打一条“发送人字段与连接身份不符，按连接身份改写”的告警，然后 copySelfField 把发送人强制覆盖成连接身份。之后 seedchatMsg 插进 message_info 的 seed_name，和推给对方的 109 里带的发送人，用的都是覆盖之后的值。这个覆盖必须同时作用于入库和转发两条路：只改报文不改入库，库里就留下署别人名的记录；只改入库不改报文，对方看到的署名和数据库对不上。身份的源头是连接而不是报文字段，所以改包最多触发一条告警，改不了最终署名。
- **正文超过两千字节，服务端会不会截断之后照样入库？** 不会，超限走拒绝。checkChatMsgStrict 同时看报文声明的 msgLen、totalLen 和实际携带的字节：声明大于实际、正文没有终止符、长度超过 CHAT_MAX_BODY_BYTES，都算不合法。它返回 false 时根本不进 seedchatMsg，message_info 里不会多这一行，也不会触发 deliverChat 转发，发送方从 16 应答只拿到一个写入失败的结果码，连接保持。日志里只记 uiMsgLen 和拒绝原因，不落正文明文。我选拒绝而不是截断，是因为静默截断会让发送方以为整段都发出去了、接收方看到的却是另一段；截断只保留在接收端解析已有报文时的防御性钳制，而且要裁到完整码点。
- **如果产品要允许非好友之间发私聊，我这套链路要改哪里？** 入库和投递本身不用动，要补的是准入和防骚扰那一层。我现在的私聊路径只做两件事：用连接身份覆盖发送人、按字节边界校验正文，然后入库分 ID、按在线状态决定推还是留。好友这个前提体现在会话能不能被打开、列表里有没有这个人，不在 chat() 的入库判定里。要放开陌生人聊天，得先说清陌生人消息是单独一个收件箱还是混进正常会话、被叫方能不能拒收或拉黑、同一个发送人对同一个目标的频控怎么算、正文上限要不要另设一个更小的值。这些不定下来就直接复用好友口径，等于把好友之间的信任当成陌生人之间的信任用。落点是在 seedchatMsg 之前加一次准入判定，被拒的消息不回成功码，也不给接收方推 109。
- **私聊正文直接写进数据库有 SQL 注入风险吗，参数绑定解决了什么？** 没有可用的注入面，因为正文从不拼进 SQL 字符串。seedchatMsg 里的语句是提前写好的 insert into message_info(seed_name,rev_name,msg,issuccess,seed_time)，值全部用问号占位，正文和两个用户名走绑定参数交给驱动，数据库拿到的是一个数据值而不是脚本片段。用户输入引号、分号或者看着像语句的内容，只会原样存进 msg 列、原样读回来显示。绑定解决的是“这是数据还是代码”这条边界，它不代替另外两件事：正文长度仍要在 checkChatMsgStrict 里按字节卡，驱动不管塞了多大；显示端仍要把正文当纯文本渲染，否则风险只是从数据库挪到界面上。
- **加好友那一刻对方是在线的，我发私聊时服务端为什么还要再判一次在线？** 因为好友关系和在线状态是两种生命周期完全不同的东西。关系写进好友表，加上就一直有效；在线只是此刻这条 TCP 连接还在服务端连接列表里。加好友可能是一周前，发消息在这周的任何时刻，中间对方早下线了。真到投递那一刻，deliverChat 是遍历当前连接列表按登录名找目标连接，而不是读库里的 online 字段——库内那份在线是连接生灭的滞后副本，拿它当门槛会让在线的人反而漏收 109。找不到连接就返回 0、打一条留待补发的告警，消息保持 issuccess=0，等对方下次用 111 拉。所以加好友时在线最多说明当时那一次转发可以尝试，从来不能当作发消息时的依据。

##### 三、投递与接收确认

- **消息 ID 在这条私聊链路里起什么作用，为什么还需要一个单独的请求标识？** 消息 ID 是 seedchatMsg 写 message_info 时由自增主键分配的稳定身份，定了就不再变：109 实时推送在 caData 第三十二到四十节带它，110 确认是一串 ID，111/112 补拉每条带它，117 历史分页的游标也是它，接收端的排序和去重全按它。请求标识管的是另一段时间上的问题：我从点发送到拿到 16 应答这段过程里，这条消息在服务端可能还没入库、消息 ID 还不存在，但我必须能把刚发出去的那一次和回来的应答对上，不然界面不知道该把哪条“发送中”改成成功。两个标识一个表示消息在系统里的身份，一个表示发送动作和它结果之间的关联，缺前者无法排序去重，缺后者应答回来就没人认领。
- **消息 ID 和请求标识能不能合成一个？** 不能，两者产生的时机不同。消息 ID 由服务端插入 message_info 时的自增主键决定，客户端发出报文那一刻拿不到，也不该自己编一个，两边都编就会撞号。请求标识是客户端在发送前就生成、随 14 报文一起带上去的，服务端在 16 应答里原样回带，Chat::handleSendAck 用它匹配 m_pendingSelf 里那条待确认项，命中才把自发消息落到本地库。这条回带路径专门解决结果未知时怎么认领：应答丢了我不知道入没入库，重试时必须还能认出是同一次发送；只留消息 ID 的话，重试要么在库里变成两行，要么我根本没法把应答归到某一条“发送中”上。要合并就得让客户端预分配 ID，那会引入撞号和伪造署名两个新问题。
- **接收端判重是按什么条件，只比正文行不行，两条正文和时间都一样的消息怎么办？** 实时推送和离线补发携带的是同一个服务端消息 ID，接收端按“发送人 + 当前账号 + 消息 ID”判重，本地落库也以消息 ID 作为唯一身份，同一条消息经两条路到达只留一份。只按正文去重不行，连续发送相同内容本来就合法；两条消息时间相同也没关系，不同 ID 就是两条，都保留。本地还有一道按账号、会话加去重键建的索引做兜底判重，界面显示那层也有一份已显示键的缓存，重复到达不会刷出第二行。
- **110 接收确认里为什么要带具体消息 ID，它确认到哪一步？** 因为它要确认的是“接收端已经把这一条保存好了”，指向必须精确到行。客户端在 msghandler 里收到 109 或者 112，先渲染、再落本地消息表，然后把已经处理成功的 ID 拼进 110 的正文发回去；服务端 markChatDeliveredFor 的更新条件是收件人等于当前连接身份、issuccess 仍为 0、并且 id 在这次带回的集合里，三个条件同时命中才置成已送达。用在线状态、socket 写成功或者界面画出来当确认都不行：写成功只到内核缓冲，界面显示甚至可以是内存降级，只有落库之后回的 ID 才代表对方设备上真有这一份。伪造别人的 ID 也命中不了，收件人这一条先把不属于本账号的行排除在外。
- **接收确认可以一次确认一批消息，还是必须一条一回？** 可以批量。110 的正文就是若干个 qint64 消息 ID 串起来的结构，客户端处理 112 的整批补拉时，是把这一批全部渲染落库之后一次性回一串 ID，服务端 markChatDeliveredFor 用 id in (...) 一条更新语句收掉，比一条条回少很多往返。但批量不等于只回一个最大值：中间可能有一条我这轮没成功落库，本地就是有空洞，如果按最大 ID 假定更小的都收到了，那条以后再没人补给我，状态却已经是已送达。所以回的是明确处理成功的那组 ID，服务端只按集合点名置位，没被点名的行继续停在 issuccess=0，下次 111 还会再来一遍。
- **110 确认包在路上丢了，或者服务端这次状态更新执行失败，会怎么样？** 两种结果都是那一行仍停在 issuccess=0，消息不会丢。服务端没有收到确认就一直把它当待投递，对方下次用 111 拉未送达记录时会再次拿到同一条，消息 ID 一模一样；接收端按 ID 判重，界面不会多一行，落库命中已有记录也不会写第二份，处理完再回一次 110。更新本身是幂等的：markChatDeliveredFor 的条件里带 issuccess=0，重复执行第二次影响 0 行，既不会把已送达改回去，也不累加任何计数。我不需要让发送方重发一条新消息，那只会在库里留下内容相同、ID 不同的两行。代价是可能多投一次报文，我认这个代价，宁可重投也不能丢，去重放在接收端比让发送方猜干净。
- **实时推送比离线补拉先到达，或者同一条消息两条路都到了，界面怎么处理？** 两条路到达的是同一条消息，共用这一个会话的消息集合，最终按消息 ID 排位置，不按到达时间追加。109 实时推送和 112 补拉带的 ID 是服务端入库时分配的同一个，接收端落本地库时以它作为唯一身份，第二条命中已有记录就判重丢掉，界面上不会重复出现。反过来如果我按到达顺序追加，就会看到补拉的旧消息插在实时新消息后面，用户以为对方先说了后一句。这里排序解决的是已经拿到的消息该显示在第几行，完整性是另一件事：顺序排对了不代表一条不缺，缺的那些还得靠 issuccess=0 的补拉回来。
- **我这套私聊链路里，消息在什么情况下会乱序到达，发送方向会不会也倒挂？** 只要消息来自多路就会：实时推送、补拉、历史分页、本地回显各走各的，到达顺序和消息 ID 顺序没有必然关系。断线重连、重投时最明显——断线期间消息留在待投递，重连后补拉旧的、推送新的天然交错；ACK 丢了服务端还会重投旧消息，它完全可能晚于新消息到达。发送侧反而不会倒挂：单条连接 TCP 有序、服务端按序入库分配 ID，目前也没有超时重发；将来真要重试，复用请求标识保证幂等，重放不会变成第二条消息，ID 也不会后置。

##### 四、离线补发与历史分页

- **对方离线时消息存在哪里，他回来怎么拿，积压很多时一次能拿完吗？** 存在服务端 MySQL 的 message_info 表里，那一行保持 issuccess=0，客户端不替他占任何位置。他双击打开会话，客户端先用本地消息表把这段会话的最近记录铺到界面上，同时发 117 取服务端最新一页；未送达的补发走 111，getchatMsg 的查询条件是发送人为这个会话的对方、收件人为我、issuccess=0，按 id 升序取一批。积压超过单批上限时装不完，服务端多取一条用来判定截断，112 响应里带截断标记，客户端把这一批渲染落库、回 110 确认之后，对同一个会话再发一次 111，一批批往新的方向推进直到取尽。所以离线积压不靠一次大包，也不把整段历史重传，只重传发给本人且仍未送达的那些行。
- **聊天历史分页为什么用游标分页，而不用好友列表那套 offset 分页？** 游标锚定内容，offset 锚定位置。消息 ID 递增分配，翻页条件是只取 id 小于游标的消息，翻更早历史的过程中进来的新消息 ID 一定更大，不会挤进当前页；offset 是按行数跳过，中间新增或删除记录就会让页码漂移，翻到第 4 页突然错位。好友列表那种一次加删就整体偏移的代价，在聊天场景里会被每一秒都可能进来的新消息放大，所以我这里从一开始就没考虑 offset。
- **历史分页的游标具体是什么值，客户端和服务端各怎么把它往前推？** 游标传 0 表示从最新一页开始：服务端按 id 倒序取 50 条，再多取 1 条用于判断hasMore，并把本页最旧的消息 ID 随响应带回。翻更早历史时，客户端把上一页返回的最旧 ID 当作游标，查询条件改成 id < cursor；服务端仍按倒序取 50 条，再用新页最旧 ID 覆盖游标，当 hasMore=false 时不再请求。因为游标是内容锚点而不是位置，翻页期间进来的新消息 ID 一定更大，根本挤不进 id < cursor 的结果，删消息也不会像 offset 那样错位。
- **关掉会话窗口重新打开，或者点了清空本地记录之后，聊天内容靠什么恢复？** 重开不需要特殊处理，还是同一条路径：Chat 打开时先读本地消息表里这段会话的最近记录铺界面，再发 117 用游标 0 取服务端最新一页，两边重叠的消息按消息 ID 判重，只显示一份。清空不一样，它只调 clearConversation 删本机这个账号这段会话的行，水位保留，服务端 message_info 一行不动，所以清完界面是空的，之后可以靠 117 一页页往更早翻把内容拉回来，能拉多少取决于服务端库里还留着多少。已确认送达的消息不会因为本机清空就被服务端重发一遍，因为补拉 111 只挑 issuccess=0 的行，那些早就是 1 了。
- **断线重连之后离线补拉和实时推送同时进行，怎么保证中间不漏消息？** 靠先后顺序把这个缝隙关掉：先让这条连接具备收推送的能力，再去拉未确认记录。服务端投 109 是遍历连接列表按登录名找目标写的，所以 111 要在这条连接登记好之后才发；顺序反过来就有一段“查询已经跑完、推送还没接上”的空隙，这期间入库的消息不在刚才那批结果里，也没人推给我，只能等下次拉取才发现。按现在的顺序，最坏情况是同一条消息既在补拉结果里又被实时推一次，两边带的是同一个消息 ID，接收端判重收成一条，重叠是无害的。我验证这一步是让对方刚上线的瞬间连发几条，再对本地库条数和界面条数，日志里对照那条“S->C(私聊推送)”的帧有没有落下。
- **TCP 本身是有序可靠的，接收端为什么还要再按消息 ID 排一次序？** 因为 TCP 的有序只管一条连接上的字节顺序，管不到我这里有几路来源。界面上的消息至少有四份：本地发送回显、109 实时推送、111/112 未送达补拉、117 历史分页，它们在不同时刻到达，拼起来之后到达顺序和消息 ID 顺序没有必然关系。排序解决的是已经拿到的消息该显示在第几行，这只能按服务端分配 ID 的先后算。完整性是另一件事，顺序排对了不代表一条不缺，缺的那些还得靠 issuccess=0 的补拉回来。所以我没在收到时按到达追加，而是把消息 ID 同时当作位置和身份的唯一依据。
- **展示消息时为什么不直接按客户端时间排序，非要用消息 ID？** 因为时间在我这里只是给人看的标签，不能当顺序依据。聊天两端各有一台机器，时钟可以差几秒也可以被用户手动改，本地时间串随 14 报文一起进去、原样存进 message_info 的 seed_time，服务端不改它。真按它排序，我这边把时钟调快一分钟，就能把自己的一批消息整段插到对方后面，双向交错时顺序会莫名其妙地乱掉。消息 ID 由服务端在入库那一刻用自增主键分配，对所有客户端单调、也不是报文里能填的，所以排序和去重都只用它。界面上仍然打印那个时间串，用户对时间有直观预期，这部分不受影响。
##### 五、本地存储

- **收到的私聊在本地是怎么存的，重复补发会不会写出好几条？** 存在本机应用数据目录下的 chat_msg.db，表是 message，主键 (user, conv_key, seq)：user 是当前账号，conv_key 是这段会话的对方，行里还带发送人、收发方向、正文、时间串和去重键。写入路径是 Chat::persist 交给 MessageStore::append，消息身份用服务端消息 ID，重复到达命中已有身份就返回 Duplicate 不写第二行，另外还有一道按去重键的判重兜底。水位单独放在 conv_cursor 表的 last_seq 里，和这行落库在同一步推进，写游标失败就把刚插进去的行撤掉，不允许两边分叉。所以补发重复多少次本地都只有一份，账号、会话、消息身份三层条件一起限定，也不会串到别人的会话里。
- **本地水位指的是什么，为什么不能直接拿消息表里最大的那个消息 ID 代替，中间有洞时会不会把落库卡死？** 水位是“已连续落库的消息 ID 上限”，不是表里最大的消息 ID——最大 ID 可能越过尚未补到的消息，也看不出中间有洞。收到越界消息时只留在内存里展示，等缺口补齐后再按 ID 顺序晋升落库，水位本身存在 conv_cursor 表的 last_seq 一列，写入时拿消息 ID 跟它比，接得上才推进，所以它只增不减、也不会自己跳过中间那段；缺口补齐后按序晋升落库，不会被卡死，也不会因为先写了后面的消息就证明连续性。
- **收到一条消息为什么不立刻写库，先留在内存里有什么好处？** 因为直接写会让水位越过中间那个洞。MessageStore::append 只接受正好接在水位后面一格的序号，落一条推一格；越界的返回越界结果，条目留在内存暂存里，界面照常渲染它，用户看不出差别。等缺的那条从 111 补拉或者 117 历史里回来，从水位往上一格一格连着取，接得上的段落就按序晋升落库，水位推到哪，本地表就保证哪一段是连续的。要是来一条写一条，水位会跳到那条新消息后面，中间缺的那条以后虽然还能显示，但本地库已经证明不了它存在过，读历史时就是一段没解释的空白。代价是越界消息在落库前如果程序被关掉会丢，这一段下次靠服务端补拉回来。
- **本地每段会话只保留最近五百条，为什么按消息 ID 截断而不按显示时间？** 因为消息 ID 表达服务端分配顺序，时间串可能重复或者不可信。保留条数是 MessageStore 构造时给的 m_keepLimit，默认 500，裁剪时按序号倒序数到第 limit 条找到要保留的下界，再用一条 delete from message 按 user、conv_key 加上小于这个下界删掉更旧的。按时间裁就有两个问题：同一秒里的多条谁该留不确定，用户改过本地时钟还能把自己一批消息排到最旧那一头去。这里的序号跟服务端消息 ID 的先后一致，所以“最新五百条”这个说法本地和服务端能对上，界面上翻不到更早的也解释得清：那是本地按条数裁掉了，往更早翻还能用 117 从服务端取。
- **用户主动清空本地历史之后，服务端会自动把消息重新发一遍吗？** 不能这样承诺。清空只调 clearConversation 删本机这个账号、这段会话的消息行，水位保留，界面上的文字也清掉，同时把 m_pendingSelf 里这段会话还在等 16 应答的条目一并作废，免得迟到的确认把刚清空的消息又写回来。服务端 message_info 一行没动，补拉 111 挑的是 issuccess=0 的行，那些已确认的消息早就是 1，不会被重投。想找回内容只有 117 分页这条路，它读的是服务端的全部历史，能拉回多少取决于库里还留着多少，我没有做归档和保留期承诺，所以最多说到“可以按会话向更早翻页”，不能说清空后一定自动重发。
- **本地消息库打不开或者损坏了，聊天还能不能照常进行？** 网络收发不受影响，损失的是本地历史和持久化。MessageStore::open 打开 chat_msg.db 失败时，这一路的 available 标记就是 false，lastError 里留着具体原因；界面照常从内存里显示消息，14 发送、109 接收、111 补拉都不依赖本地库，落库调用在不可用时直接返回不可用结果，不抛错也不挡住渲染。影响是重开程序或者切回这段会话时读不到之前的记录，只能靠 117 从服务端按页往回拉；水位也在这个库里，本地库整个没了，连续性的记录就断了。我把它做成降级而不是拒绝聊天，是因为读不到历史比聊不了天轻得多。
- **一条消息已经显示在界面上但本地写库失败，要不要把界面那一行撤掉？** 不撤。界面显示表达的是这条消息我确实收到了，本地落库表达的是这台设备上以后还能读到它，是两件事。客户端处理 109 的口径就是：渲染、尝试落库，然后照样回 110，落库失败只降级为内存展示，仍然确认，避免服务端无限重投。如果因为写库失败就不回确认，服务端那一行会一直停在 issuccess=0，被反复重投，界面上反而出现一条已经被撤掉却又不断回来的消息，更难解释。反过来说撤回显示也没意义，消息到达这件事是真的。代价是这台设备上的持久记录可能比界面少一段，这一段下次靠服务端分页补回来。
- **磁盘写满的时候，本机的聊天历史会丢吗？** 丢的是这台设备上的可恢复性，服务端那份消息不受影响。空间不够时落库的插入或者游标更新会失败，lastError 里是数据库报出来的错误；因为写行和推水位是同一步做、失败要回滚，水位不会跨过写失败的这一条，后面的消息会留在内存暂存里等缺口补上，不至于把洞盖掉。已经写进去的旧行还在文件里，能读多少读多少，但文件本身是否完好要看实际状态，我不保证一定没事。这期间界面照常渲染、确认照回，用户重启后可能读到一段断档，用 117 往更早翻页能从服务端把内容取回来；要恢复持久化，得先在这台机器上腾出空间或者清掉旧会话的记录。
- **消息为什么不全部只放服务端、界面每次都去读，本地还要再存一份？** 两边职责不一样，替代不了。服务端 message_info 是权威那一份：消息 ID 在这里分配，投递状态 issuccess 在这里推进，跨设备补拉和按会话分页都只能以它为准。本地 chat_msg.db 管的是打开速度和离线可看：双击好友时先把这段会话的最近记录直接铺到界面上，不用等一次网络往返，没网的时候也能翻存过的历史。全放服务端意味着每次打开会话都要拉包、断网就是一片空白，每条消息的读取都变成服务端的查询；全放本地则没有可信的消息身份，也没法在另一台设备上补投。所以我让服务端保存全部、本地按会话只留最近一段，靠消息 ID 把两份对齐。
- **同一台设备上切换账号，怎么保证新账号看不到上一个账号的聊天记录？** 本地文件的隔离粒度不到账号——chat_msg.db 是整个应用共用的一个，隔离靠行上的 user 列和打开时绑定的当前账号。MessageStore::open 用登录名建立这次读写的范围，所有语句都带 user 这个条件：取最近记录按当前账号加会话取，clearConversation 只删这个账号这段会话，账号注销走按 user 删除的那条路径把这个账号的消息和水位一起清掉，同名重新注册不会复用旧记录。切换时先关闭旧实例、把数据库连接摘掉，再用新账号名重新打开，界面上的显示缓存一并清空。所以要越界得同时伪造 user 值和会话键，而这两个都来自登录之后的连接身份，不是报文里能填的东西。
##### 六、多端与模型对比

- **群消息那套序号和补洞机制已经跑通了，私聊为什么不直接复用同一套模型？** 群聊需要群内稠密序号来算未读、检查连续性、补洞和推游标，代价是协议和双端状态复杂度；私聊只有全局递增的消息 ID，配本地水位就能完成去重、排序和乱序处理，刻意不引入群序号与补洞机制。私聊已对齐群消息“入库受理 + 接收确认”的骨架，但两者的序号语义不同是有意保留的：落到表上就是群消息那张表带群内 seq 和发送端消息键用来算连续性和补洞，私聊这边只有 message_info 的自增 id 一个身份，多出来的那套状态我换不起。
- **同一个账号在两台设备上同时登录、同时拉取私聊，会发生什么？** 基础口径是唯一有效登录，正常情况下不会出现两个客户端并行拉同一个账号。真发生了，后果也只是同一批 issuccess=0 的行被读两遍：getchatMsg 的查询只读、不置标记，谁先拉谁拿到；两边各自落自己的本地库、各自回 110，服务端 markChatDeliveredFor 只把仍是 issuccess=0 的那些行置成 1，第二次执行影响 0 行，没有副作用。消息身份是同一个消息 ID，两台设备各自按它判重，不会各自多出一份。我没有为此加分布式锁，因为幂等更新加接收端判重已经把重复的坏处吃掉了，防重不靠“提前标记”这种把状态推给还没确认那一方的做法。
- **如果让你重做一遍私聊的消息存储，你会保留什么、补什么？** 主链路原样保留：服务端入库时用自增主键分配消息 ID 作为唯一身份、接收端保存之后回带 ID 的 110 确认、本地按 ID 判重、历史用游标分页读。这四件事撑住了顺序、去重和恢复，用一次同步写库换权威身份，我觉得是这套里最值的取舍。要补的第一件是发送请求的幂等：现在结果未知时靠 16 应答回带的标识认领待确认项，重做会把请求标识做成真正的唯一键，超时重试复用同一个键，服务端命中已有记录就直接回原来那个消息 ID，库里不会留两条内容几乎一样的行。第二件是规模上的能力：单批拉取上限、批量确认、服务端历史保留策略。已读回执我会单独评估，它需要新报文和新状态列，不能借 issuccess 表达，加了还得定多端合并规则，所以不排在第一件。

##### 七、测试与验证

- **私聊的入库成功、在线转发、接收成功这三层，我实际是怎么分开看出来的？** 开两个客户端登两个账号，A 给 B 发一条，先去服务端查 message_info：有没有这一行、id 是不是 16 应答里带回去的那个、issuccess 是不是还停在 0，这一步只看入库。然后让 B 在线收 109，B 落库回 110 之后再刷同一条记录，issuccess 变 1，中间这一步在日志里对照那条“S->C(私聊推送)”的帧，如果打的是“目标无在线连接，留待补发”，说明这条压根没走实时。再把 B 的网络断开发一条，确认 A 仍然拿到入库成功、库里停 0，B 重连打开会话后消息出现且只出现一次，那一行这时才变 1。已读那层我看的是它不存在：确认完成之后界面上没有任何状态推进到已读。
- 表达脉络：故障注入到入库/转发/接收写库 -> 对照投递标志、应答、界面、本地库四方 -> 判据一：确认前标志不推进 -> 判据二：重投按消息 ID 去重 -> 判据三：已读无回执不冒充
- **实时推送和离线补发交错到达时，我怎么检查有没有漏、有没有重、顺序对不对？** 我先让内容本身可区分：A 依次发出带编号的文字，这样不用对 ID 也认得出是哪一条。把 B 断网发一批，恢复网络但先不开会话，然后实时推几条新的、同时点开会话触发补拉，让两条路故意撞在一起。核对分三处：服务端 message_info 里这段会话的行数和 id 序列、B 界面上渲染出的条数、B 本地 chat_msg.db 里这段会话落库的条数，三者都该等于发送条数，界面和本地都不能多出一份。接着连发两条正文完全相同的消息，看它们是不是两个不同 id、界面上留两行。最后关掉会话重开，本地读出来顺序不变、按消息 ID 归位，日志里两条路的推送帧各自落在哪一条上也能对上。
- 表达脉络：构造可区分消息集合 -> 补发与实时推送交错送达 -> 统计服务端/展示/落库三方数量 -> 重开会话核对持久结果 -> 双路撞车按消息 ID 合一 -> 相同正文不同时间为不同 ID -> 乱序按消息 ID 归位
