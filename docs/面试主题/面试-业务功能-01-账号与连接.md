
# 账号与连接：01—08

实现定位：[桌面客户端](../Client/client.cpp)、[客户端响应处理](../Client/msghandler.cpp)、[网页认证状态](../web/frontend/src/stores/auth.js)、[服务端请求处理](../Server/msghandler.cpp)、[连接分发](../Server/mytcpsocket.cpp)、[会话注册表](../Server/mytcpserver.cpp)、[账号数据库操作](../Server/operatedb.cpp)、[Redis 状态适配](../Server/redisstore.cpp)。PDU（协议数据单元）是客户端和服务端交换的应用报文。

> 口径说明：下文按“客户端实例级会话”的目标架构整理，用于面试中的业务设计表达，不代表当前代码已经完整实现。核心变化是：`clientId` 跨 TCP 连接标识同一客户端，`connId` 只标识一次物理连接；Redis 用 `session:{clientId}` 保存账号、登录版本、认证状态、恢复凭据校验值和会话 TTL，`online:{user}` 只负责在线展示。`clientId` 负责找到会话，但不能单独充当认证凭证。

### 01. 注册账号

#### 功能目标

建立唯一账号及个人云盘的初始目录。注册请求通过 `clientId` 关联验证码状态；账号记录创建成功与目录创建成功是两个边界，不能说成同一个原子事务。

#### 主回答（完整业务实现链路口述版）

用户填写账号、密码和验证码后，客户端检查必填项和长度，并携带持久保存的 `clientId` 发送注册请求。服务端按 `clientId` 校验并消费验证码，再校验账号名、查重、生成随机盐，把口令摘要写入账号表，唯一索引保证并发注册时只保留一个账号。账号写入后再创建用户目录，目录失败不回滚账号，后续登录时补建或交给补偿任务。注册成功只代表账号建立；如果客户端需要自动登录，还要继续完成登录会话建立，不能直接把注册响应当成认证成功。

#### 表达脉络（记忆钩子）

1. 携带 `clientId` 提交注册 -> 2. 按客户端实例消费验证码 -> 3. 校验账号、查重并加盐写库 -> 4. 唯一索引处理并发同名 -> 5. 建目录失败不回滚账号 -> 6. 自动登录仍需另建会话

失败分支：验证码、参数校验或写库失败即注册失败；目录失败不回滚账号，登录时惰性补齐。

#### 追问卡片

**详细业务实现链路（分步版）**

1. 客户端持久保存 `clientId`，先按它获取验证码，再提交账号、口令和验证码。
2. 服务端根据 `clientId` 读取 Redis 验证码状态，校验成功后原子消费原验证码。
3. 服务端重新校验账号名长度和字符，不信任客户端的界面检查。
4. 数据库执行查重和账号写入，唯一约束作为并发同名的最终仲裁。
5. 服务端为账号生成独立随机盐，只保存口令摘要，不保存明文口令。
6. 账号提交后创建个人目录，失败则记录补偿，并在后续登录时补建。
7. 返回注册结果；随后自动进入登录，再按登录流程建立 Redis 会话。

**记忆钩子**：码随客户端，密不入库，名由唯一索引守，目录失败另补偿。

- **账号建成但目录创建失败怎么办？** 我把它当成两个独立的提交点，不承诺同时成功：账号那行的账号名、随机盐和口令摘要已经落库，只是个人根目录这一次没建出来，应答里仍然说清“账号已建立、目录待补”。补建走两条路：登录成功后经过目录初始化那一步，用 `QDir::mkpath()` 幂等建一遍，目录已存在就直接当成功返回；另一条是把失败路径写进补偿队列，由服务端周期性重试到成功。我不回滚账号，因为回滚等于把刚注册的名字释放出去，可能被别人抢注，那比一个空目录严重得多。代价是要承认存在“账号已建、目录还没有”这个中间态，所以列目录、上传落地这类入口都得先确认沙箱根目录在不在、缺了就补，不能把“注册返回过成功”当成目录已经存在的前提。
- **既然知道 MD5 不适合存密码，为什么项目还采用加盐 MD5？** 这是我这个项目里的实现取舍，不等于生产环境的安全方案，这个结论我认。做法是每个账号注册时生成一份独立随机盐，和加盐后的口令摘要一起存在账号表同一行，登录时把盐读出来对用户输入的口令重算一遍再比对，所以相同口令在不同账号上得到不同摘要，一张彩虹表没法批量匹配整库。选 MD5 是因为 Qt 的 `QCryptographicHash` 现成就有，不用引第三方库。但我很清楚它挡在哪：MD5 一次计算几乎不花时间，整库泄露后攻击者能在本地高速枚举弱口令，盐只抬高了批量成本，没抬高单账号的破解单价。换成 Argon2id 或 bcrypt 这类带成本参数的密码哈希才是生产做法，盐和存储结构那套设计可以原样复用。
- **验证码能防住哪些注册滥用，还存在哪些不足，怎样减少限流对正常用户的影响？** 图片验证码增加简单脚本批量注册的成本，冷却、有效期和连续错误锁定限制持续破解与高频尝试；Redis 按 `clientId` 保存这些状态，同一客户端重连不会重新计数。但它挡不住图像识别、更换实例标识和多客户端分布式注册，因此还要结合 IP 异常频率、账号失败比例与请求行为做共享限流，并用短时退避、递进等待和高风险升级验证减少共用出口误伤。
- **注册时，客户端和服务端各做什么？** 分工是客户端只管体验层，服务端做真正的准入。客户端在注册界面检查账号名和密码是否必填、长度够不够、两次输入是否一致，把用户填的验证码连同一直持久保存的 `clientId` 一起发出去，本地不合格就不发请求。服务端先按 `clientId` 去 Redis 读 `cap:{clientId}:code` 比对验证码，通过就原子消费掉；然后独立重跑一遍账号名长度和字符白名单，不采信客户端那句检查；再查重、生成该账号独立的随机盐，只把加盐后的摘要写进账号表，同名由数据库唯一约束做最后仲裁。这么分是因为客户端的任何校验都能被绕过——直接对着 TCP 端口构造一份注册报文就行——所以服务端一旦信任客户端的结论，规则等于不存在。代价是同一套校验我维护了两遍，改账号名规则时两边要同步，界面那道校验只当减少无效往返的优化。
- **账号名参与用户目录路径，怎么保证没有路径穿越？** 采用“账号名白名单＋路径沙箱”两层校验：拒绝路径分隔符、`.`、`..` 和绝对路径；拼接后用 `QDir::cleanPath()` 归一化，再检查结果必须位于统一存储根目录内。后续文件操作再通过 `isPathInSandbox()` 比较规范化路径，防止通过 `../` 或符号链接逃逸。
- **两个客户端同时用同一个账号名注册会怎样？** 谁赢由数据库的唯一索引决定，不是由“先查一次”的结果决定。两个请求很可能都执行了账号查重、都看到这个名字可用，然后同时发起 INSERT，这时只有一个能提交成功，另一个撞上唯一约束冲突。我把唯一冲突这类数据库错误码明确翻译成“账号已存在”返回，让客户端提示改名，而不是丢一个含糊的服务端内部错误；关键是失败的那个请求绝不能再回去更新已存在那行的盐或口令摘要，否则后来的人会把先来的人的密码顶掉，那比注册失败严重得多。我没有改成“先在 Redis 上抢一把锁再查重”，因为唯一索引本来就兜住了这件事，加锁只是把同一条判定挪到另一个存储上多维护一套状态，还要处理锁过期和进程崩溃后的残留；这个方案的代价只剩一个：必须认真做数据库错误到业务语义的映射，不能笼统报“操作失败”。
- **注册应答返回成功，用户的个人目录就一定已经建好了吗？** 不一定，注册成功只承诺账号这条记录落库了，建目录是账号事务提交之后另起的一步。我刻意把它们分开，是因为目录创建要碰磁盘，失败原因（权限、磁盘满、路径异常）跟账号写入完全无关，用一次磁盘失败去否定已经写好的账号，用户就要从头再来，还可能撞上名字被别人抢注。所以应答语义是“账号已建立”，目录失败记进补偿队列，真正保证目录存在的位置是使用点：登录成功后的目录初始化会幂等 `mkpath` 一次，文件操作前的沙箱检查也会先确认根目录在不在。我能声称到的程度是“注册成功后第一次真正用到目录时它一定被建出来”，不是“收到成功应答时目录已经在磁盘上”；如果一定要后者，就得把建目录挪到写库之前，代价是磁盘故障会连带让注册整体失败。
- **注册时给密码加的盐，需要当成秘密保护起来吗？** 不需要，盐和口令摘要放在账号表同一行里明文存就行，它不是秘密。盐要解决的是“相同口令得到相同摘要”：没有盐，攻击者拿到一份泄露库可以先按摘要值把账号分组，一条彩虹表命中就批量还原；有了每账号独立的随机盐，同一个口令在不同账号上产生完全不同的摘要，攻击者必须一个账号一个账号地枚举，成本从一次摊到 N 次。所以我把盐定位成“防批量”的参数，真正抬高离线破解单价的是哈希算法本身的计算开销，这也是我把它和算法分开看的原因。边界要说清：盐挡不住针对单个账号的字典攻击，而 MD5 太快，整库泄露时弱口令照样会被逐账号撞出来，要抗住这一步得换成 Argon2id 或 bcrypt 这类带成本参数的算法，盐那部分设计可以直接复用。
- **为什么建议用不可变的用户编号来拼用户目录路径，而不是直接用账号名？** 因为账号名是给用户看的显示字段，我在设计里让物理路径只拼不可变的用户编号，账号名只出现在登录和展示的地方。这样字符规则从“必须能安全出现在路径里”降级成“能安全显示就行”，路径分隔符、`..`、绝对路径这些穿越面不用再靠命名白名单去挡；将来放开改名或做大小写不敏感时，不用去重命名磁盘上整棵目录树，也不会出现改名瞬间正在传输的文件落到旧路径；两个只差大小写或全角半角的账号名也不会撞成同一个目录。代价是路径不能直接从账号名得到，要多一次编号到名字的映射，并且所有按名字索引文件的位置都要改成按编号，所以我在新写的路径构造里统一走编号，不回头迁移已经按名字建好的旧目录。

### 02. 登录账号

#### 功能目标

把有效凭据转换成属于 `clientId` 的可信逻辑会话，再把会话绑定到当前物理连接。后续授权依据服务端会话和登录版本，不依据报文自称的账号名。

#### 主回答（完整业务实现链路口述版）

客户端携带 `clientId` 获取验证码，再提交账号、密码和验证码。服务端按 `clientId` 消费验证码并校验凭据，随后在数据库事务中分配新的 `loginVersion`、记录登录并更新在线状态。事务成功后，服务端写入 `session:{clientId}`，保存账号、登录版本、认证状态、恢复凭据校验值和会话 TTL，同时维护 `online:{user}`。当前 socket 只绑定 `clientId` 和会话关联信息，不再独占认证状态。不同客户端的新登录推进版本并使旧会话失效；同一客户端异常断线后的恢复不推进版本。客户端收到成功应答后保存必要的恢复凭据并初始化页面，后续账号与连接请求通过 `clientId` 找到会话，再核对状态和版本。

#### 表达脉络（记忆钩子）

1. `clientId` 获取并提交验证码 -> 2. 校验凭据 -> 3. 数据库分配登录版本 -> 4. Redis 建立客户端会话和在线状态 -> 5. 当前连接绑定会话 -> 6. 后续按会话与版本授权

失败分支：验证码、凭据或数据库事务失败均不建立会话；数据库提交后 Redis 写失败时，按已分配版本做幂等补偿，在会话就绪前不能宣称登录已可恢复。

#### 追问卡片

**详细业务实现链路（分步版）**

1. 客户端提交持久保存的 `clientId`、账号、口令和验证码。
2. 服务端消费该客户端的验证码，复核账号凭据和请求参数。
3. 数据库事务原子分配 `loginVersion`，写登录记录和在线状态。
4. 服务端创建会话恢复凭据，并把其校验值、账号和版本写入 Redis 会话。
5. 在线键单独记录账号展示状态，不能替代认证会话。
6. 当前 socket 绑定 `clientId`，服务端使其他客户端的旧版本会话失效。
7. 客户端保存恢复凭据并初始化页面，后续请求接受会话与版本检查。

**记忆钩子**：先验码，再验密；库发版本，Redis 立会话，连接只认会话。

- **会话已经有跨连接的 `clientId` 了，为什么还要额外发一个恢复凭据？** 因为 `clientId` 在我这套设计里只是关联键，不是认证凭证：它要在重连前后稳定存在，只能明文躺在客户端本地，可能被复制、伪造或重新生成，服务端拿它只能回答“该找哪个会话”，回答不了“来人是不是会话主人”。恢复凭据是登录成功时服务端生成、只下发给这一份客户端的额外认证材料，`session:{clientId}` 里只存它的校验值不存原文。恢复时我同时核对三件事：`clientId` 找得到会话、请求带上来的凭据校验值跟会话里存的一致、会话的登录版本还等于数据库当前分配的那一版，任一项不过就拒绝恢复。为什么不直接把 `clientId` 当凭证：那等于把会话所有权交给一个必须长期存在客户端磁盘上的标识，泄露了没法单独撤销，除非换掉 `clientId`，而换掉它“同一客户端跨连接”这个语义就断了。代价是多一份凭据的生成、下发和校验，换来一个可以单独吊销的恢复能力。
- **登录成功时 Redis 里到底写了哪些东西，为什么会话键用 `clientId` 而不是 `connId`？** 两块：`session:{clientId}` 保存账号、登录版本、认证状态、恢复凭据校验值和会话 TTL；`online:{user}` 只保存给用户列表看的在线展示状态。用 `clientId` 做键是因为会话要跨物理连接活下来——断线重连之后 `connId` 必然变，新 socket 是一个新号，会话如果按 `connId` 存，重连就查不到原会话，只能重新输密码，跨连接恢复这件事直接不成立。`connId` 在我这里只标识一次物理连接，绑定到 `clientId` 上做响应投递。`online:{user}` 我特意跟会话分开：它按账号名可查、给好友和在线列表用，如果把授权挂在它上面就变成“看到在线就当已认证”，而且同账号多端展示时一条展示记录也对应不上具体哪份会话。代价是登录要写两处状态，退出和踢人也得分别清理，对账时必须同时看这两类键，不能只按其中一类下结论。
- **数据库里的版本记录和 Redis 里的会话状态不一致时，以哪一边为准？** 以数据库为准，Redis 只是当前逻辑会话的一份带 TTL 的副本。分工是：登录版本由数据库那次登录事务原子分配，它是“哪一次登录是最新的”唯一权威；`session:{clientId}` 记录这份客户端此刻的会话快照。冲突的典型形态是 Redis 里的版本落后于数据库，或者会话 TTL 没到但账号已经被注销、被新登录顶掉。判定规则放在我这边就是：恢复和受保护请求都要拿会话里的版本去比数据库当前版本，落后、被撤销或者恢复凭据校验值对不上，一律拒绝，绝不拿 Redis 里那条旧缓存去覆盖或续用数据库的结论。为什么不反过来让 Redis 当权威：它是易失存储，整份丢了或者过期了，没人能说出某个账号现在该是哪一版，把认证建立在它上面等于把身份结论挂在一个会自己消失的地方。代价是关键请求要多一次数据库版本确认，所以我会先用会话里已缓存的账号和认证状态过一道，把不必要的那次查询省掉。
- **数据库登录事务已经提交，但 Redis 会话写入失败，这次登录怎么收场？** 我不会报成“登录成功、可以恢复”，也不会退回去用 socket 自己那一套私有身份顶上。因为登录版本已经在数据库里推进了，客户端如果按普通失败重试，就会再推进一版、把刚分配的这版作废，越重试越乱。我的做法是按已经提交的这一个版本幂等重建会话：同一个 `session:{clientId}`、同一个登录版本重写一遍，写成功就正常返回成功；仍然失败就返回一个明确的可重试状态，让客户端保留这次拿到的恢复凭据、只补会话不重新登录。判定“登录可用”的门槛我卡在会话就绪上：Redis 那份会话没落地之前界面不进已登录页，因为这一步之后所有请求都靠它授权。另一条路是把 Redis 写塞进数据库事务里，我没走——那等于让 MySQL 事务挂着不放去等一次外部网络往返，还没有真正的两阶段提交，失败面反而更大。代价是这个窗口内状态不完美，得靠幂等写和可重试语义把它解释清楚。
- **Redis 整个不可用的时候，登录和已登录客户端的受保护请求分别怎么处理？** 原则是认证失败关闭，展示可以降级。登录这步必须写会话，Redis 写不进去就不发成功——哪怕密码完全正确也不算登录完成，因为后面每个请求都要靠 `session:{clientId}` 授权，此刻放行只会把用户送进一个马上要报错的状态。已登录客户端发来的受保护请求同理，查不到会话就拒绝，绝不回退成“按报文自报的账号名放行”，那等于把整层认证删掉。可以降级的是在线展示：谁在线这种信息我可以退回查数据库里的在线字段，或者干脆显示未知，最多是列表不准，不影响权限判断。我为什么不做“Redis 挂了就用服务端进程内内存继续维护会话”：那样多实例之间会各自为政，踢人和版本判断立刻不一致，是把一个可用性问题换成更难查的正确性问题，而我这边版本权威在数据库，内存副本救不了场。代价是 Redis 故障期间新用户登录会直接失败，客户端得把它提示成服务暂时不可用，而不是误导成密码错误。
- **密码校验通过但数据库登录事务提交失败，这种情况算登录成功吗？** 不算。密码对不对只回答“这个人有没有资格”，我这边登录成功还要求服务端真的分配了登录版本、写了登录记录，这两件事在同一个数据库事务里；提交失败意味着版本没推进，我就拿不到一个能写进 `session:{clientId}` 的版本号，后面的授权、互踢、代次判断全都没有依据。所以流程到这一步直接返回失败：不写 Redis 会话、不下发恢复凭据，客户端停在登录页提示重试。这里我特意防着一种看起来更友好的写法——凭据对了就先放行、会话回头再补，那样客户端会带着一个服务端不认的身份去发请求，第一个受保护请求就失败，用户看到的是“登录后马上报错”，比登录失败更难解释。代价是数据库抖动期间登录不可用，我不做“先发一个不带版本的临时会话”这种降级，因为无版本会话在互踢判定里没有可比对象，会绕开新登录顶掉旧登录这条规则。
- **服务端进程重启之后，Redis 里那些会话还能用来恢复登录状态吗？** 能，条件是会话本身仍然有效。Redis 是独立进程，服务端重启不动它，`session:{clientId}` 里的账号、登录版本、认证状态和恢复凭据校验值都还在，TTL 没到期就仍然算活。但旧的 TCP 连接肯定没了，这点要说清：重启后每条 `connId` 都要重建，客户端得先重连，再带着 `clientId` 和恢复凭据走恢复流程，我核对凭据和版本通过后才把这条新 socket 绑到原会话上，不用重新输密码。恢复过程不推进登录版本，因为它不是新登录，是同一份客户端的延续。边界在 TTL 上：会话是靠心跳续期的，服务端宕机时间长过 TTL 那份键自然过期，就只能走完整登录；我也没在启动逻辑里加“全局失效所有会话”，那等于把一次崩溃重启当成服务端主动把所有人踢下线，跟跨连接恢复这个设计目标是反的。
- **多个服务实例共享同一份 Redis 会话之后，是不是就能直接跨实例互踢了？** 还不能画这个等号：统一鉴权可以，主动关掉别人进程里的那条 socket 不行。共享了 `session:{clientId}` 和登录版本之后，任何一台实例收到请求都能判断这份会话还是不是当前代次，所以旧客户端不管连在哪台实例上，下一个请求都会被版本检查拒掉，这是被动失效。但“立刻断掉那条物理连接并告诉对端你已在别处登录”做不到，因为那条 socket 的文件描述符只在持有它的实例进程里，我这一台写 Redis 也关不到它。要补上这一步得加一条失效通知通道，比如踢人的实例朝一个按 `clientId` 或实例号划分的通知主题发一条消息，持有连接的实例订阅到之后自己关；换消息队列也是同一个道理。我这套按单实例部署收口，多实例时这条通道就是要补的那一环。代价除了多一个组件，还要处理“通知丢了”的情况，所以被动的那条版本检查我不会因为有通知就省掉，两者是兜底关系。
- **客户端在请求报文里自报的账号名跟会话里的登录账号不一致时，服务端按哪个处理？** 按会话里那个，自报字段不改变操作主体。服务端先用 `clientId` 找到 `session:{clientId}`，里面存的账号才是这次请求的发起者；报文里的账号名只是一个普通业务参数，比如“要查谁的资料”，它回答的是“对谁操作”，跟“我是谁”是两码事，把两者混起来就等于让客户端自己声明身份。所以我的授权链路是固定顺序：先用会话定主体和登录版本，过认证和版本检查，再看请求参数决定这个主体能不能碰那个对象，不存在用自报账号切主体这条路。不一致时我也不做“以会话为准静默改写参数”这种掩盖，好友资料请求带别人的名字本来就该正常。真正要防的是日志和审计里写成自报账号，那样事后查不清是谁干的，所以记操作者我一律从会话取。代价是每个业务处理都得先拿到会话上下文才写得下日志，协议处理上多了一层强制的前置检查。
- **既然登录版本已经能让旧会话的请求失效，为什么还要主动去关闭那条旧连接？** 因为版本检查是被动的，只有旧客户端下一次发请求时才生效，主动关闭是为了不让那条连接占着资源装死。不同客户端的新登录把旧会话顶掉之后，旧那一端可能还挂着一条状态正常的 TCP，手里有排队中的上传分块和等了一半的响应；不主动关，就得等它下次请求才被拒，这段时间连接、缓冲都是白占的成本，对一个正在传大文件的用户来说，界面上还显示“传输中”，等它察觉已经过去很久。所以我在踢人时先下发一条明确的被踢通知、再断开，让界面能给出“账号在别处登录”这句人话，而不是笼统一句网络异常。但我没把关闭当安全边界：万一通知丢了、或者那条连接因为网络原因关不掉，安全性不受影响，因为版本已经推进，它后续任何请求都过不了会话校验。代价是要处理踢人通知和最后一条业务响应的先后顺序，我的规则是通知先入队，否则客户端只会看到一次断线。
- **被踢下线的那一端应该自动重新登录回去吗？** 不应该盲目自动重登。被踢这个事件本身说明数据库里的登录版本已经推进到别人那一次登录了，如果客户端拿着本地存的口令或恢复凭据自动重登一次，就会把刚登录的那个人又顶下去；两端都装自动重连就能无限来回踢，现象是两个人互相把对方弹下线，事后看日志每步都“正常”，最难查。所以我的处理是：被踢时清掉本地会话状态、停在登录界面并把原因写明白，要不要再登录由用户点一下决定，人来做这个取舍。免密的恢复流程我也限定在同一份客户端跨连接这个场景——带上的 `clientId` 找得到会话、恢复凭据校验值对得上、登录版本还是当前那版才放行，被别人顶过就走不通这条路。真要支持自动重连，前提是产品明确接受“最后写入者赢”或者能确认对面就是自己的另一台设备，而我这套账号语义是单端在线，所以保持人工确认。代价是多一次点击，换来的是不会形成踢人循环。
- **踢掉一条连接，能撤销这个旧会话之前已经完成的操作吗？** 不能，这是我要划清的一条边界。踢人做的三件事是让 `session:{clientId}` 失效或版本落后、断开那条物理连接、把 `online:{user}` 的展示改掉，作用点全在“之后”；之前已经提交的东西——写进库的好友关系、落盘的文件对象、已经送达的消息——都不回滚。原因有两个：一是服务端没有一份“哪个副作用属于哪个会话”的账，业务表记的是账号，不是会话代次；二是就算能对上，业务上也不该因为一次异地登录把用户自己的数据撤掉，那会造成比会话被劫持更大的损失。我能声称到的是：从踢人那一刻起，旧会话再发任何请求都过不了版本检查，拿不到新的权限。还有一个方向要说清：如果被踢时旧会话有一次操作正在执行、事务已经提交，那次就正常生效，我的判定只看请求进来之时会话有效无效，不做时间回溯。真要做撤销，得靠按操作者和登录版本留痕的业务回滚入口，不是连接层能顺手提供的能力，我也没往互踢里塞这个语义。
- **一次登录成功之后，系统里一共建了哪几处状态？** 分四层，各自职责不一样。数据库那边：在同一个事务里原子分配一个新的 `loginVersion`、写一条登录记录、更新账号的在线字段，这层是权威。Redis 那边：`session:{clientId}` 存账号、登录版本、认证状态、恢复凭据校验值和会话 TTL，这是后续请求授权的依据；`online:{user}` 单独写在线展示。物理连接这边：当前 socket 只绑 `clientId` 和会话关联信息，不独占认证结论，连接断了会话还在。客户端本地：保存恢复凭据和页面初始化要用的数据，收到成功应答才切到已登录界面。我把这几处分开列，是因为它们的失效条件完全不同——版本由数据库推进、会话靠心跳续 TTL、连接由网络决定、恢复凭据存在客户端盘上，排查“登录状态不对”时真正要问的是哪一层先不一致，而不是笼统查一个登录标记。代价是登录这条路径上任何一处写失败都得有明确说法，所以顺序我定成数据库先、Redis 第二、最后才应答客户端，宁可少发一次成功，也不让客户端进到一个服务端不认的登录态。
- **账号名、口令摘要这些用户可控的值进 SQL 时，怎么防注入？** 全部走预编译语句的占位符绑定，值永远不拼进 SQL 文本。注册和登录用到的那几条——按账号名查重、插账号行、按账号名取盐和摘要——我写的都是带 `?` 的语句，账号名、盐、摘要作为参数绑上去，数据库拿到的是“结构”和“数据”分离的两份东西，账号名里塞 `' OR '1'='1` 或者注释符，它也只是个奇怪的字符串，改不了语义。这一点在账号名上尤其不能省，因为它是唯一允许用户自由输入、又直接当查询条件的字段。占位符之外还有两道：账号名的长度和字符白名单在进 SQL 之前就把明显异常的输入拒掉；连接数据库用的账号只给业务需要的最小权限，不给 FILE、不给跨库，万一哪里漏了拼接也能限制破坏范围。我没走“自己写一个转义函数替换危险字符”这条路，转义要跟字符集和 SQL 模式走，漏一个场景就是突破口，而占位符是驱动层保证的。代价是动态排序字段、动态列名这类不能绑参数的位置必须自己做白名单映射，不能用参数化一句话糊过去。
- **服务端启动时做会话对账，为什么不能把找不到对应连接的会话直接删掉？** 因为在我这套模型里“没有活着的 socket”和“会话无效”是两件事。会话按 `clientId` 存、带 TTL，它存在的意义就是撑过断线：客户端临时掉网、进程崩了、或者服务端自己刚重启，那一刻 Redis 里所有会话都没有对应 socket，如果按“有没有连接”来清理，一次重启就把所有人的登录状态清空，全员重新输密码，跨连接恢复这个设计当场失效。所以我启动对账只碰两类确实是崩溃残留的东西：展示状态（数据库里的在线字段和 `online:{user}`）以及进程内那份连接记录，把它们重置成“当前一条连接都没有”这个事实。会话被清理只有几个正当理由：TTL 自然过期、用户主动退出、被新登录顶掉、账号注销，每个都有明确发起方。判定依据我落在版本上——会话里的登录版本还等于数据库当前版本就留着，不等才作废。代价是系统里必须接受“会话存在但没有连接”这个正常中间态，在线列表和统计不能拿它当在线依据。

### 03. 验证码获取与校验

#### 功能目标

为注册和登录增加一次识别校验与频率限制。验证码状态属于客户端实例，而不是某条 TCP 连接；同一客户端重连后继续使用原状态。

#### 主回答（完整业务实现链路口述版）

客户端携带 `clientId` 请求验证码。服务端先读取 `cap:{clientId}:lock` 和 `cool`，允许生成时创建答案，用带 TTL 的 `code/cool` 保存，并只返回图片。用户提交注册或登录时仍携带同一 `clientId`，服务端按锁定、存在、过期、匹配的顺序校验。错误时通过 `fail` 累计次数，达到上限写入带 TTL 的 `lock`；成功后原子消费 `code` 并清理 `fail`，冷却键按原 TTL 结束。由于所有状态都按客户端实例关联，重连不会重新获得一张无限制的新状态，也不会绕过原锁定。

#### 表达脉络（记忆钩子）

1. 携带 `clientId` 取码 -> 2. Redis 检查锁定和冷却 -> 3. 写带 TTL 的验证码状态 -> 4. 只返图片不返答案 -> 5. 按同一实例校验和计数 -> 6. 成功消费，失败锁定，重连不重置

失败分支：锁定、过期和不匹配分别返回；连续错误达到上限后锁定，TTL 到期自动恢复。

#### 追问卡片

**详细业务实现链路（分步版）**

1. 客户端读取本地 `clientId`，在获取验证码和后续提交中保持同一个值。
2. 服务端读取 `cap:{clientId}:lock/cool`，不满足条件就直接返回剩余时间。
3. 生成六位随机答案并绘制干扰线和噪点，只把图片字节返回客户端。
4. 使用 SETEX 保存 `code/cool`，让答案和冷却各自按 TTL 到期。
5. 登录或注册提交时按同一 `clientId` 找回答案，依次检查锁定、过期和匹配。
6. 错误原子累计 `fail` 并按阈值写 `lock`；成功原子消费 `code` 并清理 `fail`。
7. TCP 重连只改变 `connId`，原验证码、失败计数和锁定仍从 Redis 读取。

**记忆钩子**：码跟客户端，错随 TTL；换连接不清零，换实例才算新状态。
- **客户端 ID 是如何生成的，如何保证唯一性？** 首次启动时由客户端使用密码学安全随机源生成 UUID v4，桌面端可用 `QUuid::createUuid()`，网页端使用 `crypto.randomUUID()`，不能只用时间戳、自增数或 `Math.random()`。生成后持久保存在本地，重连和重启都复用同一个值，只有明确重置客户端实例才重新生成。UUID v4 有 122 个随机位，碰撞概率可以忽略，但不是数学上的绝对唯一；服务端发现 `session:{clientId}` 已存在时不能直接覆盖，必须先用恢复凭据证明是原客户端，否则要求更换 ID。`clientId` 只负责关联验证码和会话，可以被复制或清除，不能据此证明设备可信。
- **客户端不点获取验证码按钮、绕过界面倒计时直接构造请求，这套限制还拦得住吗？** 拦得住，因为限制不在界面上。我这边的倒计时、按钮置灰只是交互优化，真正的判定在服务端：每来一次获取验证码请求，我先读 `cap:{clientId}:lock` 和 `cap:{clientId}:cool`，锁定就直接返回锁定剩余时间，冷却没结束就返回剩余秒数，压根不生成新答案；提交注册或登录时同样按 `clientId` 去核对，不看客户端有没有“显示过验证码”。所以有人直接对着 TCP 口构造报文，他拿到的仍然是一个“请等待 N 秒”的答复，绕不过去。反过来这也是我为什么坚持验证码答案不上链路、只下发图片：答案只要下发到客户端这一侧，它就成了公开信息，任何界面层的限制都只是礼节。代价是这类拦截要准确回时间，我得把剩余 TTL 一起返回给前端，否则客户端只能盲猜重试节奏，用户看到的就是干等的报错。
- **验证码连续输错被锁定之后，客户端断开再重新建立一条 TCP 连接，能绕过锁定吗？** 同一份客户端绕不过去，因为我的验证码状态根本不挂在连接上。失败计数在 `cap:{clientId}:fail`，锁定是 `cap:{clientId}:lock` 带 TTL，两个键都按客户端实例存，重连只换掉 `connId`，`clientId` 是从本地文件里读回来的同一个值，新连接上第一次校验照样读到那个锁定键、直接返回剩余时间。这也是我把状态从连接挪到客户端实例上的原因：只要按 `connId` 存，断开重连就等于白送一次新的尝试预算，锁定形同虚设。但我要说清这条路挡的是谁：脚本如果去改或者重新生成 `clientId`，它就落进另一套键空间，等于换了个身份重来，我这层就管不住了。所以我把它当成“同一实例内的频率约束”，跨实例的部分要靠账号维度的失败比例、来源 IP 的异常频率和行为特征一起判，单靠客户端标识做不了全局限流。
- **为什么验证码要拆成 `cap:{clientId}:` 下面的 `code/cool/fail/lock` 四个键，而不是合成一个状态对象？** 因为这四样的生命周期和写入时机各不相同，塞在一个键里就得用一个 TTL 去迁就四件事。`code` 存答案本身，一次性的，校验成功就要原子消费掉，它自己的有效期是“这张图能活多久”；`cool` 是发码冷却，生成一张新图就写、按自己的 TTL 到点自然消失，而且刷新验证码不应该清掉冷却；`fail` 是连续错误计数，只在错的时候自增、成功时清零，它不该有自己的过期语义却又要防止永久残留，所以也给一个滑动 TTL；`lock` 只在计数触到阈值时写，控制的是恢复时间。分开之后每一步都是单键操作，SETEX 和 INCR 这些原语天然可用，读的时候按 lock、存在、过期、匹配的顺序判。我也考虑过存一个 hash 用 HSET 加整体 EXPIRE，字段是清楚了，但冷却和锁定的剩余时间就得分开记时间戳自己算，还丢掉单字段独立 TTL 这件事，反而更绕。代价是一次校验要发多个键的命令，我用管道合并往返，这点开销换语义清楚是划算的。
- **同一个客户端把同一张验证码并发提交两次，会不会两个请求都通过校验？** 不会，前提是消费必须是一次原子操作。我原来的写法有典型漏洞：先 GET `cap:{clientId}:code` 拿到答案、比对通过、再 DEL 这个键——两个请求可以在同一个窗口里都 GET 到同一个答案，双双通过，一张码就变成两次成功机会。所以我把“读取、比对、删除、返回结果”合成一个原子步骤提交给 Redis，用一段服务端脚本一次做完，只有真正读到并删掉答案的那个请求得到“通过”，第二个请求读到的已经是空键，判成过期。失败计数那边我也按同样思路处理，用自增这种原子命令而不是“读出来加一再写回去”，否则并发失败会把计数丢掉，锁定阈值就形同虚设；触到阈值写 `lock` 也只在自增结果正好等于阈值那一次做。代价是这条消费逻辑从几条普通命令变成一段脚本，可读性和调试都比直白写法差一些，得靠日志把“为什么这次判过期”记出来。
- **Redis 不可用的时候，验证码状态能不能暂时退回服务端进程内存、按连接自己记？** 不能无声退回，这是我刻意守住的一条。表面上看退回内存能保住“可用性”，但退回去之后状态的归属就从客户端实例掉回了单条连接：同一份客户端断线重连换一条连接，计数和锁定就被清零，等于白送重试预算，我这整套“重连不清零”的设计当场作废；更糟的是多台实例各自在自己的内存里记一套，同一个客户端在两边各得一份额度，行为还随负载均衡怎么分配而变，出问题根本对不上。所以 Redis 读不到写不进的时候，我让它失败关闭：不发新验证码，也不放行校验，返回一个明确的“服务暂不可用、请稍后重试”，让客户端把它显示成系统问题而不是“验证码错误”，否则用户会以为自己一直输错、反而去反复试。真要在没有 Redis 的环境跑，我能接受的形式是一份统一的外置状态存储，或者整体降级成更严的策略（比如暂时停掉注册），而不是让每条连接各算各的。代价是 Redis 故障期间注册和登录会不可用，我选的是宁停不放，因为这条路上放过去的是认证的第一道闸。
- **验证码输对了但密码错，这张验证码还能留着下次直接用吗？** 不能，它在那一次就已经消费掉了。我的校验顺序是先看 `cap:{clientId}:lock` 有没有锁定、再看 `code` 在不在和过没过期、最后比对答案，比对通过就立刻原子消费掉 `code` 并把 `fail` 清零——这一步发生在口令校验之前，不存在“等密码也对了再算这张码用过”。理由是验证码要防的是“一次人机识别换多次尝试”：如果它绑在登录成功上，密码错的请求等于白白消耗了一次网络往返但额度还在，脚本可以拿着一张正确的码去穷举口令，那这道闸就退化成每次攻击开始前的一次性成本。所以现在的语义是：一张码只授权一次“进入凭据校验”的机会，用完即废，要再试就得再取一张，而取码本身又被 `cool` 冷却和 `lock` 锁着。代价是用户手滑输错密码就要重新看一张图，交互上烦一点；我也不做“密码错但同一次提交里允许重用这张码”的宽限，因为那等于给每个会话开一次免检重试，撞库要的正是这一次。
- **有 `clientId` 这个客户端实例标识，是不是可以直接拿它当限流维度？** 只能当一个维度，不能当全部。它擅长的是“把同一份客户端的状态串起来”：验证码的 `cap:{clientId}:code/cool/fail/lock`、会话的 `session:{clientId}` 都挂在这上面，所以同一份客户端重连、换 IP、断线再上来，计数和锁定都是连续的，不会因为换了 `connId` 就重置。但限流要的是“这个来源还能不能再给他一次尝试”，而 `clientId` 是客户端自己生成、自己保存在本地、随请求带上来的字符串，服务端没法验证它是不是真来自一个新实例——脚本每跑一次就重新生成一个 UUID，等于换了个身份，按它限流就是按攻击者愿意提供的标识限流，额度可以无限领。所以我把它用在状态归并上，不用在信任判定上；跨实例的那一层要看账号名的失败比例、来源 IP 的请求频率和账号新注册速率这些服务端自己观察得到的量。代价是攻击者只要不停换 `clientId` 就能让我这层失效，这正是我要用冷却、锁定加上口令校验失败本身也要计数这三样叠起来的原因，任何单独一层都不足以兜住。
- **只按来源 IP 做验证码频率限制，够不够？** 不够，两个方向都出问题。误伤方向：校园网、公司出口、运营商大内网后面可能几十上百个人共用一个公网 IP，按 IP 卡频率的话一个人刷验证码会把同出口的正常用户一起关在门外，而且这些人换不来 IP，只能干等；漏放方向更直接，攻击者拿一堆代理或者拨号换 IP，每个 IP 只用几次，IP 维度的阈值永远碰不到。所以 IP 在我这里只用来做“异常信号”，比如同一 IP 短时间内出现大量不同 `clientId`、或者失败率异常高，触发的是加严验证而不是直接封死。真正的一次尝试预算我放在客户端实例加账号这两个维度上：`cap:{clientId}:cool/lock` 管同一份客户端的重试预算，账号维度的失败比例用来判断是不是有人在拿别人的账号试密码。三层各有各的绕过成本，叠起来才可用。代价是要维护多套阈值和一套合并判定，正常用户在小概率下仍然可能被误判，所以我给的是递进式等待而不是硬封，让误伤可以靠时间自然恢复。
- **这套验证码的行为你是怎么验证的？** 我按状态机去手工构造场景，看每一步 Redis 里剩下什么。冷却：取一张码之后立刻再请求一次取码，看返回的是不是剩余秒数，同时用 `TTL cap:{clientId}:cool` 确认那个键真的在倒计时而不是被刷新；再把 `cool` 手动删掉，请求应该立刻放行，这能证明拦截是服务端判的、不是界面倒计时。有效期：把 `code` 的 TTL 调到几秒，等它自然消失后再提交原来那张图的答案，应该报“已过期”而不是“不匹配”，这两个返回码我特意分开。连续错误锁定：故意连错到阈值，看 `fail` 是不是每次自增、`lock` 是不是只在触阈值那一次出现，然后确认锁定期内即使输对答案也被拒，等 `lock` 的 TTL 到点后再输同一个答案应该恢复。重连不重置：同一份客户端断开重连（换了 `connId`）之后继续输错，看计数是不是接着上一次涨。原子消费：正确答案提交两次，第二次必须判失败。最后是隔离性：换一份 `clientId` 应该拿到全新的状态，说明键空间没串。这些我都是看着 Redis 里键的值和 TTL、加上服务端带前缀的校验日志来判断的，不靠界面提示反推。
- **这套验证码方案换来什么、又让不掉什么？** 换来的是两件我认为最要紧的：答案不上链路，服务端只把画好的图片字节下发，答案一直留在 `cap:{clientId}:code` 里，客户端抓包看不到明文答案，界面层也就没什么可改的；限制状态按客户端实例存而不是按连接存，重连、换 IP、进程重启都清不掉 `cool` 冷却、`fail` 计数和 `lock` 锁定，正好补上“断开重连就白送额度”这个漏洞。让不掉的是它本质上只是一次抬高成本的检查，不是身份认证：现在有现成的 OCR 和打码平台，识别一张图对脚本来说成本很低；`clientId` 是客户端自己生成带上来的，重新生成一个就换了一整套键空间；分布式来源下每个出口只发几次请求，任何单维度阈值都碰不到。所以我给它的位置是注册和登录前面的一道频率闸门，真正判断“你是不是你”的还是口令加盐摘要、会话里的登录版本和恢复凭据那几层。再往上抬一档是行为验证或滑块，代价是误伤和实现复杂度都跟着上去，我没有往这个方向做。

### 04. 退出登录

#### 功能目标

主动撤销当前客户端的逻辑会话，保留账号和业务数据。退出后即使原 TCP 或 Redis 残段仍在，也不能再恢复已撤销会话。

#### 主回答（完整业务实现链路口述版）

客户端携带 `clientId` 发送退出请求，服务端根据会话中的账号和版本受理，不使用报文自报账号。验证当前会话后，服务端删除或标记撤销 `session:{clientId}`，使恢复凭据失效，并在没有同账号有效会话时更新数据库和 Redis 在线状态。当前 socket 解除会话绑定，可以继续作为匿名连接存在，也可以物理关闭；两种选择都不能保留业务权限。客户端清除本地会话材料和已登录页面。以后重连必须重新完成完整登录，不能恢复这次已经主动退出的会话。

#### 表达脉络（记忆钩子）

1. 携带 `clientId` 请求退出 -> 2. 核对会话和版本 -> 3. 撤销 Redis 会话与恢复凭据 -> 4. 更新在线状态 -> 5. 解除当前连接绑定 -> 6. 清理本地状态，重连需重新登录

#### 追问卡片

**详细业务实现链路（分步版）**

1. 客户端提交 `clientId` 和退出请求，不把自报账号作为退出依据。
2. 服务端读取 `session:{clientId}`，核对认证状态、账号和登录版本。
3. 删除会话或写入撤销状态，同时使对应恢复凭据失效。
4. 根据账号是否还有其他有效会话，更新数据库和 Redis 在线展示状态。
5. 当前 socket 清除会话绑定，后续业务请求按匿名连接处理。
6. 客户端删除本地恢复凭据、账号页面和内存中的敏感会话状态。
7. 再次连接时查不到可恢复会话，只能重新获取验证码并登录。

**记忆钩子**：退出撤会话，在线按剩余会话算；连接可留，权限不留。

- **退出登录时为什么可以只撤销会话、不切断那条 TCP 连接？** 因为在我这套模型里权限挂在 Redis 的逻辑会话上，不挂在 socket 上。服务端收到退出请求后做的是撤销 `session:{clientId}`、让那份恢复凭据失效、按这个账号还剩几份有效会话去更新在线展示，而当前这条连接的 `connId` 只是解除会话绑定，链路本身还在。这样做的好处是退出这个动作不再牵动网络层：连接上可能还有已经排队要发的响应，硬关掉客户端就会把它显示成一次异常断线，用户看到的错误和自己点的操作对不上。而且留着这条连接也不会有权限风险——它上面后续任何业务请求都会先查 `clientId` 对应的会话，查不到就按匿名连接拒掉，最多还能取验证码这种公开接口。我另一种选择是直接物理关闭，两种都对，只要保证一点：连接在或不在，业务权限都不能留。真正的代价是要接受“连接还活着但已经登出”这个状态，日志和排查时不能拿连接是否存在去推断登录状态，这两件事在我的设计里已经解耦了。
- **退出时只把 `online:{user}` 这个在线键删掉就够了吗？** 不够，那是把展示当成了权限。`online:{user}` 只服务一件事：好友和在线列表上那个绿点，它按账号名可查，里面没有任何认证材料。退出的实质动作必须落在 `session:{clientId}` 上——把会话删掉或写入撤销状态，同时让这次登录下发的恢复凭据失效，这样带同一个 `clientId` 再来恢复时，找会话、核对凭据、比对登录版本这三样没有一样能过。顺序我在意的是先撤会话，再看这个账号名下还有没有其它有效会话，最后才决定在线展示怎么改。反过来先删在线键，就会出现一种最难查的现象：列表里显示离线，可那份会话还活着、还能免密恢复继续发请求，看起来像“退了但没退干净”。代价是我在更新在线状态时要多判一次“还剩几份有效会话”，单端在线时这步简单，将来放开多端它就是必须的，否则一个人退出会把整个账号的在线抹掉。
- **退出请求到了服务端，但 Redis 那次会话删除失败，可以直接返回“退出成功”吗？** 不能，这个应答我说成功就是假的。退出的完成条件不是“客户端界面回到了登录页”，而是服务端那份 `session:{clientId}` 已经不可用；删除失败意味着会话还留在 TTL 里、恢复凭据仍然有效，客户端断开之后随时能拿同一个 `clientId` 免密恢复回去继续发受保护请求。所以我按“未完成”处理：物理连接该关还是关，不然用户会觉得界面卡在那里；但返回给客户端的是可重试的失败，本地不清恢复凭据，下次进来先补一次退出。故障期间这个 `clientId` 上的受保护操作我一律失败关闭，不能因为它“大概还没退成”就当已认证放行。我没选“先应答成功、后台慢慢删”，因为退出常常是用户在不是自己的电脑上做的动作，成功的语义必须是“真的撤销了”，晚点删不等于安全。代价是 Redis 抖动时退出会失败、要用户重试一次，这里我宁愿多一次重试也不要一个假的成功。
- **退出请求因为网络异常根本没到达服务端，这次退出算发生了吗？** 不算，我把它和主动退出严格分开。判据是服务端有没有真的撤销：请求没到，`session:{clientId}` 就还在 TTL 里、恢复凭据仍然有效，客户端重连后带上 `clientId` 和凭据、版本还是当前那一版，就能恢复成登录态——这属于跨连接恢复该有的行为，我不当漏洞处理。风险在于用户的认知：他点了退出就以为已经安全了，尤其在人多的场合用别人电脑登录时，本地清干净并不等于服务端撤销了。所以我把这两件事分开收口：本地状态立刻清、界面回到登录页，同时把“这次退出还没被服务端确认”留在客户端，等下一次连上任何一台实例先补发一次退出请求；补不上就一直按未确认处理。我没有做成“请求没到就强制让会话失效”，因为服务端此时压根没收到指令，只能靠 TTL 被动等，那反而给了一个不确定的窗口。要说边界：如果那台机器之后再也不联网，我这套补救就不会发生，真正需要立刻失效的场景应该用另一台设备上的登录版本推进来踢掉它，而不是依赖退出请求本身。
- **退出登录会把客户端本地已经存下的聊天记录一起清掉吗？** 不会，退出清的是会话材料，不是业务数据。我这边退出的动作是删掉恢复凭据这类认证材料、清掉内存里的已登录状态、界面回到登录页；聊天记录、已经下载的文件、任务列表跟着本地存储走，不跟着一次登录的生命周期走。理由很直接：重新登录之后用户期望历史还在，退出顺带清记录的话，一次误点就是不可恢复的损失，这个风险比“本机多留一份数据”大得多。但剩下的暴露面要说清：这台机器如果别人能碰到，本地记录不会因为退出而消失，所以本地数据要按账号目录隔离，公用设备的场景应该由注销账号或者一个明确的“清除本机数据”入口负责，我不把它偷偷塞进退出按钮里。代价就是“已退出”不等于“本机不留痕”，这两件事的差别得让用户看得见，而不是靠退出顺手做掉。
- **服务端已经撤销会话、但那条 TCP 还没有关掉，这一刻退出算成功了吗？** 算，判据在服务端状态而不在连接状态。`session:{clientId}` 被删掉或者标成撤销、恢复凭据跟着失效之后，这条连接上再来的任何请求都会走到“按 `clientId` 找会话、找不到”这一步被拒，它已经拿不到任何业务权限；连接什么时候真正断是网络层的事，可能客户端收到应答就关，也可能等失联检测超时才被服务端回收，甚至因为链路问题一直挂着——挂着的那段时间它只是一条匿名 socket。我不把“连接已关闭”写进退出成功的条件，是因为这件事我根本保证不了：对端断电、链路静默丢包时服务端要等心跳超时才知道，如果拿它当判据，一个本地点击的退出就变成要等几十秒才能确认的操作。代价是这段时间对端看起来“还连着”，所以在线展示必须按还有几份有效会话来算，不能按连接是否存在来算，否则列表上会出现一个已经离线的人挂着在线。
- **主动退出之后，还能用同一个 `clientId` 免密恢复这次会话吗？** 不能，这是主动退出和断线重连之间要分清的一条区别，我把两者走的路径完全分开。恢复要同时满足：`clientId` 能在 Redis 里找到 `session:{clientId}`、请求带上来的恢复凭据跟会话里存的校验值一致、会话的登录版本还是数据库当前那一版。主动退出那一步已经把会话删掉或标成撤销、校验值一起失效，所以这条路走不通，`clientId` 本身只是查找键不是凭证——它之所以设计成稳定不变，是为了让服务端能找到状态，而不是为了证明自己有权用这个状态。这么定的原因是退出必须是服务端记得住的一个决定：如果退出之后同一个 `clientId` 还能凭旧凭据回去，用户在别人电脑上点的那个退出就只是把界面关掉，风险直接落回会话被复用那一类问题上。要再用只能重新完整登录：取验证码、校验口令、数据库分配新版本、写一份新会话。误退出的代价就是重输一次密码，我用界面记住账号名去补这个不便，不开会话语义的口子。

### 05. 注销账号

#### 功能目标

删除当前认证账号的核心记录，并撤销该账号及相关客户端的可恢复会话。注销成功不等于所有物理文件和失败补偿已经同步完成。

#### 主回答（完整业务实现链路口述版）

用户在已登录状态下再次输入口令，客户端携带 `clientId` 发起注销。服务端通过 Redis 会话确定认证账号并核对登录版本，不能按报文自报账号切换目标。随后在数据库事务中复核口令，删除账号、好友、私聊和相关记录，失败则回滚。数据库提交后清理用户目录或登记补偿，同时撤销该账号的会话、登录版本记录和恢复凭据，删除在线状态并解除当前连接绑定。客户端清理本地会话材料；以后同名注册属于新的账号生命周期，旧 `clientId` 和旧会话都不能继承权限。

#### 表达脉络（记忆钩子）

1. 携带 `clientId` 和口令确认 -> 2. 按会话确定账号 -> 3. 事务复核并删除关联 -> 4. 提交后清理目录或登记补偿 -> 5. 撤销会话、版本和在线状态 -> 6. 清理本地材料，同名视为新生命周期

失败分支：凭据或数据库提交失败保留账号；目录清理与数据库无共同事务，失败进入补偿。

#### 追问卡片

**详细业务实现链路（分步版）**

1. 客户端携带 `clientId` 和二次确认口令发起注销。
2. 服务端从 `session:{clientId}` 取得账号，并验证会话与登录版本。
3. 数据库事务复核该账号口令，拒绝通过自报账号删除别人。
4. 核心账号及关联记录删除成功后提交，任一步失败都回滚。
5. 提交后删除用户目录，失败则记录补偿，不反向伪装数据库未提交。
6. 撤销该账号相关 Redis 会话、恢复凭据、版本登记和在线键。
7. 客户端清理本地凭据与页面，旧连接和同名新账号均不能继承旧权限。

**记忆钩子**：先认会话再删号，库内回滚、库外补偿，会话版本一起销。

- **注销账号时，用户已经登录了，为什么还要再输一次口令？** 因为登录状态和“我要永久删除这个账号”是两种强度完全不同的意图，我不想让后者被前者的便利带过去。会话证明的是“这次登录是本人”，但注销接口一旦被误点、被旁边的人点、或者被一个仍然有效的旧会话发出来，代价是不可逆的：账号行、好友关系、私聊记录一起没了，不像退出还能重新登录补救。所以我在服务端事务里再复核一次口令——按会话确定的那个账号去查盐、算摘要、比对——这等于要求一次“当下的重新认证”，把误操作和借用他人未锁屏的会话这两类情况挡在同一道门里。也可以做成等价形式：要求近期完成过一次认证，或者弹一个独立的确认挑战，判据是“这次删除动作有独立的本人证据”。代价是流程多一步、用户嫌烦，但我不把它省掉，也不接受用报文里的账号名代替这次核对：核对对象必须来自 `session:{clientId}` 里的账号，否则这次校验就成了攻击者自己指定的。
- **有人能借注销接口把别人的账号删掉吗？** 删不掉，关键是删除目标不由报文决定。我的链路是：请求带上 `clientId`，服务端用它去 Redis 找 `session:{clientId}`，从会话里取出账号和登录版本，核对会话仍然是当前有效的那一版，然后用这个账号去做口令复核和后续删除。报文里就算另外写了一个账号名，它也不参与“删谁”这件事——这是所有账号类操作的同一个规则，操作主体只从会话取。另外还有一道：注销要求在会话里再输一次口令，而口令摘要是按会话里那个账号查的，所以即便有人伪造 `clientId` 命中了别人的会话，他也要知道那个账号的口令才能删。要绕到“猜一个别人的 `clientId` 撞会话”这条路，得先猜中一个随机生成的 UUID v4，并且这份会话还得没过期、还属于当前版本。代价是我在接口上必须始终拒绝自报账号这条路，一旦哪天图省事加了“没有会话就按报文账号处理”的兜底，这道防线就没了，所以我把这个顺序当成接口的硬约束而不是可选优化。
- **注销账号时，这个人生前上传过的群文件和被内容去重共用的物理对象会一起删掉吗？** 不能按“谁上传的就删谁的磁盘文件”处理，这是两套归属。群文件的归属在群那边：记录挂在群上，成员退出或者某个账号注销都不该把群里的东西带走，我要做的是把这个人从群成员和群相关的关联关系里摘掉，文件记录本身保留，除非群本身被解散才走群文件的清理路径。内容去重的那份物理对象更敏感：多个逻辑条目按内容摘要指向同一份物理数据时，它天生不属于任何一个账号，删之前必须先解掉我这个账号名下的逻辑引用，再看这份物理数据还有没有别的引用，引用归零了才进回收。所以我没有把注销写成“递归删目录”一句话，个人目录下的东西可以按用户根目录清理，公共存储区的对象必须走引用释放这条路。代价是磁盘回收可以晚于数据库提交、由补偿继续做完，这也是我把“注销成功”定义成核心记录已删、而不是所有字节都已消失的原因。
- **注销账号时 Redis 那边要清掉哪些状态，只删数据库那行记录不行吗？** 只删数据库行不够：数据库管的是“这个账号还存在吗”，Redis 里那份会话管的是“某条请求现在有没有权限”，两者不是一回事。要清的有这几处：这个账号名下所有客户端的 `session:{clientId}`，让所有还连着的实例上下一个请求都找不到有效会话；跟这些会话配套的恢复凭据校验值，它跟着会话一起消失，否则断线的那端还能凭旧凭据恢复一个已经不存在的账号；`online:{user}`，不删的话在线列表里会挂着一个点进去全是错误的人；登录版本登记也要撤。这里最容易出问题的是同名重注册：如果旧会话只是按账号名关联、没有撤销，那旧 `clientId` 就可能带着一个还存在的有效会话落进新账号的生命周期里，等于继承了别人的权限，所以会话里必须带着“这是哪个账号生命周期”的判定依据。至于验证码那组 `cap:{clientId}:code/cool/fail/lock`，我让它们按各自 TTL 自然到期就够了，那些键再也找不到对应会话，多写一套清理换不来安全收益。
- **注销成功之后那条 TCP 连接还没断开，它上面还能继续发起操作吗？** 不能，而且这里比退出登录更彻底。注销时这个账号名下所有客户端的 `session:{clientId}` 都被撤销了，所以这条连接上下一个请求走到“按 `clientId` 找会话”这一步就找不到，直接按未认证拒掉，跟连接活不活着无关。想重新登录也不行：账号记录已经在事务里删掉了，口令校验那步连盐都取不到，界面应该被踢回登录页并明确说明是账号已注销，不是“登录失败请重试”，否则用户会一直在那儿试密码。将来有人注册了同名账号，那也是一段新的生命周期——新的账号行、新的盐、新的登录版本，旧 `clientId`、旧连接、旧恢复凭据都继承不到任何权限，这一点必须在会话里靠“属于哪个账号生命周期”的判定来保证，不然就会出现旧会话落到新账号头上的越权。我不依赖“连接会自己断”来收这个口，因为断开时机我控制不了：客户端可能崩了、链路可能静默丢包，服务端只能等失联检测超时，那段时间里安全结论必须由会话撤销来给，不能由连接状态给。
- **注销时目录清理失败这件事你是怎么验证的？** 我手工构造一个会让删目录失败的现场：把存储根目录改成只读，或者在用户目录里放一个被别的进程占着句柄的文件，再走一次完整注销，然后逐处核对而不是只看那个应答。数据库这边按账号名查账号行、好友关系、私聊记录这几张表，确认事务确实提交、行已经没了；Redis 这边用 `EXISTS session:{clientId}` 和 `GET online:{user}` 确认会话和在线状态都撤销了；文件系统这边去看那个用户目录还在不在、还剩哪些文件，这时候应该还在，这就是我要复现的中间态；再看服务端带前缀的日志，应该有一条目录清理失败并登记重试的记录，能对上账号或者路径。之后我把只读改回来，等补偿那一轮跑过，再去看目录是不是被清掉、日志里有没有成功的那条。最后用同一个账号名重新注册一次，看新账号的目录是不是干干净净、能不能正常读写，确认旧目录的残留不会串到新账号名下。这几处状态本来就该短暂不一致，因为我把注销成功定义成核心记录已删、磁盘回收允许晚到。

### 06. 重复登录互踢

#### 功能目标

同一账号只保留最新有效登录会话。同一客户端断线恢复属于“续用会话”，不同客户端重新登录才属于“替换会话”。

#### 主回答（完整业务实现链路口述版）

不同客户端登录同一账号时，先完成验证码和凭据校验，再由数据库原子递增 `loginVersion`。事务提交后，服务端为新 `clientId` 建立 Redis 会话并更新在线状态，旧会话因版本落后失效。服务端可以向旧连接发送失效通知并主动关闭，释放其物理资源；即使通知或关闭延迟，后续请求和心跳也会在会话与版本检查时被拒绝。同一 `clientId` 的断线恢复只读取既有会话，不推进版本，因此依旧会进行登录版本校验，若是最新登录版本会复用之前会话，若不是就会清理缓存，重新登录。

#### 表达脉络（记忆钩子）

1. 先区分同实例重连与新客户端登录 -> 2. 新登录由数据库推进版本 -> 3. Redis 建立新会话 -> 4. 通知并清理旧物理连接 -> 5. 入口版本检查兜底 -> 6. 条件清理防止误删新状态

失败分支：凭据或事务失败不推进版本、不踢旧会话；已提交业务不因互踢追溯撤销。

#### 追问卡片

**详细业务实现链路（分步版）**

1. 根据 `clientId` 判断请求是同实例恢复，还是另一个客户端的新登录。
2. 新登录完成验证码和凭据校验，在数据库中原子分配更大登录版本。
3. 为新 `clientId` 写 Redis 会话，并更新账号在线展示状态。
4. 按版本识别旧会话，发送失效通知并在锁外关闭旧物理连接。
5. 旧连接后续请求仍核对会话与版本，不能只依赖关闭通知。
6. 同实例重连恢复原会话，不分配新版本，但是同样会进行登录版本校验，若是最新登录版本会复用之前会话，若不是就会清理缓存，重新登录。

**记忆钩子**：同客户端是续，不同客户端是替；版本分新旧，清理带条件。

- **判断“哪一次登录还算数”，为什么不能只看数据库的在线字段或者 `online:{user}`，而要多一个 `loginVersion`？** 因为在线是一个布尔状态，它只能回答“现在有没有人登着”，回答不了“现在算数的是哪一次登录”。互踢要的恰好是后者：新登录进来要把旧的那份顶掉，我得有个东西能比出谁更新。如果只拿在线字段做依据，新登录时先看到“已在线”再去清状态，中间那一段里旧会话照样能过认证，旧连接上的请求不会有任何变化；更糟的是清完之后旧连接的心跳一上来又把在线改成真，新登录那份反倒被覆盖了。有了单调递增的登录版本，判定就变成一次数值比较：请求带进来的会话里记的版本等不等于数据库当前版本，不等就直接拒，旧会话不需要谁去“通知”它失效，它自己下一次请求就撞上检查。`online:{user}` 在我这里只留着做展示，因为它按账号名可查、没有代次概念，同账号多份展示状态也分不出彼此。代价是每次登录要多一次数据库原子递增、每个请求多一次版本比较，换来的是不依赖任何清理动作时序的正确判定，我认为这笔买卖划算。
- **两个客户端几乎同时登录同一个账号，最终哪一份会话有效？** 谁拿到更大的 `loginVersion` 谁有效，而这个先后不是我看日志时间猜的，是数据库给的。两个请求都可能各自过了验证码和凭据校验，然后在事务里对同一个账号做原子递增——数据库行锁会把这两次递增串行化，一个拿到 N、一个拿到 N+1，拿 N+1 的就是最后一次登录。之后 Redis 侧必须按这个结论写：写 `session:{clientId}` 和更新在线状态时都带上自己那一版，遇到比当前记录版本小的迟到写入就丢掉，绝不能让慢了一步的旧请求把新状态倒写回去，否则会出现“版本大的会话被版本小的覆盖”这种最难查的错乱。判定谁有效只看版本比较，不看请求到达顺序，也不看 TCP 建立时间——那两个在并发下都不可信。代价是拿 N 的那一端会看到一次“登录成功但马上被踢”，因为它的确通过了校验，只是又被别人顶了；这种观感我只能在客户端把被踢原因说清楚，不做“检测到同账号并发登录就干脆都拒”的处理，那等于把正常的换设备登录也一起禁了。
- **Redis 里那份会话记的登录版本比数据库当前版本低，它还能继续用吗？** 不能用，一律按失效处理，而且要顺手清掉。这个状态的含义很明确：有一次更新的登录已经发生过，这份会话属于上一代。所以任何走 `clientId` 找会话的路径，取到会话之后立刻拿会话里的版本和数据库当前版本比一次，低了就直接拒绝并把这份会话删掉，不给它续期——心跳也走同一个检查，而且检查必须在续期之前，否则会出现“会话已失效却被心跳养着”，用户看着自己在线、实际什么请求都发不出去。恢复流程同样卡这一条：不能只凭 `clientId` 找得到会话、恢复凭据也对得上就放行，版本这一项必须单独过，因为它防的正是“凭据仍然正确但登录代次已经被替掉”。为什么不反过来让 Redis 的版本说了算：那迟到的旧写入就能把数据库已经推进的版本改回去，一次网络重排就把互踢逻辑打穿了。代价是关键请求要多读一次数据库版本，我用会话里缓存的认证状态先过一道，只在需要确认代次时才去查库。
- **旧会话被踢掉的那一刻它正在上传一个大文件，这事儿怎么处理？** 我按“已提交的保留、后续的拒掉、状态收敛到失败”处理，不假装能撤销。已经落盘的分块和写进数据库的进度不回滚——回滚更危险，会出现物理数据删了但元数据还在的不一致。被踢后这条连接下一个请求撞上会话和版本检查被拒，上传任务在某一块上失败；客户端把任务标成失败并保留已确认的偏移和会话记录，用户重新登录回来还能从断点接着传。服务端还要防一种隐蔽情况：任务是异步推进的，踢人时可能有回调正在写进度或收尾，回调落库前要再核对这条上传记录所属客户端的登录版本还是不是当前那版，不是就丢掉这次写入并留一条日志，避免失效会话把文件对象推成“完成”。代价是被踢一方看到的是一次突兀失败而不是干净的停止通知，尤其在被踢通知和最后一个分块响应赛跑的时候；我接受，因为要保证的是不再持有写入权限，不是体验连贯。
- **既然版本检查这个兜底已经在每次请求上跑了，为什么还要再发一次失效通知主动踢旧连接，两件事不重复吗？** 不重复，它们管两个不同的失效场景，我两个都要。版本检查是被动的，保证正确性：旧会话不管因为什么还留着，下一个请求一定被拒。但它有两个缺口。一是实时性：旧客户端只要不发请求就一直停在登录界面，正在跑的上传还在按旧会话往队列里塞块，用户看不到任何异常，中间白干；发通知才能让他立刻看到“你在别处登录”。二是覆盖范围：通知顺带把那条 TCP 关掉、清掉实例内的连接映射，这些被动检查做不到——请求不来，那些资源就一直挂着。所以主动踢管体验和资源回收，被动检查兜正确性。我不把主动踢当安全边界：通知到对端那段链路本来不可靠，丢了也没关系，每个旧请求照样会在版本检查这里被拒。这层分工要写清楚，否则哪天有人觉得“反正有通知”就把检查挪走，系统就悄悄不安全了。
- **被踢那条连接的延迟清理回调跑起来时，会不会把 Redis 里刚写入的新会话一起删掉？** 不带条件地删就一定会，所以我的清理全是条件清理。时序是：新登录进来，服务端给旧连接发失效通知并安排一次延迟清理，要收掉 `session:{clientId}` 和 `online:{user}`；这中间旧客户端自己重连并成功登录了一次，Redis 里现在躺着的是那份更新的会话，回调无脑 DEL 就把合法的新会话删了，用户表现为“明明登录上了，一会儿又掉线”，现场看着像 TTL 或 Redis 抖动，很难归因。所以清理前我要比对自己手里那份预期值：要清的这个 `clientId` 在会话里是不是还是我认的那个、版本是不是我以为的那一版，匹配才执行删除，不匹配就说明状态已经被更新过，回调安静退出。这个“比较再删”必须用一段 Redis 脚本合成一次原子操作，否则比较和删除之间又插进来一次新登录，条件就白写了。在线键按账号名存，同理要先确认它现在代表的是不是我要清的那次登录。代价是清理要多读一次会话内容，换来的是不再依赖它跑的时机碰巧没人登录。
- **多台服务端实例的情况下，只靠共享 Redis 会话能把互踢做完整吗？** 做不完整：共享 Redis 会话只解决了判断，没解决执行。判断够用——`session:{clientId}` 和数据库分配的 `loginVersion` 每台实例都能读，收到旧会话请求的实例自己就能得出“版本落后、拒绝”。缺两件事：版本必须由数据库那一次事务原子分配，两台实例各持本地计数发号、或者把读旧版本加一写回拆到不同进程，就会出现两个客户端拿到同一个版本，互踢依据当场失效；旧连接的套接字在另一台进程里，我这里写 Redis 关不到它，只能靠一条按 `clientId` 或实例号划分主题的失效通知，让持有连接的实例自己关掉并清掉进程内映射。另外 `online:{user}` 在多实例下要按“该账号还有没有至少一份有效会话”聚合，任何一端断开都不能把整体写成离线。我这套按单实例部署收口，多实例时这两环都要补。
- **数据库、Redis 会话、物理连接和在线键这几处都带着登录版本，是不是存重了？哪一处的版本算数？** 不算重，它们是同一个值在链路上的不同角色，权威只有数据库一处。新登录在数据库事务里原子递增 `loginVersion`，它是“哪次登录最新”的唯一定义，别的副本只读不改。Redis 的 `session:{clientId}` 里带版本，是为了让鉴权不必每个请求都回库比对，属缓存性质，可以按 TTL 消失也可以重建；当前连接上绑的那份只是本次请求上下文的快照，让处理链路和异步回调不用再去找一圈，随连接生灭，不承载结论；`online:{user}` 带版本是给展示和条件清理用的，清理时比一下现在这份在线是不是自己那次登录留下的。这样冲突永远以数据库为准，其余三处只比较，不会出现两边都推进、谁大不知道的局面。代价是登录、踢人、恢复每条路径都得把这几处写全，漏一处就不一致，所以我把“只有数据库能发号、其余只读”当成硬规矩。
- **为什么这套账号模型默认不做多端同时在线？** 这是业务选择。我按“一个人同时只有一处在线”定语义，互踢就是这条语义最省的解释方式：新版本一来旧会话作废，用户看到的现象和他的预期一致，不用去理解“同一账号在三台设备上状态各不相同”。开多端要改的远不止把互踢那一步删掉：一个账号名下要挂多份 `session:{clientId}` 并各自撤销，就得有一张账号到会话的索引，注销和“改密码后踢掉所有端”从撤一份变成按账号遍历撤销，漏一份就是权限残留；`loginVersion` 的语义要换，多端下拿它判失效会让后登录的把先登录的一起顶掉，得改成每份会话自己的状态标记加一个全局撤销代号；在线要变成设备列表，未读得按会话维度算，不然手机上读过、电脑上还显示未读；再往上是多端同时改同一个目录、同一个任务时的冲突规则。代价就是“手机和电脑同时挂着”这个常见需求我满足不了，换设备得重新登录。
- **被顶掉的旧客户端一直发心跳，能不能把那份已经失效的会话续住？** 不能，心跳在我这里没有这个权力。心跳做的事只有两件：证明这条连接还活着，以及把 `session:{clientId}` 的 TTL 往后推一推。但它在动手之前必须先过同一道认证检查——按 `clientId` 找会话、比对会话里的登录版本还等不等于数据库当前版本，版本落后就直接回失效，连续期那一步都不执行。这条顺序很关键：如果实现成“先 EXPIRE 再判断”，旧客户端靠三十秒一次的频率就能把一份本该消失的会话一直养着，TTL 这条兜底线形同虚设，而它偏偏是会话被撤销之外唯一自动清理的路径。被顶掉的会话正确的消失方式是两种：要么在踢人的时候就被撤销或删掉，要么 TTL 到点自然过期，不管旧客户端多勤快都不会延长。心跳还有一处要当心：客户端一直发心跳但已经不再发业务请求时，在线列表会显示它挂着，所以在线状态也要跟着认证结论走，认证不过就把它写成离线，不能只按“最近收到过字节”算在线。代价是判定失效要多一次版本比对，我把它放在续期之前，宁可对失效会话回得快一点。
- **同一台设备重新登录，会不会把自己原来的会话误踢掉？** 要分两种情况，按走哪条路径区分。断线后的重连不会：同一个 `clientId` 带恢复凭据走的是恢复流程，服务端只读那份既有的 `session:{clientId}`，核对凭据和登录版本后把新的 `connId` 绑上去，全程不碰数据库里的 `loginVersion`，所以不存在新旧代次交替，用户不用重输密码。但如果用户是在登录界面上主动做一次完整登录——填账号密码、过验证码——那就是真的一次新登录，数据库分配更大的版本，原来那份会话按规则失效，包括同一台设备上先前那份。这不是误伤，我故意让显式登录有权把状态推平：会话卡死、恢复凭据在本地丢了，都需要这条路径。也想过同一 `clientId` 重新登录就复用旧版本，但那会让版本不再等于“第几次登录”，别处的旧登录反而清不掉。代价是主动重登会让上一份失效，这一点我在界面上明说，不让它悄悄发生。
- **互踢流程里的锁是怎么安排的，为什么关闭动作要放到锁外面做？** 规则是一句话：锁只保护进程内那张连接和会话映射，所有对外、可能慢、可能触发回调的动作都放锁外。拿到映射保护后我只做一件事——按 `clientId` 和登录版本把要作废的旧连接从表里摘成一个本地列表，然后立刻释放；出锁后再逐个发失效通知、关闭 socket。原因是关连接会触发这条连接的断开回调，而回调通常也要动同一张表（清绑定、更新在线状态），我还握着锁的话同一线程走到回调里再抢一次这把锁就自锁死；实现成不可重入锁或者把回调派到别的线程，就变成看运气的不一致——单连接测试好好的，多端并发登录才偶发卡死，这种最难复现。另外关闭和发通知可能阻塞几十到几百毫秒，放在锁里会把新登录的临界区拖长，所以数据库查询和 Redis 往返也一并出去，锁里只允许碰内存那张表。代价是摘出来的列表出锁后可能已经变化，后续清理都得做成条件清理。

### 07. 心跳与失联检测

#### 功能目标

识别物理连接失联并回收僵尸资源，同时维护可恢复逻辑会话和在线展示的 TTL。超时只表示怀疑失联，不证明具体故障原因。

#### 主回答（完整业务实现链路口述版）

连接建立后，客户端启动周期心跳，PING 携带 `clientId`。服务端先读取并验证 Redis 会话和登录版本，合法心跳再续期 `session:{clientId}` 与 `online:{user}`，同时刷新物理连接活跃时间；普通业务请求可以刷新连接活跃时间，但不默认续期逻辑会话。客户端按最近 PONG 判断服务端是否失联，服务端按最近活动扫描僵尸连接。异常断线时释放 socket、上传下载流等物理资源，但不立即删除仍可恢复的 Redis 会话；没有后续心跳时，会话和在线键分别按自己的 TTL 收敛。主动退出和注销则显式撤销会话，不能走异常断线的恢复路径。

#### 表达脉络（记忆钩子）

1. PING 携带 `clientId` -> 2. 校验会话和版本 -> 3. 合法心跳续期会话与在线键 -> 4. 双方按各自时间判断失联 -> 5. 异常断线只收物理资源 -> 6. 会话等待恢复或 TTL，主动退出直接撤销

判据边界：心跳超时不能单独区分断网、进程卡死和互踢，在线状态也不是瞬时一致。

#### 追问卡片

**详细业务实现链路（分步版）**

1. 客户端定时发送携带 `clientId` 的 PING，并记录最近 PONG 时间。
2. 服务端根据 `clientId` 读取会话，检查未过期、未撤销且版本有效。
3. 合法心跳刷新物理活跃时间，并续期 Redis 会话和在线键。
4. 客户端按最近 PONG 判断服务端失联，服务端按最近活动扫描僵尸连接。
5. 超时后在锁内收集连接、锁外关闭，避免回调重入连接表锁。
6. 异常断线释放 socket 和传输上下文，但保留仍在有效期内的逻辑会话。
7. 重连按会话规则恢复；没有恢复或心跳时由 TTL 清理，主动退出则立即撤销。

**记忆钩子**：心跳先验会话再续期，断线收物理、留逻辑，过期才清场。

- **TCP 自己有保活机制，为什么还要在应用层再加一套心跳报文？** 因为 TCP 保活回答的问题和我需要的不是一回事。保活是内核在维护的，周期通常长到以小时计、在 Windows 上还要改注册表或 socket 选项才好调，我要的是几十秒这个量级的判定，等不起。更关键的是它能证明的太少：链路中间的 NAT 设备、拨出代理这些常常能替内核应答保活探测，于是内核说“连接还在”，但我的服务端进程可能已经卡在事件循环里，或者对端程序早就崩了只是端口还被系统撑着；这种“通道通、应用死”的状态保活看不出来。应用层的 PING 是走完整收发路径的：它要能被对端取到、解析、按 `clientId` 找到会话并通过登录版本检查，然后回一个 PONG，这一圈跑通说明的是“对面那个程序还在正常处理报文”。顺带我还用它做了一件保活根本做不了的事——心跳校验通过时去续 `session:{clientId}` 和 `online:{user}` 的 TTL，把逻辑会话的存活和物理链路的存活绑在同一个动作上。代价是链路空闲时也有固定报文往返，连接数一多这部分开销要算进来，还要自己维护超时判定和误判处理，不像交给内核那样省事。
- **为什么不直接把业务请求当成心跳用，反正有请求就说明活着，还要单独发 PING？** 因为业务请求的节奏是用户决定的，而我要的探测周期是我决定的。用户可能挂在好友列表上一页不动，五分钟没有一条业务报文；如果只靠业务流量判断存活，这段时间里服务端要么把这条连接当僵尸收掉（误踢），要么完全不知道对端已经没了（僵尸占着资源），两种都错。固定周期的 PING 提供的是一条与业务量无关、时间可预期的信号，双方各自按“最后一次收到对方报文的时间”判失联，逻辑简单。我这边的分工是：普通业务请求可以刷新物理连接的活跃时间，因为能发请求当然说明链路通；但它不默认去续 `session:{clientId}` 的会话 TTL，会话续期只走心跳那条路径。这么切是为了让“逻辑会话活了多久”这件事只有一个来源，否则一个长任务连续传半小时文件就把会话 TTL 悄悄顶到无限长，我想按 TTL 收敛一份不再恢复的会话都做不到了。代价是有业务流量时那几次 PING 看着多余，报文略多一点点，但我换来的是判定条件只有一条、不用去推“这次业务请求算不算心跳”。
- **客户端放在那里没有任何用户操作，服务端怎么知道它只是空闲而不是已经失联？** 空闲和失联靠的是同一条与用户行为无关的周期信号：客户端登录之后就起一个定时器，每 30 秒自己发一个携带 `clientId` 的 PING，不需要任何点击触发；服务端每收到一次就把这条物理连接的最近活动时间往前推，同时校验会话和登录版本、续 `session:{clientId}` 与 `online:{user}` 的 TTL。所以我判定的依据是“最近 90 秒内有没有收到过它任何东西”，而不是“用户有没有操作”。这样两边都能把情况分开：连接在、PING 照常来，就是活着但空闲，在线展示继续挂着；连接看起来还没断但 PING 停了三拍，才判失联去回收。为什么不看 TCP 层的事件：链路静默断开时内核不一定及时通知应用，socket 可能一直“好看”地挂着，僵尸连接就是这么来的，只能靠应用层的周期报文加超时扫描识别。代价是空闲期也有固定往返流量，连接多时要算这部分开销；另外定时器挂在事件循环上，如果界面线程被长任务卡住，PING 也发不出去，会把“本机卡顿”误判成“失联”，所以耗时处理我都挪出事件线程，判据只放在 90 秒这个量级上。
- **正在传一个大文件的时候，会不会因为心跳没及时处理被误踢下线？** 按设计不应该，我防的就是“忙到没法发心跳”这一类误判。判失联用的是 90 秒窗口，30 秒一次的 PING 由定时器自己发，跟在不在传文件无关；传输过程中链路上本来持续有分块报文，服务端收到任何报文都会刷新这条连接的最近活动时间，所以正常推进的上传只会让活跃时间一直更新，不会往超时那边走。真会出问题的是另一种情况：事件线程被自己人堵住。把大块数据落盘、算校验这类耗时处理放在事件循环里同步做完，几十秒内定时器根本轮不到执行，PING 发不出去，服务端看就是三连拍静默，现象还像网络问题，很难一眼归因。所以我的规则是把耗时动作挪出事件线程，出站方向按拍推进、每拍只推一块，让发送循环始终有机会处理心跳定时器；超时判定用最近收到 PONG 的时间算，不是简单计失败次数。代价是真卡满 90 秒就会被判失联、连接被回收，这时候靠重连带 `clientId` 和恢复凭据走会话恢复，再用已经确认的偏移续传，不从头再来。
- **断电和网络黑洞这两种失联场景，你是怎么分别验证的？** 我构造三种断法，核对同一份清单。正常关闭：客户端点退出或直接关程序，服务端立刻收到连接关闭事件，回收 socket 和传输上下文，不留半开连接。连接复位：进程被强杀、链路回 RST，服务端同样能及时知道，但这条路径不算主动退出，所以不能撤销会话——我去 Redis 确认 `session:{clientId}` 还在、TTL 还在自己往下走，再让客户端重连一次，凭 `clientId` 和恢复凭据能免密回到登录态就对了。网络黑洞最难：用防火墙把这条连接的包静默丢掉，链路既不报关闭也不回 RST，看点是超时判定在两侧各自独立发生——服务端按最近活动时间扫到超过 90 秒收掉僵尸连接，客户端按最后一次 PONG 的间隔判失联、把界面切到未连接并把重连按钮放出来。然后核对物理资源确实回收（进程内连接映射表和文件句柄数量降回去，带前缀的日志能对上），而逻辑会话没被这次断线删掉，它只在 TTL 到点后才消失。最后撤掉黑洞：TTL 没过该恢复成功，过了就只能重新登录，两种都算正确。
- **既然怕业务把心跳堵死，为什么不干脆给心跳单独开一条 TCP 连接？** 我考虑过，但好处不多，代价实打实。好处只是“业务再忙，另一条连接上的 PING 照发”，可真正会堵住心跳的是事件循环被占住，把耗时处理挪出事件线程就解决了，换一条连接并不改变这一点。代价是：一条逻辑会话对应两条物理连接，`clientId` 到 `connId` 的绑定从一对一变成一对多，连接表、会话绑定和清理都得处理“业务连接断了但探活连接还活着算什么”“两侧超时阈值不一致时以谁为准”这类凭空造出来的状态；连接本身有握手、缓冲和句柄成本，数量直接翻倍，中间过 NAT 和防火墙时多一条长连接就多一处行为不一致的地方。最关键的是判定语义会分叉：我现在只有客户端最近 PONG、服务端最近活动两个时间戳，超时即失联，简单到不容易写错；拆两条就出现“一半活着”这种最难解释也最难测的中间态。真要做流控分离，也应该拆业务通道而不是给心跳单开一条。
- **被踢下线、网络断开和服务端假死这三种情况，客户端怎么区分？** 我用三种不同的证据分开，不让它们共用一个“连接异常”。被踢是有明确语义的：失效通知先到，或者下一次请求按 `clientId` 找到的会话里登录版本比数据库当前版本小，这是服务端给的确定结论，界面就写“账号已在别处登录”。网络断开只有链路证据——socket 报了断开，它只说明通道没了，所以只提示“连接已断开，可以点重连”，不能弹一句“账号异常”。服务端假死是第三种：连接还在、没收到任何断开事件，但按 30 秒周期发的 PING 一直没有 PONG 回来，超过 90 秒这个窗口我判成“疑似失联”，先降级界面、允许点重连；用“疑似”是因为同样现象也可能是本机休眠、中间设备丢包或对端整机卡住，超时只支持“该怀疑”，不足以指认原因。重连做成手动而不是自动也是这个理由：判据不可靠时自动重连会放大问题，一批客户端会在服务端刚恢复的瞬间一起涌回来，代价是恢复慢一点。
- **一次心跳 PING 过去，具体会续期 Redis 里的哪些键？** 只有两个，而且顺序不能反。服务端先按 `clientId` 读 `session:{clientId}`，确认会话存在、没被撤销、里面的登录版本还等于数据库当前版本，这个前置校验通过之后才做续期：把 `session:{clientId}` 的 TTL 推回完整时长，让这份逻辑会话能撑过下一次断线；再刷 `online:{user}` 的 TTL，让在线展示跟得上实际存活。校验不过就一条续期命令都不发——版本落后、已被踢掉或已注销的会话绝不能靠心跳续命，否则被顶掉的那端会一直把自己养着。验证码那一组 `cap:{clientId}:code/cool/fail/lock` 我明确不让心跳去碰：它们管的是取码和试错的节奏，靠自己的 TTL 到点恢复；心跳若能顺手延长它们，就等于让一个一直在线的客户端永远走不出冷却。物理连接的活跃时间是进程内记的时间戳，不进 Redis，也不代表逻辑会话有效。代价是每次心跳要一次会话读加两次续期，我把它合进同一次管道往返，好处是每个键的存活理由都很单一。
- **在线状态存在 Redis 里，好友列表要显示谁在线时怎么查，怎么避免一个一个键去问？** 先说查询：在线标记是 `online:{user}`，按账号名一个键，所以列表既不能按账号名去遍历键空间（Redis 上没有安全的遍历，扫 keyspace 会拖慢整个服务），也不能循环单条 GET——一屏 50 个好友就是 50 次往返，界面明显发顿。我用批量方式：一次 MGET 把这一屏要显示的账号名一起问掉，或者用管道把多条 GET 合进一次往返再按顺序解析回来，翻页时攒够一批再问，不在循环里发命令。就算这次批量读失败或者超时，我也只做一件事：把在线小圆点显示成未知，不动列表本身。因为在这套设计里在线键只承担展示，认证永远走 `session:{clientId}` 加登录版本那条路，读不到在线信息时权限判断不受影响——展示可以退化，安全不能退化。顺带划清三个含“在线”字样的东西：进程内的连接表管物理 socket 有没有活着，Redis 会话管逻辑会话和权限，`online:{user}` 只管绿点。代价是在线状态是拉取式的，两次刷新之间会有短暂不一致。
- **心跳周期为什么定成 30 秒一次、90 秒才算超时，而不是 10 秒或者 5 分钟？** 这两个数是一对权衡。30 秒的探测周期管的是“空闲时多久能发现异常”和“每条连接每小时发多少报文”之间的平衡：调到 10 秒，失联发现得快三倍，报文量、服务端 wake-up 和 Redis 续期操作同倍上涨，而大多数掉线本来就该由 TCP 关闭事件立刻报上来，不需要靠更密的心跳去抢那二十秒；拉到 5 分钟，一个僵尸连接就白占五分钟的 socket、缓冲和在线名额，用户看到的是“还在线但什么都发不出去”。90 秒取三倍周期，是为了容忍几次抖动：一次 PING 或 PONG 被丢、进程被系统调度或杀软拦一下、笔记本切个网络，都不该被误判成失联；只留两倍的话，一次丢包加一次重传就能凑出误踢。另外我把 TTL 跟这两个数分开配：`session:{clientId}` 的 TTL 按“允许断线多久还能免密恢复”来定，比失联判定长得多才有意义，`online:{user}` 的 TTL 只需要跟展示刷新节奏匹配。代价是故障发现延迟落在几十秒这个量级，即时性只能靠手动重连补上。
- **服务端进程启动的时候，跟心跳和在线状态有关的对账具体做什么？** 我把它限定成“把上一世遗留的物理状态清零，把逻辑状态留给 TTL 和版本去判”。启动那一刻，这个进程手里一条连接都没有，但数据库里的在线字段可能写着某人在线、`online:{user}` 可能还没过期，这些都是上一次进程被杀时来不及收的残段。所以先把“按最近活动扫描僵尸连接”的定时器起来，让后续新增的僵尸由它负责；再把展示层拉回事实：现在没有任何连接，就不该有人被算成在线，数据库在线字段和在线键都对齐到这个结论。第三步是我特意留白的地方——不去动 `session:{clientId}`：会话是按 `clientId` 存、带 TTL 的，它的存在恰恰是为了撑过服务端重启，如果因为“找不到对应 socket”就把它删了，等于每次重启强制全员重新输密码，跨连接恢复这个设计当场作废。会话该不该作废只由两个条件决定：数据库里的登录版本还等不等于它记的那一版，以及 TTL 有没有到。代价是启动后短时间内在线列表可能都显示离线，要等客户端各自重连、心跳把在线键重新写回来才好看。
- **服务端里哪些地方有权把一个账号写成离线？** 我把写权限收在三个发起方上，其它路径一概不许改。一是用户主动退出：服务端按 `clientId` 确认过会话、用会话里的账号受理之后，先看这个账号名下还有没有其它有效会话，没有才改在线状态。二是注销账号：那次会把这个账号相关的会话全部撤销，在线跟着清掉，不用再看剩几份。三是最后一个有效会话消失，也就是 TTL 到点或被新登录顶掉之后确认再无有效会话，由收敛那条路径更新。明确不许写离线的是这几类：某条物理连接断开，它只说明 `connId` 没了，同一份客户端可能马上重连接上，会话仍然有效；心跳超时同理，那是失联判定不是登出判定；还有被踢那条连接的延迟清理回调，它最容易出错，因为回调跑起来时很可能已经有一次新登录把在线写成了在线，它无条件改就会造成“明明登录上了却显示离线”。所以清理一律带条件：比较它预期的 `clientId` 和登录版本跟当前值一致才动手。代价是要接受“会话还在但没连接”这种在线显示滞后的中间态。
- **`clientId` 是客户端自己生成、每次请求都带上来的，能把它当成可信的设备身份吗？** 不能，我把它定位成关联键而不是身份凭证。它是首次启动时客户端用随机源生成的一个 UUID 存在本地、之后每个请求原样带上来的，服务端没有任何办法验证这个值确实来自我第一次见过的那台机器——它可以被复制走、被清空重新生成，也能被脚本随手伪造。真当可信身份用，就等于把“你是谁”这个结论交给客户端随口声明：拿到别人的 `clientId` 就能声称是那个客户端，或者每次违规后换个新的重来。所以我的信任链建立在服务端能自己核对的东西上：口令校验证明凭据、数据库原子分配的 `loginVersion` 确定代次、恢复流程再核一份存在会话里的恢复凭据校验值，`clientId` 只负责把这几样串到同一条会话记录上。它适合做的确实是关联：把验证码的 `cap:{clientId}:code/cool/fail/lock` 归并到同一份客户端、让重连不重置计数、让踢人时能定位要撤哪份会话。代价是挡不住“换标识”这条路，所以跨实例的频率约束我要叠加账号维度失败比例、来源 IP 异常这些服务端自己观察得到的信号。
- **如果要允许多端同时在线，心跳和在线状态这一块需要改什么？** 现在这套是照“一个账号一份有效会话”写的，改多端要动三处。第一处是判定依据：`session:{clientId}` 这个形状本身能并存多份，问题在心跳和业务请求都拿会话里的登录版本去比数据库当前版本，多端并存时后登录那端会把先登录的几端一起判成过期；所以版本不能只表示“哪次登录最新”，要换成全局撤销代号加每份会话自己的有效标记，正常登录只推进自己的状态，改密码、注销这种要踢全端的操作才推进全局代号。第二处是心跳续期：PING 带的还是 `clientId`，续的也只是自己那一份会话的 TTL，这部分反而更清楚，各端独立存活、独立过期。第三处是在线和离线：`online:{user}` 不能再由一次退出或一次超时直接写离线，要变成按账号聚合的结果；每次有会话建立、失效或 TTL 到点时去看这个账号名下还剩几份有效会话，从有到无那一刻才算离线。代价是撤销、注销、对账、展示都得同步换判定，所以我现在按单端在线收口。
- **既然 `online:{user}` 能查到某个账号在线，能不能直接拿它当认证依据，省一次会话检查？** 不能，这两件事的强度差得远。在线键回答的是“这个账号现在值不值得在列表上显示一个绿点”：按账号名存，谁都可以读，里面没有任何只有客户端才持有的材料，TTL 也只跟刷新节奏有关，不反映任何认证结论。认证我这边要核对的是三样：按 `clientId` 找得到的 `session:{clientId}` 里认证状态是有效的、随请求带上来的恢复凭据跟会话里存的校验值一致、会话记的登录版本还等于数据库当前版本。如果允许用“在线”放行，就会出现几种实在的漏洞：别人账号在线，我只要发个带那个账号名的请求就过去了，等于完全不做认证；一个已经被踢、会话撤销掉的旧连接，会因为在线键还没到期就继续被当成合法。安全结论和展示结论必须分开，这正是我把它俩拆成两个键的原因：在线读不到时列表显示未知、界面照常能用，会话读不到时请求必须拒。代价是我要接受两者短暂不一致，刚被踢的一端可能还挂在在线列表里，要等清理或 TTL 才消失。

### 08. 手动重连与会话恢复

#### 功能目标

断线后先恢复传输通道，再尽可能恢复同一客户端原有的认证会话；会话不可恢复时回退到完整登录，同时保留可解释的任务结果。

#### 主回答（完整业务实现链路口述版）

连接失联后，客户端停止在途任务并保存快照，清理旧 socket 和拆帧状态，再重新建立 TCP/TLS 连接。通道建立后，客户端携带原 `clientId` 和会话恢复凭据发起恢复请求。服务端查询 `session:{clientId}`，核对恢复凭据、会话未过期、未撤销且 `loginVersion` 仍为最新。校验通过就把原账号会话绑定到新 socket，不重新取码、不推进版本，也不触发互踢；随后恢复页面并核对未完成任务。若会话不存在、已经退出或注销、被互踢、恢复凭据错误或 TTL 到期，则回退到验证码加账号密码登录。

#### 表达脉络（记忆钩子）

1. 停止任务并保存快照 -> 2. 重建 TCP/TLS 通道 -> 3. 携带 `clientId` 和恢复凭据 -> 4. Redis 校验会话、状态和版本 -> 5. 成功绑定原会话，失败回退完整登录 -> 6. 恢复页面并核对任务

失败分支：握手失败、会话恢复失败、重新登录失败和任务恢复失败分别处理，不混成一个“重连失败”。

#### 追问卡片

**详细业务实现链路（分步版）**

1. 失联后停止在途任务，保存续传数据、任务快照和原 `clientId`。
2. 清理旧 socket、心跳和拆帧状态，重新完成 TCP/TLS 握手。
3. 客户端发送 `clientId` 和会话恢复凭据，不先提交账号密码。
4. 服务端读取 Redis 会话，核对凭据、撤销状态、TTL 和最新登录版本。
5. 校验通过，把原账号会话绑定到新 `connId`，不推进版本、不重新取码。
6. 校验失败则回到完整登录；主动退出、注销和被互踢的会话禁止恢复。
7. 会话恢复后重建页面，再按当前数据确认传输起点和任务结果。

**记忆钩子**：先连线，再拿证；会话在就续，不在就重登，任务另核对。
- **断线之后你为什么做成用户手动点重连，而不是让客户端自己静默自动重连？** 因为我判失联的依据本身不可靠。失联是从“超过 90 秒没有收到对方的东西”推出来的，同样现象也可能是本机休眠、切网络或者服务端在重启，它只支持“该怀疑”，不支持“确定对端没了”。这种判据下做静默自动重连有两个害处：一是打断用户，正打字或者正在传文件时界面突然闪一下、任务被中止又重启，比停在那里等一只手点更难受；二是一批客户端在服务刚重启那刻全部自动回连，等于把重连做成风暴，反而把刚起来的实例再压一次。所以我让界面明确降级成未连接、把原因和下一步写出来，由用户点重连，这一次点击同时是“用户现在要用”的意图信号。要分清一件事：手动重连不等于重新输密码。点击之后走的是通道重建加会话恢复，服务端按 `clientId` 找到 `session:{clientId}`、核对恢复凭据和登录版本，通过就免口令回到原来的登录态。代价是用户不在屏幕前时不会自动恢复，在途任务带着续传信息停在可解释的失败态，等他点一下再接上。
- **重连之后为什么还能沿用原来那个 `clientId`，不必当成一次新登录？** 因为逻辑会话不属于那条 socket，属于 `clientId`，而且它存在 Redis 里、不随连接销毁。断线时消失的是 `connId` 和它的缓冲区、拆帧状态这些物理东西，服务端先前写好的 `session:{clientId}` 还在 TTL 内、里面的账号和登录版本也还在。新连接建立起来后我做的事情只是换绑定：把新的 `connId` 挂到原来那份会话上，会话本身完全不动——所以它跟“不同客户端的新登录”是两条路径，后者要推进 `loginVersion`、要把旧那份顶掉，前者不推进版本，只是同一份会话换个传输通道。不这么设计的话，任何一次几十秒的网络抖动都得让用户重输密码、重过验证码，跨连接恢复这个目标就没有意义了。但身份可以沿用不等于信任自动成立：恢复时要单独递一份只在登录成功那一刻下发过的恢复凭据，服务端比对 `session:{clientId}` 里存的校验值，还要确认这份会话没被撤销、版本仍是数据库当前那版，三项全过才绑定。代价是本地要多保存一份恢复材料，我只放恢复真正需要的那几项、存在当前用户配置目录下，口令永不落盘。
- **会话恢复时服务端具体去 Redis 读哪些东西、按什么顺序核对？** 读的就是一份 `session:{clientId}`，里面装着账号、登录版本、认证状态、恢复凭据校验值，再加键自己的 TTL。核对顺序我固定成由便宜到贵、由外到内：先看这个键在不在，不在就是没得恢复，直接回“需要重新登录”；在的话看认证状态，被撤销过（主动退出、注销、被踢都会走到这里）同样拒；再比对请求带上来的恢复凭据跟里面存的校验值是否一致；最后拿会话里的登录版本去跟数据库当前版本比，落后就拒并顺手把这份旧会话清掉，免得它继续被心跳养着。四项都过才把新的 `connId` 绑到这份会话上、把 TTL 续回完整时长。为什么不是一次性比完而是分这几步：每一步失败原因不一样，返回给客户端的语义就不一样，糊成一个“恢复失败”用户就只会反复重试。代价是这里要读 Redis 一次、读数据库版本一次，恢复频率本来很低，我认为换来可解释的失败原因值得。
- **如果 Redis 里只剩 `online:{user}` 这个在线键、`session:{clientId}` 已经不见了，还能恢复登录吗？** 不能，这种“只剩在线”的状态完全可能出现，我不会拿它当依据。在线键的 TTL 只跟展示刷新挂钩，它的存活不代表任何认证结论；会话键带自己的 TTL，过期、被撤销、注销时被清掉都可能，两者生命周期不同步。恢复的入口条件很明确：必须按 `clientId` 读到一份会话，里面的认证状态是有效的、恢复凭据校验值对得上、版本还等于数据库当前那版，缺一个就回“需要完整登录”。为什么不加个查数据库在线字段的兜底：那等于给认证开了第二条路，而这条路上没有任何只有客户端才持有的材料，只要猜中一个账号名或者 `clientId` 就能过，前面所有会话和版本设计都白做。残留的在线标记由它自己的 TTL 到期或启动对账收掉，我不为了让列表好看去反推权限。真要排查，我会先看服务端日志里这次恢复卡在哪一步——是键不存在、状态被撤销还是版本不匹配，前两种要重新登录，最后那种还得提示这次登录已在别处被顶掉，界面上不能混成同一句“请重新登录”。
- **恢复请求只要把 `clientId` 带上，服务端不就知道该恢复谁的会话了吗，为什么还要一份单独的恢复凭据？** 知道恢复谁，和有权恢复谁，是两件事，`clientId` 只能回答前者。它是客户端首启时自己生成、明文存在本地、每个请求原样带上来的一个 UUID，服务端没有任何办法验证它的来源：能被复制、被清掉重新生成，也能被脚本随便编一个。如果凭它就放行，等于任何拿到这个字符串的人都能续上别人的登录态。所以我把它定位成查找键：服务端用它去 Redis 取 `session:{clientId}`，这一步只确定“要核对哪一份状态”。真正的授权由另外三样给：请求带上的恢复凭据要跟会话里存的校验值一致，这是只有那份客户端持有、服务端只存校验值的东西；会话的认证状态不能是已撤销；登录版本还得等于数据库当前版本，用来挡住“凭据仍然正确但登录代次已被替掉”这种情况。代价是本地要多保存一份恢复材料，我只存恢复真正需要的那几项、放在当前用户配置目录里，口令和摘要一概不落盘；公用机器上这种场景本来就该走完整登录而不是免口令恢复。
- **用户点了重连、界面重新连上了，这算登录成功吗？** 不算，我把它拆成两个独立的阶段，各有各的成功条件。第一段是通道恢复：清掉旧 socket 和拆帧残留、重做 TCP 握手，TLS 的话还要完成加密协商，这一步只说明“我又能跟服务端说话了”，一个字的权限都还没有。第二段才是会话恢复：在这条新连接上带 `clientId` 和恢复凭据发一次恢复请求，服务端读 `session:{clientId}`，核对认证状态未撤销、凭据校验值一致、登录版本仍是数据库当前那版，通过了才把新的 `connId` 绑到原来那份会话上，从这一刻起客户端才重新进入已认证状态，界面才允许拉好友、云盘这些要鉴权的数据。这两段不能合成一步的原因很实在：握手成功的报文里没有任何认证依据，如果把“连上了”就当登录态，那条连接就成了一个匿名通道却被赋予权限。所以我的状态机上“已连接”和“已认证”是两个状态，界面提示也跟着分：握手没成是“连接不上”，恢复被拒是“登录状态已失效、请重新登录”。代价是多一次往返、重连时间略长，而且任务恢复必须放在会话确认之后，顺序不能颠倒。
- **哪些情况下会话恢复一定失败、必须回到验证码加口令的完整登录？** 我按恢复流程那几步核对，任何一步不过就回退：按 `clientId` 在 Redis 里找不到 `session:{clientId}`，包括 TTL 过期和被对账收回；找到了但认证状态是已撤销，也就是用户主动退过出、账号注销过、或者被新登录顶掉过；请求带上来的恢复凭据跟会话里的校验值不一致，比如本地那份文件被删了或改动过；最后是会话里记的 `loginVersion` 比数据库当前版本小，说明期间发生过一次更新的登录。通道本身没建立起来时无所谓回退，那时连恢复请求都发不出去，界面停在“未连接”而不是“要重新登录”，这两种提示我不混。回退之后是完整的登录流程：重新取验证码、按 `clientId` 走那套校验、重新验口令、数据库分配新版本、写一份新会话。这里有个我要控制住的诱惑——“凭据不对但会话还在，能不能只让用户重输口令、跳过验证码”，答案是不能：验证码这一层防的是自动化重试，恰恰在最像异常的情况下最不能省。代价是这几种情况用户都得重填一次，但失败原因分开返回，界面上能说明白为什么这次要重登。
- **同一份客户端断线后重连，会不会触发互踢、把自己别的连接顶掉？** 不会，因为互踢只在“新登录推进版本”这个动作上发生，而恢复路径根本不碰版本。恢复流程是拿 `clientId` 找到那份既有的 `session:{clientId}`，核对恢复凭据、认证状态和登录版本，通过就把新的 `connId` 绑上去，数据库里的 `loginVersion` 一动没动——既然没有更新的代次出现，就没有任何一份会话会因为这次重连被判成过期。这条区分是我刻意设计的：断线重连是同一份客户端的延续，换设备或者在登录页主动重登才是“替换会话”，后者会分配新版本。边界要说清：如果这次“重连”实际上走了完整登录（本地恢复材料没了或会话已过期），那它就真是一次新登录，会推进版本、顶掉这个账号名下的旧会话，这是应有的结果，不是误踢。另外同一份客户端如果因为异常同时挂着两条连接，恢复新连接不会踢掉旧的，旧的要靠失联检测或者下一次请求上的版本与会话检查来收。代价是客户端要把恢复和重新登录分成两条明确路径，绝不能在恢复失败时偷偷降级成一次静默完整登录。
- **会话恢复成功之后，之前中断或者失败的那些传输任务会自动全部续上吗？** 不会自动全续，会话恢复只把“我是谁、我有什么权限”这件事还原了，任务能不能接着跑要逐项核对。核对的清单是这几样：源文件还在不在原来的路径、有没有被用户改名或改动（拿快照里记的文件标识和大小去比，不一致就不敢续）；服务端那边那次上传会话记录还有效吗、已经确认收到的偏移是不是还和我本地记的一致，对不上就回退到双方都认可的那个位置；下载方向要看已经落地的分块和临时文件是否完整，缺的分片重新要；任务状态本身以服务端返回为准纠正本地快照。所以恢复之后界面是任务列表从快照重建出来、一条条标成“待核对”或者“已停止”，由用户点继续。为什么不自动续：一是几十个任务同时涌进来会冲击出站队列，比正常使用时更冲击；二是失败的语义会被抹掉，用户不知道刚才其实断过。代价就是要多点几下，但偏移对得上的任务确实能从断点接上，不用整个文件从头再传。
- **会话恢复成功之后，客户端怎么把界面重新填起来？** 原则是一句话：本地快照只用来占位和解释，内容一律重新向服务端拉。会话恢复给我的是账号和有效权限，我按这个账号重新发一轮状态请求：好友列表和在线情况、群和成员、云盘目录，其中好友与在线列表按分页取。为什么要重新拉——断线那段时间服务端可能已经变了：有人把他移出群、文件在另一处被改名，旧内存里的界面和真实状态对不上，用户会照着过期的界面去做操作，然后一路撞错误。本地快照留着做三件事：任务列表按会话记录重新对一遍状态和偏移，能对上才允许续传；正在输入的文本和滚动位置这类纯界面状态恢复回去；断线期间没发出去的草稿单独列出来让用户决定发还是删，我不静默重发，因为一条已经送达的消息再走一次就成了重发事故。代价是恢复完成后要先跑一批请求、界面有几秒钟不完整，我用明确的“正在同步”提示，比给他一份看着齐全但其实过期的列表诚实。
- **用户是主动点退出下线的，之后重连时还能免口令恢复这次会话吗？** 不能，而且我在客户端就把这条路堵掉，不让它去试。退出和异常断线在界面上都是“连接没了”，但在服务端留下的证据完全不同：异常断线只是 `connId` 消失，`session:{clientId}` 还在 TTL 里、恢复凭据仍然有效；主动退出那一次服务端已经按会话里的账号和版本撤销了这份会话、连带恢复凭据的校验值一起失效，恢复流程连“找到有效会话”这一步都过不了。所以客户端在用户点退出成功后就清掉本地那份恢复材料、把状态机停在“未登录”，重连按钮根本不出现，只留一个去登录的入口。原因很直白：如果界面还挂着“重连”、背后又拿一份注定被拒的凭据去试，用户看到的就是“点了没反应”，日志里全是本该发生的失败。恢复被拒的原因我也是分开返回的，被撤销、版本落后、找不到会话、凭据不匹配各说一条。边界是用户在退出瞬间正好断网、请求没到服务端，那份会话就还活着，重连确实能恢复——这时按异常断线处理是我认的语义。
