
# 群与成员管理：14—23

实现定位：[群管理界面](../Client/group.cpp)、[群协议解析](../Server/msghandler.cpp)、[群业务与事务](../Server/operatedb.cpp)、[在线群事件分发](../Server/mytcpserver.cpp)。`group_info`（群信息表）、`group_member`（群成员表）、`group_invitation`（群邀请表）共同维护状态；群主、管理员、普通成员分别对应 owner、admin、member（群角色值）。

### 14. 创建群

#### 功能目标

建立群，并同时赋予创建者群主身份，避免出现“群已创建但没有群主”的半成品。建群请求先过连接级群请求号判重：建连后双方记录都置 0，第一个群请求从 1 起编，之后每个动作加 1。同一次动作的重发沿用原号（避免重复执行，代价是拿不到结果），已经收到失败应答后的新尝试必须换新号；服务端只受理大于记录值的号，受理后把记录更新为该号，同号或更小的重发直接丢弃、不执行建群事务。

#### 主回答（完整业务实现链路口述版）

用户在群管理页面输入群名称，客户端校验非空及 UTF-8 长度，取下一个群请求号——一次建群动作只分配一个号、重发不换号——发送创建群请求，请求正文带群协议信封（群协议版本、信封长度、请求关联号），建群尚无群标识，创建者不能由客户端任意指定。服务端先完成拆帧、连接认证上下文与登录版本核验，再由群协议入口检查信封和参数边界并比较群请求号，小于等于已记录值判为重发直接丢弃，不进入建群事务。通过后群生命周期操作以认证主体作为群创建者，取得数据库连接租约并开始事务、复核群名称，事务插入有效群组记录取得群标识，再插入创建者的有效群成员关系并把群角色设为群主，任何步骤失败均回滚。请求号在受理时就已推进到本连接记录里、提交阶段不再重复记；数据库提交后返回新群标识和结果码，界面不依赖先填一条本地群记录，群必须由服务端返回。服务端封装创建群响应并保留请求关联号，客户端据此匹配本次动作，成功时刷新群列表并允许进入群摘要、成员或群聊页面。名称非法、写库失败或响应超时分别提示；建群没有业务幂等键，重发只有两种结局——沿用原号会被判重丢弃、拿不到结果，换新号则是一次新的建群动作、可能再建一个群，因此超时不等于没创建，正确做法是先拉群列表核对；若连接已断，走重连流程，重连后不重放建群动作，只按服务端群列表恢复。

#### 表达脉络（记忆钩子）

1、输入群名校验取请求号 -> 2. 发请求带信封无群标识 -> 3. 拆帧验认证比较判重 -> 4. 事务建群插群主关系 -> 5. 提交返群标识刷新列表 -> 6. 超时拉列表核对不重放

失败分支：名称非法、写库失败、超时分别提示；同号重发被丢弃，换号等于一次新建群动作

#### 追问卡片

- **我这个建群流程，为什么不在插入群记录之后再异步把创建者加成群主，而要在一个事务里做完？** 因为异步方案会留下“群已存在但还没有群主”的窗口，我选择用同库短事务一次做干净：建群事务先在 `group_info` 插入有效群组记录拿到 `group_id`，紧接着在 `group_member` 插入创建者的有效成员关系并把 `role` 置为 owner，任何一步失败整个事务回滚，库里不会留下半成品。如果拆成两步，中间窗口里所有权限判定都会落到“无主群”这个特殊分支，转让、解散、设置角色的代码都得额外处理“群主缺席”，而且第二步失败还要引入补偿逻辑去对账补插。同事务的代价是这两个写入必须一起成功、事务稍长，但两条都是本地 MySQL 的单行插入，锁持有时间可忽略；换来的不变量很值钱：只要群存在，群主必然存在且唯一，后续任何分支都可以直接假设群主在场。
- **两个人建了同名群，服务端会当成重复群拒绝第二个吗？** 不会，群的唯一身份是服务端分配的 `group_id`：建群事务往 `group_info` 插入记录时拿到自增标识，两个同名群就是两条不同标识的记录，各自有独立的成员关系、消息序号和群版本。我不给群名加唯一约束，因为群的稳定身份是成员与版本而不是展示名——名字将来允许修改，唯一性绑在名字上，改名或解散重建就要连带迁移引用；且权限判定全按 `group_id` 走成员表，名字唯一对安全性没有贡献。同名只是用户在列表里分不清，靠界面展示创建时间和成员数解决，属展示层问题，不下沉成数据库规则；所以“全服是否唯一”这类限制在当前业务里不存在，我也不臆造一个。
- **建群请求的响应在网络上丢了，客户端把同一个请求重发一遍，一定不会多建一个群吗？** 只要沿用原群请求号重发就不会执行第二次：服务端在群协议入口、进业务事务之前比较请求号，小于等于本连接已记录值的直接判为重发丢弃，建群事务根本不会跑。但要说清楚另一面：被丢弃的重发也拿不到原来的应答——服务端不保存、不回放上次结果，所以客户端依然不知道群到底建没建成，建群不能靠重发来补应答。正确的恢复动作是换一次新请求去拉自己的群列表（协议 78），服务端按认证主体查 `group_member` 关联 `group_info`，对照想建的群名和创建时间确认是否已建成，拿到群标识后再进入会话。建群没有业务幂等键，重发的两种结局——原号拿不到结果、新号可能再建一个——最终都只能靠查询当前状态来收口。
- **建群报文里能不能带一个字段指定创建者，替别人建一个群？** 不能，服务端不读报文里的任何“创建者”字段，群创建者一律从这条连接的认证上下文派生。群协议入口先核验连接认证上下文和登录版本，然后群生命周期操作把认证主体写成 `group_info` 的创建者、同时以 owner 角色插入 `group_member` 的成员行，这两处身份是同一个来源，链路上没有给客户端留“代填他人”的入口。如果创建者能由报文字段指定，任何人都能替别人建群、伪造归属，把群主的管理责任和后续解散权限安到无关账号头上，鉴权模型直接被击穿。这也是我全部群协议共同的写法：报文可以表达“做什么、对谁做”，但“我是谁”永远取自连接绑定的身份，不接受自报。
- **建群请求超时或响应丢失，客户端怎样恢复界面？** 不靠重发建群来恢复：换号重发等于一次新建群动作、可能再建一个群，同号重发只会被判重丢弃、拿不到结果。正确动作是新起一次查询——给当前账号发群列表请求（协议 78），服务端按认证主体查 `group_member` 关联 `group_info` 返回全部有效成员群，客户端拿返回的群名和创建时间与刚才想建的那个对照：命中说明其实建成了，刷新列表、拿到服务端下发的群标识再进入摘要或群聊；确认没有，才提示创建失败，允许用户换新请求号重新发起一次建群。在核对完成之前界面保持“创建中”状态，不能先在本地插一条群记录占位——群标识只能由服务端事务产生，本地伪造的占位记录会让后续所有按群标识定位的请求打到不存在的群上。
- **群管理统一信封中的请求关联号，为什么不等于所有群操作已经幂等？** 它提供的是连接级去重：只受理大于本连接已记录值的请求，同号或更小的重发直接丢弃，所以同一连接上的一次动作不会被重复执行。但它不保存也不回放上次结果，连接一断计数就重新协商，跨实例还要换共享存储，因此不等于通用幂等；群消息的 `client_msg_id` 和邀请的 `request_key` 负责的才是带结果回放的业务幂等。
- **这个项目的群管理，为什么所有动作要套一个统一的协议信封，而不是每个动作各定一套报文？** 一句话：公共逻辑进信封、差异字段进操作体、所有动作进同一个入口。我的群报文外层是固定信封——协议版本、信封长度、请求关联号、群标识——管四件公共的事：帧解析、请求与响应匹配、连接级请求号判重、按群标识定位群组；内层操作体承载各动作的差异化字段，比如邀请带目标账号、设置角色带角色枚举值。好处是所有动作都走同一个入口 `MsgHandler::groupRequest()`，共用同一套拆帧、认证上下文核验、请求号判重和结果码回包流程：新增动作只需扩展操作体和业务分支，不必重写接入与应答骨架，也不会出现某个动作漏做信封校验或判重这种单点失误。版本号还承担能力识别：服务端据此知道对面客户端会讲哪一版协议，将来加字段或加动作时，旧客户端至少能正确识别信封并安全拒绝或忽略未知操作体，不会因协议碎片化导致解析错位。代价是每个简单动作也要带信封和结果码，报文大几个字节，在本项目体量下可接受。
- **服务端广播群事件时，通知目标名单为什么必须和权限检查用同一个成员关系来源？** 结论：授权和通知必须都落在 `group_member` 的当前有效成员数据上，各信一份名单就会分叉。我的实现里，权限检查拿认证主体查这张表的 `status` 和 `role`，提交变更后广播成员变更事件（协议 84）的目标集合也是从同一张表查出当前有效成员，两处天然一致。假如权限查库、广播却使用客户端提交的旧名单，会有两个具体后果：已被移除的人还在旧名单里、继续收到群事件，等于群内信息泄露给非成员；真正的新成员不在旧名单里、反而漏收变更，视图长期滞后。更糟的是客户端名单可被篡改，攻击者能把自己塞进任意群的通知目标。都从服务端查的代价是每次通知多一次成员查询，当前规模可忽略；边界是目标集合在提交后查询，查完到送达之间刚被移除的人可能收到最后一条事件，语义无害——他下一次请求仍会被拒。
- **有人猜到或乱填了另一个群的 `group_id` 放进报文，能直接操作那个群吗？** 不能。群标识在这套协议里只是定位输入，决定“操作哪个群”；决定“能不能操作”的是连接认证上下文和该认证主体在这个群里的当前角色。服务端拆帧后先核验认证上下文与登录版本，再用连接绑定的认证主体去 `group_member` 查这个 `group_id` 下的行：没有行、或 `status` 不是 active，就按“非成员”结果码拒绝，业务分支根本不执行；有行时再按 `role` 判断这个动作允许不允许。攻击者可以枚举编号，但枚举不出别人连接上的认证身份，也改不了数据库里的角色，所以“编号存在”永远不会被当成“可以执行”。代价是每个请求都多一次 `(group_id, user_name)` 主键点查，这个成本我认为必须花：它把授权边界收敛到服务端一处，判断依据只有库里事实，没有任何客户端可影响的输入。
- **把群请求号这条横向机制一次讲清楚：它存在哪、怎么编、怎么判、怎么失效，最后为什么仍然只是去重而不是幂等？** 分四层说。①**存哪**：每个群请求号是连接级会话状态，放在服务端该连接的内存记录里，不落数据库、不进任何业务表——它描述的是"这条连接上这个动作要不要执行"，不是"这条业务记录存不存在"。②**怎么编**：客户端建连后本地计数从 0 起，第一个群请求取 1，之后每个动作取一次就加 1；关键约定是"一次动作只取一个号、同一次动作的重发不换号"，只有收到失败应答后决定另起一次新动作时才换新号。③**怎么判**：请求在群协议入口拆帧、认证、信封校验之后、进入具体业务事务之前，把携带的请求号与本连接已记录值比较——受理大于记录值的号，受理后立刻把记录推进为该号（先推进后执行），小于等于记录值的同号或更小号判为重发、在入口直接丢弃、不执行建群事务。④**怎么失效**：连接断开即会话结束，重连后双方计数重新从 0 协商，这条防线不跨连接延续。收口：正因为它是"比较并推进、不保存也不回放上次结果"，所以同一连接上的一次动作不会被执行第二次（去重），但丢弃的那次重发也拿不到结果——想要"重发还能拿到原结果"必须靠 `client_msg_id`、`request_key` 这类带结果回放的业务幂等键，那才是幂等；请求号本身只是连接级去重，两者不能混为一谈。

### 15. 查看、刷新自己的群列表

#### 功能目标

返回当前账号仍具有效成员关系的群，并展示其群状态和角色。查询范围不是所有群，也不是只依赖客户端缓存。群列表请求同样带群请求号，重复刷新只会执行一次，不会叠加多次查询和多次渲染。

#### 主回答（完整业务实现链路口述版）

客户端登录成功或用户点击刷新时，取下一个群请求号向服务端发送群列表请求，收到群成员变更事件时也可触发刷新。服务端完成拆帧、认证状态和登录版本核验，检查群协议信封并比较群请求号判重，再把认证主体交给群生命周期操作。数据库通过群成员关系关联群组，按认证主体筛选有效成员关系，读取群标识、群名称、群状态、本人群角色和群版本，按群更新时间排序；群状态与成员状态分别返回，有效成员关系不自动说明群仍可写，已解散群的成员关系可能继续展示。服务端将记录数与变长群记录装入响应并写回请求关联号，数据库连接租约在查询结束后归还。客户端按数量和字段长度检查响应，替换群列表展示数据，保留群标识用于后续打开群聊或群文件，不能只用展示名称定位群。查询失败或超时不能伪装成权威空列表，之后的群管理、消息和文件动作仍独立核验当前成员关系与群状态。

#### 表达脉络（记忆钩子）

1.登录或刷新取号发请求 -> 2. 拆帧验认证比较判重 -> 3. 按认证主体查有效成员 -> 4. 关联群信息按更新排序 -> 5. 装响应回关联号校验替换 -> 6. 失败不伪装空列表独立核验

失败分支：查询失败或超时不能伪装成空列表；成员事件只是提醒，漏收靠刷新重建

#### 追问卡片
- **客户端已经收到群成员变更事件了，为什么还要再发一次群列表查询？** 因为在我的设计里事件只负责提醒“数据变了”，不负责告诉“数据现在是什么”。成员变更事件（协议 84）携带的是群标识和群版本这类提示信息，客户端收到后做的动作是触发一次群列表（协议 78）或成员列表（协议 80）查询，服务端按认证主体查 `group_member` 关联 `group_info`，返回带群名、群状态、本人角色的完整当前行，客户端整体替换展示数据。我不在事件里携带完整数据、让客户端做增量修改，因为入群、退群、移除、角色变更、解散每一类变更都要被正确序列化并在客户端正确回放，事件一旦漏收或乱序，本地视图就和数据库永久分叉；改成“收到提醒就重查、一切以库为准”，客户端不需要理解变更语义，逻辑简单得多。代价是多一次请求往返，换来的是任何事件丢失都能被下一次刷新纠正。
- **客户端漏收了一次群成员变更事件，群列表会不会从此一直是错的？** 视图不会自愈，但一定能重建：我的事件是在线即发即弃——只投递给当时在线的有效成员，不落库、不补发、不重试，离线或瞬时丢失就是丢了。但展示数据的权威来源始终在数据库，用户点一次刷新，或者重新登录后客户端自动发起群列表查询，返回结果整体替换本地数据，之前漏掉的任何事件在这一次全部被覆盖。所以我这套对实时性的声称只到“最终一致”：漏刷新的窗口内界面可能显示已经解散的群或已离开的成员，但所有后续动作仍以服务端每次核验为准——旧列表里点进已解散的群，写操作会被群状态和成员关系检查拒绝，不会产生越权。要让事件本身可靠就得持久化加序号加补拉，等于为一个刷新就能解决的功能重建一套可靠消息，我认为不划算。

### 16. 查询群摘要

#### 功能目标

获取指定群的简要信息，供界面展示和后续状态同步使用。摘要查询仍是受成员权限约束的业务读取，请求同样经群请求号判重。

#### 主回答（完整业务实现链路口述版）

用户选中群组或打开相关详情，客户端取下一个群请求号，连同群标识封装群摘要请求。服务端拆帧并检查认证状态、登录版本和群协议信封，比较群请求号判重后，禁止以客户端填写的账号名代替认证主体。群生命周期操作通过群标识定位群组，检查群存在及认证主体仍有有效群成员关系，不存在、非成员和数据库故障按结果码返回；数据库读取群名称、群状态与群版本并统计有效成员数量，这是只读查询，不修改群版本或成员状态。服务端封装群摘要响应，回带请求关联号和群标识；客户端验证响应后更新详情，不把缓存中的角色展示当成后续操作授权，若收到群成员变更事件或主动刷新，再次查询摘要与成员列表。

#### 表达脉络（记忆钩子）

1.选群组取号带群标识发 -> 2. 拆帧验认证比较判重 -> 3. 禁客户端填账号代主体 -> 4. 定位群核验存在与成员资格 -> 5. 读群名状态版本统计成员 -> 6. 回响应刷新详情角色只展示
失败分支：不存在、非成员、数据库故障分别返回；摘要推不出消息末序号、已读与未读

#### 追问卡片

- **打开群详情时，为什么还要再查一次群摘要，直接用群列表里已有的数据不行吗？** 列表数据在那一刻已经是历史快照。群列表是刷新那一瞬间的批量结果，从选中群到打开详情之间，群可能已改名、成员可能已进出、甚至群已解散，直接吃缓存等于在详情页展示过期事实。所以打开详情要发一次群摘要请求（协议 86），服务端按 `group_id` 读 `group_info` 的群名称、群状态、群版本，并从 `group_member` 统计有效成员数，返回的是查询时刻的权威值。我也不在这一步顺带拉完整成员列表：摘要只要展示字段加一个计数，轻量便宜；成员列表是用户真要挑管理对象时才单独请求的。代价是多一次请求往返；边界是摘要返回后到界面展示之间仍存在微小变化窗口——摘要能证明的是“读取时如此”，展示可以信它，写不写得回去仍由每个操作当场核验群状态与成员关系。
- **群摘要返回的群名称、状态和成员数，能保证来自同一瞬间的一致快照吗？** 不能严格保证。摘要里的群字段读取和成员统计在服务端是一次只读查询，这条查询看到的是它开始时刻的数据库快照：之前提交的变更可见、之后提交的要到下一次才可见，反映的是“读取时间窗内的某个瞬间”，不是和其他并发请求协调过的定格画面。我没有为这次读取包显式长事务或做事后版本核对，因为拿到的是展示字段的严格同时性，付出的是群记录被共享持有、并发写被拖慢，而展示场景本来就容忍秒级陈旧。所以我能声称的口径是：摘要返回时这些值同为库内事实，误差只有一个查询往返；客户端不基于摘要做跨字段的一致性判断——比如拿成员数非零去推断群还能写——能不能写永远看群状态字段和后续操作自己的校验。
- **群被解散之后，再查它的群摘要，服务端返回什么、界面应该怎么做？** 摘要还能查，但群状态字段会明确告诉客户端这是终态。解散只把 `group_info` 的状态改成已解散，成员关系行不会立即删除，所以有效成员仍能取到群名、群状态和当前剩余成员数；客户端拿到“已解散”后要做的不是让群凭空消失，而是把该群置为只读：列表标记已解散，摘要正常展示，发消息、上传、管理类入口全部禁用。规则边界按稿内口径收口：群状态与成员状态是分别返回的，成员关系有效不代表群可写；群文件上传、下载、删除一律拒绝，只有文件列表对有效成员只读可见、随周期清理逐步变空；而已退出或被移除的账号连摘要都查不到，因为摘要查询本身就要求查询者具有有效成员关系。一句话：能看见它存在过、处在什么状态，但不能再用它。
- **群摘要和群成员列表为什么要拆成两个协议，而不是合成一个接口一起返回？** 因为两者的拉取频率和成本完全不对称，拆开才能各取所需。摘要（协议 86/87）只返回群名称、群状态、群版本加一个有效成员计数，选中群就刷、收到变更事件也刷，属于轻量展示的热门路径；成员列表（协议 80/81）返回全部成员的账号、角色和加入时间，只在用户真打开成员页或要挑邀请、移除、转让的对象时才发，属于低频重路径。如果合成一个接口，每次刷详情服务端都要全量查成员明细再组包，包体和渲染成本随成员数线性涨，而多数时候用户只关心群名和人数，白花这些开销。拆开的代价是打开一个完整页面可能要发两次请求，且两份数据之间可能恰好跨过一次变更——所以成员页以自己的列表结果为准、摘要计数只作参考，真正的操作判定以操作时刻数据库为准，不拿两份缓存互相印证。
- **只要知道对方的 `group_id`，就能查询任意群的群摘要吗？** 不能，摘要查询是成员权限约束下的读取：服务端拆帧、核验连接认证上下文和登录版本之后，拿请求里的 `group_id` 去 `group_member` 查当前认证主体的那一行——没有这一行，或者行的 `status` 不是 active，就按“非成员”结果码拒绝，群数据一个字段都不会下发。也就是说可见性由“你在这个群里吗”这个数据库事实决定，群标识只负责定位查哪个群；群状态反而不是读取的障碍，已解散群的有效成员仍可查摘要看到终态，限制的是圈外人而不是圈内人。我有意没有做“按编号查看任意群”的群目录能力：那需要另外定义哪些字段可以对非成员暴露、如何防枚举，当前业务没有这个诉求，所以读取范围保持最窄，猜编号换不到任何信息。

### 17. 邀请用户入群：完整链路

#### 功能目标

覆盖发起邀请、待处理查询、接受或拒绝、成员建立与通知。邀请是有身份、状态、到期和幂等规则的持久化业务，不只是弹一个确认框。去重分两层：群请求号挡同一次动作的重发，邀请幂等键保证同一邀请不被重复创建并回放原结果。

#### 主回答（完整业务实现链路口述版）

客户端生成请求号和幂等键后发送入群邀请。服务端先做请求去重，再锁定群记录，校验邀请人的群角色、目标账号和邀请状态；相同幂等键已经处理过时直接返回原结果，未处理时才写入邀请记录并发送邀请事件。受邀人查询待处理邀请后，可以接受或拒绝，服务端会根据邀请记录反查群和目标身份并复核邀请是否仍在有效期内。接受时建立成员关系并推进群状态，拒绝时只更新邀请状态。

#### 表达脉络（记忆钩子）

1. 生成请求号和幂等键发送邀请 -> 2. 判重、锁群并校验邀请权限 -> 3. 命中幂等键回放、未命中写记录 -> 4. 发事件并让受邀人查询 -> 5. 接受或拒绝时反查邀请并复核期限 -> 6. 接受建关系、拒绝改状态

失败分支：无权、群已解散、已在群、过期或已处理分别返回，接受与拒绝各自回包；通知只是提醒，离线靠列表补查

#### 追问卡片

**原完整链路补充（追问时展开）**

**发起邀请**：群主或管理员在群管理页面选择目标账号，客户端取下一个群请求号并生成邀请幂等键（`request_key`，重试保持不变），一起放入邀请请求 62。
**接入与权限**：服务端完成认证和群协议信封校验，先比较群请求号（`≤` 已记录值判为重发丢弃），再用认证主体确定邀请人；数据库事务锁定群组，检查群有效、邀请人角色允许邀请、目标账号存在且不已是有效成员。
**幂等判定**：数据库按群邀请幂等键查询已有结果，再检查针对该受邀人的待处理群邀请；重复请求回放对应结果，不能重复插入同一邀请。
**落库与通知**：允许邀请时写入群邀请记录（`group_invitation`），保存邀请人、受邀人、邀请状态、期限和幂等键，提交后返回邀请标识；服务端基于通知目标集合发送群邀请变更事件 85 并返回邀请响应 63，在线事件只是提醒，数据库群邀请才是后续接受依据。
**受邀人处理**：受邀人登录后或打开邀请页发送查询请求 82，服务端按其认证主体筛选待处理群邀请，经响应 83 返回，即使错过在线通知仍能补查；受邀人选择接受或拒绝时分别发 64 或 66 并携带邀请标识，服务端先根据数据库邀请确定群标识，不信任客户端随意填写的群标识。
**事务与结果**：数据库在事务中锁定群组及邀请，核验受邀人、邀请状态、期限和群状态，过期、已处理或不属于本人的邀请不能创建成员关系；接受分支建立或重新激活普通成员的群成员关系、把邀请置为已接受、按实现追加系统类型群消息并推进群版本，拒绝分支只更新处理状态与处理时间，这些修改在同一事务内提交或回滚。提交后返回 65 或 67，并按结果发送群成员变更事件、群邀请变更事件及必要的系统群消息在线事件；客户端刷新待处理邀请、群列表、成员列表和摘要，入群后的文本或文件请求仍重新检查成员状态。

- **邀请入群为什么要设计成“待处理记录加对方接受”两步，管理员直接把目标账号加进群不行吗？** 直接加入确实实现最简单，一条成员插入就完事，但它剥夺了接收者的选择权：任何人都能被静默拉进陌生的群，从此持续收到这个群的消息和成员事件，这在聊天产品里是不可接受的。我把邀请做成有身份、状态、期限和幂等规则的持久化业务：`group_invitation` 表里一条记录带邀请人、受邀人、状态、七天期限和幂等键 `request_key`，受邀人登录后通过待处理查询（协议 82）看到它，由本人点接受（64）或拒绝（66），只有接受在校验通过后才建立成员关系。多出来的代价是一张表、一套状态机和过期处理，换来的是可拒绝、可追溯、离线也不丢的加入流程——邀请记录在库里，错过在线通知还能补查，发起方也无法绕过本人意愿完成拉人。
- **用户手快连点几次邀请按钮，会对同一个目标产生多份邀请记录吗？** 不会，这里有三层拦截。第一层是群请求号：同一次动作的重发沿用原号，服务端在群协议入口比较连接记录值，`≤` 已记录值的直接判重丢弃，业务根本不执行；第二层是邀请幂等键 `request_key`：客户端如果把这次点击当新动作、换新号发出来，但同一次邀请语义复用同一把键，服务端按键查到已处理结果就直接回放原邀请标识，不再插一条新记录；第三层是业务校验：即便换了新键，服务端仍会检查该群对该目标是否已有 pending 状态的待处理邀请、目标是否已是有效成员，命中就按对应结果码拒绝。所以连点最坏的结果是被丢弃或被拒绝，不会产生第二份邀请。边界在第一层的回放缺席：被判重丢弃的那次点击拿不到结果，客户端想要答案就查一次邀请列表，这是去重和幂等的固有差别。
- **受邀人一直拖着没处理，等他点接受的时候群已经被解散了，还能照常入群吗？** 不能，发起时的有效不代表接受时还有效。接受分支在自己的事务里先按邀请标识反查 `group_invitation` 确定这条邀请属于哪个群——群标识取自数据库记录，不信任客户端回填——然后锁定该群记录，检查 `group_info` 的当前状态：只有群仍是有效的才继续走成员关系建立；群状态是已解散，就直接按当前状态返回拒绝，邀请不会被置成已接受，成员行也不会插入。这些判定全部发生在持有群锁之后，所以不存在“检查时群还在、提交前被解散”的穿插。留下的那条待处理邀请会随着清理任务在第二阶段被删掉，即使清理还没跑到，它也已经是一条永远无法被接受的记录，过期判断和群状态判断都会拦住。界面侧，受邀人接受失败后刷新邀请列表和群列表，看到的就是解散后的真实终态。
- **之前退过群或被移除的人，还能再被邀请回来吗？回来时成员数据怎么处理？** 能，只要他现在不是该群的有效成员就可以重新受邀。接受分支的处理不是无脑插新行，而是先看 `group_member` 里 `(group_id, user_name)` 这条复合主键的现有记录：存在且状态是 left 或 removed 的，就把这一行重新激活成 active、角色置为普通成员；完全没有这一行的才插入新的成员记录。这样同一个人同一个群永远只有一行，主键不会撞，他当初退出或被移除的状态痕迹也保留在同一行上。有两点要讲清楚：重新进来一律从普通成员开始，管理员或群主角色不会因为“以前当过”而自动恢复，想要角色就得群主再设置一次；接受时的其余校验一个都不省——群必须有效、邀请必须属于本人且未过期未处理、幂等键照常回放，二次入群和首次入群走的是同一条事务路径。
- **数据库事务已经提交，但随后的在线事件推送失败了，这怎么对账？** 已提交的事实成立，推送失败只按通知丢失处理：我从不把通知成功当作提交条件，提交成功后也不会因为发不出去而把事务撤回——否则外部通道的故障会倒灌进数据库状态，而且撤了也没用，对方可能已经收到一半。具体到邀请场景，受邀人后续接受所依据的是 `group_invitation` 表里那条记录，不是 85 号邀请事件：事件丢了，他登录或打开邀请页时通过待处理查询（协议 82）照样把邀请拉回来；群侧同理，接受成功后的成员变更事件（84）漏给某些在线成员，他们下一次刷新群列表或成员列表也会追平。这个设计把事件定位成纯提醒，数据库才是唯一凭据，代价是依赖事件的界面会滞后一个刷新周期；兜底是每个受保护操作都按库内当前状态重新鉴权，滞后不会变成越权。
- **你这套群邀请的有效期是多久，过期之后系统怎么处理这条邀请？** 创建邀请时服务端为它写入七天期限，过期采用惰性判定：接受或拒绝动作在自己的事务里反查邀请记录，拿当前时间和期限比较，过期就不进入成员关系建立，返回明确的过期结果码；受邀人的待处理查询（协议 82）只按状态仍是待处理过滤，再套一层最近三十天、单页最多两百条的截断窗口，同时把每条的期限字段一起回带给客户端，不在查询里替我做过期判定。我没有安排一个定时任务去把过期记录批量改成“已过期”状态，因为期限只在判定的那一刻有意义，惰性检查已经封死了所有操作入口，加一个调度器只会多一套要维护的状态迁移；代价是单看 `group_invitation` 表，可能存在形式上还挂着 pending、实际已过期作废的行，要人工拿期限字段比对才能分辨，而这些行最终会随解散群的周期清理或后续治理被收走。
- **受邀人连点两次接受，会不会建立两次成员关系或者产生两条系统消息？** 不会。接受请求先过群请求号判重，同一次动作的重发在入口就被丢弃；即便第二次点击作为新请求进到业务里，接受事务锁群和邀请记录之后的第一件事是检查 `group_invitation` 的当前状态：第一次接受已经把它置为已接受，第二次命中“已处理”检查，直接按已有结果返回，不再走成员建立分支，系统群消息和群版本推进也就只属于第一次的提交。最后一道兜底在表结构上：`(group_id, user_name)` 是 `group_member` 的复合主键，同一个人同一个群物理上不可能有两行有效关系，最多是把已激活的行再确认一次。客户端侧我也做了配合——点接受后立即置灰入口、按 65 号响应刷新状态——但正确性从不依赖这层，全部判定以服务端事务内的状态检查为准。
- **重发邀请时如果客户端换一把新的幂等键，是不是就能绕过查重、把同一个人邀请两次？** 换键绕过的只是 `request_key` 这一层的原结果回放，前面和后面各还有一道闸：前面是群请求号——重发想被受理必须用比连接记录值更新的号，沿用旧号在入口就被判重丢弃；后面是业务校验——受理之后服务端按当前库内事实重新判定，该群对该目标已存在 pending 邀请的，按“已有待处理邀请”拒绝，目标已经是有效成员的，按“已在群”拒绝，这两条检查跟键是什么、新不新毫无关系。所以拿换键这条路去重复邀请同一个人，拿到的是拒绝结果码而不是第二份邀请。真正会产生新邀请的只有一种合法场景：上一份已经被拒绝或已经过期作废，此时按业务理应可以再次邀请。结论是幂等键负责“同一语义可回放”，状态校验负责“换什么键都绕不过约束”，谁也不是唯一防线。
- **邀请这套状态和权限的交叉场景这么多，你实际是怎么动手验证权限矩阵、以及接受与解散或重复接受撞在一起时的行为的？** 我用两个客户端加直接查库来做。权限那一半：一台登群主、一台登普通成员，对同一个目标账号分别发邀请，看普通成员的那次返回无权限结果码、`group_invitation` 表里没有他的行；再拿非成员账号试一次，确认在成员校验就被拒掉。交叉时序那一半：群主端先发邀请、紧接着解散群，然后受邀端点接受，查这条邀请的 `status` 还停在 pending、`group_member` 里没有多出这个人的 active 行，确认解散挡住了接受；接受和对同一邀请的重复接受挨着点，最后看成员表里 `(group_id, user_name)` 只有一行、系统群消息也只追加了一条。重发我分三种手动做：同群请求号重发，看服务端 `[GROUP]` 前缀日志里判重丢弃那一行，并确认库里没有第二次写入；同 `request_key` 换新号，确认响应回放的是原邀请标识；换新键，确认结果是按当前状态重新判定的。离线补查的验证是把受邀端断开，在线发邀请，重连后刷新邀请页能查到那条待处理记录。
- **在你的设计里，一个账号从被邀请到真正变成群成员，中间经过哪些必须通过的关口？** 关键口径是：邀请本身不产生成员身份，它只是在 `group_invitation` 表里落下一条待处理记录，能推动这条记录的只有受邀人本人。完整链路：群主或管理员发邀请（协议 62），服务端校验邀请人角色、群仍有效、目标账号存在且不是有效成员，写入带七天期限和幂等键 `request_key` 的记录，提交后发邀请事件（85）；受邀人查询待处理列表（82）后选择接受（64）或拒绝（66）。接受才动成员数据，且在一个事务里：锁定群和邀请，核验这条邀请属于本人、状态还是 pending、没过期、群没解散，然后为 `group_member` 插入新行或把原有 left/removed 行重新激活为 active 普通成员，邀请置为已接受，追加系统群消息并推进群版本；拒绝只更新处理状态和时间，什么都不会插入。提交后广播成员变更事件（84），各端重查列表——同一幂等键的重复请求只回放原结果，不会产生第二条邀请或第二行成员关系。
- **邀请这一层为什么同时需要群请求号和 `request_key`，它们各自挡住什么、合起来才是什么？** 因为这是"去重"和"幂等"最容易被混为一谈的地方，两层各挡一件事。第一层是群请求号：连接级去重，挡的是"同一次动作的重发被执行第二遍"——同连接上沿用旧号的点击在入口就被判重丢弃，代价是被丢弃的那次拿不到结果，所以它只保证"不会重复执行"，不保证"重发还能拿到答案"。第二层是邀请幂等键 `request_key`：业务级幂等，挡的是"同一份邀请被建两次、并且重发方要能拿回原结果"——客户端对同一次邀请语义固定复用同一把键，服务端按键查已处理结果，命中就回放原邀请标识而不是再插一条。两层叠起来才构成"重复点击既不产生第二份邀请、又能稳定拿到同一份邀请"的完整语义：只有请求号则换号重发仍会另建一份、旧号重发又拿不到结果；只有幂等键则连接级的那次重发不会被挡在执行之外。所以正确讲法是——请求号提供去重（同连接不重复执行），`request_key` 提供幂等（跨重发可回放结果），去重不等于幂等，邀请入群靠的是这两层分工而不是其中任意一层。

### 18. 查看群成员列表

#### 功能目标

让有效成员查看群内当前有效成员及角色，为邀请、移除和转让等管理操作提供选择依据。成员列表请求同样带群请求号，重复请求只会执行一次。

#### 主回答（完整业务实现链路口述版）

用户从自己的群列表选中群组并打开成员列表，客户端取下一个群请求号，发送带群标识的请求。服务端完成认证状态、登录版本及信封边界检查，比较群请求号判重后，将认证主体和群标识送入群生命周期操作。数据库确认群存在和查询者的有效群成员关系，再查询该群有效成员，取得账号名、群角色及成员状态，按加入时间组织后将成员数量与记录装入响应。客户端逐条校验字段长度，更新成员列表和角色标记；查看时的角色只用于展示，执行移除、设置角色或转让群主时服务端重新核验权限和目标成员状态，被移除后保留旧窗口不保留查询权。群成员变更事件包含群标识及群版本等信息，通知客户端重新查询相关视图，通知目标集合来自当前成员关系，不直接信任客户端广播名单。当前成员列表是一次性全量拉取，服务端一次查出全部有效成员、一次组包、客户端一次渲染，因为当前用户量和单群规模都不大，全量在查询、协议体积和渲染上都不构成压力，反而省掉分页游标、翻页期间成员变动以及"已加载条数不等于总人数"的额外复杂度；规模真变大再改递进式拉取——首批返回一部分成员加续取游标，客户端滚动或点加载更多时带游标取下一批，服务端按加入时间或成员主键稳定排序保证翻页不重不漏，总人数一律用服务端统计而非本地列表长度。无论全量还是分批，查询失败或超时都只说明这次没拿到数据，不能当作自己已经退出群的充分证明，是否在群仍以服务端成员关系为准。

#### 表达脉络（记忆钩子）

1.选群取号发带标识请求 -> 2. 验认证判重送群标识 -> 3. 核群与成员资格查成员 -> 4. 按加入时间组包装响应 -> 5. 收变更事件重查视图 -> 6. 全量拉取规模大改游标

失败分支：群不存在、非成员、故障分别返回；管理操作在事务内重新核验；规模变大改游标式递进拉取

#### 追问卡片

- **群成员列表为什么只返回当前有效成员，不把退过群或被移除的历史成员一起带出来？** 因为这个视图的职责是支撑操作：邀请、移除、设置角色、转让都要从这里挑目标，而这些动作只允许作用在有效成员上。把 left 和 removed 状态的历史成员混进来，客户端就得自己再按状态过滤一遍，稍有遗漏就出现“看得见、点不动”的幽灵条目，还把已经离开的人的身份继续暴露给全群——这在没有审计需求的现在是不必要的信息扩散。数据其实都还在 `group_member` 表里，只是查询统一带 `status='active'` 条件；“谁曾经是成员、当时什么角色”属于历史审计，它的可见范围、查询权限、展示形态都还没有和业务确认过，我不塞一个半成品接口进来。所以当前能声称的口径是：成员列表等于此刻的完整成员集合，不等于群的全部历史；历史只存在库里和系统群消息里。
- **客户端已经把无权限的按钮置灰了，服务端是不是可以省掉每次请求里的角色校验？** 不行，界面禁用只能算体验优化，不构成安全边界。第一，界面状态是渲染那一刻的快照：按钮还亮着的时候，操作者可能刚被降权或移除，目标可能刚被提升，拿旧快照做放行依据等于允许过期权限执行；第二，客户端本身可被绕过，报文是能手写的，禁用逻辑挡不住一个直接构造请求的人。所以我的每个群管理请求进了群协议入口、过了群请求号判重之后，都在事务里锁定群记录，用连接绑定的认证主体现查 `group_member` 的 `role` 和 `status`，目标行也一样现查现判，不合规按结果码拒绝——数据库里的当前角色是唯一裁决依据。代价是每个操作多两次主键点查，这个钱我乐意付：它换来越权判定完全不用考虑客户端状态新旧，界面错成这样都影响不到授权。
- **单群成员数如果变得很大，你现在的成员列表一次性全量拉取还撑得住吗？** 现在撑得住，这是我按实际规模做的取舍：用户量和单群成员数都小，服务端一次查出全部有效成员、一次组包，客户端一次校验字段长度、一次渲染，全量在查询、协议体积和渲染上都构不成压力，还天然回避了分页的三件麻烦——游标怎么定义、翻页期间成员变动导致重漏、已加载条数被误当总人数。规模真上来时我的扩展路径已经想好：改成递进式拉取，首批返回一部分成员加续取游标，客户端滚动时带游标取下一批，服务端按加入时间或成员主键稳定排序保证翻页不重不漏，人数一律用服务端统计值而不是本地列表长度。当前实现里我保留的是底线语义：拉取失败或超时只说明这次没拿到数据，不能当成自己已退群的证据，在不在群永远以服务端成员关系为准。
- **群主、管理员和普通成员打开成员列表，看到的内容有区别吗？** 没有区别，这是我当前的明确口径：成员列表的读取门槛只有一个——你是这个群的有效成员，过了这道门，所有人拿到同一份完整列表，账号、群角色、加入时间逐条一致，群主并不会看到更多字段。角色差异不体现在“看到什么”，而体现在“能做什么”：能不能邀请、能不能移除别人、能不能设置角色，是每次管理操作执行时在事务里现查 `group_member` 的 `role` 列判定的，和列表返回无关。我没有实现按角色脱敏的多级成员视图，因为成员账号在群内本来就互相可见，拆分视图需要先定义哪种角色能看哪些列、不同视图间的群版本怎么对齐，这些业务预期没有确认，我不擅自做，也不会在面试里声称已经实现了分级展示。
- **群相关的每个请求，权限具体是怎么一步步校验的？按这套校验，被踢出群的人还能看到群的历史消息吗？** 校验是一条固定路径：请求拆帧后先核验连接认证上下文和登录版本，确认这是一个登录中的连接；然后进群协议入口做信封校验和群请求号判重；进业务之后，拿请求里的 `group_id` 加连接绑定的认证主体去查 `group_member`，必须命中 `status='active'` 的行，这一步决定“你在不在群里”；行里的 `role` 列（owner、admin、member）再决定“这个动作你配不配做”——邀请、移除、设置角色、转让各查各的角色前置条件。发消息、拉历史、已读确认、群文件访问都必须先过成员这一道，管理动作再过角色这一道。据此，被移除或退出的人查不到 active 行，拉历史消息（协议 91）会被直接拒绝——消息本身还在 `group_message` 表里，直到群解散才被清理任务删除，但对已失效的账号不再可见；他本地已经落盘的部分可以离线继续翻，那是客户端数据，服务端不再为它提供任何新读取。
- **成员规模变大以后，除了列表拉取，群管理整条链路还会在哪些地方遇到压力？** 有三处开销随成员数或操作密度放大。一是同群写操作串行化：移除、转让、设置角色、接受邀请这些写路径都要先锁群记录保证不变量，管理动作频繁时它们在同一把锁上排队，单群吞吐有天然上限，这是我为了“唯一群主、角色变更原子”主动买的正确性保险。二是通知扇出：每次成员变更都要从成员表查出当前有效成员集合、向全体在线成员广播事件，查询和发送量随成员数线性涨，服务端广播队列有满时丢弃的实时投递保护——[GROUP] 前缀日志会记下丢弃的连接数——宁可丢提醒也不拖垮连接。三是鉴权读放大：我刻意不缓存成员和角色，每次核验都点查库，操作越密集查询越多。应对顺序上我会先做通知合并下发、再考虑只读视图的短 TTL 缓存，但写操作的授权核验坚持现查库不放——那是安全边界，不是性能选项。当前规模离需要动这些还很远，我按现状保持简单。
- **群里有人退出或被移除之后，同群其他还在线的客户端是怎么知道的？** 靠服务端提交变更后的广播：移除、退出、角色设置、转让这些写事务提交成功后，服务端从 `group_member` 查出该群当前有效成员集合，向这些在线连接推送成员变更事件（协议 84），事件里带群标识和群版本；在线客户端收到后不直接改本地数据，而是触发对群列表、摘要或成员列表的重查，用查回来的结果替换展示。有两个细节是刻意的：通知目标集合以库为准而不是客户端上报的名单，所以被移除的人不在这次广播名单里，他的界面变化由单独发给发起端和被移除者的应答来驱动；离线成员收不到也不补发，回来登录或刷新时列表整体重建。事件的定位自始至终是提醒——它只说“这个群变了”，变了什么、现在是什么，一律以查询为准，所以事件漏了最多是视图晚一步，不会造成权限错误。

### 19. 退出群

#### 功能目标

结束本人有效成员关系并立即收回后续群操作权限，保留必要历史。群主必须先转让或解散，不能直接留下无主群。退出请求按群请求号判重，同号重发不会重复改写成员状态。

#### 主回答（完整业务实现链路口述版）

用户在群管理页面确认退出，客户端取下一个群请求号，发送带群标识的退出群请求。服务端完成拆帧、连接认证上下文、登录版本及群协议信封检查，先比较群请求号判重，再以认证主体作为退出者。数据库开启事务并锁定群组，确认群有效、退出者具有有效群成员关系，群主必须先转让群主或解散才能退出；随后将本人群成员关系由有效改为已退出并检查更新确实命中预期行，追加退出群的系统类型群消息并共用群内消息序号，推进群版本并提交事务，失败回滚成员状态、系统消息和版本。提交后查询通知目标集合，发送群成员变更事件和必要的系统群消息在线事件，封装退出响应；由于已退出者不在有效成员通知名单内，发起端要处理自己的应答。客户端成功后刷新群列表、失效化相关群操作入口，之后发送、拉取、已读确认和群文件新请求都要按当前成员关系重新鉴权。退出在客户端是断增量、留存量：群会话窗口置为只读，群列表标记为已退出，不再接收该群的消息、成员变更事件和群摘要更新，也不再向服务端补拉历史，本地已落盘的聊天记录和已下载的群文件保持原样、仍可离线查看，退出不触发任何本地清理动作。

#### 表达脉络（记忆钩子）

1.确认退出取号发带标识请求 -> 2. 验认证判重确定退出者 -> 3. 锁群核验群主先转让解散 -> 4. 改退出写系统消息推版本 -> 5. 发事件响应发起端自处理 -> 6. 断增量留存量不删本地

失败分支：群主直接退、无成员关系、群已解散分别返回；重复退出不重放首次结果；不删群历史也不清本地

#### 追问卡片
- **退出群为什么只把 `group_member` 那行的状态改成已退出，而不是把成员行直接删掉？** 因为留着行就留着依据：这个人在这个群的身份是同一行记录，退出只是把 `status` 从 active 改成 left，他的加入时间、历次角色变化都在这一行上延续，被重新邀请时接受分支直接把这行激活回普通成员，不用插新行也不会撞 `(group_id, user_name)` 复合主键；将来要做“谁进出过群”这类审计，数据本来就在。删行看着干净，实际是把语义删没了——历史记录断档，同一个人二次入群变成全新插入，任何按成员行做关联的逻辑都要重新建立。这个设计的代价我明确承担：既然状态都留在一张表里，所有权限和列表查询就必须统一带上 `status='active'` 过滤，漏掉一处就会把退出者当现役成员放行；所以成员关系的查询和状态流转我收敛在群业务层的固定几个函数里做，不散落各处手写 SQL，用收口来防这个坑。
- **普通成员可以想退就退，为什么群主必须先转让或解散才能退出？** 因为群主直接退会留下一个无主群：设置角色、转让、移除、解散、触发群文件清理这些只有群主能做的操作从此没人可执行，群变成永远到不了终态的孤儿数据。替代方案是系统自动指定下一个群主，但那要先回答一串没有好答案的问题——按加入时间还是角色选候选、候选人拒绝了怎么办、全员都是群主相关状态怎么收敛，每条规则都是争议点；以我当前的群规模，这套裁决机制的复杂度远超它省下的点击。所以我选了最直白的硬规则：退出事务里锁定群记录后检查操作者 `role`，是 owner 就拒绝并返回明确结果码，把决定权交回人——要么显式把群主转让给选定的人，要么解散让群进入终态。代价是群主退出要多一步操作；收益是“凡是存在的群必有唯一群主”这条不变量永远成立，下游所有权限分支都不用处理群主缺席这种情况。
- **用户退群的时候正好有一个群文件下载在传输中，这个下载会被立即掐断吗？** 不会在字节层面瞬时撤回，这是我把话说准的地方。我的授权粒度是请求时核验：退出提交后，这个账号发起的任何新请求——包括重新发起的下载——都会在成员校验处被拒，因为 `group_member` 里他的行已经不是 active；但已经在途的传输不会逐块回头重查成员表，剩余字节会按既定会话继续传完落盘。要做到严格瞬时撤回，就得每个数据块都查一次权限，或者给传输会话做一个服务端强制失效通道，这两样的查询开销和中断复杂度，都超过它们防住的风险——暴露面只是退出前已合法发起的那一个会话的剩余部分，传完之后他再也访问不到这个文件。所以我能声称的边界是：退出和移除即刻收回的是“发起新动作的资格”，在途动作按初始化时点和完成时点的权限检查自然收尾，不把请求时授权说成对所有在途字节瞬时生效。

### 20. 移除群成员

#### 功能目标

允许有管理权限的人移除普通成员，限制越级管理。当前群主、管理员都不能通过该分支直接移除管理员或群主。移除是写操作，请求先经群请求号判重，同号重发不会改两次成员状态。

#### 主回答（完整业务实现链路口述版）

群主或管理员在成员列表选中目标账号并确认移除，客户端取下一个群请求号，连同群标识和目标账号发送移除请求。服务端验证连接认证状态、登录版本与群协议信封，先比较群请求号做去重，再以认证主体确定操作者；随后在事务中锁定群组并确认群有效，读取操作者的有效成员关系与群角色，普通成员不能发起移除，再锁定目标成员关系，要求目标当前有效且角色为普通成员——管理员和群主不能从这个入口被移除。校验通过后把目标成员状态改为已移除，追加系统类型群消息并推进群版本，任一步失败都回滚。
提交后按当前通知目标集合发送群成员变更事件和系统群消息在线事件，并返回移除响应；被移除者已不在有效成员集合中，因此会单独收到一次被移除群聊的响应。发起端匹配应答后刷新成员列表和群摘要，目标端即便还开着窗口，其下一次受保护的群操作也会因当前成员状态失效而被拒绝；已保存到本地的聊天记录和已下载文件不因成员移除自动撤回，正在执行的传输也要按初始化和完成阶段的权限检查边界来处理。

#### 表达脉络（记忆钩子）

1、选目标发带号移除请求 -> 2. 验认证判重定操作者 -> 3. 锁群核验角色与目标 -> 4. 标已移除写消息推版本 -> 5. 发事件响应目标单独回 -> 6. 双端刷新目标失权不撤

失败分支：非管理角色、越级移除管理员或群主、目标已失效分别返回；同号重发只丢弃不重写状态，提交后通知失败也不回滚；被移除者不在通知名单内，故单独回包；本地记录与已下载文件不撤回

#### 追问卡片

- **群主看某个管理员不顺眼想直接移除，按当前规则该怎么做？为什么不让群主接口直接删任何人？** 操作上是两步：群主先用设置角色（协议 72）把目标从管理员降为普通成员，这一步在自己的事务里更新 `group_member` 的 `role` 列、推进群版本；然后再从移除入口（协议 70）发起，这时目标已经是有效普通成员，通过“目标必须 active 且 role 为 member”的前置校验，正常移除。移除分支被硬限定成只能动普通成员，不是界面疏忽，是我故意保住的不变量：管理员和群主的处置必须经过一次显式的角色变更，降级和移除是两笔各自有系统群消息和版本推进的事务，权限变化留痕清晰；如果放开成群主可直删任意角色，同一个请求里就要内嵌“对不同类型目标规则不同”的分层判定，越界风险和维护成本都更高。代价就是群主多一次操作，我认为这个冗余换来的是可解释性，值得。
- **移除成员发起前，目标恰好被另一笔操作升成了管理员，这次移除会怎样收场？** 会以移除失败收场，判定发生在事务内而不是发起时。移除请求过了认证和群请求号判重之后，在事务里锁定群记录，然后现查目标的 `group_member` 行：移除的前置条件是目标 active 且 `role` 为普通成员，此刻查出来 role 已经是 admin，条件不满足，事务回滚、返回“目标角色不允许移除”的结果码，界面据此提示群主先降级再移除。关键在于角色设置和移除都要锁同一条群记录，所以“升级”和“移除”这两笔操作在同一把锁上强制串行：不管报文先到后到，后执行的那笔一定看得见先提交的那笔造成的新状态，永远基于当前角色重新裁决，不存在按发起时的旧角色放行、把刚上任的管理员偷偷删掉的中间态。代价是界面上看着十拿九稳的操作可能被拒一次，但这正是我要的行为——服务端只认执行时刻的库内事实。
- **移除一个成员，会不会把他之前在群里发过的消息一并删掉？** 不会，而且我认为不该。移除这个事务改的只有三样：目标在 `group_member` 里的 `status` 置为 removed、追加一条系统类型的群消息记录这次变动、推进群版本；`group_message` 里他历史上发的消息一条不动，其他成员翻聊天记录时一切如常。理由是消息属于群的共享历史而不是成员行的附属品——按人删消息会把群消息序列挖出空洞，上下文和引用断裂，还得为其维护一套“按成员批量清历史”的机制，风险和复杂度都不划算。在我的规则里，整群消息的唯一释放点是群解散：状态切到已解散后由周期清理任务分批删 `group_message` 等数据，运行期永久保留。效果上移除只作用于未来：他从此刻起拉不到任何群消息（查询入口按 active 拒绝），但已保存到他本地聊天库里的记录我也不做远程擦除——“对他不可见”和“从世上删除”是两件事，各自有各自的边界。
- **移除已经写库成功，之后通知事件推送失败了，这次移除会被撤销吗？各方界面怎么恢复？** 不会撤销。成员状态变更在数据库事务提交那一刻就是既成事实，事件是在提交之后才发出的旁路提醒，我的设计从不把通知成功当作提交条件——否则一个网络毛刺就要倒灌回数据库，状态反而不可信了。各端界面靠别的路径收敛：发起端直接从移除应答（协议 71）里拿到结果码，应答里保留请求关联号，匹配成功后自己刷新成员列表和群摘要，不依赖事件回环；被移除者本来就不在提交后查询出的有效成员广播名单里，服务端单独给他回一条被移除的应答，就算这条也丢，他的下一次受保护请求会被成员校验拒绝，界面随之失效化，不需要靠事件来“通知自己被踢”；其他在线成员漏收事件的，列表晚一步，刷新即追平。我不为通知做补发重试——丢了最多是展示滞后，数据库是唯一凭据。
- **移除这个功能，你实际是怎么动手验证角色规则、以及与对方角色变更并发时的正确性的？** 我分三组动作来做。权限矩阵：用两个客户端分别登录群主、管理员、普通成员和一个不在群里的账号，对同一个普通成员、一个管理员、群主分别发移除（协议 70），看每次的应答结果码，再查 `group_member` 表对应行的 `status` 列有没有被改成 removed——预期只有群主和管理员移除普通成员会动库，越级的一律拒绝且表里纹丝不动。并发交错：在移除报文发出的同时用群主做设置角色把目标升为管理员，事后查库里这一行的最终 role 和 status，只能落在“已升级、移除被拒”或“先移除成功、设置角色因目标已失效被拒”两种合法结果之一，不能出现既 removed 又 admin 的半态。重发验证：同号重发看服务端 `[GROUP]` 前缀日志的判重丢弃行、确认系统群消息没有第二条；换号对已移除目标重发，确认返回按当前状态判的失败而不是回放首次成功。最后拿被移除者的旧窗口挨个点管理、发消息、开群文件，逐个确认被拒。
- **被移除的人如果一直没收到移除应答、群窗口还开在屏幕上，他能不能趁界面没变继续管理或查询这个群？** 不能，界面活着不等于权限活着。窗口只是让用户“以为还能操作”，所有真正做事的是服务端：他从这个窗口发出的每一条请求——拉成员列表、设置角色、发消息、访问群文件——都会走完整的校验路径，其中群请求号判重要求这个连接用递增的新号（旧号重发在入口就被丢弃），业务校验要在 `group_member` 里查到他的 active 行，而移除事务已经把他的 `status` 改成了 removed，于是每一条都被结果码拒绝，客户端收到拒绝后把窗口置为失效状态。也就是说最坏体验是“窗口多活了一会儿，操作一次死一次”，不存在能被实际利用的越权窗口期；唯一的残余在途传输按初始化时点的授权自然收尾，不新增任何访问。授权与展示分离，就是我敢让界面滞后的底气。

### 21. 设置成员角色

#### 功能目标

由群主调整其他有效成员在管理员和普通成员之间的角色。不是任意修改角色字符串的通用接口。角色变更请求同样先经群请求号判重。

#### 主回答（完整业务实现链路口述版）

群主在成员列表选定目标账号和管理员或普通成员角色，客户端取下一个群请求号，发送设置角色请求。服务端校验认证状态、登录版本和群协议信封，比较群请求号判重后进入业务；数据库开启事务并锁定群组、确认群有效，核验操作者的有效成员关系且当前群角色为群主，更新目标群成员关系时同时要求目标有效且当前角色不是群主。校验通过后检查更新命中的行数，再推进群版本并提交，目标失效、角色不允许或提交失败均回滚并返回错误。提交后服务端发送群成员变更事件并返回响应，客户端按请求关联号确认结果，重新读取成员列表与摘要。

#### 表达脉络（记忆钩子）

1.选目标角色发带号请求 -> 2. 验认证角色字段判重 -> 3. 锁群核验群主与目标 -> 4. 命中行推版本否则回滚 -> 5. 发成员变更事件与响应 -> 6. 重读列表权限按库不按缓存

失败分支：非群主、非法角色值、目标已失效或恰是群主均回滚并返回错误；同号重发在入口判重丢弃；换号重设同一角色受命中行语义影响，若要“已是该角色”也算成功需显式定义；后续权限以数据库当前角色为准，不依赖客户端缓存

#### 追问卡片

- **转让群主为什么单独做一个协议，而不是复用“改某个人角色”的通用设置角色接口，先改目标成群主再改自己成管理员？** 因为群主身份是一对必须原子成立的约束：新群主上任的同一刻旧群主必须卸任，任何时候群里恰好一个 owner。通用接口是单行修改，拆成两次调用就制造了两个非法中间态——先升目标则短暂双群主，期间任何一端都有全权；先降自己则短暂无主，第二次调用若失败群就永久卡在没人能管的死角，还得人工补数据。我也评估过让通用接口支持“一次改两行”，但那等于往通用语义里塞特例，接口不再是“改角色”而是“改出一对耦合状态”，校验逻辑反而分裂。所以转让做成专门事务：锁群记录，核验操作者是当前群主、目标是有效非群主成员，两条 UPDATE 各自检查影响行数，全成才连同群版本推进一起提交，任一失败整体回滚——“唯一群主”这个不变量从头到尾只在数据库层被保证，不泄漏到任何一次调用间隙里。
- **恶意客户端能不能在建群或设置角色的报文里自称群主，或者伪造一条成员变更事件骗其他客户端？** 两条路都不通，而且不通的机理不一样。冒充操作者这条路：我的报文里根本没有“操作者是谁”这个可填字段——请求体能表达的只有“对哪个群、改谁、改成什么角色”，操作者永远取自这条 TCP 连接绑定的认证主体，是握手登录阶段就定死的服务端状态，当前角色由 `group_member` 现查，自称什么都没地方放。伪造事件发给别人这条路：事件（84、85）是服务端向在线成员集合的单向推送，客户端没有任何“向他人发事件”的信道；就算攻击者想办法让某客户端收到一条假的变更提醒，那也只是提醒——收到后做的事是发起一次查询，数据从服务端库里来，假事件的破坏力封顶是“让对方多刷了一次列表”，改不动数据库一个字节。这套的支点在于：所有状态权威在库，报文和事件要么是请求、要么是提示，全都参与不了授权裁决。
- **设置角色这个功能，你是怎么实际验证“只有群主能改、只能改对范围”，以及两笔角色操作撞在一起时的结果的？** 权限用多身份客户端对着查：分别登录群主、管理员、普通成员发同一条设置角色（协议 72），只有群主那次应答应为成功，其余看返回的结果码，再查 `group_member` 的 `role` 列确认没被改动；目标范围我构造三类边界——目标已退出（status 是 left）、目标就是群主本人、角色值填一个枚举外的字符串，前两类靠服务端事务里的条件更新挡下（UPDATE 带着“目标 active 且 role 不是 owner”的条件，影响行数为零即回滚报失败），非法枚举值在群协议入口的参数边界检查就被拒；伪造操作者则直接手写报文试，确认身份取的是连接不是字段。并发用两台机器互撞：设置角色和转让群主几乎同时发、或对同一目标连发两条不同角色，落定后查这一行 `role` 只会有一个终值，各请求的应答和后续操作权限要与这个终值对得上——不会出现应答说失败但库里改了、或者半程更新。判定一律以查库加看 `[GROUP]` 前缀日志的服务端裁决为准，收到的事件通知只当提醒，不当结果。
- **每个群请求都现查一遍成员和角色，这条 SQL 会不会成为瓶颈？** 每次都会查库，这是事实，但查的形态决定了它便宜：`(group_id, user_name)` 是 `group_member` 的复合主键，鉴权那条 SELECT 是主键等值点查，InnoDB 顺着聚簇索引直达单行返回，成本更接近一次网络往返本身，而不是什么聚合或扫描；同请求里事务已经要为写操作摸一次这张表，读锁也省不掉。我也认真考虑过把角色缓存在连接会话或内存表里，放弃的理由是失效难题：降权、移除、转让、退出每一笔都要精确打掉对应缓存项，漏打一处就是越权放行，打错了又是不该拒的被拒——为了省一次主键点查引入一套会出安全问题的失效协议，明显亏。当前用户量下这条查询离瓶颈很远；真到压力出现的那天，我会先给只读的摘要类查询加短 TTL 缓存，而写操作的授权核验保持现查不缓存，那是边界所在。

### 22. 转让群主

#### 功能目标

在保留群的前提下更换唯一负责人。当前规则是目标升为群主，原群主降为管理员。转让请求同样先经群请求号判重，同号重发不会执行第二次角色转移。

#### 主回答（完整业务实现链路口述版）

当前群主从有效成员中选择目标并确认转让，客户端取下一个群请求号，发送带群标识和目标账号的转让请求。服务端完成连接认证上下文、登录版本与群协议信封核验，比较群请求号判重后，以认证主体确定原群主；数据库开启事务并锁定群组，确认群有效及操作者仍是群主，目标须是有效成员且不是已有群主。同一事务先把目标群角色改为群主，再把原群主降为管理员，两个更新都要求准确命中预期成员记录，任何一项失败立即回滚、不能保留只完成一半的角色转移，两项成功后推进群版本并提交。提交后服务端发送群成员变更事件并返回转让响应，不把通知成功作为角色变更的提交条件，一切状态以数据库为准。客户端刷新群角色、成员列表和相关按钮，原群主从此按管理员权限操作、新群主按当前数据库事实受理；若应答丢失可查询成员角色和群版本确认结果，之后所有的原群主的重发请求都按照转让后的新权限来进行处理了。

#### 表达脉络（记忆钩子）

选目标确认转让发带号请求 -> 2. 验信封判重确定原群主 -> 3. 锁群核验操作者与目标 -> 4. 升目标群主降原主管理员 -> 5. 推版本提交发事件响应 -> 6. 刷新按钮重发按新权限

失败分支：目标先退出、并发转让、非群主发起均回滚，不留半个群主；同号重发判重丢弃、不回放结果，换号重发因原群主已降级按权限失败，不能默认重发得到相同结果；通知成功不作为角色变更的提交条件

#### 追问卡片

- **转让群主之后，原群主为什么被降成管理员，而不是直接退出群或者降成普通成员？** 这是我定死的一条业务规则，取向是“交权不赶人”。原群主往往是建群和最了解群的人，降为管理员让他保留邀请、移除这类协助能力，新群主有个平稳的交接期；同时留在群里意味着他的成员行不变、只动 `role` 一列，历史消息、已读位置、已下载文件全部连续。对比两个替代：转让即退出，等于强迫所有“只想卸管理责任”的人彻底离群，想要这个结果的人反而没有选项，而且退出会把他从通知集合里摘掉，交接期连协助都做不了；降成普通成员则太激进，交接期里新群主连个能搭手的老人都没有。代价我清楚：转让后群里同时存在新群主和身为管理员的原群主两个高权限账号，信任没完全交出去之前，新群主可以再一步把原群主设为普通成员或不活跃处置——路径存在，选择权留给了在任群主，这比在协议里替他做决定合理。
- **群主点了转让确认之后、转让请求执行之前，目标自己先退出了群，这次转让会怎样？** 转让整体失败并干净回滚，绝不会出现“把已退出的人任命成群主”。判定在事务内执行：转让分支先锁定 `group_info` 那条群记录，确认操作者此刻仍是 owner，然后对目标做条件更新——UPDATE 语句带着“这一行必须 status 为 active 且 role 不是 owner”的前置条件，目标刚退出的话他的行已经被退出事务改成了 left，条件不命中、影响行数为零，代码据此判为失败，事务回滚后返回明确结果码，原群主角色分毫未动。之所以能确定“点了之后发生的事也算数”，是因为退出和转让要锁同一条群记录：目标退出先提交，转让就看见 left；转让先提交，目标就已是新群主、随后走的是“群主必须先转让或解散才能退出”的另一条规则，两头都堵死。界面上群主会收到失败提示，重新从最新的成员列表里挑目标即可——成员列表是查库现拉的，不会给他幽灵候选人。
- **两笔群主转让几乎同时到达服务端，比如群主手抖把转让发给了两个不同的人，最终状态怎么保证不乱？** 靠群记录上的行锁把它们排成先后。转让事务的第一步永远是锁 `group_info` 这一行，所以两笔请求不可能并行改角色：先拿到锁的那笔完整执行——目标升 owner、原群主降 admin、推版本、提交；后拿到锁的那笔不是接着旧上下文做完，而是重新跑一遍前置核验，其中“操作者当前仍是群主”这条用的是它现在查到的角色——发起转让的那位已经在上一笔里被降成 admin，检查不通过，回滚返回无权限结果码。所以手抖两次转让的结局是确定的一种：先到者生效、后到者被拒，群里自始至终恰好一个 owner，没有“后一笔把群主又换回去”的连环翻转，因为换回去的那笔同样要先过操作者=群主这道闸。这也再次说明为什么权限只认执行时刻的库内事实：请求排队期间世界会变，我的事务每次都在锁后重新看清这个世界。
- **转让事务已经在数据库提交成功，但转让应答（协议 75）丢在了网络上，客户端怎么知道群主其实已经换了？** 认数据库不认应答：应答丢了不会让已提交的角色变更倒回去，权威事实——目标成为 owner、原群主成为 admin、群版本前进——已经落在 `group_member` 和 `group_info` 里。恢复动作是查询而不是重发：客户端拉一次成员列表（协议 80），看 `role` 列里谁是 active 且 owner，再比对摘要里的群版本，就知道转让成没成、界面该怎么画。我不建议用重发转让来“问结果”：同号重发在群协议入口就被判重丢弃，本来就拿不到应答；换新号重发则是一笔新转让，而原群主已经降级，它会以“操作者非群主”失败——结果无害但错误信息容易让人误以为上次没成功。转让没有业务幂等键、不保存上次结果，这正是群请求号只是连接级去重不是幂等的直接后果，应答缺失的口子统一靠“查询当前状态”来收口。
- **转让群主这个跨两行的角色变更，你实际是怎么验证失败和中途打断都不会留下无主或双主群的？** 我分两路手工构造。失败路径：转让是“升目标、降原主”两条 UPDATE 加版本推进在同一个事务里，我要制造第二条失败的观感——用目标行和原主行其中一个条件不成立的方式（转让前让目标先退出，或构造对同一目标的重复转让）让事务回滚，然后查 `group_member` 里新旧两人的 `role` 列，确认两行都停在转让前的值，绝没有“目标已是 owner、原主也还是 owner”或“原主已降、目标没升”的半程状态；再用服务端进程在请求处理中被打断这种更粗暴的方式重启一次，看 InnoDB 对未提交事务的自动回滚同样落在原状态上。并发路径：两笔转让发向两个不同目标几乎同时点下，落定后数一条硬指标——全群 `role='owner'` 且 `status='active'` 的行有且仅有一行，输的那笔拿到无权限结果码。每一步的判定都拿查库结果和应答包对，收到 84 号成员变更事件不算数，事件只是提醒。
- **转让如果在提升目标和降低原主之间失败，会不会留下两个群主或者一个都没有？** 两者都不会，因为这两条 UPDATE 不是两次独立提交，而是同一个事务里的两步，外面还罩着群记录的行锁。事务顺序是：锁定 `group_info` 该行，核验操作者当前 role 是 owner、目标是 active 且非 owner，然后升目标为 owner、降原主为 admin，两条更新各自检查影响行数恰好命中预期行——第二条失败、行数不对或数据库报错，整个事务回滚，两人的角色一起退回到转让前的值；只有两条都命中的成功路径才推进群版本并提交。对组外的请求来说，行锁保证它们要么看到转让前的完整旧状态、要么看到转让后的完整新状态，“双主”和“无主”作为事务中间态从不对外存在。剩下唯一的间隙在通知：提交之后成员变更事件如果没送达，部分客户端界面会短暂还显示旧群主，但那只是显示滞后——他们发出的任何操作都按库里新角色裁决，旧群主名字还挂在按钮上，请求也已经不是群主的请求了。

### 23. 解散群

#### 功能目标

由群主终止群的正常写业务。解散请求本身只把群状态切到已解散，相关数据清理交给周期性任务分批分阶段完成，而不是在解散事务里一次删完。解散是写操作，请求先经群请求号判重。

#### 主回答（完整业务实现链路口述版）

群主确认解散群组后，客户端取下一个群请求号，发送带群标识的解散请求。
服务端完成认证和群协议信封校验，比较群请求号判重后，在数据库事务中锁定群组，确认群有效、操作者具有有效成员关系且角色为群主。
随后只把群状态改为已解散，不在事务里物理删除群表、全部消息和文件内容，避免长事务与锁放大拖垮在线业务。
校验通过后推进群版本并提交，失败则回滚；数据清理不放进解散事务，由周期性清理任务分批分阶段执行——第一阶段清理群文件引用，逐条减少对应物理文件对象的引用计数，减到无引用的对象按锚点进入待回收，再由回收调度器复核后物理删除，否则引用计数永远大于零、文件清不掉等于泄漏磁盘；第二阶段分批清理邀请记录、群消息和成员关系等群相关数据，每批控制规模，避免一次性大事务，清理进度以清理水位记录、可断点续做。
提交后服务端按通知目标集合发送群成员变更事件并返回响应，客户端刷新群列表、摘要与操作入口。
解散不是删除，而是让群进入不可用终态：后续写操作全部拒绝，读操作要求群有效，群文件列表是唯一例外——清理任务尚未处理时，仍有有效成员关系的账号可只读查看列表，但上传、下载、删除均已拒绝，随引用清理推进列表逐步变空，已退出或被移除的账号连列表也查不到；服务端每个新请求都按权威群状态处理，不能把旧窗口可见当成群仍可用。

#### 表达脉络（记忆钩子）
1、群主确认解散发带号请求 -> 2. 验信封判重锁群核群主 -> 3. 只切群状态不物理删除 -> 4. 推版本提交周期分阶清理 -> 5. 发事件响应刷新群入口 -> 6. 写全拒读查有效文件列表例外

失败分支：非群主、重复解散、数据库失败分别返回；同号重发在入口判重丢弃；解散不同步物理删除，清理由周期任务分批完成、可断点续做；群文件上传与下载均拒绝、列表随清理逐步变空，群消息拉取仍要求群有效

#### 追问卡片

- **解散群的时候，为什么不趁这一个请求把群记录、消息、成员、文件数据全部物理删干净？** 因为一个群背后挂着四类数据和一套引用计数：`group_info`、`group_member`、`group_invitation`、`group_message`，加上群文件记录指向的、可能同时被个人目录复用的物理文件对象。把这些删除全塞进解散事务，就是一个持着群记录锁不放到底的长事务——期间这个群的所有读写在锁上排队，删到一半失败还留下“删了消息没删文件”的半清理状态，恢复逻辑比不清理更麻烦。所以我的解散事务只做一件快事：把 `group_info` 的状态改成已解散、推进群版本、提交，从这一刻起所有写入口按状态拒绝，业务上的“群没了”已经生效。真正的物理删除交给周期性清理任务分阶段分批做，每批控制规模，进度记在清理水位上、断了续做。代价是磁盘空间要等清理周期才回收，解散到清完之间数据仍躺在库里——但对外已经不可见不可写，这个滞后是我用钱（磁盘）换稳（在线业务不被大事务拖垮）的自觉选择。
- **如果解散后的周期清理一直不执行，群文件占用的磁盘会发生什么？** 会泄漏，这正是我把释放引用定为清理任务第一阶段的原因。我的文件内容是物理对象加引用计数共享的：一条群文件记录、个人目录里的条目，引用的是同一个对象，只有引用计数归零，对象才有资格被回收。解散只切群状态、不动文件表，如果没人去递减，这个群占的每个对象计数永远大于零，回收调度器永远等不到它们，磁盘用量只涨不降，删一万次的存储效果等于零。所以第一阶段逐条遍历该群的文件记录、减少对应 `file_object` 的计数，减到无引用的对象按锚点挂进待回收队列，回收调度器动手物理删除前还要复核一次计数——防止这中间恰好又有个人目录引用了同一对象，误复核就删了活文件。第二阶段才分批清邀请、消息、成员关系这些行数据，每批限规模、按水位断点续做。设计上的诚实说法是：清理是这套解散方案兑现“删掉了”承诺的那一半，缺了它，解散就只是把账挂到了磁盘上。
- **群解散之后，群文件的上传、下载、删除和查看列表分别是什么待遇？** 三个写全拒，列表是唯一例外。文件链路的权限检查比普通读写多一道群状态：上传初始化、下载请求、删除操作都以“所属群仍有效”为前置，群状态一旦是已解散，不管操作者是不是群主、成员行是不是还 active，一律拒绝——解散的语义就是这个群的写业务终止，不给任何角色留后门。查看文件列表则是刻意留的只读口子：仍有有效成员关系的账号可以列出文件清单，动机是给用户一个把已共享文件转存或确认的最后窗口，且这个窗口是自然收缩的——清理任务第一阶段逐条释放群文件引用，列表随推进逐步变空直至查无可查；已退出或被被移除的账号连列表也查不到，成员校验先挡。所有判定看服务端权威群状态、每请求现查，旧窗口里还挂着的文件列表不构成任何操作资格，点下去就是拒绝结果码。已下载到本地的文件不受影响，那是客户端数据。
- **解散群和有人正在发群消息赶在同一时刻，这条消息算发出去了还是被拒？** 按两笔事务对群记录的加锁先后定，且一旦定局就不翻案。发消息和解散都要碰同一个群：消息写入路径要检查群状态仍有效才插 `group_message`、共用群内消息序号；解散事务检查操作者是群主后把状态改成已解散。锁把两者排成串行——消息先提交、解散后进锁，那条消息就是合法历史，之后随清理任务一起被分批删除，解散不回撤任何已提交消息；解散先提交、消息后进锁，状态检查失败，发送方拿到“群已解散”的结果码，界面提示发送失败。不存在“检查时群还有效、写入前被解散”的灰色地带，因为检查和写入在同一把锁的同侧。解散后的拉消息同样要求群有效，所以成员也拿不到那条窗口期之后的一切。另外群消息本来就不支持编辑和单条撤回，解散也不是删除个别消息的后门——它只把整群数据交给周期清理，粒度是群，不是消息。
- **解散这个功能你是怎么实际验证的——角色限制、和邀请或发消息或读文件的交叉，还有清理链路到底跑没跑通？** 角色这条最直白：两个客户端分别登录群主和管理员发解散（协议 76），看群主那次成功、管理员被结果码拒绝，再查 `group_info` 的 `status` 列确认只有授权那次改动；同一人重复解散，第二次按当前已解散状态返回，库里版本不再前进。交叉场景挨个构造：先发邀请再解散、然后受邀端点接受，查 `group_member` 确认没多出 active 行；开着发送窗口时解散提交，之后拉消息（协议 91）确认拿不到解散后的新内容；解散后用成员账号依次发起上传、下载、删除、列列表，预期前三样全拒、只有列表只读可见并随清理变空，非成员连列表都查不到。清理链路查库加看目录：跟着周期任务看 `file_object` 引用计数逐批下降、归零对象经回收调度器复核后从磁盘消失，群邀请、消息、成员的行数沿清理水位递减到完成。我的口径始终是：解散等于切终态加逐步回收，既不等于同步删光，也不等于数据永久躺着。
